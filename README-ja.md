# MailCare

English version: [README.md](README.md)

## 1. 概要

MailCare は、監視しているメールアドレスに届く「配信できませんでした」「配信が遅れています」といった通知メール（バウンス）を集め、
原因ごとにまとめて、メールの送信側で対応が必要なものを知らせるツールです。
Windows / macOS / Linux で動く単一の実行ファイルで、ブラウザから操作します。

### 1.1 主な機能

- **メールアドレスの監視** — 複数のメールアドレスを IMAP で監視し、決まった時刻（既定 6:00 / 12:00 / 18:00）に自動で新しいメールを取り込みます。
- **バウンスの判定とまとめ** — 取り込んだメールからバウンスを見分け、「送信 IP のブロック」「送信ドメインの認証失敗」「宛先アドレスが存在しない」などの原因ごとにまとめます。
  宛先アドレスや相手サーバーが違っても、対応する内容が同じものは 1 つにまとまります。
  DMARC 集計レポートも読み取り、DMARC に不合格だった記録を「SPF レコードの未設定」「DKIM 署名の検証失敗」「送信認証なし」に分けて、送信元 IP とともにまとめます。
  名前解決の失敗（「Host not found, try again」など）を知らせる通知は、その名前を引き直して確かめ（DNS 検証）、宛先ドメインが存在しないのか、宛先側の DNS の問題か、自分たちのメールサーバーの名前解決の不調かを見分けます。
- **アラート** — 送信側で対応が必要なものだけをアラートとして表示します。宛先側の問題（宛先不明、容量超過など）は「対象外」として分けて表示します。
  アラートごとに「未対応 / 対応済 / 無視」の状態を管理できます。
  アラートの概要と統計は PDF のレポートとしてダウンロードでき、元のメール一式（原文・ヘッダー・本文と索引の記録）とあわせて ZIP でもダウンロードできます（ZIP にはファイルの配置とデータ形式を説明する README.md が入ります）。
- **AI による原因分析** — AI エージェント（Codex CLI）が、アラートごとに原因の分析と対応方法の提案を作成します。
  新しいアラートや、既存のアラートに新しい種類の通知が届いたときに自動で分析します。原因を確定できない報告には「要確認」が付きます。
  分析のために、アラートの概要（宛先アドレスを含む）、見本の通知（ヘッダー、返送された元メールのヘッダー、本文の抜粋。本文全体もファイルとして渡します）と DNS 検証の結果を Codex CLI に渡し、Codex CLI はそれらを OpenAI に送ります（1.6）。
- **メール通知** — 対応が必要なアラートの一覧を、通知先に選んだ利用者へメールで送ります。
  利用者ごとに、その人の言語（日本語 / 英語）とタイムゾーンで送ります。通知の時刻と間隔（毎日〜7 日ごと）を設定できます。
- **確認メール（配信の確認）** — 決まった時刻（既定 7:00 / 11:00 / 15:00 / 19:00）に、各メールアドレスから実際に確認メールを送り、確認メールサーバー（IMAP）に届いたかを確かめます。
  最後の送信から遅延判断時間（既定 30 分）後にすべての確認メールの到着をまとめて確認し、届いていなければ「遅延」、障害判断時間（既定 120 分）を過ぎても届いていなければ「障害」として、ダッシュボードとアラート画面に表示し、障害は通知先の利用者にメールで知らせます。件名には送信した日時とアドレスが入るので、どのメールが届いていないかを追えます。
  遅れて届いたものは遅延・障害だったことを残したまま「回復」と表示し、到着を待たずに理由を選んで解決済みにすることもできます（アラートと同じく一般利用者も操作できます）。到着を確認できた確認メールは、容量を空けるために確認メールサーバーから削除します。
- **迷惑メールの判定** — 監視ドメインや他の組織を騙る差出人名、監視アドレスを埋め込んだ外部サイトへのリンク、監視ドメインを騙る From、他のサイトへのリンクを含むか差出人の認証に失敗した偽の「配信失敗」通知といった典型的なフィッシングと、スパム判定されたメールを「迷惑」として見分けます。自分たちのメールサーバーから送っていないメールの配信失敗通知（誰かが自分たちのアドレスを差出人に使ったもの）も「迷惑」にします。
  迷惑メールはアラートにはせず、件数を分けて表示します。
- **メールの閲覧** — 取り込んだメールを、すべて / 処理対象 / 迷惑 / その他に分けて閲覧できます（本文のテキスト / HTML 表示、原文のダウンロード）。
- **自動整理** — 毎日決まった時刻（既定 2:00）に、保持日数（既定 180 日）を過ぎた取り込み済みのメールを自動で削除します。
  バウンス・自動返信・DMARC レポートなどの通知メールと迷惑メールは、メールアドレスごとに設定した日数（新規登録時の既定 60 日。メールの保持日数以下。0 で削除しない）を過ぎたら IMAP サーバーからも削除できます。件名や差出人名だけで判定した通知メール、システムが自動生成したメール、一般のメールはサーバーに残します。
  IMAP サーバーからの削除は元に戻せず、迷惑メールの判定が誤ることもあります。法令や社内規程で保存が必要なメール（電子取引の記録など）を受け取るアドレスでは、保持日数を 0 にするか、先にメールをアーカイブしてください。
- **利用者と権限** — 管理者と一般利用者を分けられます。一般利用者は、ダッシュボード・アラート・メールの閲覧と、アラートの状態の変更ができます。設定、ツール、ジョブと、接続に関する情報（メールアドレスの IMAP と SMTP サーバー（送信）の設定、自分たちの送信元、DNS 検証のリゾルバー）は管理者だけが扱えます。画面は日本語 / 英語、ライト / ダークに対応しています。
- **コマンドライン** — 起動・停止、利用者やメールアドレスの登録、同期などの操作はコマンドラインからも行えます。

### 1.2 動作要件

- **OS**: Windows / macOS / Linux（64 ビット。amd64 / arm64）。
- **ポート**: Web 画面は 9790 番（変更可）。利用者のブラウザからこのポート（またはリバースプロキシ）に届くようにしてください。
- **監視するメールアカウント**: IMAP で接続できること。IMAP サーバーからのメール削除を使う場合は、メールを削除できる権限が必要です。
- **AI による原因分析を使う場合**: [Codex CLI](https://github.com/openai/codex) をインストールし、MailCare を実行する OS ユーザーでサインインしておいてください（`codex login`）。
  Codex CLI が無くても、原因分析以外の機能は動作します。
- **メール通知を使う場合**: 送信に使える SMTP サーバー。
- **DNS 検証**（初期状態で有効。任意）: 名前解決の失敗を知らせる配信失敗の通知が届くと、MailCare がその名前を引き直して確かめます。設定で指定したリゾルバー（既定は Cloudflare の 1.1.1.1、Google の 8.8.8.8、Quad9 の 9.9.9.9）への外向きの DNS（UDP / TCP 53 番）が必要です。対象ドメインのネームサーバーへ直接問い合わせるのは、自分たちのメールについての通知のときだけで、OS のリゾルバーだけを使う設定では問い合わせません。
  有効なあいだは、監視アドレスのドメインの SPF も読みます。自分たちの送信元のホスト名は常に引きます（まず OS のリゾルバーで）。無効にすると、OS のリゾルバーで自分たちの送信元のホスト名を引くこと以外の DNS の問い合わせはしません（保存済みの検証結果は引き続き通知の振り分けに使います）。
  リゾルバーに到達できない環境では、「設定 → 一般設定」で無効にするか、リゾルバーを変更するか、OS のリゾルバーだけを使う設定にしてください。問い合わせで相手に伝わることは 1.6 を参照してください。

### 1.3 インストールと初期設定

1. 配布されている ZIP（`mailcare_<版>_<OS>_<CPU>.zip`）を展開し、実行ファイル `mailcare`（Windows は `mailcare.exe`）を設置先のディレクトリに置きます。
2. サーバーを起動します。

   ```bash
   mailcare service start
   ```

   主な起動オプション（指定した値は保存され、次回からは省略できます）:

   | オプション | 内容 |
   | --- | --- |
   | `--web-listen` / `--web-port` | 待ち受けるアドレスとポート（既定 `0.0.0.0` / `9790`） |
   | `--data-dir` | データの保存先（既定は実行ファイルと同じ場所の `data/`） |
   | `--check-time` | 自動チェックの時刻（`--check-time 06:00 --check-time 12:00` のように複数指定） |
   | `--workers` | 同時に実行する処理の数（1〜16、既定 2） |
   | `--mail-keep-days` | 取り込んだメールの保持日数（既定 180） |

3. ブラウザで `http://<サーバー>:9790/` を開き、初期設定画面で最初の管理者を作成します。
4. 「設定 → メールアドレス」で監視するメールアドレスを登録し、「接続テスト」で IMAP に接続できることを確認します。
5. 必要に応じて設定します。
   - 「設定 → メールアドレス」: アドレスごとに、そのアドレスのメールを送信する「SMTP サーバー（送信）」を、そのサーバーが自分で名乗る名前（例: `mail.example.jp`）で入れます（任意）。確認メールを使う場合は、同じ「送信サーバー」欄で接続方式・ポート・ユーザー名・パスワードも設定します。設定しなくても動作しますが、アドレスにホスト名が無い（ここにも一般設定にも無い）と、そのアドレスでは送信元から送っていないメールの配信失敗通知を見分けないため判定が正しくないことがあり、確認メールも送りません。
   - 「設定 → 一般設定」: チェック時刻、クリーンアップ時刻、メールの保持日数、AI エージェント（モデル、推論レベル、自動分析の有効 / 無効）、メールアドレスに紐づかない自分たちの送信元（IPv4 / IPv6 とホスト名。ここのホスト名はすべてのアドレスに効きます）、DNS 検証
   - 「設定 → 通知」: SMTP サーバーと通知先の利用者、通知の時刻と間隔
   - 「設定 → 確認メール」: 確認メールの宛先と、それを受信する確認メールサーバー（IMAP）、送信時刻、遅延判断時間・障害判断時間。確認メールを送るメールアドレスごとに、「設定 → メールアドレス」の「送信サーバー」で SMTP サーバー（ホスト名に加えて接続方式・ポート・ユーザー名・パスワード）を設定します（「テスト送信」で宛先に届くか確かめられます）。確認メール専用のアドレスを用意してください（到着を確認したメールを削除するので、削除できる権限が必要です）
   - 「設定 → 利用者」: 利用者の追加と権限

`mailcare service start` はフォアグラウンドで動きます。常駐させる場合は、OS のサービスとして登録してください。Linux（systemd）の例:

```ini
[Unit]
Description=MailCare
After=network-online.target

[Service]
User=mailcare
ExecStart=/opt/mailcare/mailcare service start
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

停止は `mailcare service stop`、状態の確認は `mailcare service status` です。

### 1.4 データとバックアップ

- データはすべて `data/`（`--data-dir` で変更可）に保存されます。取り込んだメール、アラートと分析結果、設定、利用者、DNS 検証の結果（メールの保持日数 + 1 日保存）、自分たちの送信元のアドレスの取得結果（最大 90 日保存）が含まれます。
- IMAP / SMTP のパスワードを暗号化する鍵も `data/mailcare.db` の中にあります。**`data/` ディレクトリをまるごとバックアップ**してください。
  鍵だけを別に保管する必要はありません。
- バージョンアップは、サーバーを停止して実行ファイルを置き換え、再び起動するだけです。データは起動時に自動で新しい版に合わせて更新されます。
- すでに取り込んだメールは、新しい判定規則で自動的には判定し直されません。通知の判定方法が変わるバージョンアップのあと、および自分たちの送信元（「設定 → 一般設定」やメールアドレスの SMTP サーバー（送信））や DNS 検証の設定を変えたあとは、一度「再判定」（ツール画面、または `mailcare reclassify`）を実行してください。
  - DNS 検証が有効なあいだは、再判定でも、保存済みの通知のうち直近 2 日以内のものが報告した名前を引き直します（それより古い通知は、保存済みの検証結果だけを使います）。
  - 再判定で以前の通知が迷惑メールになることがあり、メールアドレスの保持日数を過ぎた迷惑メールは次のクリーンアップで IMAP サーバーから削除されます。先にメール一覧の「迷惑」タブを確認するか、確認が済むまでそのアドレスの保持日数を 0 にしてください。
  - メールが 1 通も無くなったアラートは、状態と対応履歴ごと削除されます。

### 1.5 セキュリティ

- MailCare と Codex CLI は、`data/` 以外を読めない専用の権限の低い OS ユーザーで実行してください。
  分析対象のメールは外部から届く信頼できない入力であり、Codex CLI はその OS ユーザーが読めるファイルを読めます。
- `data/` ディレクトリは他のユーザーから読めないようにしてください（権限 0700。そうでない場合は起動時に警告します）。
- MailCare 自身は暗号化していない HTTP で待ち受けます。ネットワーク越しに使う場合は、前段のリバースプロキシで HTTPS にしてください。
  そのうえで、MailCare は `--web-listen 127.0.0.1` でプロキシからだけ受け付けるようにし、プロキシは `Host` ヘッダーを書き換えずに渡してください。

### 1.6 外部への接続

MailCare は、監視するメールアドレスの IMAP サーバーと、通知メールの SMTP サーバー（確認メールを使う場合は、各メールアドレスの送信サーバー（SMTP）と確認メールサーバー）のほかに、次の相手に接続します。

- **DNS 検証（初期状態で有効）** — 暗号化されない通常の DNS（UDP。長い答えは TCP。53 番ポート）で、「設定 → 一般設定」のリゾルバー（既定は Cloudflare の 1.1.1.1、Google の 8.8.8.8、Quad9 の 9.9.9.9）に、OS のリゾルバーだけを使う設定ならそのリゾルバーだけに、次のことを問い合わせます。
  - リゾルバーが答えるかを確かめる固定の名前（`example.com`）。その実行で初めてそのリゾルバーを使うときに、実行ごと、リゾルバーごとに 1 回まで。
  - 直近 2 日以内の配信失敗の通知が名前解決に失敗したと報告した名前（宛先のドメインの中か、そのメールサーバーの名前に限る）と、その宛先ドメインのメールサーバー（MX）。
  - その通知を出したサーバーのホスト名（自分たちのメールサーバーかどうかを見分けるため）。
  - 監視アドレスのドメインの SPF レコードと、そこから参照される名前。
  - 自分たちの送信元のホスト名のアドレス（まず OS のリゾルバーで）。

  自分たちの送ったメールについての通知だと明らかなときは、対象ドメインのネームサーバーにも直接問い合わせます（OS のリゾルバーだけを使う設定では問い合わせません）。
- **相手に伝わること** — リゾルバー、直接問い合わせたネームサーバー、途中のネットワークには、このサーバーの IP アドレス、時刻、問い合わせた名前が見えます。問い合わせる名前は通知から取るため、監視アドレスに通知を送れる人は、このサーバーに任意の名前を引かせることができ、通知を自分たちのメールについてのものに見せかければ、その人のネームサーバーに直接問い合わせさせることもできます。このサーバーの IP アドレスをそのように知られてはならない場合は、DNS 検証を無効にしてください。
- **DNS 検証を無効にしたとき**（「設定 → 一般設定」、または `mailcare settings set dns_check_enabled 0`） — DNS の問い合わせは、OS のリゾルバーで自分たちの送信元のホスト名を引くことだけになります。保存済みの検証結果は引き続き通知の振り分けに使います。「OS 既定のリゾルバーだけを使う」は、検証を有効にしたまま、すべての問い合わせを OS のリゾルバーに送り、ネームサーバーへは直接問い合わせません。
- **保存される結果** — DNS 検証の結果（リゾルバーとネームサーバーごとの答えを含む）は、メールの保持日数 + 1 日のあいだ `data/` に保存します。自分たちの送信元のアドレスの取得結果は最大 90 日保存します。
- **AI による原因分析** — Codex CLI をインストールしてサインインしていると、分析のために、アラートの概要（宛先アドレスを含む）、見本の通知（ヘッダー、返送された元メールのヘッダー、本文の抜粋と、ファイルとして本文全体）、DNS 検証の結果を Codex CLI に渡し、Codex CLI はそれらを OpenAI に送ります。「設定 → 一般設定」で自動分析を無効にすると自動の分析は止まりますが、管理者が手動で分析を実行することはできます。OpenAI に何も送らないようにするには、MailCare を実行する OS ユーザーで Codex CLI をインストール・サインインしないでください。

### 1.7 コマンドライン

サーバーが起動していれば、コマンドラインからの処理はサーバーに依頼されます。主なコマンド:

| コマンド | 内容 |
| --- | --- |
| `mailcare user create --username admin --role admin` | 利用者を作成する |
| `mailcare mailbox add --address a@example.com --host imap.example.com --username a@example.com` | 監視するメールアドレスを登録する（パスワードは入力を求められる） |
| `mailcare sync --wait` | 今すぐ全メールアドレスを同期する（取り込み → まとめ → 分析）。`--all-time` を付けると期間に関係なくすべてのメールを確認する |
| `mailcare schedule set 06:00 12:00 18:00` | 自動チェックの時刻を変更する |
| `mailcare mailbox update a@example.com --smtp-host mail.example.jp` | メールアドレスの SMTP サーバー（送信）を設定する（`mailbox add` でも `--smtp-host` を指定できる。確認メールの送信に使う接続は `--smtp-port`、`--smtp-security`、`--smtp-username`、`--smtp-password`。`--smtp-host ""` で接続ごと消す。パスワードが保存されている間に接続を変えるときは `--smtp-password` も必要） |
| `mailcare settings show` / `mailcare settings set <キー> <値>` | 設定を表示する / 変更する |
| `mailcare settings set own_sending_hosts mail1.example.jp,mail2.example.jp` | メールアドレスに紐づかない自分たちの送信元を設定する（`own_sending_ipv4`、`own_sending_ipv6`、`own_sending_hosts`。カンマ区切り。`""` で一覧を消す） |
| `mailcare settings set dns_check_enabled 0` | DNS 検証を無効にする（`dns_check_resolvers` でリゾルバーを、`dns_check_system_resolver_only 1` で OS のリゾルバーだけを使う設定にする） |
| `mailcare cleanup` | 保持日数を過ぎたバウンスなどの通知メールと迷惑メールを IMAP サーバーから、保持日数を過ぎたメールを手元から削除し、古い一時ファイル・作業ディレクトリ・ジョブ履歴を今すぐ整理する |
| `mailcare probe send` / `mailcare probe check` | 確認メールを今すぐ送る / 届いていない確認メールの到着を今すぐ確認する |
| `mailcare settings set probe_send_times 07:00,11:00,15:00,19:00` | 確認メールの設定を変更する（`probe_enabled`、`probe_address`、`probe_imap_host` などの `probe_*`。メールアドレスの送信サーバーは `mailbox update A --smtp-host H --smtp-port N` など） |
| `mailcare jobs list` | 処理の履歴を表示する |

すべてのコマンドは `mailcare --help` で確認できます。
