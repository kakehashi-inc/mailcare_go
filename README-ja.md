# MailCare

English version: [README.md](README.md)

## 1. 概要

MailCare は、監視しているメールアドレスに届く「配信できませんでした」「配信が遅れています」といった通知メール（バウンス）を集め、
原因ごとにグループにまとめて、メールの送信側で対応が必要なものを知らせるツールです。
Windows / macOS / Linux で動く単一の実行ファイルで、ブラウザから操作します。

### 1.1 主な機能

- **メールアドレスの監視** — 複数のメールアドレスを IMAP で監視し、決まった時刻（同期時刻。既定 6:00 / 12:00 / 18:00）に自動で新しいメールを受信します。
- **バウンスの判定とグループ化** — 受信したメールからバウンスを見分け、「送信 IP のブロック」「送信ドメイン認証の失敗」「宛先アドレスが存在しない」などの原因ごとにグループにまとめます。
  宛先アドレスや相手サーバーが違っても、対応する内容が同じものは 1 つのグループになります。
  DMARC 集計レポートも読み取り、DMARC に不合格だった記録を「SPF レコードの未設定」「DKIM 署名の検証失敗」「送信認証なし」に分けて、送信 IP とともにグループにまとめます。
  名前解決の失敗（「Host not found, try again」など）を知らせるバウンスは、その名前を引き直して確かめ（DNS 検証）、宛先ドメインが存在しないのか、宛先側の DNS の問題か、送信側のメールサーバーの名前解決の不調かを見分けます。
- **アラート** — 送信側で対応が必要なものだけをアラートとして表示します。宛先側の問題（宛先アドレスが存在しない、容量超過など）は「対象外」として分けて表示します。
  アラートごとに「未対応 / 対応済 / 無視」の状態を管理できます。対応済・無視にしたアラートに、その判断で片付いていないことを示すバウンスが届くと、「対応済（再確認）」「無視（再確認）」として一覧に戻ります。
  アラートの概要と統計は PDF のレポートとしてダウンロードでき、元のメール一式（原文・ヘッダー・本文と索引の記録）とあわせて ZIP でもダウンロードできます（ZIP にはファイルの配置とデータ形式を説明する README.md が入ります）。
- **AI エージェントによる原因分析** — AI エージェント（Codex CLI）が、アラートごとに原因の分析と対応方法の提案（分析結果）を作成します。
  新しいアラートや、既存のアラートに新しいパターンのバウンスが届いたときに自動で分析します（自動分析）。原因を確定できない分析結果には「要確認」が付きます。
  分析のために、アラートの概要（宛先アドレスを含む）、見本のバウンス（ヘッダー、返送された元メールのヘッダー、本文の抜粋。本文全体もファイルとして渡します）と DNS 検証の結果を Codex CLI に渡し、Codex CLI はそれらを OpenAI に送ります（1.6）。
- **通知メール** — 対応が必要なアラートの一覧を、通知先に選んだ利用者へメールで送ります。
  利用者ごとに、その利用者の言語（日本語 / 英語）とタイムゾーンで送ります。通知時刻と通知間隔（毎日〜7 日ごと）を設定できます。
- **迷惑メールの判定** — 監視ドメインや他の組織を騙る差出人名、監視アドレスを埋め込んだ外部サイトへのリンク、監視ドメインを騙る From、他のサイトへのリンクを含むか差出人の認証に失敗した偽の「配信失敗」通知といった典型的なフィッシングと、スパム判定されたメールを「迷惑メール」として見分けます。送信元（設定に登録した送信サーバー。1.3）以外から送信されたメールのバウンス（第三者が監視アドレスを差出人に使ったもの）も迷惑メールにします。
  迷惑メールはアラートにはせず、件数を分けて表示します。
- **メールの閲覧** — 受信したメールを、すべて / 処理対象 / 迷惑 / その他に分けて閲覧できます（本文のテキスト / HTML 表示、原文のダウンロード）。
- **クリーンアップ** — 毎日決まった時刻（クリーンアップ時刻。既定 2:00）に、メールの保持日数（既定 180 日）を過ぎたメールを自動で削除します。
  バウンス・自動返信・DMARC レポートなどの通知メールと迷惑メールは、メールアドレスごとに設定した日数（サーバーでの保持日数。新規登録時の既定 60 日。メールの保持日数以下。0 で削除しない）を過ぎたら IMAP サーバーからも削除できます。件名や差出人名だけで判定した通知メール、自動生成メール、一般のメールはサーバーに残します。
  IMAP サーバーからの削除は元に戻せず、迷惑メールの判定が誤ることもあります。法令や組織の規程で保存が必要なメール（電子取引の記録など）を受け取るアドレスでは、サーバーでの保持日数を 0 にするか、先にメールをアーカイブしてください。
- **利用者と権限** — 管理者と一般利用者を分けられます。一般利用者は、ダッシュボード・アラート・メールの閲覧と、アラートの状態の変更ができます。設定、ツール、ジョブと、接続に関する情報（メールアドレスの IMAP 接続と「SMTP サーバー（送信）」、送信元、DNS 検証のリゾルバー）は管理者だけが扱えます。画面は日本語 / 英語、ライト / ダークに対応しています。
- **コマンドライン** — 起動・停止、利用者やメールアドレスの登録、同期などの操作はコマンドラインからも行えます。

### 1.2 動作要件

- **OS**: Windows / macOS / Linux（64 ビット。amd64 / arm64）。
- **ポート**: Web 画面は 9790 番（変更可）。利用者のブラウザからこのポート（またはリバースプロキシ）に届くようにしてください。
- **監視するメールアカウント**: IMAP で接続できること。IMAP サーバーからのメール削除を使う場合は、メールを削除できる権限が必要です。
- **AI エージェントによる原因分析を使う場合**: [Codex CLI](https://github.com/openai/codex) をインストールし、MailCare を実行する OS ユーザーでサインインしておいてください（`codex login`）。
  Codex CLI が無くても、原因分析以外の機能は動作します。
- **通知メールを使う場合**: 送信に使える SMTP サーバー。
- **DNS 検証**（初期状態で有効。任意）: 名前解決の失敗を知らせるバウンスが届くと、MailCare がその名前を引き直して確かめます。設定で指定したリゾルバー（既定は Cloudflare の 1.1.1.1、Google の 8.8.8.8、Quad9 の 9.9.9.9）への外向きの DNS（UDP / TCP 53 番）が必要です。対象ドメインのネームサーバーへ直接問い合わせるのは、送信元から届いた通知（監視アドレスの受信サーバーが記録した接続元が送信元のもの）のときだけで、「OS のリゾルバーだけを使う」をオンにした設定では問い合わせません。
  オンのあいだは、監視アドレスのドメインの SPF も読みます。送信元のホスト名は常に引きます（まず OS のリゾルバーで）。オフにすると、OS のリゾルバーで送信元のホスト名を引くこと以外の DNS の問い合わせはしません（保存済みの検証結果は引き続きバウンスの振り分けに使います）。
  リゾルバーに到達できない環境では、「設定 → 一般設定」の「送信元と DNS 検証」で DNS 検証をオフにするか、リゾルバーを変更するか、「OS のリゾルバーだけを使う」をオンにしてください。問い合わせで相手に伝わることは 1.6 を参照してください。

### 1.3 インストールと初期設定

1. 配布されている ZIP（`mailcare_<版>_<OS>_<CPU>.zip`）を展開し、実行ファイル `mailcare`（Windows は `mailcare.exe`）を設置先のディレクトリに置きます。
2. サーバーを起動します。

   ```bash
   mailcare service start
   ```

   主な起動オプション（指定した値は保存され、次回からは省略できます）:

   | オプション | 内容 |
   | --- | --- |
   | `--web-listen` / `--web-port` | 待ち受けるアドレスとポート（既定 `0.0.0.0` / `9790`） |
   | `--data-dir` | データの保存先（既定は実行ファイルと同じ場所の `data/`） |
   | `--check-time` | 同期時刻（`--check-time 06:00 --check-time 12:00` のように複数指定） |
   | `--workers` | 同時実行数（同時に実行するジョブの数。1〜16、既定 2） |
   | `--mail-keep-days` | メールの保持日数（既定 180） |

3. ブラウザで `http://<サーバー>:9790/` を開き、初期設定画面で最初の管理者を作成します。
4. 「設定 → メールアドレス」で監視するメールアドレスを登録し、「接続テスト」で IMAP に接続できることを確認します。
5. 必要に応じて設定します。
   - 「設定 → メールアドレス」: アドレスごとに、そのアドレスの送信に使う SMTP サーバーのホスト名（例: `mail.example.jp`）を「SMTP サーバー（送信）」に入力します。アドレスにホスト名が無い（ここにも一般設定の「送信元ホスト名」にも無い）と、そのアドレスでは送信元以外から送信されたメールのバウンスを見分けられません。
   - 「設定 → 一般設定」: 同期時刻、クリーンアップ（クリーンアップ時刻、メールの保持日数）、再確認までの日数、送信元と DNS 検証（メールアドレスに結び付かない送信元を「送信元 IPv4」「送信元 IPv6」「送信元ホスト名」に登録。ここのホスト名はすべてのアドレスに効きます）、同時実行数、AI エージェント（プロバイダー、モデル、推論レベル、自動分析の有効 / 無効）
   - 「設定 → 通知」: SMTP サーバーと通知先の利用者、通知時刻と通知間隔
   - 「設定 → 利用者」: 利用者の追加と役割

`mailcare service start` はフォアグラウンドで動きます。常駐させる場合は、OS のサービスとして登録してください。Linux（systemd）の例:

```ini
[Unit]
Description=MailCare
After=network-online.target

[Service]
User=mailcare
ExecStart=/opt/mailcare/mailcare service start
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

停止は `mailcare service stop`、状態の確認は `mailcare service status` です。

### 1.4 データとバックアップ

- データはすべて `data/`（`--data-dir` で変更可）に保存されます。受信したメール、アラートと分析結果、設定、利用者、DNS 検証の結果（メールの保持日数 + 1 日保存）、送信元のアドレスを引いた結果（ホスト名のアドレスと SPF。最大 90 日保存）が含まれます。
- IMAP / SMTP のパスワードを暗号化する鍵も `data/mailcare.db` の中にあります。**`data/` ディレクトリをまるごとバックアップ**してください。
  鍵だけを別に保管する必要はありません。
- バージョンアップは、サーバーを停止して実行ファイルを置き換え、再び起動するだけです。データは起動時に自動で新しい版に合わせて更新されます。
- 受信済みのメールは、新しい判定規則で自動的には判定し直されません。バウンスの判定方法が変わるバージョンアップのあと、および送信元（「設定 → 一般設定」やメールアドレスの「SMTP サーバー（送信）」）や DNS 検証の設定を変えたあとは、一度「再判定」（ツール画面、または `mailcare reclassify`）を実行してください。
  - DNS 検証がオンのあいだは、再判定でも、保存済みのバウンスのうち直近 2 日以内のものが報告した名前を引き直します（それより古いバウンスは、保存済みの検証結果だけを使います）。
  - 再判定で以前のバウンスが迷惑メールになることがあり、サーバーでの保持日数を過ぎた迷惑メールは次のクリーンアップで IMAP サーバーから削除されます。先にメール一覧の「迷惑」タブを確認するか、確認が済むまでそのアドレスのサーバーでの保持日数を 0 にしてください。
  - メールが 1 通も無くなったアラートは、状態と対応履歴ごと削除されます。

### 1.5 セキュリティ

- MailCare と Codex CLI は、`data/` 以外を読めない専用の権限の低い OS ユーザーで実行してください。
  分析対象のメールは外部から届く信頼できない入力であり、Codex CLI はその OS ユーザーが読めるファイルを読めます。
- `data/` ディレクトリは他のユーザーから読めないようにしてください（権限 0700。そうでない場合は起動時に警告します）。
- MailCare は暗号化していない HTTP で待ち受けます。ネットワーク越しに使う場合は、前段のリバースプロキシで HTTPS にしてください。
  そのうえで、MailCare は `--web-listen 127.0.0.1` でプロキシからだけ受け付けるようにし、プロキシは `Host` ヘッダーを書き換えずに渡してください。

### 1.6 外部への接続

MailCare は、監視するメールアドレスの IMAP サーバーと、通知メールの SMTP サーバーのほかに、次の相手に接続します。

- **DNS 検証（初期状態で有効）** — 暗号化されない通常の DNS（UDP。長い答えは TCP。53 番ポート）で、「設定 → 一般設定」のリゾルバー（既定は Cloudflare の 1.1.1.1、Google の 8.8.8.8、Quad9 の 9.9.9.9）に、「OS のリゾルバーだけを使う」がオンなら OS のリゾルバーだけに、次のことを問い合わせます。
  - リゾルバーが答えるかを確かめる固定の名前（`example.com`）。その実行で初めてそのリゾルバーを使うときに、実行ごと、リゾルバーごとに 1 回まで。
  - 直近 2 日以内のバウンスが名前解決に失敗したと報告した名前（宛先のドメインの中か、そのメールサーバーの名前に限る）と、その宛先ドメインのメールサーバー（MX）。
  - そのバウンスを出したサーバーのホスト名（送信側のメールサーバーかどうかを見分けるため）。
  - 監視アドレスのドメインの SPF レコードと、そこから参照される名前。
  - 送信元のホスト名のアドレス（まず OS のリゾルバーで）。

  設定のリゾルバーへの問い合わせ（リゾルバーの確認を含む）には、このサーバーのネットワーク（サブネット）を他のネームサーバーへ伝えないようリゾルバーに求める指定（EDNS Client Subnet。プレフィックス長 0）を付けます。
  対象ドメインのネームサーバーに直接問い合わせるのは、送信元から届いた通知のときだけです。送信元かどうかは、監視アドレスの受信サーバーが通知を受け取ったときに記録した接続元の IP アドレスで決め、通知の中身（ホスト名、`Received` の行、DKIM 署名）は見ません。「OS のリゾルバーだけを使う」がオンなら直接は問い合わせません。
- **相手に伝わること** — リゾルバー、直接問い合わせたネームサーバー、途中のネットワークには、このサーバーの IP アドレス、時刻、問い合わせた名前が見えます。問い合わせる名前はバウンスから取るため、監視アドレスにバウンスを装ったメールを送れる第三者は、このサーバーに任意の名前を引かせることができます。通知の中身を書き写しても直接の問い合わせにはなりませんが、監視アドレスのドメインの SPF が他の利用者と共有する範囲（大手のメールサービスなど）を含む場合、受信サーバーの前のプロキシや NAT が接続元をプライベートの IP アドレスとして記録する場合、送信元として登録したサーバーが監視アドレスの受信サーバーを兼ね、グローバルな IP アドレスで中継する場合は、第三者の通知でもそのネームサーバーに直接問い合わせることがあります。このサーバーの IP アドレスをそのように知られてはならない場合は、DNS 検証をオフにしてください。
- **DNS 検証をオフにしたとき**（「設定 → 一般設定」、または `mailcare settings set dns_check_enabled 0`） — DNS の問い合わせは、OS のリゾルバーで送信元のホスト名を引くことだけになります。保存済みの検証結果は引き続きバウンスの振り分けに使います。「OS のリゾルバーだけを使う」は、DNS 検証をオンにしたまま、すべての問い合わせを OS のリゾルバーに送り、ネームサーバーへは直接問い合わせません。
- **保存される結果** — DNS 検証の結果（リゾルバーとネームサーバーごとの答えを含む）は、メールの保持日数 + 1 日のあいだ `data/` に保存します。送信元のアドレスを引いた結果は最大 90 日保存します。
- **AI エージェントによる原因分析** — Codex CLI をインストールしてサインインしていると、分析のために、アラートの概要（宛先アドレスを含む）、見本のバウンス（ヘッダー、返送された元メールのヘッダー、本文の抜粋と、ファイルとして本文全体）、DNS 検証の結果を Codex CLI に渡し、Codex CLI はそれらを OpenAI に送ります。「設定 → 一般設定」の「自動分析を有効にする」をオフにすると自動分析は止まりますが、管理者が手動で分析を実行することはできます。OpenAI に何も送らないようにするには、MailCare を実行する OS ユーザーで Codex CLI をインストール・サインインしないでください。

### 1.7 コマンドライン

サーバーが起動していれば、コマンドラインからの処理はサーバーに依頼されます。主なコマンド:

| コマンド | 内容 |
| --- | --- |
| `mailcare user create --username admin --role admin` | 利用者を作成する |
| `mailcare mailbox add --address a@example.com --host imap.example.com --username a@example.com` | 監視するメールアドレスを登録する（パスワードは入力を求められる） |
| `mailcare sync --wait` | 今すぐ全メールアドレスを同期する（受信 → グループ化 → 分析）。`--all-time` を付けると期間に関係なくすべてのメールを確認する |
| `mailcare schedule set 06:00 12:00 18:00` | 同期時刻を変更する |
| `mailcare mailbox update a@example.com --smtp-host mail.example.jp` | メールアドレスの「SMTP サーバー（送信）」を設定する（`mailbox add` でも `--smtp-host` を指定できる。`--smtp-host ""` で消す。パスワードは不要） |
| `mailcare settings show` / `mailcare settings set <キー> <値>` | 設定を表示する / 変更する |
| `mailcare settings set sending_source_hosts mail1.example.jp,mail2.example.jp` | メールアドレスに結び付かない送信元を設定する（`sending_source_ipv4`、`sending_source_ipv6`、`sending_source_hosts`。カンマ区切り。`""` で一覧を消す） |
| `mailcare settings set dns_check_enabled 0` | DNS 検証をオフにする（`dns_check_resolvers` でリゾルバーを設定し、`dns_check_system_resolver_only 1` で OS のリゾルバーだけを使う） |
| `mailcare cleanup` | サーバーでの保持日数を過ぎたバウンスなどの通知メールと迷惑メールを IMAP サーバーから、メールの保持日数を過ぎたメールを MailCare から削除し、古い一時ファイル・作業ディレクトリ・ジョブ履歴を今すぐ削除する（クリーンアップ） |
| `mailcare jobs list` | ジョブの履歴を表示する |

すべてのコマンドは `mailcare --help` で確認できます。

### Go 操作コマンド

デバッグモジュールの追加・更新

```bash
go install github.com/go-delve/delve/cmd/dlv@latest
```

モジュールの追加

```bash
go get <package-name>
```

モジュールの追加・ビルド

```bash
go install <package-name>
```

モジュールファイルの作成

```bash
go mod init <module-name>
```

モジュールのダウンロード（モジュール名を省略するとgo.modの全て）

```bash
go mod download <module-name>
```

モジュールの最適化（ソースとgo.modの双方向での一致）

```bash
go mod tidy
```

モジュールの最新化

```bash
go get -u
```

Go バージョンの更新

```bash
go mod tidy --go=1.26
```

キャッシュのクリア

```bash
go clean --cache --testcache
```

### 起動

```bash
go run . service start
```

<http://localhost:9790> でWeb画面が開きます（`service stop` / `status` は同じポートのコントロールエンドポイントへ接続します）。
実行時データ（マスター DB、メールアドレスごとの索引と原文・本文セクション、エージェントの実行ディレクトリ）は実行ファイルと同じ場所の `data/` に作成されます。
