- コマンドラインリファレンス（[日本語](command-line-reference-ja.md) / [English](command-line-reference.md)）: CLI のコマンドとオプション

## 1. 用語定義

| 用語（日本語） | English | 説明 |
| --- | --- | --- |
| 利用者 | User | Web 画面にログインして閲覧・操作する人（`users` テーブル） |
| 管理者 | Administrator | 役割 `admin` の利用者。利用者管理・設定・メールアドレス登録・ツール実行ができる |
| 一般利用者 | Member | 役割 `user` の利用者。ダッシュボード・アラート・メールの参照、アラート（グループ）の状態変更、各自のプロフィールの変更ができる。分析の実行と、ツール・ジョブ・設定の画面は使えない |
| 運用者 | Operator | サーバーの起動・停止、CLI 操作、データディレクトリの管理をする人 |
| データディレクトリ | Data directory | 実行時データ（DB、メール原文、エージェント作業領域）を置くディレクトリ |
| マスター DB | Master database | `data/mailcare.db`。利用者・トークン・設定・メールアドレス・ジョブ・DNS 検証結果（`dns_checks`）・送信元の取得結果（`sending_source_lookups`）・確認メールの記録（`probe_mails`）を保持する |
| 索引 DB | Mail index | `data/mails/<address>.sqlite`。メールアドレス単位の索引。原文ファイルから再生成できる派生データ |
| メールアドレス | Mailbox | 監視対象の 1 メールアドレスとその IMAP 接続設定（`mailboxes` テーブル） |
| 受信 | Fetch | IMAP から未受信のメールを取り込み、原文を保存して索引に載せる処理（判定・グループ化はしない） |
| グループ化 | Grouping | 未処理のメール（画面の「グループ化待ち」）を判定し、カテゴリと対応単位でグループに束ねる処理 |
| 分析 | Analysis | AI エージェントで対応対象のグループの原因を分析する処理。新しいバウンスについて同期の後に自動で行うものを自動分析（Automatic analysis）と呼ぶ |
| 同期 | Sync | 1 アドレスについて受信 → グループ化 → 分析の投入を続けて行う処理。「全アドレス同期」は有効な全アドレスに 1 件ずつ投入する |
| 原文 | Original message | `.eml` として保存した受信メールそのもの |
| メールキー | Message key | 1 メールを表すファイル名の基底（`YYYYMMDD-HHMMSS_<12桁hex>`） |
| バウンス | Bounce | メールデーモン（MAILER-DAEMON 等）が送る配信不能・遅延などの通知メール |
| 対象判定 | Classification | 受信メールが自動通知・迷惑・一般のメールのどれか、どの種類かを判定する処理（[メール判定仕様](メール判定仕様.md) 2 章） |
| 自動通知 | Notice | 監視アドレスが受け取る、メールシステムや自動応答が自動で送るメール（バウンス・自動返信・DMARC 集計レポートなど。`is_bounce` = 1）。MailCare が利用者へ送る通知メール（下記「通知」）とは別 |
| 一般のメール | Ordinary mail | どの判定規則にも一致しないメール（`is_bounce` = 0、`bounce_kind` は空） |
| 処理対象 | Target mail | 本アプリが確実な根拠で自動通知（バウンス、自動返信、DMARC 集計レポートなど）と判定したメール。保持日数を過ぎたらクリーンアップで IMAP サーバーから削除する（5.6.1）。定義は [メール判定仕様](メール判定仕様.md) 5 章。件数はメール画面のカードに表示する（[画面仕様](画面仕様.md) 6.1） |
| 迷惑 | Junk mail | フィッシングやスパムと判定したメール（`bounce_kind` = `junk`）。グループに入れず（アラートに載せない）、処理対象とは別に数え、処理対象と同じくクリーンアップで IMAP サーバーから削除する。判定は [メール判定仕様](メール判定仕様.md) 2.4。メール画面のカードに件数を、メール一覧に専用のタブを表示する（[画面仕様](画面仕様.md) 6.1） |
| DMARC 集計レポート | DMARC aggregate report | 受信側が DMARC の評価結果を送信ドメインの管理者へ送るレポート（`bounce_kind` = `report`）。不合格の記録ごとにグループに入れる（[メール判定仕様](メール判定仕様.md) 4.2） |
| 送信元 | Sending source | 登録した送信サーバー（一般設定の「送信元 IPv4」「送信元 IPv6」「送信元ホスト名」、各メールアドレスの「SMTP サーバー」と、それらから自動で引いたアドレス。[メール判定仕様](メール判定仕様.md) 2.7）。メールの From は「差出人アドレス」（From address）と呼び、送信元とは呼ばない |
| グループ | Group | バウンスと DMARC 集計レポートの不合格の記録を対応単位で束ねたもの（`groups` テーブル。コードでは `BounceGroup`）。対応対象のグループがアラートに載る |
| カテゴリ | Category | グループが表す問題の種類（送信 IP のブロック、差出人アドレスの拒否、送信ドメイン認証の失敗、宛先アドレスが存在しない、宛先の容量超過など）。対応単位・対応対象かどうかを決める |
| 対応単位 | Action unit | 送信側のメール管理者が対応する対象そのもの（送信 IP、差出人アドレス、送信ドメイン、送信側の MTA。対象外なら宛先アドレス・宛先ドメイン）。`groups.unit_value` |
| 判定元 | Decided by | 結果を決めている相手（ブラックリストの提供元、宛先ドメイン）。登録先が違えば別グループになる。`groups.authority`（コードと API では authority） |
| 対応対象 | Actionable | 送信側のメール管理者が対応すべきグループ（`groups.actionable` = 1）。宛先側の問題（宛先アドレスが存在しない、容量超過など）は対象外 |
| 対象外 | Excluded | 宛先側の問題のグループ（`groups.actionable` = 0）のうち未対応（`state = 'open'`）のもの。対応状態の区分も件数の管理も持たない。対応済・無視にすると対応対象の一覧に移り、未対応に戻すと対象外に戻る（`actionable` 列は変えない。9.2 の `GET .../groups` の `scope`） |
| 対応内容 | Action taken | グループを対応済にするときに選ぶ「何をしたか」（選択式で必須。`groups.state_reason`）と、任意の詳細（自由入力。`groups.state_note`）。選択肢は 5.9 |
| 判断理由 | Reason for ignoring | グループを無視するときに選ぶ「なぜ無視するか」（選択式で必須）と、「その他」を選んだときだけ書ける詳細（任意）。選択肢は 5.9 |
| 対応履歴 | State history | グループの状態変更の記録（`group_state_changes`）。変更のたびに状態・選んだコード・詳細・変更者・日時を残す。未対応に戻すとグループの理由・詳細は空になるが、履歴には残る |
| 再確認 | Re-check | 対応済・無視にしたグループに、その判断で片付いていないことを示すバウンスが届いたとき、もう一度判断を求めること（`groups.needs_recheck`）。アラートでは「対応済（再確認）」「無視（再確認）」のタブに移り、自動で分析され、通知メールに載る。状態は利用者が変えるまで変わらない（条件は [メール判定仕様](メール判定仕様.md) 4.5、状態の変更は 5.9）。下の「再判定」とは別 |
| 再判定 | Reclassify | 受信済みのメールの判定とグループ化を全件やり直すジョブ（`reclassify`。ツール画面の「再判定」、CLI `reclassify`。5.5） |
| 索引の再構築 | Rebuild index | 保存済みの原文から索引 DB を作り直し、判定とグループ化もやり直すジョブ（`reindex`。ツール画面の「索引の再構築」、CLI `reindex`。5.5） |
| 診断テンプレート | Diagnostic template | 診断文からアドレス・IP・ID・数値などの揺れを除いた正規化文字列。カテゴリを判定できない場合のグループ化の鍵になる（[メール判定仕様](メール判定仕様.md) 4.1） |
| 対応者区分 | Responsible party | グループに対して対応すべき立場（`sender` 送信側のメール管理者 / `recipient` 宛先アドレスの所有者 / `domain` 宛先ドメインの管理者 / `unknown` 担当不明。画面（項目名「対応者」）と分析結果はこの呼び名で統一する、6.3） |
| AI エージェント | AI agent | 外部 CLI（Codex CLI 等）。グループの原因分析と対応方法の提案（分析結果）を作成する。本書では「エージェント」とも書く |
| プロバイダー | Provider | エージェント CLI の種類（`codex` ほか、追加可能） |
| 分析結果 | Analysis report | AI エージェントが作成した報告（`agent_reports` テーブルと `REPORT.md`。本書では「報告」とも書く）。画面の状態は 未分析 / 分析中 / 分析済み / 分析エラー / 分析不可 |
| ジョブ | Job | バックグラウンド処理の 1 単位（同期 / 受信 / グループ化 / 分析 / 索引の再構築 / 再判定 / クリーンアップ / 通知メール送信 / 確認メール送信 / 確認メール到着確認）。`jobs` テーブル |
| ワーカー | Worker | ジョブを実行する goroutine。数は設定 `workers`（画面の「同時実行数」）。同じ IMAP サーバー・同じ索引・エージェントを使うジョブは直列化される |
| スケジューラ | Scheduler | 同期時刻に全アドレス同期を、通知時刻に通知メールの送信を、クリーンアップ時刻にクリーンアップを、確認メールの送信時刻に確認メールの送信を、予定の時刻に到着確認を投入する常駐処理 |
| 通知 | Notification | 対応が必要なグループの一覧を通知先の利用者へメール（通知メール）で送る機能。SMTP 設定と通知設定（通知時刻・通知間隔・通知先）から成る |
| 通知先 | Notification recipient | 通知メールを受け取る利用者。利用者に任意で登録したメールアドレス（`users.email`）へ送る |
| 確認メール | Probe mail | 配信の確認のために、送信確認をするメールアドレスから確認メールの宛先へ送るメール（`probe_mails` テーブル。7.6）。この機能全体も「確認メール」（Delivery probe）と呼ぶ |
| 送信確認 | Send check | メールアドレスごとの「送信確認をする」（`mailboxes.detail_info.probe_enabled`）。オンのアドレスだけが、その SMTP サーバーで確認メールを送る |
| 確認メールサーバー | Probe server | 確認メールの宛先を受信する IMAP のメールボックス（設定 `probe_imap_*`）。到着確認で読み、検証済みの確認メールだけを削除する |
| 到着確認 | Arrival check | 確認メールサーバーで未着の確認メールを探すジョブ（`probe_check`） |
| 遅延 | Delayed | 遅延判断時間（`probe_delay_minutes`、既定 15 分）を過ぎても届いていない確認メールの状態。通知先にメールで 1 回知らせる |
| 障害 | Failure | 障害判断時間（`probe_failure_minutes`、既定 60 分）を過ぎても届いていない確認メールの状態。送信できなかったもの（送信失敗）とともに通知先にメールで 1 回知らせる |
| 回復 | Recovered | 遅延判断時間を過ぎてから届いた（または送信失敗の後に届いた）確認メールの状態。到達した段階（遅延・障害）は残る |
| 到着待ち | Awaiting arrival | 送信した確認メールが、遅延判断時間を過ぎる前でまだ届いていない状態（`pending`） |
| 送信失敗 | Send failed | SMTP サーバーが確認メールを受け付けなかった状態（`send_failed`）。障害として通知先に知らせる。後で届けば回復 |
| 対応済（確認メール） | Resolved | 遅延・障害・送信失敗の確認メールを、利用者が理由を選んで閉じた状態（`resolved`）。確認メール・送信確認・メールアドレスが無効になったときはシステムが閉じる（理由 `probe_disabled`）。アラートの「対応済」と同じ語 |
| 遅延判断時間 | Delay threshold | これを過ぎても届かない確認メールは遅延（`probe_delay_minutes`）。未着がある間、最後の送信から障害判断時間まではこの間隔で到着を確認する。送信時刻の間隔より短い |
| 障害判断時間 | Failure threshold | これを過ぎても届かない確認メールは障害（`probe_failure_minutes`）。以降はこの間隔で到着を確認する。遅延判断時間より長い |
| 確認メールの宛先 | Probe address | 確認メールを送る先のアドレスで、確認メールサーバーで受信する（`probe_address`） |
| 確認番号 | Probe ID | 確認メールごとの番号（16 進 16 桁の乱数。`probe_mails.token`）。件名の `[<識別子>:<確認番号>]` と `X-MailCare-Probe` ヘッダーに入れ、到着確認で照合する。管理者にだけ表示する |
| 識別子 | Identifier | 確認メールの件名の先頭に付ける語（設定 `probe_subject_tag`、既定 `MC`。英数字と `.` `_` `-` の 16 文字まで）。件名は `[<識別子>:<確認番号>] Probe ...`。確認メールサーバーを共有する MailCare どうしは別の識別子にする |
| 送信時刻 | Send time | 確認メールを送る時刻（`probe_send_times`、サーバーのローカル時刻。24 個まで、15 分以上空ける） |
| 公開 URL | Public base URL | 通知メール内のリンクの元になる、利用者がブラウザで開く MailCare の URL（設定 `public_base_url`） |
| トークン | Token | 将来の API 実装のために予約した秘密文字列（`mlc_` 接頭辞）。利用者とは無関係で、ログインには使わない |
| デフォルトトークン | Default token | `is_default` = 1 のトークン。サーバー起動時に無ければ識別子 `default` のトークンが自動作成（または既存の `default` が昇格）される |
| セッション | Session | Web ログイン後の Cookie（`mlc_session`）による認証状態 |
| コントロールエンドポイント | Control endpoint | ループバックからだけ、コントロールトークンを付けて使える停止・状態確認・ジョブ投入用 HTTP エンドポイント（`/control/*`、9.1） |
| SPA | Single Page Application | バイナリに埋め込まれて配信される React 製の Web 画面 |

## 2. 全体構成

```text
+---------------------------------------------------------------------------+
| mailcare (single binary)                                                  |
|                                                                           |
|  main.go -- kong CLI --> app/modules (commands, jobs, scheduler, auth)     |
|                              |                                            |
|            +-----------------+-----------------+                          |
|            v                 v                 v                          |
|   app/modules/mailengine  app/modules/agent   app/workers (HTTP server)   |
|   IMAP受信/読み取り/判定/グループ化  エージェントCLI実行  Web :9790          |
|            |                 |                   /api/v1/*  JSON (cookie) |
|            v                 v                   /web/*     login/logout  |
|         app/models  <-------+                    /control/* loopback only |
|            |                                     /*         embedded SPA  |
|   +--------+---------+                                                    |
|   v                  v                                                    |
| data/mailcare.db   data/mails/<address>.sqlite + <address>/<YYYY>/<MM>/*.eml .txt .html|
|                    data/agent/<address>/<group_key>/<report_id>/          |
|  embed.go: frontend/dist/** + frontend/src/i18n/*.json, embedded/**      |
+---------------------------------------------------------------------------+
```

- HTTP サーバーは Web サーバー 1 つ（既定ポート 9790）。外部公開 API は無く、`/api/v1/*` は Web 画面専用の内部 API（Cookie 認証）です。
- 依存方向は `main -> workers -> modules -> {mailengine, agent, dnscheck} -> models` の一方向です。`dnscheck`（名前解決の失敗の検証と送信元の取得）は `mailengine` の型（`DNSFailure`、`DNSOutcome`、`DNSVerifyStatus` など）と `models` を使い、`mailengine` から呼ばれるときもインターフェース（`DNSVerifier` など）越しで、`mailengine` は `dnscheck` を import しません。PDF レポートの `pdfreport` は `modules`（言語ファイル、埋め込みファイル）を使い、`workers` から呼ばれます（`workers -> pdfreport -> modules`）。`modules` から `workers` のサーバーを起動するため、`workers` が `init()` で `modules.StartServer` を登録します。
- `mailengine` と `agent` はマスター DB に触れません。必要な値（メールアドレス行、復号済みパスワード、パス、DNS 検証の部品、保存済みの DNS 検証を引くコールバック）は `modules` が渡します。マスター DB の `dns_checks` を読み書きするのは `dnscheck`（`modules` が渡した `*sql.DB` で）と `modules` で、`sending_source_lookups` は `modules` だけが読み書きします。

### 2.1 パッケージと責務

| パス | 責務 |
| --- | --- |
| `main.go` | 起動パラメータの定義と解釈（kong）。埋め込んだファイルを `modules.FrontendFS` / `modules.EmbeddedFS` / `dbschema.FS` に、バージョンを `modules` に渡す。IANA のタイムゾーンデータベース（`time/tzdata`）を同梱し、利用者のタイムゾーンは OS の zoneinfo の有無に関係なく読める（サーバーのローカル時刻 `time.Local` は従来どおり OS の設定: Linux は `TZ` / `/etc/localtime`、Windows は OS のタイムゾーン） |
| `embed.go` | バイナリへの埋め込みをここだけで行う（`go:embed` はほかのパッケージに置かない）。埋め込むのは 2 つだけ: frontend（`frontend/dist` と言語ファイル `frontend/src/i18n/*.json`）と `embedded/` |
| `embedded/` | frontend 以外に埋め込むファイルの置き場。`templates/`（`agent/`、`mail/`、`export/`）、`fonts/`（PDF レポートのフォント）、`migrations/`（`master/` = マスター DB、`index/` = 索引 DB の goose マイグレーション） |
| `app/modules/dbschema/` | DB スキーマのマイグレーションの適用（`migrate.go`: `dbschema.Apply`。`lock.go`: `dbschema.ApplyLocked`（プロセス間のロックファイルで直列化した適用。11 章）。SQL は `embedded/migrations/` から main が `dbschema.FS` に渡す。未設定なら DB を開くときにエラー） |
| `app/models` | テーブルごとのデータ構造とアクセス関数（マスター DB と索引 DB の両方） |
| `app/models/mailindex.go` | 索引 DB の open（マイグレーションの適用。`dbschema.ApplyLocked`）/ clear、JSON・日時ヘルパー |
| `app/modules/constants.go` | アプリ名、既定値、設定キー、状態値などの定数 |

## 3. データ配置

データディレクトリに作るのは SQLite ファイル、メールごとの `.eml` / `.txt` / `.html`、エージェントの実行ディレクトリだけである（稼働中のサーバーのコントロールトークン `control.token` とロック `server.lock`、SQLite が動作中に作る `-wal` / `-shm`、マイグレーションの適用中だけ DB ファイルの隣に置くロックファイル `<DB ファイル>.migrate.lock`（11 章）と、書き込み中の一時ファイル `.<name>.<random>.tmp` を除く。中断で残った一時ファイルは日次の `cleanup` ジョブが削除する、5.6）。

```text
data/
  mailcare.db                 マスター DB（利用者、トークン、設定、メールアドレス、ジョブ、DNS 検証結果、送信元の取得結果、確認メールの記録）
  control.token               稼働中のサーバーのポートとコントロールトークン（JSON、権限 0600。待ち受けを始めるたびに作り直し、正常な停止で削除。9.1）
  server.lock                 稼働中のサーバーが持つ排他ロック（中身はプロセス ID。ファイルは残る。9.1）
  mails/
    user@example.com.sqlite   索引 DB（メール、バウンス詳細、グループ、分析結果）
    user@example.com/         原文ディレクトリ（アドレスを安全化した名前）
      2026/                   メールキーの年（メールの日付、UTC）
        09/                   メールキーの月
          20260901-120000_ab12cd34ef56.eml       原文（受信したバイト列のまま。添付も含む）
          20260901-120000_ab12cd34ef56-1.txt     本文テキストの 1 つ目のセクション（UTF-8）
          20260901-120000_ab12cd34ef56-2.txt     2 つ目以降のセクション（-2, -3, ...）
          20260901-120000_ab12cd34ef56-1.html    HTML セクション（同じ規則。内容のある場合のみ）
  agent/
    user@example.com/
      <group_key>/
        <report_id>/            分析 1 回分の作業ディレクトリ（AGENTS.md, evidence/<message_key>.txt, PROMPT.md, RESULT.log, REPORT.md）
```

- 秘密鍵（パスワードの暗号化とセッション署名に使う 256 ビット鍵）はファイルではなく `settings.secret_key` に置く。
- メールは設定 `mail_keep_days`（既定 180 日、1〜3650）の保持日数を過ぎるまで残す。メールの日付（`messages.date`）が `now - mail_keep_days` より古いメールは、毎日クリーンアップ時刻（設定 `cleanup_time`、既定 02:00）に 1 回実行される `cleanup` ジョブ（7.1 / 7.3。ツール画面と CLI `cleanup` からも実行できる）が原文 `.eml`・本文セクションファイル・索引の行をまとめて削除する（`mailengine.PruneMailbox`、5.6）。所属していたグループは件数を数え直し、メールが無くなったグループは分析結果ごと削除する。受信・索引の再構築ではメールを削除しない。
- エージェントの作業ディレクトリは分析の実行ごとに作る（`report_id` は `agent_reports.id`）。設定 `agent_keep_days`（既定 30 日）より古い実行ディレクトリは同じ `cleanup` ジョブが削除する（6.2 の 5）。

### 3.1 アドレスの安全化（`mailengine.SanitizeAddress`）

- 使用可能文字は `A-Z a-z 0-9 . _ - @ +`。それ以外（`< > : " / \ | ? *`、制御文字、空白、非 ASCII）は `_` に置き換える。
- 末尾の `.` と空白は Windows で不可のため `_` に置き換える。
- Windows 予約名（`CON`, `PRN`, `AUX`, `NUL`, `COM1-9`, `LPT1-9`）に一致する場合は先頭に `_` を付ける。
- 結果が空なら `_`。大文字小文字は保持する（衝突検出のためアドレスは登録時に小文字化して保存する）。
- 安全化後の名前が他のメールアドレスの安全化後の名前と一致する登録・改名は拒否する（`a!b@example.com` と `a_b@example.com` は同じ `a_b@example.com` になる。`CreateMailbox` / `UpdateMailbox` が "mailbox %q conflicts with %q (same data directory name)" で拒否し、改名では改名するメールアドレス自体は除外する）。

### 3.2 メールキーとファイル名

`<日付>_<hash>`。日付は `Date` ヘッダー（無ければ INTERNALDATE、無ければ取り込んだ時刻）の UTC を `YYYYMMDD-HHMMSS` で表し、hash は `sha1(folder + "\x00" + uidvalidity + "\x00" + uid)` の先頭 12 桁（hex）。同一メールは常に同じキーになる。UIDVALIDITY が変わった後の受信で識別情報を付け替えた行（5.1 の 3）はキーを変えない（キーはファイル名であり、索引の再構築は識別情報をキーごとに旧索引から引き継ぐため）。

メール 1 件のファイルはすべてキーから決まる（`mailengine.MessageDir` / `SectionFilePath`）。置き場所は原文ディレクトリの下の `<YYYY>/<MM>/`（キー先頭の年と月。つまりメールの日付の UTC の年月）で、ファイル名はキーそのままとする（DB の `message_key`・URL・原文のダウンロード名と一致させ、ファイル単体でも日時が分かるようにするため）。1 つのディレクトリに全メールを置くと、Windows ではファイル数の増加でファイル操作が大きく遅くなるため月単位に分ける。

原文ディレクトリを走査する処理（索引の再構築の `.eml` 列挙、一時ファイルの削除）は `<YYYY>/<MM>/` の中だけを見る（`walkMailboxFiles`）。索引の再構築は、キーが示す年/月ディレクトリ以外にある `.eml` を無視する。

| ファイル | 内容 |
| --- | --- |
| `<key>.eml` | 原文（受信したバイト列のまま） |
| `<key>-1.txt`, `<key>-2.txt`, ... | 内容のある `text/plain` セクションを MIME 順に 1 ファイルずつ（1 つしか無くても `-1`、以降連番）。UTF-8 |
| `<key>-1.html`, `<key>-2.html`, ... | 内容のある `text/html` セクション（同じ規則） |

- セクションファイルの数は索引の `messages.text_count` / `html_count` と常に一致する（受信・索引の再構築でファイルと行を同時に書く）。空白だけ・骨組みだけのセクションはファイルにならず数えない。番号は欠けなく連続する。
- 索引行に無い情報（ヘッダー一覧、delivery-status の内容、埋め込み元メールのヘッダー）が必要なときは `.eml` を読み取り直す。
- 受信も索引の再構築も本文セクションのファイルは同名で上書きするだけで、削除は行わない（ファイルの整理は保持日数によるクリーンアップだけが行う）。
- IMAP 由来の識別情報（folder / uidvalidity / uid）と受信の記録（size / received_at / fetched_at）はファイルではなく索引行だけが持つ。索引の再構築はそれらを旧索引から引き継ぎ、旧索引に無いキー（手で複製した原文など）は uidvalidity 0、folder `INBOX`、uid = キーの FNV-32（既存行と衝突すれば +1 ずつ空きを探す）、received_at = `.eml` の更新日時で登録する（5.5）。

## 4. 認証と権限

- 利用者はユーザー名、表示名、任意の通知用メールアドレス（`users.email`。空なら通知先にならない）、画面の言語（`users.language`: `ja` / `en`、既定 `ja`）、表示用タイムゾーン（`users.timezone`、IANA 名、既定 `Asia/Tokyo`）、テーマ（`users.theme`: `auto` / `light` / `dark`、既定 `auto` = ブラウザの設定に従う）、役割を持つ。画面での言語・テーマ・入力項目の並びは [画面仕様](画面仕様.md) 2.1。
- 日時の扱い: データベースにはすべて UTC で保存する。API の応答は RFC 3339（UTC）のままで、Web 画面がログイン利用者のタイムゾーンで変換して表示する（[画面仕様](画面仕様.md) 2.1）。CLI の表示はサーバーのローカル時刻。通知メールの日時は受信する利用者のタイムゾーン（7.4 の「言語とタイムゾーン」）。同期時刻（`check_times`）と通知時刻（`notify_time`）はサーバーのローカル時刻で実行する。
- 利用者はユーザー名とパスワード（bcrypt、コスト 12）でログインする（`POST /web/login`。JSON 本文のみ。フォーム形式・クエリ文字列は受け付けない）。メールアドレス（`users.email`）を設定している利用者は、ユーザー名の代わりにメールアドレスでもログインできる（`modules.AuthenticateUser`: 入力に `@` を含めばメールアドレスとして小文字化して照合し、含まなければユーザー名として照合する。ユーザー名には `@` を使えないため両者は衝突しない）。
- メールアドレスは利用者間で一意とする（保存時の小文字化後に比較し、空は対象外）。利用者の作成（初期設定・管理画面・CLI）、プロフィール変更、管理者による編集で、ほかの利用者が使っているアドレスを指定すると拒否する（`models.ErrEmailTaken`。Web API は 400 `{"key":"validation.user.emailTaken"}`）。
  - UNIQUE 制約は使わない。`models.InsertUser` / `UpdateUser` / `UpdateUserProfile` が書き込みの SQL 文そのものに「ほかの利用者が同じアドレスを持たない」条件（`NOT EXISTS`）を含め、影響行数 0 のときに `ErrEmailTaken` を返す。SQLite は 1 文を原子的に実行するため、確認と保存の間に別の書き込み（別プロセスの CLI を含む）が割り込むことはない。
  - 更新で現在のアドレスを変えない場合は条件を検査しない。一意化より前に同じアドレスを共有していた利用者も、アドレス以外の項目を変更できる。ただし一度外したアドレスを付け直すことはできない。このような重複がある場合、メールアドレスでのログインは最も古い利用者（id 最小）に対して照合する。
- トークン（`mlc_` + 40 桁 hex、有効期限任意）は利用者と無関係な将来の API 用の予約機能で、ログインには使えない。
- ログインの試行制限（`modules.LoginLimiter`。メモリ上のマップで、再起動で消える）: 接続元 IP（TCP の相手アドレス。転送ヘッダーは信用しない）とログイン名（入力されたユーザー名またはメールアドレス。小文字化・前後空白除去）の組ごとに連続失敗回数を数え、5 回連続で失敗すると 30 秒の待機に入り、待機後にさらに失敗するたびに待機を倍にする（上限 15 分）。待機中の要求はパスワードを検査せず 429 `{"key":"result.session.tooManyAttempts","params":{"seconds":N}}`（`Retry-After` ヘッダー付き）で拒否し、失敗回数には数えない。ログイン成功で記録を消す。失敗（`login failed for "<user>" from <ip>`）と拒否（`login refused for ...`）はサーバーログに残す。1 時間以上動きのない記録は破棄する。
- デフォルトトークン: サーバー起動時に `is_default` = 1 のトークンが無ければ、識別子 `default` のトークンがあればそれをデフォルトにし、無ければ識別子 `default`（無期限、`is_default` = 1）を作成して値をログに 1 度だけ出す。他のトークンの有無は問わず、`default` 以外のトークンを昇格させることはない。自動生成されるのは `default` だけで、利用者の作成や DB ファイルの作成とは連動しない。
- 初回起動で利用者が 0 人のときは Web が初期設定画面（`/setup`）を表示し、最初の管理者を作成する。CLI の `user create --role admin` でも作成できる。`POST /web/setup` はサーバー内のミューテックスで直列化し、ロック内で利用者数を再確認するため、同時に複数の要求が届いても管理者は 1 人しか作られない（残りは 403）。
- セッションは AES-256-GCM で封印した Cookie（`mlc_session`、HttpOnly、SameSite=Lax）。中身は `user_id`、`sha256(password_hash)`、有効期限、保持フラグ。パスワード変更で既存セッションが無効になる。サーバー側にセッション表は無いため、ログアウト（`POST /web/logout`）は Cookie を削除するだけで、複製された Cookie 値は有効期限まで（またはパスワード変更まで）使える。
- HTTPS の前提: サーバーは平文 HTTP だけを話す。ネットワーク越しに使うときは TLS 終端をリバースプロキシで行い、Cookie の `Secure` 属性はプロキシ側で付与する（`proxy_cookie_flags` 等）か、`web_listen` を `127.0.0.1` にしてプロキシ経由以外で到達できないようにする。プロキシは `Host` ヘッダーを書き換えずに渡すこと（9.1 の同一オリジン検査が `Host` と `Origin` を比べるため）。
- 秘密鍵: セッションの封印と保存パスワード（IMAP / SMTP）の暗号化に使う 256 ビットの鍵は `settings.secret_key`（16 進 64 桁）に置く。初回に必要になった時点で生成して保存し、以後どの経路でも再生成しない（読めない・壊れている場合は鍵を作り直さずエラーで止める。鍵を変えると保存済みパスワードが読めなくなるため）。鍵ファイルは作らず、`mailcare.db` のバックアップだけで鍵も保全される。`settings show` は鍵を表示せず、`settings set secret_key` は未知のキーとして拒否する。
- ログイン画面の「ログイン状態を保持する」（`remember`）を付けると Max-Age 付きの永続 Cookie（既定 720 時間、スライド更新は 24 時間に 1 回）になる。付けない場合（既定）はブラウザを閉じると消えるセッション Cookie で、サーバー側の有効期限は 24 時間、更新はしない。初期設定でのログインは保持なし。

## 5. 受信・グループ化（`app/modules/mailengine`）

受信（`FetchMailbox`）、グループ化（`GroupMailbox`）、分析（`agent.AnalyzeGroup`）は互いに独立した関数で、制御側（`app/modules/jobs.go`）がジョブとして個別に、または同期ジョブとして順に呼び出す。受信は判定・グループ化をせず `messages.classified = 0` で索引に載せるだけで、グループ化は `classified = 0` のメールだけを処理する（全件やり直しは `full = true`）。

### 5.1 受信（`FetchMailbox`）

1. IMAP に接続（ポートの既定は 993。`imap_security`: `ssl` = IMAPS / `starttls` / `none`）、ログイン、`folder`（既定 `INBOX`）を SELECT。
2. 対象期間: 索引 DB にそのアドレスのメールが 1 件も無い（初回）なら `initial_days`（既定 90 日）、それ以外は `recent_days`（既定 10 日）。ただし制御側（`jobs.go` の `fetchOne`）が `mail_keep_days`（`ResolveMailKeepDays`）から `now - mail_keep_days` を `FetchOptions.NotBefore` として渡し、`FetchMailbox` は対象期間の開始日と `NotBefore` の遅い方を検索開始日にする（保持日数より前には遡らない。`mailengine` はマスター DB を見ないまま）。開始日が `NotBefore` で決まったときは進捗の "searching since ..." 行に "limited to the mail retention" を添える。`SEARCH SINCE <開始日>` で UID を列挙する（SINCE は INTERNALDATE で判定するため、到着が新しく `Date` ヘッダーだけ古いメールは取り込まれ、次の `cleanup` で削除される）。
   全期間（`FetchOptions.AllTime`。`sync` / `fetch` ジョブの target `*`、ツール画面の受信期間「全期間」、CLI `--all-time`）では対象期間と `NotBefore` を使わず、条件なしの `UID SEARCH`（フォルダーの全 UID）で列挙し、進捗に "searching the whole folder (all time)" を出す。索引に既にある UID を飛ばすのは同じ。保持日数より古いメールも取り込むので、その中のバウンス等はグループ化の後の `cleanup` で IMAP サーバーから削除できる（5.6.1）。保持日数より古い一般のメールは次の `cleanup` で手元から削除され、次の全期間受信で再び取り込まれる。列挙の後の進捗は "found N messages, M new"。
3. フォルダーの UID はそれぞれ別のメールとして扱う。同じ Message-ID のメールがサーバーに複数ある場合（差出人が同じメールを再送したなど）も、UID ごとに原文と `messages` 行を持つ（索引の再構築でも原文ごとに同じ行ができる）。索引に無い (folder, uidvalidity, uid) のみを取り込み、既に索引にある UID は再び受信しない。
   UIDVALIDITY が前回と異なる場合（フォルダーの作り直し）も同じ手順で、新しい UID はすべて未受信として扱う。受信したメールと同じ Message-ID で、識別情報が古い行（同じフォルダーで uidvalidity が現在と違う、または合成 ID（uidvalidity 0））があり、`server_deleted_at` が NULL なら、そのメールは保存せず、その行の folder / uidvalidity / uid を現在の値に付け替える（`models.ReidentifyMessage`。候補が複数あれば size が一致する行、次に date・id の古い行。message_key・受信の記録・ファイルは変えない）。付け替えた数は `FetchResult.Reidentified` に数える。現在の UIDVALIDITY で索引済みの行は付け替えない（同じフォルダーの別 UID は別のメールなので新しい行として保存する）。同時に走った受信が同じ UID を先に登録していた場合（UNIQUE 違反）は、登録済みとして何もしない。
4. 未受信の UID を `FETCH (UID RFC822.SIZE INTERNALDATE)` でサイズと INTERNALDATE を確認した後、`FETCH (UID INTERNALDATE RFC822.SIZE BODY.PEEK[])` で本文を受信する（`\Seen` を付けない）。大きさによる制限や切り詰めは無く、どのメールも丸ごと取り込む。
5. 原文を `.eml` に保存し、読み取った本文セクションを `-1.txt` / `-2.txt` / ... と `-1.html` / `-2.html` / ...（3.2）に保存し、索引に `messages` 行（`classified = 0`）を追加する。行に入れるのはヘッダー（message_id、subject、from_address / from_name、to_address / to_name、date）、IMAP 由来の識別情報と受信の記録（folder、uidvalidity、uid、size、received_at、fetched_at）、セクション数（`text_count` / `html_count`）と受信時点の `body_source`（優先本文の側）。それ以外の読み取り結果（ヘッダー一覧、delivery-status の内容、元メールのヘッダー）はファイルにも DB にも保存せず、必要な時に `.eml` を読み取り直す。`FetchResult`（受信数・付け替え数・UIDVALIDITY）を返す。判定とグループ化は行わない。
6. 受信では保持日数（`mail_keep_days`）による削除を行わない。受信したメールは `Date` ヘッダーに関係なく保存し、保持日数を過ぎたメールの削除は日次の `cleanup` ジョブだけが行う（5.6、7.1）。

### 5.2 読み取り（`ParsedMessage`、メモリ上のみ）

`go-message`（`charset` 登録で IANA / HTML の文字コード名を解決）で読み取る。文字コードは次の順で扱う: (1) 別名表で正規化（`cp932` / `ms932` / `windows-31j` / `x-sjis` → Shift_JIS、`iso-2022-jp-ms` / `-1` / `-2` / `-3` → ISO-2022-JP、`x-euc-jp` → EUC-JP、`utf8` → UTF-8、`latin1` / `cp1252` → Windows-1252 など）、(2) 宣言どおりに UTF-8 へ変換、(3) 宣言が無い・未知・変換失敗のときは自動判定（正しい UTF-8 ならそのまま、ISO-2022-JP のエスケープ列があれば ISO-2022-JP、続いて Shift_JIS、EUC-JP の順に試し、どれも成立しなければ原文バイトを保持）。RFC 2047 のエンコード語（件名・差出人・宛先）と HTML の meta charset にも同じ規則を適用する。`.eml` は受信したバイト列をそのまま保存し、セクションファイル（`.txt` / `.html`）は UTF-8 で書く。ヘッダー: Message-ID、Subject（MIME デコード済み）、From（アドレス / 表示名）、To（アドレス / 表示名）、Date、Return-Path、Auto-Submitted、Content-Type、ヘッダー一覧。本文: 埋め込み元メール（`message/rfc822` / `message/global` / `text/rfc822-headers` 配下。`message/global` は国際化メールの元メールで、`message/rfc822` と同じに扱う）と添付（`Content-Disposition: attachment`）を除く `text/plain` と `text/html` のパートを、種類ごとに MIME 順の**セクション配列**（`TextSections` / `HTMLSections`）として持つ（`Content-Disposition: inline; filename=...` の text/plain もセクションになる）。内容のあるセクション（plain は空白以外の文字がある、HTML はタグ・スタイル・スクリプト・コメントを除いた後に文字が残る。骨組みだけの HTML は無し）だけを数え、`text_count` / `html_count` に記録して 1 セクション 1 ファイル（3.2）で保存する。本文の大きさは制限しない（受信にも大きさの上限は無く、取り込んだメールの本文はすべて保存する）。`ParsedMessage` はメモリ上だけの構造体で、ファイルにも DB にも直列化しない（グループ化・索引の再構築は `.eml` から読み取り直す）。

判定・抽出に使う本文の規則（優先本文と副本文、`body_source`）は [メール判定仕様](メール判定仕様.md) 2.1。

### 5.4 グループ化（`GroupMailbox`: `category.go` + `grouping.go`）

グループ化は判定の規則（5.3）で 1 通ずつ判定し、グループに束ねる。

- 実行の部品（`modules.groupOptions(mb)`。`groupdns.go`）: 制御側は `GroupMailbox` / `Reindex` の実行ごとに、その監視アドレス `mb` の部品（送信元、DNS 検証、送信元の取得とそのキャッシュ）を作り直して渡す（何も解決しない）。DNS 検証の有効・無効でどの部品を渡すか、監視アドレスの一覧を読めないときにジョブをエラーで終えることは [メール判定仕様](メール判定仕様.md) 4.4 の「実行場所」。
- グループ化の 1 メールの手順（`groupMessage`）: `.eml` を読み取り（5.2）→ 対象判定（監視アドレスと送信元を渡す。`classifyWithSources` → `ClassifyWith`。送信元の取得をいつ行い、取得が不完全なときどう判定するかは [メール判定仕様](メール判定仕様.md) 2.6）→ `failed` / `delayed` なら抽出（`ExtractBounce`。同 3 章）→ 診断文に名前解決の失敗があれば検証（`dnsVerification.verdict`: 直接の問い合わせの可否（`aboutSentMail`）、保存済みの結果の再利用、検証と、マスター DB の `dns_checks` への保存。同 4.4）→ 検証結果が `exists` なら、通知元が送信側のメールサーバーかの判定（同 4.4）→ カテゴリ判定（`CategorizeWith`。同 4.1・4.4）、DMARC 集計レポートなら不合格の記録ごとのカテゴリ判定（`dmarcRecordsFor`。同 4.2）。ここまで（判定・抽出・検証・解決・カテゴリ判定）はすべて**トランザクションを開く前**に行い（`planGrouping`）、SQLite の書き込みトランザクションを保持したままネットワークに出ない。その後に実行が取り消されていれば何も書かず、メールは `classified = 0` のまま残る → 索引への書き込みを 1 つのトランザクションで行う: (1) 関係するグループを `UpsertGroup`（説明列のみ）、(2) `bounces` 行を `group_key` 付きで upsert（`bounces` 行を持たないメールは古い行を削除。`models.DeleteBounce`）し、`dmarc_records` の行をそのメールの分だけ入れ替える（`models.ReplaceDMARCRecords`。記録が無ければ削除だけ）、(3) 関係するグループごとに件数を数え直し（`RefreshGroupCounters`: 所属メール数、宛先アドレス（`bounces.recipient`）と相手側 IP（`bounces.remote_ip` と `dmarc_records.source_ip`）の空以外の種類数、最古 / 最新のメール日時。`bounces` と `dmarc_records` をそれぞれ `group_key` で絞ってから合わせる）、対応対象で、そのバウンスまたは記録のパターンをグループの最新の決着した報告（完了した報告、または分析不可で終わった報告）が扱っていなければ `needs_analysis = 1`（`models.PatternCovered`）、(4) `messages` 行の判定列を更新（`UpdateMessageClassification`。`classified = 1` になるのはここ）。順序が groups → bounces / dmarc_records → messages なので、トランザクションが使えない状況で途中で止まっても「未分類のまま」に倒れ、判定済みなのに詳細が無いメールは生じない（`models` の関数は `*sql.DB` と `*sql.Tx` の両方を受ける `models.Execer` を取る）。`.eml` が読めないメールは飛ばして `classified = 0` のまま残す（次回再試行）。グループ化は必ず原文から読み取り直す（セクションファイルは書き換えない。再生成は索引の再構築で行う）。
- 再確認: 対応済・無視のグループ（再確認待ちでないもの）にメンバーを入れたときは、上の分析フラグの判定の代わりに再確認の判定（`recheckBasis.sendsBack`。[メール判定仕様](メール判定仕様.md) 4.5）を行う。再確認待ちのグループは未対応と同じ規則（最新の決着した報告が扱っていないパターン）で分析フラグを立てる。
- 増分: `classified = 0` のメールだけ処理する。グループの件数はメールごとのトランザクション内で数え直す。分析の要否はパターンで決める: 完了した報告は分析時点のグループのパターンキーを `agent_report_patterns` に記録し（6.2）、新しいバウンスまたは DMARC の記録のパターンが最新の決着した報告（完了した報告、または分析不可で終わった報告）に無い対応対象グループにだけ `needs_analysis = 1` を立てる。完了報告の無いグループ（新規グループを含む）は最初のバウンスまたは記録で立つ。既に扱ったパターンの通知が増えただけなら件数を更新するだけで再分析しない（同じ原因の通知が届き続けるグループを定時の同期のたびに分析し直さないため）。`RefreshGroupCounters` 自体は件数を数えるだけで旗を立てない。対象外グループ（`actionable` = 0）は `needs_analysis` = 0 のまま。どのメールが `bounces` 行・`dmarc_records` 行を持ってグループに入るかは [メール判定仕様](メール判定仕様.md) 1 章。処理済みは `classified = 1`。
- 全件（`full = true`）: `ClearMailClassification`（1 トランザクションで `bounces` と `dmarc_records` を全削除し、`messages` の判定列（`is_bounce` / `bounce_kind` / `rule` / `body_source` / `classified`）を戻す）後に全メールを処理し、`DeleteEmptyGroups` で空グループを消す（状態・対応履歴（`group_state_changes`）・分析結果もカスケードで消える。判定の規則・送信元の設定・DNS 検証の結果で所属が変わり、メンバーがすべて別のグループへ移ったグループも同じ。[メール判定仕様](メール判定仕様.md) 4.4 の「通知のグループが変わるとき」）。既存グループの状態と分析結果は保持する（キーが同じ限り）。報告が扱ったパターンが変わらなければ再分析の旗は立たない（パターンを記録していない報告しか無いグループは立つ）。
- 戻り値 `GroupResult`: 処理したメール数、自動通知の数（`is_bounce` = 1。DMARC 集計レポートを含む）、`GroupsTouched`（この実行で分析の旗が立った対応対象グループのキー）、グループ総数。

### 5.5 索引の再構築・再判定

- `Reindex`（受信相当 + 全件グループ化）: まず旧索引（`<address>.sqlite`。直接開く）から (a) `messages` の message_key ごとの IMAP 識別情報と受信の記録（folder、uidvalidity、uid、size、received_at、fetched_at、server_deleted_at。`models.ListMessageSources`）、(b) `groups` の状態の列（state、state_updated_at、state_reason、state_note、needs_recheck、needs_analysis）、(c) `agent_reports` の全行と `agent_report_patterns` の全行、(d) `group_state_changes` の全行と `group_state_change_patterns` の全行を読み出し、`<address>.sqlite.rebuild` に新しい索引を構築する（これも `models.OpenMailIndex` で作るので、マイグレーションの適用はロックファイル `<address>.sqlite.rebuild.migrate.lock` で直列化される。11 章）。旧索引は `models.OpenMailIndex` で開くので、読み出す前に最新のスキーマまでマイグレーションされる（古い版の索引からも引き継げる）。開けない・読めない場合だけ何も引き継がずに作り直す。ディレクトリの `.eml` を全件読み取り（本文セクションは 1 セクション 1 ファイルで同名のファイルを上書きする。ファイルの削除は行わない）→ 行挿入（(a) にあるキーは旧行の識別情報をそのまま、無いキーは合成 ID: uidvalidity 0、folder `INBOX`、uid = キーの FNV-32、received_at = `.eml` の更新日時。合成 ID の挿入が UNIQUE 違反になったときは uid を +1 して最大 1000 回まで再試行し、それでも入らなければ進捗に "error: skipping <key>: ..." を出して `ReindexResult.Skipped` に数え、他のメールの索引は続ける。読めない `.eml` も同様に数える）→ 判定 → グループ化。キーが再び現れたグループには状態の列・対応履歴（記録した再確認キーを含む。元の `id` のまま）・分析結果（扱ったパターンを含む）を引き継ぎ（未対応と再確認待ちのグループの `needs_analysis` は旧値 OR 対応対象で最新の決着した報告（完了した報告、または分析不可で終わった報告）が扱っていないパターンがある。`models.GroupHasUncoveredPattern`。対応済・無視で再確認待ちでないグループは、メンバーのどれかが再確認の条件に当てはまれば再確認待ちにする（`groupSentBack`。[メール判定仕様](メール判定仕様.md) 4.5）。再確認キーの無い履歴の行は、引き継いだ後にメンバーから記録する）、現れなかったグループの報告は捨てる。報告は元の `id` のまま挿入する（`models.RestoreAgentReport`。実行ディレクトリ `data/agent/<address>/<group_key>/<report_id>/` との対応を保つため。以後の新しい報告は引き継いだ最大 id より後の id を得る）。最新の決着した報告の対応者区分を再適用し（`reapplyReportResponsible`。6.2 と同じく確定値 `sender` / `recipient` / `domain` のときだけ。`unknown`・空・不正値は機械判定の値を残す）、成功したときだけ本体と入れ替える（`swapIndexFiles`: 旧索引の削除と `.rebuild` の改名は、Windows で開かれたままのファイルに対して失敗し得るため、100 ms 間隔で最大 5 秒再試行してからエラーにする）。失敗・中断（コンテキストのキャンセル）時は `.rebuild`（と `-wal` / `-shm` / `-journal`）を必ず削除し、旧索引はそのまま残る。
- 再判定は `GroupMailbox(full = true)`: `messages`・`groups`・`agent_reports` を残し、`ClearMailClassification`（`bounces` と `dmarc_records` の全行と `messages` の判定列を消す）後に `.eml` を読み取り直して判定とグループ化をやり直す。グループは `UpsertGroup` で説明列だけ更新され（状態は保持）、最新の決着した報告（完了した報告、または分析不可で終わった報告）が扱っていないパターンのバウンスまたは DMARC の記録があったときだけ `needs_analysis` が立つ。メールが 1 件も無くなったグループは `DeleteEmptyGroups` で削除され、その報告と対応履歴もカスケードで消える。最新の決着した報告の対応者区分を再適用する（索引の再構築と同じく確定値のときだけ）。
- 索引の再構築・再判定でも保持日数による削除は行わない。`.eml` があるメールは日付に関係なく索引に載せ直し、保持日数を過ぎたものは次の `cleanup` ジョブが削除する（5.6）。
- 索引 DB を開くと未適用のマイグレーションが当たる（11 章。ジョブ、索引の再構築、CLI が同じ索引を同時に開いても、適用は 1 プロセスずつ）。開くことで索引の再構築が起きることはない。列を足した結果、既存の行に値を入れ直す必要があるときは再判定（または索引の再構築）で行う。

### 5.6 保持日数による削除（`PruneMailbox`）

`cleanup` ジョブ（7.1）が対象アドレスごとに呼ぶ。`keep`（`mail_keep_days` を日数から換算。正の値のみ）を受け取り、次の順で処理する。

1. 索引の `messages.date`（`Date` ヘッダー、無ければ INTERNALDATE、無ければ取り込んだ時刻。すべて UTC）が `now - keep` より古い行を古い順に列挙する（`models.ListMessagesOlderThan`: id、message_key、text_count、html_count、所属グループのキー（`bounces` の group_key と、そのメールの `dmarc_records` の group_key））。
2. 各行について、本文セクションファイル（`<key>-1.txt` 〜 `<key>-<text_count>.txt`、`<key>-1.html` 〜 `<key>-<html_count>.html`）を削除してから原文 `<key>.eml` を削除する（無いファイルは飛ばす。原文を最後に消すので、途中で失敗しても原文が残り索引の再構築でセクションを作り直せる）。空になった月ディレクトリと年ディレクトリも削除する。ファイルを消せなかった行は残して次回に持ち越し、残りの行の処理は続ける。
3. 行を削除する（`models.DeleteMessage`。`bounces` 行と `dmarc_records` 行は ON DELETE CASCADE で消える）。
4. 削除したメールの所属グループごとに `RefreshGroupCounters` で件数・宛先数・IP 数・初回/最終日時を数え直す（`RefreshGroupCounters` は `needs_analysis` を立てない）。メールが 1 件も無くなったグループは `DeleteEmptyGroups` で削除し、その `agent_reports` はカスケードで消える（実行ディレクトリは `agent_keep_days` の規則で消える）。
5. `PruneResult`（削除したメール数 `Removed`、削除したグループ数 `RemovedGroups`）を返す。削除があったときだけ進捗に "removed N message(s) older than D days[, M group(s) left empty and removed]" の 1 行を出す。失敗は `errors.Join` でまとめ、途中までの結果と一緒に返す。コンテキストのキャンセルはその時点で打ち切り、消した分のグループは数え直す。

併せて `cleanup` ジョブは、原文ディレクトリ（年/月ディレクトリ）に残った書き込み中の一時ファイルの残骸（`.<name>.<random>.tmp`。原子的な書き込みが中断されたもの）のうち更新日時が 1 日より古いものを削除する（`RemoveStaleTempFiles`。削除があれば進捗に "removed N stale temporary file(s)" の 1 行を出し、結果行の件数には含めない）。

受信の検索開始日は保持日数より前に遡らない（5.1 の 2）ので、削除したメールが次の同期で再び受信されることはない（到着日が保持日数内で `Date` ヘッダーだけが古いメールと、全期間の受信を除く）。

### 5.6.1 サーバー上の保持日数による削除（`DeleteFromServer`、`serverdelete.go`）

`cleanup` ジョブ（7.1）が、有効なメールアドレスで `server_keep_days`（メールアドレスごとの設定。画面の表示名は「サーバーでの保持日数」。`mailboxes.detail_info`。0〜3650、0 は削除しない、新規登録の既定 60（`mail_keep_days` の方が短ければその値）、設定の追加前に保存したアドレスは 0）が 1 以上のときだけ、手元の保持日数による削除（5.6）より**前に**呼ぶ（先に手元の行が消えると、そのメールはサーバーから削除できなくなるため）。

`server_keep_days` は `mail_keep_days` 以下でなければ保存できない（`checkServerKeepDays`。Web・CLI・API 共通。超えると `validation.mailbox.serverKeepDaysOverMailKeep`）。ただし更新で値が保存済みの値のまま（後から `mail_keep_days` を短くしたために超えている）なら、他の項目の変更を妨げないよう受け付ける。`cleanup` は `server_keep_days` と `mail_keep_days` の短い方の日数でサーバーから削除する（`effectiveServerKeepDays`。短くなったときは進捗の日数に "(limited to the mail retention)" を添える）。`mail_keep_days` を過ぎたメールは同じ `cleanup` で索引から消え、その後はサーバーから削除できなくなるため。

1. 索引から候補を選ぶ（`models.ListServerDeletionCandidates`）: 判定済み（`classified` = 1）で、処理対象または迷惑の規則で判定したメール（`rule` が `mailengine.serverDeletionRules` のいずれか。一覧と理由は [メール判定仕様](メール判定仕様.md) 5 章。グループの状態は問わない）のうち、メールの日付（`messages.date`）が `now - 日数`（上記の短い方）より古い、`server_deleted_at` が NULL（削除済みのメールは再び試みない）、フォルダーがメールアドレスの監視フォルダー、`uidvalidity` が 0 でない（受信したことのない原文から索引した行は除く）。まだ判定していないメール（`classified` = 0。受信のみでグループ化していないもの）は対象にならない。候補が無ければ接続しない。
2. 接続してフォルダーを選択する。サーバーが UIDPLUS（または IMAP4rev2）に対応していれば、手順 4 で指定した UID だけを `UID EXPUNGE` で消す。対応していないサーバー（通常の `EXPUNGE` しか無く、`\Deleted` の付いたメールをまとめて消す）では次の手順で消す: (a) `UID SEARCH DELETED` で、今回の対象以外に `\Deleted` の付いたメール（他のメールソフトが付けたもの）があれば何も消さず `ErrOtherDeletedFlags` を返す（次回のクリーンアップで再試行）、(b) 対象に `\Deleted` を付けた直後にもう一度調べ、対象以外が増えていれば付けた印を外して同じエラーにする、(c) 対象だけであれば `EXPUNGE` する。(b) と (c) の間のごく短い間に他のメールソフトが印を付けたメールは一緒に消えるが、それはそのメールソフトが削除しようとしたメールである。参考: Dovecot（Mailu も IMAP は Dovecot）、Cyrus、Gmail、Microsoft 365 は UIDPLUS に対応している。
3. 候補のうち `uidvalidity` が現在のフォルダーの UIDVALIDITY と違うものは飛ばす（フォルダーが作り直されて UID が別のメールを指している可能性があるため）。
4. 200 件ずつ、エンベロープの Message-ID を読み出して索引の `message_id` と照合する（山括弧と前後の空白を除いて比較）。一致したものだけに `\Deleted` を付け（`STORE +FLAGS.SILENT`）、`UID EXPUNGE` でそれらの UID だけを完全に削除する（ゴミ箱への移動やアーカイブはしない）。索引に Message-ID が無い、または一致しないものはサーバーに残す。UID がサーバーに既に無いもの（他のメールソフトで削除済み）は削除済みとして扱う。
5. 削除した（または既に無かった）行に `server_deleted_at` を記録する。原文と行は手元の保持日数まで残り、メール詳細に「サーバーからの削除日時」を表示する。索引の再構築では `server_deleted_at` を引き継ぐ（5.5 の (a)）。
6. `ServerDeleteResult`（削除数 `Deleted`、残した数 `Skipped`）を返し、進捗に対象件数・飛ばした件数・削除数を出す。

この節の削除対象（処理対象と迷惑）の定義と、件数（`stats.target_messages` / `stats.junk_messages`）と手順 1 の候補が同じ規則の一覧を参照する決まりは [メール判定仕様](メール判定仕様.md) 5 章。

### 5.8 PDF レポート（`app/modules/pdfreport`）

- 描画は `codeberg.org/go-pdf/fpdf`（純 Go）でサーバーが行う。ブラウザの印刷には頼らない。
- 用紙は A4 縦、余白は左右 18mm・上 16mm・下 20mm（下余白の中にフッター: 罫線、「MailCare - <レポート名> - <表示名>」、「ページ / 総ページ」）。自動改ページは使わず、部品ごとに残りの高さを見て改ページする（見出しは続く内容の先頭と同じページに置く。1 ページに収まらない箱は改ページ位置で分ける）。
- フォント: 本文は BIZ UDPゴシック（モリサワ、SIL Open Font License 1.1。Regular / Bold の TTF を `embedded/fonts/` に置き、バイナリに埋め込む。PDF には使った字形だけをサブセットで埋め込む）。コード（対応単位、判定元、診断テンプレート、グループキー、統計の値）は ASCII だけなら Go Mono（`golang.org/x/image/font/gofont/gomono`）、日本語を含めば本文のフォント。
- 折り返しは自前（`document.wrap`）: 改行、空白の後、日本語の文字の前後で折り、行頭禁則（閉じ括弧・句読点・小書きの仮名・長音など）と行末禁則（開き括弧）を守る。1 行に収まらない語は溢れる位置で折る（fpdf の `SplitText` / `MultiCell` は漢字の位置で折ると、その字を落とすため使わない）。
- 色は Web 画面のライトテーマのトークン（`frontend/tailwind.config.js`）。バッジの色分け（カテゴリ・対応状態・重大度など）も画面と同じ。
- 文言は要求した利用者の言語の言語ファイル（`modules.LanguageFile`）から画面と同じキーで引き、日時は利用者のタイムゾーンで画面と同じ形（日本語 `2026/09/17 14:05`、英語 `09/17/2026, 14:05`）。出力日時にはタイムゾーン名を添える。PDF の文書情報にタイトル（「<表示名> - <レポート名>」）、作成アプリ（MailCare と版）、言語、作成日時を入れる。
- グループのレポート（`WriteGroupReport`）: 見出し（アプリ名とレポート名、表示名、メールアドレス、出力日時）、概要（バッジ（再確認待ちは「対応済（再確認）」「無視（再確認）」）、カテゴリの説明、項目を 2 段組み。診断テンプレートとグループキーは全幅。対応済・無視なら対応内容または判断理由と詳細を全幅で添える）、対応履歴（新しい順に日時・状態・選んだ理由・詳細・変更者。無ければその旨）、統計（宛先・IP・MTA を件数付きで全件、2 段組み。無ければ「-」）。表示名とバッジの出し分けは Web 画面の `groupHeadline` とグループ詳細の概要カード（[画面仕様](画面仕様.md) 5.4）と同じ規則。

### 5.9 対応状態と再確認

- 状態の変更（`modules.GroupStateInput` → `modules.ChangeGroupState`。Web のアラート一覧・グループ詳細、CLI `groups set-state`）は 1 トランザクションで、`groups` の状態の列（`state`、`state_updated_at`、`state_reason`、`state_note`。`needs_recheck` は 0 に戻す）を書き、`group_state_changes` に 1 行（変更者は Web ではログイン中の利用者のユーザー名、CLI では空）を足し、その時点のメンバーの再確認キーを `group_state_change_patterns` に記録する。`needs_analysis` は、未対応に戻したときは対応対象で最新の決着した報告が扱っていないパターンがあれば 1、対応済・無視にしたときは 0。同じ状態をもう一度設定でき（再確認待ちのグループの新しい判断）、そのときも履歴を残して記録し直す。
- 入力: 対応済はコード（対応内容）が必須で、詳細は任意（どのコードでも書ける）。無視はコード（判断理由）が必須で、詳細は `other` のときだけ保存し（任意）、それ以外のコードでは送られても捨てる。未対応はコードも詳細も持たない（送られても捨てる）。詳細は前後の空白を除き、空なら NULL、2,000 文字まで（`validation.group.stateNoteTooLong`）。コードが無ければ `validation.group.resolveActionRequired` / `validation.group.ignoreReasonRequired`、状態に合わないコードは `system.invalidRequest`。
- 対応内容のコード（`models.ResolveActions`、画面の表示は `value.resolveAction.<コード>`）: `delisting` ブラックリストの解除を申請した / `dns_fixed` 送信ドメインの DNS 設定（SPF・DKIM・DMARC）を修正した / `server_fixed` 送信サーバーの設定を修正した / `sender_changed` 差出人アドレスを見直した / `content_changed` 送信内容や添付ファイルを見直した / `volume_adjusted` 送信量や送信速度を調整した / `recipient_fixed` 宛先アドレスを修正または削除した / `recipient_asked` 宛先ドメインの管理者に連絡した / `other` その他。
- 判断理由のコード（`models.IgnoreReasons`、`value.ignoreReason.<コード>`）: `temporary` 一時的な問題で、すでに解消しているため対応不要 / `recipient_side` 宛先側の問題のため対応できない / `input_error` 宛先アドレスの入力誤りのため対応できない / `stopped_sending` この宛先への送信をすでに停止しているため対応不要 / `spoofing` 監視ドメインを騙った第三者による送信のため対応できない / `external_service` 送信に利用している外部サービス側の問題のため対応できない / `false_positive` 誤検知のため対応不要 / `low_impact` 影響が小さいため対応不要 / `test_mail` テストまたは検証用のメールのため対応不要 / `other` その他。コードで保存し、画面・PDF・通知メールは見る人の言語で表示する。エージェントにはコードではなく英語の説明を渡す（6.3）。
- 再確認: 対応済・無視のグループを再確認待ち（`needs_recheck` = 1）にする条件、再確認キー、再確認までの日数とその既定値は [メール判定仕様](メール判定仕様.md) 4.5。設定 `recheck_days` は、既定値と違う値だけを `category=days` のカンマ区切りで保存する。
- 分析（6.2）: 再確認のグループは、最新の状態変更の日時を境にした依頼文で分析する。未対応に戻したグループは、前の判断を背景として依頼文に載せる。
- 表示: アラートの状態タブ（「対応済（再確認）」「無視（再確認）」を含む）と件数の画面は [画面仕様](画面仕様.md) 5.3、件数の API は 9.2 の `GET .../groups`（`counts`）、通知メールは 7.4。
- 既存データ（索引マイグレーション `0004_group_state_changes.sql`）: その時点で対応済・無視のグループに、今の状態と変更日時（無ければ更新日時）で履歴を 1 行作る（コード・詳細・変更者なし）。再確認キーは SQL で計算できないため、索引を開いたとき（`mailengine.OpenIndex` の `fillStateChangePatterns`）に、キーの無い状態変更へその時点のメンバーから記録する。対応済・無視のグループの `needs_analysis` は 0 に戻す。

起動引数は `Command()` の後に、モデルが設定されていれば `ModelArgs(model)`、推論レベルが設定されていれば `ReasoningArgs(level)` を足したもの（`providerCommand`）。どちらも空なら `Command()` のまま（CLI の既定・CLI 側の設定）。

- モデル名は `agent.ValidateModel`（英数字で始まり英数字と `. _ : / @ + -` のみ、100 文字以内。先頭が `-` の値はオプションと誤認されるため拒否）で検証し、保存値が不正なら未指定として扱う。
- 推論レベルは `agent.ValidateReasoningEffort`（英小文字のみ、20 文字以内）で形を検証し、保存時に `agent.CheckReasoningEffort` でモデルとの組み合わせを検証する: モデル指定ありでそのモデルの受け付ける値が分かっていれば、その一覧に無い値は拒否する。モデル未指定（CLI の既定のモデル）なら既知の全モデルの値の和集合で判定する。受け付ける値が分からない（キャッシュが無い、指定したモデルが載っていない）ときは形だけ検証する（モデル名は自由入力で、キャッシュは参考情報のため）。推論レベルに対応しないプロバイダーで空以外は拒否する。
- 検証は保存する組み合わせ全体に対して行い、拒否されたときは何も保存しない（`modules.CheckAgentSettings` / `SaveAgentSettings`）。モデルだけを変える場合も保存済みの推論レベルと合わなければ拒否する（CLI は先に推論レベルを変えるよう案内する）。プロバイダーを別のものに変えると `agent_model` と `agent_reasoning_effort` を削除する（名前も値もプロバイダーごとに違うため）。保存済みの値が実行時に使えなくなった場合（CLI の更新など）は、通常の分析失敗として理由が記録される。
- `codex`: 起動コマンドは `codex exec --sandbox read-only --skip-git-repo-check`（プロンプトは stdin）。モデル指定時は `--model <モデル>`、推論レベル指定時は `-c model_reasoning_effort="<値>"`（Codex に推論レベル専用のオプションは無く、設定の上書きで渡す。値は TOML として解釈されるので引用符付きの文字列にする）を足す。`Models()` と `ReasoningLevels()` は Codex CLI がモデル選択用に保存しているキャッシュ `$CODEX_HOME/models_cache.json`（`CODEX_HOME` 未設定なら `~/.codex`）の `models[]` から読む: `Models()` は `visibility` が `list` のものを `priority` 順に（サインイン中のアカウントで使えるモデル）、`ReasoningLevels()` は非表示のモデルも含めて `slug` ごとの `supported_reasoning_levels[].effort`。このファイルは Codex の内部形式で公開仕様ではないため、無い・読めない・形式が違う場合は空とする。`ParseUsage()` は出力冒頭の `--------` で囲まれたヘッダーの `model:` / `reasoning effort:` 行、回答部分（エコーされたプロンプトより後）の `exec` 行の数（実行コマンド数）と `tokens used` の次の行（または同じ行）の数値（`54,394` の区切りは除く）を読む。ヘッダーが無い出力（Codex の出力でない）ではコマンド数も NULL にする。
- プロバイダーの有無は `exec.LookPath` で判定する。

分析はグループ化の一部ではなく、グループ化の完了後に制御側が「対応対象かつ `needs_analysis = 1`（新規グループ、最新の決着した報告（完了した報告、または分析不可で終わった報告）が扱っていないパターンのバウンスが来たグループ、前回の分析が失敗したグループ、再確認待ちになった対応済・無視のグループ（[メール判定仕様](メール判定仕様.md) 4.5））」のグループについて投入する（`models.ListGroupsNeedingAnalysis`。状態は問わない。対応済・無視で再確認待ちでないグループの `needs_analysis` は状態変更で 0 になり、グループ化でも分析でも立たない）。対象外（宛先側）のグループは自動では分析しない（グループ詳細の「分析」で個別に実行できる。9.2 の `.../analyze`）。

### 6.2 実行手順（`AnalyzeGroup`）

1. `agent_reports` に `running` 行を作る。その id を名前にした実行ごとの作業ディレクトリ `data/agent/<address>/<group_key>/<report_id>/`（`agent.RunDir`。`<address>` は 3.1 で安全化した名前）を作り、`embedded/templates/agent/<provider>/**`（codex では `AGENTS.md`）があれば複製する。1 回の分析の成果物（証拠、プロンプト、CLI の出力、報告）はこのディレクトリに閉じ、失敗した実行が前の実行のファイルに触れることはない。
2. 証拠を用意する（`agent/evidence.go`、`BuildEvidence`）。エージェントにはメールの保存先を読ませず、MailCare が判定の根拠を切り出して渡す。
   - グループの全メンバー（`models.ListGroupBounces`: バウンス行と DMARC の記録 + メールキー・日時・受信日時（バウンスのみ。`messages.received_at`）・`body_source`）をパターン（[メール判定仕様](メール判定仕様.md) 4.3）ごとに集計する: 件数、宛先数（DMARC の記録は送信 IP の一覧）、初回 / 最終日時。件数の多い順に並べ、`P1`、`P2`、... と呼ぶ。
   - パターンごとに最新の 1 通を見本（`S1`、`S2`、...。最大 `MaxEvidenceSamples` = 5）とし、`.eml` を読み取り直して次を取り出す: 分類（カテゴリと `category_rule`）、診断文と取った場所、通知の From と件名、delivery-status の項目（そのバウンスの宛先のブロック。無ければ 1 つ目）、返送された元メールのヘッダー（From、To、Subject、Date、Message-ID、DKIM の `d=`、Authentication-Results、Received-SPF）、本文の抜粋。DMARC の記録の見本は `.eml` を読まず、索引の記録からレポートの情報と記録の全項目を取り出す（[バウンス分析 プロンプト仕様](プロンプト仕様/バウンス分析%20プロンプト仕様.md) 2.6）。
   - 本文は判定の根拠が入っている方だけを使う: 診断文を本文から取った場合はそのセクション（`diagnostic_source`。HTML はテキスト化）、delivery-status から取った場合や診断文が無い場合は判定に使った本文（`body_source` の種類のうち状態コードを含むセクション、無ければ 1 番目）。text と HTML の両方がある通知では、もう一方の本文は「判定に使っておらず内容が違う可能性があるので使わない」と明記する。
   - 抜粋は空行の連続を 1 行に畳み、診断文（先頭 40 文字）→ 状態コード → 宛先を含む行を中心に最大 `MaxExcerptLines`（40）行（診断文を delivery-status から取った場合は本文は補足なので半分）。1 行は 300 文字まで。切った箇所には `[TRUNCATED: ... evidence/<key>.txt]` を付ける。通知に無い値は `(not found)` と明記する。
   - 診断文が名前解決の失敗（[メール判定仕様](メール判定仕様.md) 4.4。`mailengine.ParseDNSFailure`）を報告するバウンスの見本には、取り出した名前・種別・一時 / 恒久・通知元（`reporting_mta`）と、MailCare が保存した検証（結果・検証日時・通知の受信日時、`dns_checks.detail` の各行を `| ` 付きで。プロンプトは 12 行・1 行 300 文字まで、結果の値は 40 文字まで。証拠ファイルは全行）を加える。検証が無ければ `DNS verification: (not found: this name was not verified by MailCare)`。`agent` はマスター DB を開かないので、検証は `AnalyzeInput.DNSCheck`（コールバック）で得る。`analyze` ジョブは `analyzedns.go` の `dnsCheckLookup` を渡す。`dns_checks` を読むだけで問い合わせはせず（DNS 検証が無効でも渡す）、[メール判定仕様](メール判定仕様.md) 4.4 の「結果の保存と再利用」の期間（`dnscheck.ReuseRange`。名前と種別（空なら MX）が同じもの）で最も早い検証を選ぶ。ただし権威 DNS にも問い合わせたかどうか（`dns_checks.direct`）は問わないので、直接の問い合わせの対象の通知（同 4.4）では分類に使ったものと違う検証が載ることがある。どちらの検証かは証拠の 1 行目の末尾 `; authoritative servers asked yes` / `; authoritative servers asked no (resolvers only)` で示す。この見本があるか DNS のカテゴリのグループでは、プロンプトに読み方の規則を加える（[バウンス分析 プロンプト仕様](プロンプト仕様/バウンス分析%20プロンプト仕様.md) 2.3・2.4）。
   - 見本ごとの証拠ファイル `evidence/<message_key>.txt`（DMARC の記録は `evidence/<message_key>-dmarc-<記録の id>.txt`）を作業ディレクトリに書く（delivery-status の全項目・全ブロック、返送された元メールのヘッダー、本文セクションの全文（2,000 行まで）。DMARC の記録はプロンプトの見本と同じ内容）。エージェントが読んでよいのはこのファイルだけで、条件（6.3）を満たすときに限る。
   - 前回との差分: 最新の完了報告が扱ったパターン（`agent_report_patterns`）があり、その一部だけが新しいとき（更新）は、新しいパターンだけを見本にし、プロンプトに前回の報告を載せる。新しいパターンが無い（手動の再分析）・全部が新しい・前回の報告がパターンを記録していない場合は全体を分析する。
   - 再確認（対応済・無視のグループ。対応履歴の最新の行がその状態のとき）: 報告との差分ではなく、最新の状態変更の日時を境に数える（`EvidenceInput.Decided`、`Evidence.Recheck`）。パターンごとに変更前と変更後の件数、変更後のうち元メールが変更後に送られた件数（`mailengine.SentAt`）、変更後の最初と最後の日時を出す。見本は変更後に初めて現れたパターン（変更後の新しい順）→ 変更後も続いたパターン（同）→ それ以外（件数順）の順に割り当て、パターン内では変更後の最新の 1 通を使う。プロンプトに載せる報告は、状態変更の時点までに完了した最新の報告（判断の根拠になった分析。`reportBefore`）だけで、変更後の報告は載せない。
   - 未対応のグループで、対応済・無視にした後に未対応に戻した履歴があるときは、その判断（最新の対応済・無視の行と戻した日時）を背景としてプロンプトに載せる（`decisionsOf`）。
3. プロンプト（6.3）を組み立てる。プロンプトは stdin で渡し、`PROMPT.md` は CLI の終了後に（成功・失敗・タイムアウト・中止のいずれでも）作業ディレクトリに書く（エージェントが実行中にプロンプトの写しを見つけて読み直さないようにしつつ、実行の履歴として残すため）。`{prompt_file}` でプロンプトをファイルから読むプロバイダーだけは実行前に書く。ジョブの進捗に出す作業ディレクトリは `workspace <group_key>/<report_id>` の相対名だけで、絶対パスは出さない（サーバー上の配置をジョブ履歴に残さないため。ジョブ履歴は管理者だけが見られる。4 章）。進捗には `running <Label> (model <モデル>, reasoning <推論レベル>) on N messages in P patterns, S samples`（指定したものだけ括弧内に出す）と、CLI が報告した `usage: model ..., reasoning ..., tokens ..., commands ...` を出す。
4. CLI を作業ディレクトリを cwd にして実行する（`AgentTimeout` 30 分）。終了コードは信頼せず、出力に有効な REPORT ブロックがあれば成功とする。codex はプロンプト全文をエコーしてから回答するため、出力を解釈する前にプロンプト本文を取り除き、テンプレートのプレースホルダー（`<one or two sentences>` 等）を含む報告や短すぎる報告は失敗として扱う。利用上限・レート制限（`usage limit` / `rate limit` / `429` / `try again at` 等。プロバイダーごとに `DetectRateLimit` で拡張できる）を検出した場合は `error_message` に再試行時刻を含めて失敗にする。成否にかかわらず `UsageReporter` の結果を報告行に記録する（`models.UpdateAgentReportUsage`）。
5. `RESULT.log`（`Result: Success` / `Result: Failure` と理由、抽出した要約・対応者区分・重大度・確度・報告、CLI が報告したモデル・推論レベル・トークン数・コマンド数、全出力）を毎回書き、成功時のみ `REPORT.md` を書く（失敗した実行のディレクトリには `REPORT.md` が無く、成功した実行のディレクトリはそのまま残る。DB も最新の完了報告を表示し続ける）。`CompleteAgentReport`（または `FailAgentReport`）で保存する。成功時は証拠に使ったグループの全パターンキーを `agent_report_patterns` に記録し、`needs_analysis` を「対応対象で、まだ扱っていないパターンがある」（分析中に新しいパターンのバウンスが届いた場合）に合わせる（通常は 0）。META の `responsible` が確定値（`sender` / `recipient` / `domain`）で現在値と異なれば `groups.responsible` を更新する（`models.UpdateGroupResponsible`）。`unknown`・空・不正値では機械判定の値を残す（報告行にはエージェントの回答をそのまま保存する）。失敗理由: プロバイダー未登録、CLI 起動失敗、タイムアウト、中止、REPORT ブロック無し、REPORT はあるが使えない（雛形のプレースホルダー行が残る / 見出しを除いた本文が 40 文字未満 / 要約がプレースホルダー / 報告本文または要約に秘密らしい文字列が含まれる: 64 桁の 16 進、`$2a$` / `$2b$` / `$2y$` で始まる bcrypt ハッシュ、`-----BEGIN`、`mlc_` + 40 桁 16 進、`AKIA` + 16 桁の英大文字数字。理由は "report contains secret-like content"）、利用上限・レート制限の検出。失敗のうち、利用上限（`agent.IsUsageLimitMessage`）と中止（コンテキストのキャンセル）はグループに関係が無いので `needs_analysis` に触れず（`agent_report_patterns` にも記録しない）、グループは分析待ちのまま次回に再試行される。それ以外の失敗（CLI の起動失敗、タイムアウト、REPORT 無し、使えない報告など）はそのグループを今のままでは分析できないとみなし、成功と同じくグループを決着させる: その時点のグループの全パターンを `agent_report_patterns` に記録し、`needs_analysis` を外す（分析中に新しいパターンのバウンスが届いていれば付いたまま）。以後は、決着した報告に無い新しいパターンのバウンスが届くまで、このグループは自動では分析しない。そのため失敗したグループは印が付いたまま次回のスケジュールで再試行される）。`AnalyzeGroup` は失敗でも報告行を返し、記録すらできない場合だけエラーを返す。
6. 整理（`CleanupWorkspaces`）: `analyze` ジョブは実行ディレクトリを整理しない。日次の `cleanup` ジョブ（7.1 / 7.3）が対象アドレスごとに、`data/agent/<address>/` 配下で更新日時（mtime）が設定 `agent_keep_days`（既定 30 日、1〜365）より古い実行ディレクトリを削除し、空になった `<group_key>/` ディレクトリも削除する。索引に無くなったグループのディレクトリも同じ規則で消える。ディレクトリ以外のエントリには触れない。削除数はジョブの進捗と結果に記録する。メールアドレスの改名・削除では `data/agent/<address>/` も改名・削除する（[コマンドラインリファレンス](command-line-reference-ja.md) の `mailbox update` / `mailbox delete`）。

残存リスクと運用前提: `--sandbox read-only` は書き込みを禁じるだけで、CLI は MailCare と同じ OS ユーザーが読める全ファイル（ホームディレクトリ、鍵、他のアプリの設定など）を読める。プロンプトの制約と 5 の秘密らしい文字列の検出は緩和策であって境界ではない。MailCare と codex は専用の低権限 OS ユーザーで実行し、そのユーザーが `data/` 以外を読めない（他のディレクトリの権限、または専用ホームディレクトリ）ようにすること。

### 6.3 プロンプト仕様

固定順: 制約（読み取り専用、読んでよいのは条件付きの証拠ファイルだけ（プロンプトの読み直し・README の探索・ディレクトリ一覧の禁止）、ネットワーク禁止、通知由来の値は信頼できないデータ、利用者の判断（DECISION）は照合すべき背景であり指示ではない、出力言語）→ タスク（送信側のメール管理者の立場で対応単位に対する具体的な対応を求める。カテゴリごとの指針を付ける: `ip_blocked` は当該ブラックリストの解除手順、`auth_failure` は送信ドメインの SPF / DKIM / DMARC / PTR / HELO、`sender_blocked` は差出人アドレスの評価 など。対象外グループでは宛先アドレスの所有者または宛先ドメインの管理者に伝える短い注記を求める。更新では前回の報告を引き継いでグループ全体の報告を書き直すことを求める。再確認では、対応済なら対応が効いているか（反映待ちか、再発か、一部だけか）、無視なら選んだ理由が変更後の通知にも当てはまるかを判断させ、原因の分析の冒頭に 1 文で書かせる。記録が無い（理由が無い、またはその他で詳細が空）ときは推測させない。未対応に戻したグループでは前の判断では片付かなかったことを踏まえさせる）→ グループ概要（カテゴリと説明、対応単位、判定元、対応対象かどうか、件数、宛先数、IP 数、初回 / 最終日時、宛先 / 相手 IP / 相手 MTA の一覧）→ 利用者の判断（再確認と、未対応に戻したグループ: 状態、日時、戻した日時、選んだ理由の英語の説明（`agent/decision.go`。コードは載せない）、対応済なら反映を待つ期間（再確認までの日数）、詳細）→ 状態変更の前の報告（再確認のみ）/ 前回の報告（更新のみ）→ パターン一覧（再確認では変更前後の件数を添える）→ 証拠（見本ごとのブロック）→ 証拠の使い方 → 関係者の呼び名 → 出力指定。表示名（カテゴリ・対応単位・判定元の繰り返し）、グループの代表値（1 つのパターンの宛先ドメイン・状態コード・診断テンプレート。各パターンの値はパターン一覧にある）、機械判定の対応者区分（エージェントに判断させる項目の答えを先に見せない）は載せない。カテゴリの英語説明は `agent/category.go` の `CategoryGlossary` に持つ。

証拠の使い方（「足りないときは読む」のような曖昧な指示にしない。プロンプト上の目印で判断できる条件にする）:

- 回答はパターン一覧と証拠から行い、次のいずれかが成り立つときだけコマンドを実行してよい: (a) 抜粋に `[TRUNCATED]` があり、必要な部分（診断文、拒否したホスト、ブラックリスト / ポリシー名、参照 URL）が切れている、(b) 報告に必要な値がプロンプトで `(not found)` になっていて、見本の証拠ファイルにありそうだ、(c) 証拠がグループ概要のカテゴリと矛盾し、抜粋だけではどちらが正しいか分からない。
- 「念のため」「網羅のため」「他のメールも同じか確かめるため」は読む理由にならない。
- (a)〜(c) のときも、その見本の証拠ファイルだけを 1 回ずつ、合計 `MaxEvidenceReads`（3）ファイルまで、`cat` / `sed -n` で読む。スクリプトは書かない。
- それでも原因が確定できなければ推測で埋めず、推測を事実として書かない。原因の分析に、通知が示すこと・足りない情報・送信側のメール管理者が確かめる方法（どの照会・ログ・設定を見るか）を書き、担当が決まらなければ `unknown`、確度は `low` にする。
- 通知の記載（事実）と一般知識を分け、一般知識を通知に書いてあったかのように書かない。
- 機械判定のカテゴリは誤りうる。証拠と食い違えば証拠に従い、分類が誤っているようだと理由とともに書く。

プロンプト注入対策: グループ概要とパターン一覧の機械判定値（`unit_value`、`authority`、`recipient_domain`、`diagnostic_template`、状態コード、相手 MTA、宛先 / 相手 IP / 相手 MTA の各項目）と証拠の見出し行の値（診断文、From、件名、delivery-status と元メールのヘッダー）は、空白・改行の連続を 1 個の空白に畳んで必ず 1 行に収める。一覧は各 30 件（`agent.MaxPromptListItems`）、パターンは 20 件（`MaxPromptPatterns`）までとし超過分は件数で示す。本文の抜粋、前回の報告、利用者が書いた詳細、DNS の検証の証拠行（6.2）は各行の先頭に `| ` を付ける。通知の文字列に含まれる出力マーカー（`<<<MLC`）は `<<< MLC` に崩す。メール本文由来の文字列がプロンプトの行やセクションを増やしたり、REPORT / META ブロックを差し込んだりすることはできない。報告の秘密らしい文字列の検出は 6.2 の 5 を参照。

関係者の呼び名（`=== PARTIES ===`）: 報告が主語にできる関係者は次の 6 つで、それぞれ報告の言語で 1 つの呼び名だけを使わせる（同義語・略称は使わない）。日本語の呼び名は埋め込みテンプレート `embedded/templates/agent/party_names_ja.txt`（1 行 1 名、次の順）に置き、無い・6 行に満たないときは英語の呼び名を使う。あわせて、一人称・二人称の語を使わないよう指示する（MailCare の利用者は送信側の組織とは限らないため。語の扱いはプロンプト仕様 2.5）。プロンプトとカテゴリ用語集の英語の指示文も一人称・二人称を使わず、同じ役割名で書く。

| 順 | 関係者 | 日本語の呼び名 | 英語の呼び名 |
| --- | --- | --- | --- |
| 1 | 送信側（送信サーバー・送信 IP・送信ドメインと DNS レコード・差出人アドレス）を管理する人 | 送信側のメール管理者 | the sending-side mail administrator |
| 2 | 宛先アドレスの所有者（宛先リストの管理者） | 宛先アドレスの所有者 | the recipient address owner |
| 3 | 宛先アドレスでメールを受け取る本人 | 受信者 | the recipient |
| 4 | 宛先ドメイン（メールサーバー・DNS・MX）を管理する人 | 宛先ドメインの管理者 | the recipient domain administrator |
| 5 | 送信 IP を登録しているブラックリストの提供元 | ブラックリストの提供元 | the blacklist provider |
| 6 | MailCare（機械判定） | MailCare | MailCare |

画面の対応者区分の表示は [画面仕様](画面仕様.md) 2.4。

報告の見出し: 英語の見出しは `prompt.go` に持つ。日本語の見出しは埋め込みテンプレート `embedded/templates/agent/report_headings_ja.txt`（1 行 1 見出し、原因 / 影響 / 対応 / 担当の順。`AnalyzeInput.TemplatesFS` から読む）に置き、Go のソースを ASCII のみに保つ。テンプレートが無い、または 4 行に満たないときは英語の既定見出しを使う（報告言語は日本語のまま）。

出力は次の 2 ブロックを各 1 回。

```text
<<<MLC:REPORT>>>
## 原因の分析
...
## 影響範囲
...
## 推奨する対応
1. ...
## 対応すべき担当
...
<<<MLC:/REPORT>>>
<<<MLC:META>>>
{"summary":"1〜2 文の要約","responsible":"sender|recipient|domain|unknown","severity":"high|medium|low","confidence":"high|medium|low"}
<<<MLC:/META>>>
```

`confidence` は原因をどこまで確定できたか: `high` = 通知が原因を直接示している、`medium` = 通知と一般知識から推定した、`low` = 証拠では確定できない（報告に足りない情報を書く）。`low` の報告は要確認として示す（グループ詳細は [画面仕様](画面仕様.md) 5.4、通知メールは 7.4）。

REPORT は最後のマーカー対を採用する。META はコードフェンスを除去し最初の `{` から最後の `}` を JSON として解釈する。解釈できない場合や列挙値が不正な場合は無視する（報告は完了扱い）。要約が空のときは報告本文の最初の見出し以外の段落（200 文字まで）を要約にする。プロンプトの全文と実例は [プロンプト仕様/バウンス分析 プロンプト仕様.md](プロンプト仕様/バウンス分析%20プロンプト仕様.md) を参照。

## 7. ジョブとスケジューラ（`app/modules/jobs.go`, `scheduler.go`）

### 7.1 種別

受信・グループ化・分析は互いに独立したジョブで、制御側が個別にも、同期ジョブとして順にも呼び出す。

| kind | mailbox_id | target | 処理 |
| --- | --- | --- | --- |
| `sync` | 指定 | 空 = 受信期間（5.1 の 2）/ `*` = 全期間（フォルダー全体） | `FetchMailbox` → `GroupMailbox(full=false)` → 対応対象で `needs_analysis` のグループ（新規、最新の決着した報告（完了した報告、または分析不可で終わった報告）が扱っていないパターンのバウンスまたは DMARC の記録が来たもの、前回の分析が失敗したもの）があれば `analyze`（target 空）を投入。結果は `fetched N[, reidentified R], processed P, bounces B, groups G`（`reidentified` は UID を付け替えた数、5.1 の 3。0 なら出さない） |
| `fetch` | 指定 | 空 = 受信期間 / `*` = 全期間 | `FetchMailbox` のみ。結果を `mailboxes` に記録。ジョブの結果は `fetched N[, reidentified R]` |
| `group` | 指定 | - | `GroupMailbox(full=false)` → `analyze`（target 空）を投入 |
| `analyze` | 指定 | 空 = `needs_analysis` かつ対応対象のグループ / グループキー（対象外のグループも可。グループ詳細の「分析」）/ `*` = 対応対象の全グループ | `agent.AnalyzeGroup`（モデル `agent_model`、推論レベル `agent_reasoning_effort`）。分析待ちの印（`needs_analysis`）に触れるのは 3 箇所だけ: グループ化での新規グループ・新しいパターン（付ける）、ツール・グループ詳細からの分析の指示（target が `*` またはグループキーのとき、開始時に対象の対応対象グループへ付ける）、分析の決着（成功、または利用上限・中止以外の失敗で外す、6.2 の 5）。利用上限での打ち切り・上限中の見送りでは触れないので、終わらなかったグループは印が付いたまま次回のスケジュールの分析（target 空）に持ち越される。既存のパターンの通知が加わっただけでは印は変わらない。あるグループの分析が利用上限・レート制限で失敗したら（`agent.IsUsageLimitMessage`）、残りのグループは起動せず（同じく拒否されるだけなので）、進捗に "stopped: N group(s) not analyzed because of the usage limit" を出してジョブをエラーで終える。CLI が解除時刻を示していれば（`try again at 7:22 PM` など。`agent.ParseRetryTime`: 時刻は次に来るその時刻、日付付きはその日時、`3 hours` などは今からの経過）設定 `agent_limited_until` に記録する。記録した解除時刻までは、分析ジョブは CLI を起動せずに見送る（スケジュールの分析（target 空）は結果 "skipped: the agent's usage limit lasts until ..." で成功扱い、ツール・グループ詳細からの明示の分析はその文でエラー）。解除時刻が分からない上限は記録せず、次の同期時刻の同期でそのまま分析を試みる。受信とグループ化は分析とは別のジョブなので、上限中も全アドレス分行う |
| `reindex` | 指定 | - | `Reindex` → `analyze`（target 空）を投入。結果は `messages N, bounces B, groups G[, skipped S]`（索引に載せられなかった原文の数、5.5） |
| `reclassify` | 指定 | - | `GroupMailbox(full=true)` → `analyze`（target 空）を投入 |
| `notify` | NULL | 空 = 通知先へ送信 / `test:<address>` = テスト送信 | 通知メールの組み立てと送信（7.5） |
| `cleanup` | 指定 | - | （有効なアドレスで `server_keep_days` > 0 のときだけ）`DeleteFromServer`（処理対象と迷惑（5.6.1）のうち `server_keep_days` と `mail_keep_days` の短い方を過ぎたものを IMAP サーバーから削除、5.6.1）→ `PruneMailbox`（`mail_keep_days` を過ぎたメールの削除、5.6）→ `RemoveStaleTempFiles`（原文ディレクトリに残った 1 日より古い書き込み中の一時ファイル `.<name>.<random>.tmp` の削除。件数は進捗の 1 行だけで結果行には含めない、5.6）→ `agent.CleanupWorkspaces`（`agent_keep_days` を過ぎた実行ディレクトリの削除、6.2 の 5）→ `DeleteOldProbeMails`（そのアドレスの確認メールの記録のうち、状態に関わらず `mail_keep_days`（7 日より短ければ 7 日）を過ぎた行の削除、7.6）→ `DeleteOldJobs`（完了から 30 日より古い `jobs` 行の削除。ジョブ履歴は全体で 1 つなので毎子ジョブが試み、最初の子が実際に消す）→ `pruneDNSChecks`（`dns_checks` と `sending_source_lookups` の古い行の削除。同じく全体で 1 つ。下記）。結果は `deleted D server mails, removed N messages, M groups, K agent workspaces, J jobs` |
| `probe_send` | NULL | 送信時刻 `YYYY-MM-DD HH:MM`（スケジューラ）/ 空 = 手動送信 | 確認メールの送信（`SendProbes`、7.6）。結果は `sent N probe mail(s)[, F could not be sent]`、送れる状態でなければ `skipped: the probe server is not set` / `skipped: the delivery probe is off` / `skipped: no enabled mailbox has the send check on`。送信時刻付きはスケジューラだけが投入できる |
| `probe_check` | NULL | - | 到着確認（`CheckProbes`、7.6）。結果は `checked N probe mail(s): A arrived, R arrived late, M missing (D newly delayed, F newly failed)[, D deleted from the probe server][, N with another sender (left on the probe server)][; <削除のエラー>][; next check YYYY-MM-DD HH:MM]`、未着の確認メールが無ければ `skipped: no probe mail is waiting`。スケジューラが投入したものは、実行の開始時に `probe_next_check_at` を読み直し、まだならば何もしない（`skipped: the arrival check is not due`） |

- `mailbox_id` が NULL のジョブは「展開ジョブ」で、実行時に対象アドレス（`sync` / `fetch` は有効なアドレスのみ、それ以外（`cleanup` を含む）は無効なアドレスも含めた全アドレス）ごとに同種のジョブを 1 件ずつ投入して即終了する（結果は「queued N jobs」）。これにより全アドレス同期（全処理）は同時実行数（`workers`）の範囲で並列に進む。
- 後続の `analyze` 投入は `agent_enabled` かつプロバイダーの CLI が PATH にあるときのみ行う。`requested_by` は `cli` / `scheduler` / `web:<username>`。展開で作られた子ジョブと後続の `analyze` は親の `requested_by` を引き継ぎ、`jobs.parent_id` 列に親ジョブの id を持つ（直接投入されたジョブは NULL）。
- ジョブの属性はすべて実列である: 進捗（`progress`。最新 100 行）、結果（`result`。完了時の 1 行）、失敗理由（`error_message`）、`parent_id`、3 つの日時（`created_at` / `started_at` / `finished_at`）。JSON 列は持たない。
- `sync` / `fetch` の target は空か `*` だけを受け付け（それ以外は `system.invalidRequest`）、展開ジョブの target は子ジョブに引き継ぐ。target が違えば別のジョブなので、受信期間の同期と全期間の同期は重複とみなさない。スケジューラが投入する同期は常に target 空。
- `cleanup` の子ジョブは上の表の 6 段階（サーバー上の削除、メールの削除、一時ファイルの削除、実行ディレクトリの削除、確認メールの記録の削除（削除があれば進捗に `removed <n> probe mail record(s) older than <日数> days`）、ジョブ履歴の削除）を順に行い、最後にマスター DB の共通の表を整理する（`pruneDNSChecks`。`groupdns.go`）: `mail_keep_days` に再利用の期間（24 時間）を足した期間を過ぎた DNS 検証結果（`dns_checks`。保持中の通知は、受信の最大 24 時間前に検証した結果も使うため。メール判定仕様 4.4）、取得から 90 日を過ぎた送信元の取得結果（`sending_source_lookups`。メール判定仕様 2.7）、取得日時が現在より 1 日を超えて後の取得結果を削除する（全メールアドレス共通なので、どの子ジョブが行っても結果は同じで、何度行っても害はない）。削除があれば進捗に `removed <n> dns check result(s) older than the mail retention (<日数> days) and the 24-hour reuse window`、`removed <n> stored sending source lookup(s) older than 90 days`、`removed <n> stored sending source lookup(s) dated more than 24 hours in the future` を出し（結果行の件数には含めない）、どれかの削除に失敗しても残りは続けて行い、エラーはまとめて返す。日数はメールアドレスの `server_keep_days`（`mail_keep_days` で頭打ち、5.6.1）、`ResolveMailKeepDays`、`ResolveAgentKeepDays`、ジョブ履歴の保持期間（定数 `jobRetention` = 30 日）、一時ファイルの経過時間（`StaleTempFileAge` = 1 日）。前の段階が失敗しても後の段階は行い、削除数を結果行に出したうえで失敗をジョブの失敗（`error_message`）にする（消せなかったものは次回に持ち越す）。メールアドレスが 1 件も無いときは展開ジョブがジョブ履歴の削除と共通の表の整理を行い（ジョブ履歴の削除に失敗しても整理は続ける）、結果は `queued 0 jobs (no mailbox), removed J jobs`（どちらかに失敗したときは `queued 0 jobs (no mailbox)` とエラー）。スケジューラが毎日クリーンアップ時刻に投入するほか（7.3）、ツール画面と CLI `cleanup` からいつでも実行できる。
- 同じ種別・メールアドレス・対象の未完了ジョブがあれば重複投入しない（`HasActiveJob`）。
- 進捗は 500 ミリ秒に 1 回まで DB に書き、最新 100 行（`progressMaxLines`）を保持する。各行は `<追加時刻（UTC、RFC 3339）>\t<メッセージ>` の形で保存する（`stampProgressLine`）。1 件のジョブは 1 つのメールアドレスだけを扱い、アドレスはジョブの行に記録されているので、メッセージにはアドレスを付けない。CLI は端末のローカル時刻で `MM-dd HH:mm:ss <メッセージ>` と表示する（`FormatProgressLine`。Web の表示は [画面仕様](画面仕様.md) 2.5 の「ジョブの進捗」）。サーバー起動時（`ResetStaleJobs`）は `running` のまま残ったジョブと分析結果を `error` にする復旧だけを行い（報告のエラー文は中止の形式 `analysis canceled: interrupted by a server restart` にするので、分析不可とは扱われず、グループは分析待ちのまま次回に再分析される）、完了から 30 日より古いジョブ行の削除は日次の `cleanup` ジョブが行う（7.3）。
- ジョブ履歴（`jobs` 表）はメールアドレスを削除しても残り、`mailbox_id` が NULL になる。削除時はそのアドレスの待機中（`queued`）のジョブを行の削除と同じトランザクションで `canceled`（`finished_at` 付き）にし（`models.CancelQueuedJobsForMailbox`）、実行中（`running`）のジョブがあるアドレスの削除と改名は `ErrMailboxBusy`（"a job is running for this mailbox"。HTTP は 409）で拒否する（`models.HasRunningJobForMailbox`）。`queued` のジョブの取消は Web（`DELETE /api/v1/jobs/{id}`）と CLI（`jobs cancel ID`）から行える（`running` 以降は取り消せない）。`mailbox_id` が NULL のジョブのうち、親ジョブがある（`parent_id` が 0 でない）もの、または `canceled` で結果が空のものは削除済みアドレスのジョブとみなし（`modules.JobOfDeletedMailbox`。`notify` / `probe_send` / `probe_check` は対象外: アドレスを持たず展開もしない）、CLI は "(deleted mailbox)" と表示し、API は `mailbox_address` を空のまま `mailbox_deleted: true` を返す。親の無い展開ジョブは CLI では従来どおり "(all)"。Web の表示は [画面仕様](画面仕様.md) 2.5 の「ジョブの一覧」。

### 7.2 ワーカーと直列化

- ワーカーの数は設定 `workers`（画面の「同時実行数」。既定 2、1〜16。`service start --workers N`、`settings set workers N`、Web の一般設定の「ジョブの実行」）。同時に実行できるジョブ数であり、同時にアクセスするメールアカウント数の上限でもある。
- ジョブは実行時に「資源キー」の集合を占有する。占有中のキーを必要とするジョブは待機し（`queued` のまま）、キーが空いた時点で開始する。

| kind | 占有する資源キー |
| --- | --- |
| `sync`, `fetch` | `host:<imap_host 小文字>`、`mailbox:<address>` |
| `group`, `reclassify` | `mailbox:<address>` |
| `analyze` | `agent`、`analyze:<address>` |
| `reindex` | `mailbox:<address>`、`agent`（索引ファイルを入れ替えるため分析と同時に走らせない） |
| `cleanup` | `mailbox:<address>`、`agent`（分析中に同じアドレスのメールやグループを消さないため、分析と同時に走らせない）。サーバー上の削除を行うアドレス（有効で `server_keep_days` > 0）では `host:<imap_host 小文字>` も占有する（同じ IMAP サーバーの受信と重ねない） |
| `notify` | `notify` |
| `probe_send` | `probe`（送信と到着確認を重ねない） |
| `probe_check` | `probe`、`host:<probe_imap_host 小文字>`（同じ IMAP サーバーの受信と重ねない） |
| 展開ジョブ（mailbox NULL） | なし |

- 同一 IMAP サーバーのアカウントは `host:` キーで直列化され、先行ジョブの完了を待って順に開始する。エージェント CLI は `agent` キーで常に 1 本ずつ実行する。
- ワーカーは `queued` を古い順に走査し、資源キーが空いている最初のジョブを取る（`ClaimNextRunnableJob`）。
- CLI のプロセス内実行（`RunJobInline`）は同じ実行器を使い、そのプロセスが投入したジョブ（展開で生じた子と後続の分析を含む）を順に実行する。そのプロセスのジョブかどうかは `parent_id` の連鎖で判定するので、別のターミナルから同時に投入された CLI ジョブは実行も待機もしない（サーバー稼働時の `--wait` も同じ判定）。

### 7.3 スケジューラ

`check_times`（`HH:MM` をカンマ区切り、ローカル時刻）を読み、`SchedulerTick` ごとに「直前 tick から現在までに到来した時刻」があれば全アドレス同期（`sync`、mailbox NULL）を投入する（同一分に二重投入しない。有効なアドレスが 1 件も無ければ投入しない）。スケジューラは何もできないジョブを投入しない（エラーにもログにもしない。下記の各ジョブの条件）。`check_times` が空なら自動同期は行わない。全アドレスへの展開では、`sync` / `fetch` は無効（`mailboxes.enabled` = 0）のアドレスを除き、それ以外の種別（`cleanup` など）は無効なアドレスも含める。設定変更は即時反映（毎 tick で読み直す）。

利用上限後の分析（`queueAnalysisAfterLimit`）: 設定 `agent_limited_until`（7.1）の解除時刻から `AgentLimitResumeMargin`（10 分）過ぎた最初の tick で、分析待ちのグループの分析（`analyze`、mailbox NULL = 全アドレスに展開、target 空）を投入し、記録を消す。自動分析が無効（`agent_enabled` = 0）、CLI が無い、またはメールアドレスが 1 件も無いときは投入せず記録だけ消す。投入できなかったときは記録を残して次の tick で再試行する。

日次のクリーンアップ（`CleanupDue`）: 設定 `cleanup_time`（`HH:MM`、ローカル時刻、既定 `02:00`。Web の一般設定と `settings set cleanup_time`）を毎 tick 読み、現在時刻以前で直近のクリーンアップ時刻（今日の時刻を過ぎていれば今日、まだなら昨日）の日付が、設定 `cleanup_last_run_date`（前回投入したクリーンアップ時刻の日付、内部用、マスター DB の `settings` 表。未設定なら「一度も無し」）より後であれば `cleanup`（mailbox NULL = 無効なアドレスも含む全アドレスに展開）を投入し、投入できたらその日付を `cleanup_last_run_date` に書く（同じプロセス内では投入した日付も覚えておき、設定の書き込みに失敗しても同じ回を繰り返さない）。サーバー起動時（`Scheduler.Start`）にも同じ判定を行うので、停止中にクリーンアップ時刻を過ぎていれば起動直後に 1 回投入する（その回の分を補う。すでに投入済みの回なら投入しない）。1 日に実行するのは 1 回だけで、時刻を変更した日は、その日の回を投入済みなら翌日の新しい時刻から実行する。不正な保存値は既定の時刻として扱う。`cleanup_last_run_date` が今日より後の日付（時計が進んでいた間に記録されたもの）なら、その日付まで止まらないよう無視する。この 1 日 1 回の `cleanup` が、サーバー上のメール・手元のメール・一時ファイル・エージェントの実行ディレクトリ・ジョブ履歴（完了から 30 日）・DNS 検証結果（`mail_keep_days` + 24 時間）・送信元の取得結果（90 日）・確認メールの記録（`mail_keep_days`。7 日より短ければ 7 日）の保持期間を適用する唯一の定期処理である。

確認メール（`queueProbe`）: `probe_enabled` で確認メールサーバーが設定済みのとき、毎 tick で `probe_send_times` を読み、直前 tick から現在までに到来した送信時刻があれば `probe_send`（target はその回の `YYYY-MM-DD HH:MM`。1 tick で複数到来したら最新の 1 回だけ）を投入する（同一分に二重投入しない。停止中に過ぎた回は遡って送らない。確認メールを送るメールアドレス（`ProbeParticipates`）が無ければその回は投入しない）。送信時刻が来なかった tick では、設定 `probe_next_check_at` の時刻を過ぎていて、`probe_send` も `probe_check` も待機中・実行中でなければ `probe_check` を投入する（送信が次の到着確認を決め直すため。実行中の到着確認があれば、毎 tick の投入とそのログを省く）。未対応の確認メールが無ければ投入せず、未対応の無い到着確認と同じく次の到着確認の予定と失敗の続きを消す（`ClearProbeCheck`）。次の到着確認の時刻は送信と到着確認のジョブが決める（7.6）。

### 7.4 通知（`notify.go`）

- SMTP 設定: `smtp_host`、`smtp_port`（既定 587）、`smtp_security`（`ssl` = SMTPS 465 / `starttls`（既定）/ `none`）、`smtp_username`（空なら認証しない）、`smtp_password_enc`（秘密鍵で暗号化。ユーザー名に属する: ユーザー名を空にすると保存済みパスワードも消し、パスワードは要らない。ユーザー名があるのにパスワード（入力も保存も）が無い保存は `validation.connection.passwordRequired` で拒否する（ユーザー名を設定するとき、またはユーザー名を残してパスワードを消すとき。`modules.errSMTPPasswordMissing`））、`smtp_from`（差出人アドレス。From は `"MailCare" <smtp_from>`。表示名は `net/mail` で組み立てる）。認証は PLAIN、対応していなければ LOGIN。`none` は平文（画面の注意書きは [画面仕様](画面仕様.md) 9.3）。
- 保存済みパスワードの保護: 保存済みパスワードは保存したときの接続先だけに使う。パスワードが保存されている間に、ユーザー名を残したまま接続設定（`smtp_host` / `smtp_port` / `smtp_security` / `smtp_username` を別の空でない値に）を変える更新（`PUT /api/v1/settings/notifications`、CLI `settings set`）は、同じ要求に `smtp_password` が無ければ `smtp_password is required when the connection settings change`（Web API は `validation.connection.passwordRequiredOnChange`）で拒否し、何も保存しない（`modules.ErrSMTPPasswordRequired`）。ユーザー名を空にする更新はパスワードを求めない（保存済みパスワードを消す）。空のパスワード欄は保存済みパスワードを残す。CLI は 1 回に 1 キーしか設定できないため、パスワードが要る接続設定の変更（ユーザー名の設定を含む）ではパスワードを入力させ（`smtp_password` の入力と同じ方式）、まとめて保存する。テスト送信も同じ規則（下記）。
- 保存: 通知設定の更新（`PUT /api/v1/settings/notifications`、CLI `settings set`）は、要求に含まれる項目をすべて検証してから、まとめて 1 トランザクションで保存する（`modules.SaveNotificationSettings`。保存値の読み出し・検証・書き込みを設定のロックの中で行う。11 章の「設定の書き込み」。どれかが拒否されるか書き込みに失敗すれば何も保存しない。SMTP の設定が半分だけ変わることはない）。
- 通知設定: `notify_enabled`（既定 0。有効にできるのは SMTP ホスト（`smtp_host`）と差出人アドレス（`smtp_from`）があるときだけで、保存後の値で判定する。無ければ Web・CLI・API とも `validation.notification.smtpRequired` で保存しない。有効のまま片方を消すことも同じく拒否する）、`notify_time`（`HH:MM`、1 つ、既定 `09:00`。サーバーのローカル時刻）、`notify_interval_days`（1〜7、既定 1 = 毎日）、`notify_user_ids`（通知先の利用者 id をカンマ区切り）、`public_base_url`（例 `https://mailcare.example.com`。空なら `http://<web_listen または localhost>:<web_port>` を使う）、`notify_last_sent_at`（最終送信日時、内部用）。
- 送信条件: SMTP ホストと差出人アドレスがある、通知先に選ばれた利用者のうちメールアドレスが設定されている者が 1 人以上いる、対象グループが 1 件以上ある。いずれかを満たさなければ送信せず、理由をジョブ結果に記録する（`skipped: SMTP host or sender address is not set` / `no recipient is selected` / `none of the selected recipients has an email address` / `no open actionable group has a completed report and no group was sent back for a re-check`）。`notify_enabled` は定時送信だけを制御し、「今すぐ送信」（Web / CLI `notify`）は無効でも送る。成功時の結果は `sent N group(s) to <addresses>`。
- 送信タイミング: スケジューラが `SchedulerTick` ごとに評価し、`notify_enabled` のとき、直前 tick から現在までに `notify_time` が到来し、最終送信日から暦日で `notify_interval_days` 日以上経っていれば `notify` ジョブを投入する（同一分に二重投入しない。再起動後に過去分を遡って送らない。最終送信が無ければ最初の到来で送る）。SMTP サーバーが未設定、または通知先にメールアドレスのある利用者がいなければ投入しない（通知先がいないことはエラーではない）。
- 内容: 全メールアドレスの索引から「対応対象で状態が `open`、かつ完了した分析結果のあるグループ」と「再確認待ちの対応済・無視のグループ（分析結果の有無と対応対象かどうかを問わない。[メール判定仕様](メール判定仕様.md) 4.5）」を集め、本文の冒頭に「MailCare からの通知です。」と件数・日付を置き、メールアドレスごとの見出し（「メールアドレス: <アドレス>」）の下に「[未対応]」「[対応済（再確認）]」「[無視（再確認）]」（英語は `[Open]` / `[Resolved (re-check)]` / `[Ignored (re-check)]`）の小見出しを付けて（グループの無い小見出しは出さない）1 グループ 1 ブロックで並べ、末尾に自動送信である旨と通知設定の URL（`<public_base_url>/settings/notifications`）を置く。未対応のブロックは「カテゴリ名: 対応単位（判定元: <判定元>。判定元が無ければ括弧ごと出さない）」「メール数・宛先数（宛先数は 0 件なら出さない。DMARC のグループなど）」「期間（初回 〜 最終日時）」「要約（`agent_reports.summary`。無ければ報告本文の冒頭。報告の確度が `low` なら先頭に【要確認】。どちらも無ければ「（分析結果の要約はありません）」）」「そのグループを開く URL（`<public_base_url>/alerts/<mailbox_id>/groups/<group_key>`）」。再確認のブロックは、選んだ対応内容（対応済）・判断理由（無視）（言語ファイルの `value.resolveAction` / `value.ignoreReason`。無ければ「（記録なし）」）と詳細（1 行に畳む。無ければ出さない）、メール数と最終日時、要約、URL を載せる。件名は日本語が `[MailCare] 対応が必要なアラート N 件（YYYY-MM-DD）`、英語が `[MailCare] N alert(s) need attention (YYYY-MM-DD)`。本文は UTF-8 の text/plain。差出人は `MailCare <smtp_from>`、件名は RFC 2047、本文は 8bit（998 バイト超の行があれば base64）。
- 言語とタイムゾーン: 通知先の**利用者ごとに 1 通**送り、To にはその利用者だけを入れる（受信者どうしのアドレスは見えない）。文面はその利用者の言語（`users.language`）、日時（件名の日付、初回 / 最終日時）はその利用者のタイムゾーン（`users.timezone`。読めなければサーバーのローカル時刻）で組み立てる（`MailLocale` / `MailLocaleFor`）。テンプレートは `embedded/templates/mail/<種類>_<言語>.txt`（通知 `notification_`、テスト送信 `test_`。件名も同じファイルの `subject` テンプレート）。カテゴリ名と、選んだ対応内容・判断理由の表示名は言語ファイルの `value.category.<カテゴリ>.label` / `value.resolveAction` / `value.ignoreReason`（その言語のファイルが無ければ日本語）を使う。テンプレートも、その言語のファイルが無ければ日本語（`_ja`）を使う（`mailTemplatePath`）。現在は `ja` と `en` がある。グループの収集は 1 回だけ行い、同じ言語・タイムゾーンの利用者には同じ文面を使い回す。分析結果の要約はエージェントが書いたまま（報告の言語。現在は日本語）で、利用者の言語には訳さない。確度 `low` の印は日本語が【要確認】、英語が `[Needs review]`。
- 一部の宛先だけ送信に失敗した場合は、1 人でも届けば送信済みとして `notify_last_sent_at` を更新し、ジョブの結果に `sent N group(s) to <届いたアドレス>; failed: <アドレス>: <理由>; ...` と失敗を残す（ジョブは成功扱い）。全員に失敗したときだけエラーにして、送信日時は更新しない。
- テスト送信（`POST /api/v1/notifications/test`、`{to?}` 省略時は操作した利用者のメールアドレス。要求に含めた接続設定で送るので、保存前の値を試せる（画面は [画面仕様](画面仕様.md) 9.3）。ユーザー名が空なら認証しない。保存済みパスワードを使えるのは接続設定が保存値と同じときだけで、ユーザー名があってパスワードを使えなければ拒否する。9.2）は SMTP 設定だけを検証する短いメールを送る。言語とタイムゾーンは、宛先がいずれかの利用者の通知用アドレスならその利用者のもの（`MailLocaleForAddress`）、そうでなければ Web では操作した利用者のもの、CLI（`notify --test --to`）では既定（日本語・サーバーのローカル時刻）。「今すぐ送信」（`POST /api/v1/notifications/send`）は条件を満たせば通常の通知を送り、`notify_last_sent_at` を更新する。

### 7.5 CLI からの投入

ジョブのコマンド（`sync` / `fetch` / `group` / `analyze` / `reindex` / `reclassify` / `notify` / `cleanup` / `probe send` / `probe check`）は `runJobs`（`cli_jobs.go`）で実行する。どのコマンドが完了を待つか、表示、終了コードは [コマンドラインリファレンス](command-line-reference-ja.md) の 2 章に記載する。

- 投入先: 設定 `web_port` の `/control/status` が応答し、その `data_dir` が CLI のデータディレクトリと一致する（`modules.LocalServer` + `ServerStatus.ServesDataDir`）なら `/control/jobs` に投入する（`SubmitJobToServer`）。応答が無ければプロセス内で直接実行する（`RunJobInline`、7.2）。これにより同じ索引 DB への同時書き込みを避ける。
- 同じポートで別のデータディレクトリのサーバーが稼働している場合（CLI 側 DB で解決した mailbox_id はそのサーバーでは別のアドレスを指す）は投入せず、サーバーが無いときと同じくプロセス内で実行する。CLI のデータディレクトリのサーバーがコントロールトークンを拒否した場合（`ServerStatus.RefusedOwnDir`。9.1）は、同じデータに触れることになるため、プロセス内でも実行せずに止まる。
- 何もできないジョブは投入前に拒否する（`modules.ManualJobRefusal`。CLI は `ExitConfig`、Web API と `/control/jobs` は 400）: `analyze` は AI エージェントの CLI が無い（`result.agent.unavailable`）か、記録した利用上限が続いている（`result.agent.usageLimited`）とき、`probe_send` は確認メールが無効・未設定（`result.probe.disabled` / `result.probe.notConfigured`）か送るメールアドレスが無い（`result.probe.noMailbox`）とき、`probe_check` は無効・未設定か未対応の確認メールが無い（`result.probe.nothingOpen`）とき。スケジューラ（7.3）と、ほかのジョブが投入する自動分析はこれを通さない。
- 完了を待つときは、投入したジョブとその子・後続の分析を `parent_id` の連鎖で追う。サーバーの稼働時は `waitForJobTree` が `/control/jobs/{id}` を `CLIJobPollInterval`（1 秒）ごとに読み、プロセス内では `RunJobInline` がその連鎖のジョブだけを実行して `reportFollowUps` が結果を表示する（7.2）。

### 7.6 確認メール（`probe.go`、`mailengine/probe.go`）

監視アドレスから実際にメールを送り、確認メールサーバー（IMAP）に届くかを確かめて、メールの送受信の遅延と障害に気付けるようにする。

- 設定（`settings` 表。管理者のみ）: 確認メールの宛先 `probe_address`、確認メールサーバーの接続（`probe_imap_host` / `probe_imap_port`（既定 993）/ `probe_imap_security`（既定 `ssl`）/ `probe_imap_username` / `probe_imap_password_enc`（秘密鍵で暗号化）/ `probe_imap_folder`（既定 `INBOX`。改行を含む名前は不可。保存と接続テストで同じ検証 `normalizeProbeFolder`））、送信時刻 `probe_send_times`（既定 `07:00,11:00,15:00,19:00`、サーバーのローカル時刻。24 個まで（`validation.probe.sendTimesTooMany`）、互いに 15 分以上空ける（日をまたぐ間隔も。`validation.probe.sendTimesTooClose`））、遅延判断時間 `probe_delay_minutes`（既定 15 分。送信時刻の最も短い間隔（日をまたぐ間隔を含む。送信時刻が 1 つなら 24 時間）より短くなければならない: `validation.probe.delayNotBeforeNextSend`。送信時刻か遅延判断時間を変えるときに検証する）、障害判断時間 `probe_failure_minutes`（既定 60 分。遅延判断時間より長くなければならず、違反は `validation.probe.failureNotAfterDelay`）、有効 / 無効 `probe_enabled`（既定無効。宛先・ホスト名・ユーザー名・パスワードが揃っていなければ有効にできない: `result.probe.notConfigured`。有効な間はこれらを空にできない: `validation.probe.offFirst`。先に無効にする。無効にすると未対応の確認メールは対応済になる）。確認メールの宛先には監視するメールアドレスを使わない（確認メールが監視アドレスのメールとして取り込まれる）。識別子 `probe_subject_tag`（既定 `MC`。英数字と `.` `_` `-` の 16 文字まで: `validation.probe.subjectTagInvalid`。変えても失敗の続きは消さず、変える前に送った確認メールも追える）。確認メール専用のメールボックスを推奨するが必須ではない（下記のとおり確認メールしか変更・削除しない）。確認メールサーバーを共有する MailCare どうしは別の識別子にする。保存（`SaveProbeSettings` = `UpdateSettings` + `SettingsUpdate.Probe`）は保存値を読んで全項目を検証し、設定のロックの中で 1 トランザクションで書く（11 章）。パスワード保存中に接続（ホスト・ポート・接続方式・ユーザー名）を変えるときはパスワードも必要（`ErrProbeIMAPPasswordRequired`）。パスワードは API で返さず、保存の有無（`imap_password_set`）だけを返す。有効 / 無効を切り替える、または接続（ホスト・ポート・接続方式・ユーザー名・パスワード・フォルダー）を変えると、失敗の続き（下記）を消す。無効にすると、未対応（`pending` / `delayed` / `failure` / `send_failed`）の確認メールをシステムが対応済にする（理由 `probe_disabled`、対応者は空）。
- 送信確認（メールアドレスごと。管理者のみ）: 「送信確認をする」（`mailboxes.detail_info.probe_enabled`、既定オフ）をオンにしたメールアドレスの SMTP 接続（`smtp_host`（「SMTP サーバー」。送信元の判定にも使う欄で、接続先でもある）と `smtp_port`（必須）・`smtp_security`（既定 `starttls`）・`smtp_username`（任意。空は認証なし）・`smtp_password_enc`（IMAP のパスワードと同じく秘密鍵で暗号化））。送信確認がオンで、ホスト名があり、メールアドレスが有効なものだけが送る（`ProbeParticipates`）。オンでホスト名・ポートが無ければ `validation.mailbox.smtpHostRequiredForProbe` / `validation.mailbox.smtpPortRequired`。ユーザー名があるときは使えるパスワードが必要で、入力が無く保存も無ければ `validation.connection.passwordRequired`、保存済みのパスワードが別の SMTP 接続（ホスト名・ポート・接続方式・ユーザー名のどれかが違う）のものなら `validation.connection.passwordRequiredOnChange`（`smtpPasswordCheck`。テスト送信と同じ規則。ユーザー名が空ならパスワードは消す）。オフのときは `smtp_host` だけを保存し、ほかの項目（パスワードを含む）は消す。送信確認をオフにするか、メールアドレスを無効にすると、そのアドレスの未対応の確認メールをシステムが対応済にする（理由 `probe_disabled`）。パスワードは API で返さず（`smtp_password_set` だけ）、SMTP の接続の項目は一般利用者には伏せる（送信確認のオン / オフは全利用者に返す。`redactMailboxDTO`、9.2）。パスワードはログにも進捗にも書かない。
- 送信（`probe_send`、`SendProbes`）: 確認メールが無効なら送らない（`skipped: the delivery probe is off`。API の「今すぐ送信」は 400 `result.probe.disabled`、送るメールアドレスが無いときは 400 `result.probe.noMailbox`（画面のボタンは [画面仕様](画面仕様.md) 5.2）。スケジューラはその回を投入しない。7.3、7.5）。対象のアドレスごとに 1 通、その SMTP 接続で `probe_address` へ送る（エンベロープと From はそのアドレス、表示名はアドレスの表示名（無ければ `MailCare`）。From は `net/mail` で組み立て、ASCII の表示名は引用符で囲み（`,` `:` `@` などを含んでも壊れない）、それ以外は RFC 2047 の encoded-word にする。998 オクテットを超えるヘッダー行は空白で折り返す）。確認番号は乱数の 16 進 16 桁（小文字）で、件名 `[<識別子>:<確認番号>] Probe <YYYY-MM-DD HH:MM> <address>`（ASCII のみ。日時はその回の送信時刻、手動送信は送った時刻。サーバーのローカル時刻）と `X-MailCare-Probe` ヘッダー（確認番号だけ）に入れる。テスト送信の件名は `[<識別子>] Probe test ...`（確認番号なし）。本文は `templates/mail/probe_<言語>.txt`（既定の言語）。1 通ごとに `probe_mails` に送信日時を記録し（遅延はメールごとに測る）、SMTP で失敗したものは `send_failed`（段階 `failure`、エラー文付き）として記録する。最初のメールを送る前に、次の到着確認 `probe_next_check_at` を送信開始の遅延判断時間後にし（送信中に古い予定の到着確認が走らないように）、送り終えたら `probe_last_send_at` と、次の到着確認（送信終了の遅延判断時間後。それまで予定していた到着確認はこれに置き換わる）を 1 回の設定の書き込みで記録する。送信のたびに（送るメールアドレスが無いときも）、まだ知らせていない遅延・障害のメール（下記）を送る。各メールを送る直前に確認メールとメールアドレスの状態を読み直し、無効になっていれば送らない（記録しない）。送信の終わりに、送らなくなったメールアドレスの未対応の確認メール（確認メールが無効ならすべて）をシステムが対応済にする（`closeStaleOpenProbes`。無効化と送信が重なったときのため）。送信時刻付きの `probe_send`（target `YYYY-MM-DD HH:MM`）はスケジューラだけが投入でき、手動（Web・CLI・`POST /api/v1/jobs`）は target 空の「今すぐ送信」だけ。
- 到着確認（`probe_check`、`CheckProbes`）: 始めに、送らなくなったメールアドレスの未対応の確認メール（確認メールが無効ならすべて）をシステムが対応済にする（`closeStaleOpenProbes`）。未対応の確認メール（`pending` / `delayed` / `failure` / `send_failed`）が 1 通も無ければ確認メールサーバーを読まない。あれば、未着（`pending` / `delayed` / `failure`）の確認メールを判定のために、`send_failed` の確認メールを遅れて届いた場合のために、前の回のものも含めて 1 回の IMAP 接続で探す（`mailengine.CheckProbeServer`。接続は最長 3 分（`ProbeIMAPTimeout`））。検索の条件は SUBJECT（部分一致）・SINCE・BEFORE だけで、ヘッダーの検索は使わない（独自ヘッダーの検索に何も返さないサーバーがあるため）。(1) 到着（毎回）: `UID SEARCH SINCE <最も古い未対応の確認メールの送信の前日。14 日前（`ProbeSearchMaxDays`）より前には遡らない> <未対応の確認番号の SUBJECT を 50 件ずつ OR でまとめたもの>`（件数の上限なし）。(2) 記録した確認メールの掃除: 同じ形で、閉じた（未対応でない）行のうち確認メールサーバーから削除していない（`deleted_at` が空の）ものの確認番号。通常は送信から 1 日以内の行を 2 日前以降で、1 日 1 回の掃除（`probe_wide_sweep_at`）と前回の削除に失敗した後は送信から 14 日以内の行を 14 日前以降で探す。(3) 記録の無い確認メールの掃除（1 日 1 回の掃除のときだけ。削除に失敗した後の到着確認では行わない）: `UID SEARCH BEFORE <前日> SUBJECT "[<今の識別子>:"`（SINCE なし、フォルダー全体）。古い UID から 2000 件（`ProbeCleanupScanMax`）まで読み、削除は 500 件（`ProbeCleanupMax`）まで（消せないメールが古い側に溜まっても後ろのものを止めない）。残りは次の日以降。見つかったメールは UID・INTERNALDATE・ENVELOPE と `BODY.PEEK[HEADER.FIELDS (Subject X-MailCare-Probe)]` だけを読む（既読などのフラグを変えない）。件名のどこか（中継が `[SPAM]` などを前に付けてもよい。取得した Subject 欄、その RFC 2047 のデコード（非 ASCII の印を付けて符号化し直す中継のため）、ENVELOPE の件名の順に試す）に `[<識別子>:<16 進 16 桁>]` があり、`X-MailCare-Probe` ヘッダーがちょうど 1 つでその番号と等しいものだけを確認メールとみなす（件名を引用した返信・転送は対象外。件名の識別子は (3) 以外では比べないので、識別子を変える前に送った確認メールも見つかる）。候補のうち、確認番号が `probe_mails` にあり（状態は問わない）、差出人がその行の `address` と一致するものだけを検証済みの確認メールとし（`sortProbeMessages`）、INTERNALDATE（無ければ確認した時刻）を到着日時とする。確認番号は一致したが差出人が違うもの（From を書き換える中継など）は、未対応の行のものだけを数え、進捗と、届いていない行の `error_message` に `token matched, sender differs (<記録した差出人> vs <見つかった差出人>)` と残し（エラー文は管理者のみ）、サーバーに残す。未着の行に検証済みの確認メールがあれば到着日時と遅延（到着 - 送信）を記録し、遅延が遅延判断時間未満なら `arrived`、以上なら `recovered`（段階は実際の遅延と既に付いた段階の重い方）。見つからないものは経過時間を遅延として更新し、遅延判断時間以上で `delayed`、障害判断時間以上で `failure` にする（`ApplyProbeCheck`）。`send_failed` の確認メールが届いていれば `recovered` にする（段階 `failure` とエラー文は残す）。行の更新は、その行がまだ未着（または `send_failed`）のときだけ行う（`models.UpdateProbeMailCheck`。到着確認の間に利用者が対応済にした行はそのまま残し、件数にも数えず、遅延・障害のメールも送らない）。段階（`level`）は下がらず、回復・対応済になっても残る。
- 確認メールサーバーからの削除: 確認メールの保持期間は設けない。消すのは次の 2 種類だけ。(a) 検証済みの確認メール（確認番号が `probe_mails` にあり、差出人がその行の `address` と一致）: 見つかれば到着の記録を DB に書き込んだ後に消し（書き込めなければ何も消さない）、その行の見つかったものがすべて消えたら `deleted_at` を記録する（以後 (2) で探さない。一部のバッチの削除に失敗したときも、消えた分の行には記録する）。消し残し（削除に失敗したもの、対応済の後に届いたもの）は (2) で探す（送信から 1 日以内の行は毎回、それより古い行は送信から 14 日まで 1 日 1 回の掃除と削除に失敗した後だけ）。`deleted_at` の記録後に届いた同じ確認番号のメールは、今の識別子で到着から 24 時間経てば (3) で見つかり、検証済みとして消える。(b) それ以外の確認メール（記録の無いもの、閉じた行の確認番号で差出人が違うもの）: 件名の識別子が今の識別子で、INTERNALDATE から 24 時間（`ProbeLeftoverMinAge`）以上経ち（確認メールサーバーを共有するほかの MailCare がまだ探しているかもしれないため）、確認番号が未対応の行のものでないときだけ消す（差出人は比べない。1 回の到着確認で古い UID から 500 件まで）。記録の無いものは (3) で、差出人が違うものは (2) でも見つかる。前の識別子の確認メールは記録があるときだけ (a) で消える。これ以外のメール（確認メールの形でないもの、到着時刻の無いものを含む）は変更も削除もしない。削除は選んだ UID だけを `UID STORE +FLAGS.SILENT (\Deleted)` と UID EXPUNGE で消す（UIDPLUS / IMAP4rev2 が無いサーバーでは、ほかに `\Deleted` のメールが無いときだけ EXPUNGE し、あれば今回は削除しない。5.6.1 と同じ `expungeUIDs` / `expungeOnly`）。削除に失敗しても到着確認は成功とし、理由を `probe_last_delete_error` に記録して（管理者だけが見る。[画面仕様](画面仕様.md) 5.2）次の到着確認で再び試みる（(2) を 14 日前まで広げる。(3) は 1 日 1 回のまま）。`probe_last_delete_error` と `probe_wide_sweep_at` は、到着確認の間に設定が変わっても記録する（失敗の続きだけは記録しない）。確認メールサーバーのアカウントにはメールを削除できる権限が必要。
- 次の到着確認（`NextProbeCheckAt`）: 未着が残れば、最後の送信から遅延判断時間ごと（障害判断時間の手前まで）、次に最後の送信から障害判断時間後、以降は障害判断時間ごと（既定では送信の 15・30・45・60 分後、その後 120・180 分後…）。刻みは最後の送信から数えるので、手動の到着確認を挟んでも変わらない。ただし、未着の確認メールが次の段階（遅延判断時間・障害判断時間。メールごとの送信日時から）に達する時刻のほうが早ければ、その時刻にする（`probeLevelCheckAt`。1 分（`ProbeCheckCoalesce`）以内に重なる時刻と予定の到着確認はまとめ、1 回の送信のメールごとに到着確認が分かれないようにする）。未着が無ければ次の送信まで到着確認しない（`send_failed` だけが未対応なら、送信のたびに 1 回だけ探す。未対応が無い到着確認は確認メールサーバーを読まないが、まだ知らせていない遅延・障害のメールは送る）。送信中は到着確認しない、確認メールサーバーを読めないときは間隔を空けて再試行する（下記）点は変わらない。次の到着確認の時刻と、確認メールサーバーを読んだ（読もうとした）到着確認の時刻 `probe_last_check_at`・エラー `probe_last_check_error`（空は成功）は、到着確認の終わりに 1 回の設定の書き込みで記録する。エラー文は確認メールサーバーの名前を含むので管理者にだけ返す（一般利用者には `error`）。
- 確認メールサーバーを読めないとき: 続けて失敗した回数 `probe_check_failures` と最初の失敗の日時 `probe_check_failing_since` を記録し、再試行は 10 分後（`ProbeCheckRetryInterval`）から失敗のたびに倍にして、障害判断時間を上限とする（障害判断時間が 10 分より短くても 10 分。`probeRetryAfter`）。数えるのは確認メールサーバーの失敗（接続・ログイン・検索・取得・時間切れ）だけで、DB や設定の読み出しの失敗（パスワードを復号できないなど）はジョブのエラーとして `probe_last_check_error` に残し 10 分後に再試行するが、失敗の続きは変えない。ジョブが取り消されたとき（サーバーの停止など）は次の到着確認を 10 分後にするだけ。最初の失敗から障害判断時間以上読めないままなら、通知先の利用者へ 1 回だけ知らせる（`templates/mail/probe_unreadable_<言語>.txt`。エラー文は管理者の通知先にだけ載せ、一般利用者には詳細は管理者に表示される旨を載せる。送った日時 `probe_unreadable_notified_at`）。確認メールサーバーを読めた到着確認と、探す確認メールが無い（または確認メールが未設定の）到着確認で、これらとエラーを消す。到着確認の結果を記録するときに設定を読み直し、到着確認の間に有効 / 無効・接続・パスワード・失敗の回数が変わっていれば、失敗の続きとエラーは書かない（その変更が続きを消しているため）。到着確認の失敗の画面での表示は [画面仕様](画面仕様.md) 4 章・5.1・5.2。
- 遅延・障害のメール（`notifyProbeAlerts`）: 確認メールごとに、遅延になったときに 1 回（`delayed` で `delay_notified_at` が空のもの）、障害（`failure`）または送信失敗（`send_failed`）になったときに 1 回（`notified_at` が空のもの）知らせる。まだ知らせていないものを、通知設定の SMTP サーバーから通知先の利用者（`notify_user_ids` のうちメールアドレスのある利用者。一般利用者も含む）へ、利用者ごとの言語とタイムゾーンで 1 通にまとめて送る（障害と遅延を分けて載せる。件名は `[MailCare] 確認メールの障害 N 件・遅延 M 件（日時）` など。`templates/mail/probe_alert_<言語>.txt`。`notify_enabled` は関係しない）。遅延を知らせる前に障害になったものは障害としてだけ知らせ、`delay_notified_at` も記録する（後から遅延は知らせない）。知らせる前に届いた・対応済になったものと、遅延を知らせた後に届いたものには送らない。日時は受信者のタイムゾーンで示す。送信のエラー文は SMTP サーバーの名前を含むので、管理者の通知先にだけ載せ、送信失敗があるときは一般利用者に詳細は管理者に表示される旨を載せる。1 人でも届けば `delay_notified_at` / `notified_at` を記録し、同じ確認メールを同じ段階で二度知らせない。SMTP や通知先が無いなどで送れなければ、次の送信か到着確認（未着が無いときも）で再び試みる。
- 手動の対応（`ResolveProbe`、すべての利用者。アラートの状態変更と同じ）: `delayed` / `failure` / `send_failed` の確認メールを、理由（`server_recovered` / `arrived_elsewhere` / `maintenance` / `config_error` / `probe_server_issue` / `other`。必須。`probe_disabled` はシステムだけが使い、選べない）と詳細（任意、2000 文字まで）を付けて `resolved`（対応済）にする。以後は到着確認の対象外。`pending`（まだ遅延判断時間前）・到着済み・対応済のものは `result.probe.notOpen`（HTTP 409）で拒否する。
- 記録の保持: 画面の記録（`probe_mails`）は、状態（未着・遅延・障害・送信失敗を含む）に関わらず、送信からメールの保持日数（`mail_keep_days`。7 日（`MinProbeRecordKeepDays`）より短ければ 7 日）を過ぎたものを、毎日のクリーンアップ（`cleanup` の子ジョブがそのメールアドレスの行を）で削除する。メールアドレスを削除するとその記録も削除される。
- 確認番号: 秘密ではない（件名に入るので、監視アドレスに届くバウンスなどを読める人には見える）。それでも一般利用者には返さない（`token` は空、件名は `[<識別子>] Probe ...` にする）。削除と到着の判定は確認番号だけに頼らず、記録した差出人とも照合するが、差出人を偽ったメールで到着を装うことはできるため、確認メールサーバーでは SPF や DMARC に失敗したメールを拒否する。
- テスト: 確認メールサーバーの接続テスト（`TestProbeServer`。保存済みパスワードは保存した接続にだけ使う）と、メールアドレス画面のテスト送信（`TestProbeSMTP`。確認番号の無いテストメールを宛先へ送り、記録しない。保存済みパスワードは、保存したメールアドレスの保存した SMTP 接続にだけ使う）。

## 8. CLI

コマンド・オプション・値の規則・稼働中のサーバーとの関係・パスワードの入力・終了コードは、コマンドラインリファレンス（[日本語](command-line-reference-ja.md) / [English](command-line-reference.md)）に記載する。CLI の振る舞いを変えたときは、両方を同じ構成のまま更新する。ここには実装上の事項だけを置く。

- コマンドの木は `main.go` の `CLI` 構造体（kong）で定義し、各コマンドの `Run` は `app/modules/cli*.go`（2.1）に置く。ヘルプに出す既定値は `kong.Vars` で定数から差し込む（ヘルプと実装の既定値をずらさないため）。
- 終了コードは `app/modules/errors.go` の定数。コマンドは `ExitError` を返し、`main` が `Error: <文>` を標準エラーに出してその終了コードで終わる。`ExitError` 以外のエラーは `ExitGeneral`。kong が検出する引数・フラグの誤り（kong 自体は 80 で終わる）は `kong.Exit` で `ExitArgument`（2）に揃える（ヘルプの表示は 0 のまま）。
- 入力の検証は Web と同じ関数を通す: 利用者は `CreateUserFrom` / `UpdateProfile` / `ChangePassword`、メールアドレスは `CreateMailbox` / `UpdateMailbox`（`MailboxInputFrom` で保存値を詰めてから、指定したオプションだけを上書きする）、グループの状態は `GroupStateInput` → `ChangeGroupState`（変更者は空）、一覧の範囲は `GroupListScope` → `models.GroupScope*`、設定は `applySetting`（通知は `SaveNotificationSettings`、確認メールは `SaveProbeSettings`、DNS 検証は `saveDNSCheck`。7.4、7.6）。`settings set` の空の値は既定値に置き換えてから同じ検証を通す。
- パスワードの入力は `promptPassword`（`readSecret` を 2 回呼んで照合する。端末は `golang.org/x/term` で表示せずに読み、それ以外は共有の `bufio.Reader`（`stdinReader`）から 1 行ずつ読む。読み手を 1 つにして、パイプの後続の行を失わないようにする）。
- メールアドレスの改名は、原文ディレクトリ・索引 DB（`-wal` / `-shm` を含む）・エージェントの作業領域を先に改名してから行を更新し、行の更新に失敗すればファイルを元の名前に戻す（`UpdateMailbox`、`renameMailboxData`）。
- `mailbox list` の順（ドメイン → アドレス）は `models.ListMailboxes` の順で、ダッシュボード・Web の一覧・通知・全アドレスへの展開と共通。
- ジョブのコマンドは `runJobs` で実行する（7.5）。

## 9. HTTP

### 9.1 共通

- `/api/v1/*` は Cookie 認証。未認証は 401 `{"key":"system.unauthorized"}`。権限不足は 403 `{"key":"system.forbidden"}`。入力の誤りは 400 `{"key":"<キー>","params":{...}}`。
- エラー応答の形（`/api/v1/*` と `/web/*`）: `{"key": "<キー>", "params": {...}}`（`params` は文言に差し込む値。無ければ省く）。キーは言語ファイルの完全なキー（例 `validation.user.emailTaken`）で、英語の文は返さない（10.1 の「言語ファイル」）。対象が無ければ 404 `system.notFound`、実行中のジョブがあるメールアドレスの変更・削除は 409 `result.mailbox.busy`、それ以外の入力の誤り・操作の拒否は 400、内部エラーは 500 `system.internal`（原因はサーバーログにだけ残す）。`/control/*`（CLI 用）は従来どおり `{"error": "<英語の文>"}` を返し、CLI がそのまま表示する。
- `/control/*` はループバック（127.0.0.1 / ::1）からのみで、さらに次の 2 つを満たす要求だけを受け付ける（どちらも 403 `{"error": ...}`）。(a) `X-Forwarded-For` / `Forwarded` / `X-Real-IP` / `Via` のどれも付いていない（同じホストのリバースプロキシもループバックから届くため。`forwarded requests are refused`）。(b) `X-MailCare-Control` ヘッダーにコントロールトークンがある（`subtle.ConstantTimeCompare` で比べる。無い・違うときは `{"error": "control token missing or wrong", "data_dir_id": <データディレクトリの正規化したパスの SHA-256 の先頭 16 桁（秘密ではない。`DataDirID`）>}`）。トークンはサーバーの起動のたびに乱数 32 バイトから作り、待ち受けを始めた後、配信を始める前に、ポートとともにデータディレクトリの `control.token`（JSON、権限 0600。chmod に失敗したときは警告だけ。Windows ではデータディレクトリの権限で守る。一時ファイルを書いて名前を変え、Windows では名前の変更を短く再試行する）に書き、正常に停止すると消す（`controltoken.go`）。書けなければ待ち受けを閉じて起動をやめる。サーバーは起動の最初（DB を開く前）にデータディレクトリの `server.lock` を排他ロックし（Unix は flock、Windows は LockFileEx。プロセスが終われば OS が外す）、停止まで持つ。ロックを取れない 2 つ目の起動は `another MailCare server is running for this data directory` で止まり、DB にもトークンにも触れない。CLI は、使うデータディレクトリの `control.token` を読み、書かれたポートへの要求にだけトークンを付ける（別のポートには送らない）。トークンを拒否されたとき、拒否が CLI のデータディレクトリの `data_dir_id` を返していれば（別の OS ユーザーで実行した、トークンが古いなど）、CLI はジョブを CLI のプロセスで実行せずにエラーで止まる（サービスの OS ユーザー・同じ `--data-dir` での実行か、サーバーの再起動を案内する。`service stop` / `status` も同じ）。別のデータディレクトリのサーバーなら、これまでどおり CLI のプロセスで実行する（`LocalServer`）。トークン以外の理由の 403 は、その理由をそのまま表示する。
- CSRF 対策（状態を変える要求 = `/api/v1/*` と `/web/*` の GET / HEAD / OPTIONS 以外、`/control/*` の POST）: (a) `Content-Type` が `application/json`（`; charset=...` などのパラメータ付き可）でなければ 415（`/control/*` は `{"error":"Content-Type must be application/json"}`、それ以外は `{"key":"system.invalidRequest"}`。HTML フォームが送れる形式は届く前に拒否される。本文の無い POST / DELETE にも必要で、SPA と CLI は常に付ける）。(b) `Origin` ヘッダーがあれば、そのホスト（既定ポート 80 / 443 は無視。スキームは比べない: TLS 終端がプロキシの場合に備える）が `Host` と一致しなければ 403。`Origin` が無く `Sec-Fetch-Site` が `cross-site` / `same-site` なら 403（`same-origin` / `none` / 無しは許可）。403 の本文は `/api/v1/*` と `/web/*` が `{"key":"system.forbidden"}`、`/control/*` が `{"error":"cross-origin request refused"}`（`Origin` が違う）/ `{"error":"cross-site request refused"}`（`Sec-Fetch-Site`）。検査は認証より前に行う。
- 防御ヘッダー: すべての応答に `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`（メール HTML 表示 `.../messages/{key}/html/{n}` だけは SPA の同一オリジン iframe に表示するため `SAMEORIGIN`（[画面仕様](画面仕様.md) 6.2）。既存の CSP 等は維持）、`Referrer-Policy: no-referrer`。
- HTTP サーバーのタイムアウト: `ReadHeaderTimeout` 10 秒、`ReadTimeout` 30 秒、`WriteTimeout` 5 分（ジョブの完了を待つエンドポイントは無い）、`IdleTimeout` 2 分。
- DB ファイルの権限: `OpenDB` は `mailcare.db`（存在すれば `-wal` / `-shm` も）を 0600 にする。サーバー起動時にデータディレクトリの権限が 0700 でなければ警告をログに出す（Windows では判定しない）。
- 応答の日時は RFC 3339（UTC）文字列。`sql.NullTime` は `null` または文字列で返す（応答用の DTO を `dto.go` で組み立てる）。
- ジョブを投入するエンドポイント（`POST /api/v1/jobs`、`.../sync`、`.../analyze`、`POST /control/jobs`）は `{job: JobDTO, created: boolean}` を返す。新規なら 201、同一の未完了ジョブが既にあればそれを 200 `created: false` で返す。
- 未知の `/api/v1/*` は未認証なら 401、認証済みなら 404 の JSON を返す（認証の検査がルーティングより先）。未知の `/web/*` と `/control/*` は JSON の 404（`/control/*` はループバック以外なら 403）。`/api/v1`、`/web`、`/control` 以外の未知のパスは SPA のシェル（`index.html`）を返す。

## 11. データベース

- マイグレーション: マスター DB と索引 DB のスキーマはどちらも goose のマイグレーションで管理する（`embedded/migrations/master/`、`embedded/migrations/index/`。`embed.go` が埋め込み、`dbschema.Apply` が goose の Provider API（グローバルな状態を持たない）で未適用分を当てる）。各 DB はそれぞれの `goose_db_version` 表に適用済みの版を番号で記録する。変更はディレクトリごとに連番のファイル（`0002_<説明>.sql`、...）を足して行い、適用済みのファイルは書き換えない。マスター DB は開くたび（`OpenDB` → `runMigrations`）、索引 DB も開くたび（`models.OpenMailIndex`）に適用する。
- マイグレーションのロック（`dbschema.ApplyLocked`、`lock.go`）: 1 つの DB へのマイグレーションの適用は、プロセスをまたいで 1 つずつ行う（バージョンアップ後にサーバーの起動と `mailcare service status` などの CLI が同じマスター DB を開く、2 つのジョブが同じ索引を初めて開く、といったときに、両方が同じ未適用の版を当てて `goose_db_version` に 2 度記録し、2 度は実行できないマイグレーションが失敗するのを防ぐ）。SQLite にはトランザクションより長く持てるロックが無く、`flock` は Unix だけなので、DB ファイルの隣にロックファイル `<DB ファイル>.migrate.lock`（`dbschema.LockSuffix`。マスター DB は `mailcare.db.migrate.lock`、索引は `<address>.sqlite.migrate.lock`、索引の再構築中は `<address>.sqlite.rebuild.migrate.lock`）を排他的に作る（`O_CREATE|O_EXCL`。中身はプロセス ID、時刻、保持者ごとの乱数）。
  - 未適用の版が無い DB はロックを取らない（読むだけの確認。DB ファイルが無い・空、`goose_db_version` が無い、読み出しのエラーは「未適用あり」とみなし、新しいファイルへの最初の書き込みもロックの中で行う）。
  - 他のプロセスが持っていれば 50 ms ごとに 30 秒まで待ち、取れたら未適用の版を調べ直して（多くは待っている間に先のプロセスが当て終えている）残りを当てる。30 秒で取れなければエラー（`the migrations of the database are being applied by another process (lock <パス>: <中身>); if no MailCare process is running, remove the file`）。
  - 書かれた時刻（読めなければファイルの更新日時）から 2 分を過ぎたロックファイルは、異常終了したプロセスが残したものとして引き継ぐ。
  - 適用の後は、結果にかかわらずロックファイルを削除する（そのプロセスが書いた乱数のままのときだけ。他のプロセスに引き継がれた後のファイルは消さない）。
- マスター DB: SQLite（`modernc.org/sqlite`、CGO 不要）、初版は `master/0001_init.sql`、`master/0002_dns_checks.sql` は名前解決の失敗の検証結果の表 `dns_checks` を、`master/0003_sending_source_lookups.sql` は送信元の取得結果の表 `sending_source_lookups` を、`master/0004_probe_mails.sql` は確認メールの記録の表 `probe_mails` を足す（適用したファイルのログはサーバー起動時だけ出し、CLI コマンドでは出さない）。DSN で `busy_timeout(5000)`、`journal_mode(WAL)`、`foreign_keys(1)`、`_time_format=sqlite` を設定する。
- 索引 DB: 同じドライバ。初版は `index/0001_init.sql`（`messages` / `bounces` / `groups` / `agent_reports` / `agent_report_patterns` の 5 表）。`index/0002_split_auto_reply_rule.sql` は判定ルール 3 の 3 分割（`auto_reply` / `auto_reply_subject` / `auto_generated`、[メール判定仕様](メール判定仕様.md) 2.2）に伴い、`bounce_kind` = `auto_reply` の行を `classified` = 0 に戻す（それまでの行はどの根拠で一致したかを区別できないため。次の同期・グループ化で判定し直され、それまではサーバー上の削除の候補にならない）。`index/0003_dmarc_records.sql` は `dmarc_records` 表を作り、判定ルールの追加（DMARC 集計レポート、確実な自動返信、迷惑）に伴い、`bounce_kind` が `failed` / `delayed` 以外の行を `classified` = 0 に戻す（次の同期・グループ化で判定し直される）。`failed` / `delayed` の行はバウンスの詳細とグループを持つので戻さない。迷惑の規則の評価順（[メール判定仕様](メール判定仕様.md) 2.2）により、件名・表示名・本文の規則でバウンスと判定していたメールが新しい規則では迷惑になりうる。これを反映するには再判定（全件のグループ化のやり直し。グループも作り直す）を実行する。`index/0004_group_state_changes.sql` は `groups` に `state_reason`・`state_note`・`needs_recheck`（既定値 0。既存の行のため）を足し、`group_state_changes` と `group_state_change_patterns` を作り、その時点で対応済・無視のグループに履歴を 1 行ずつ作って `needs_analysis` を 0 に戻す（5.9）。文は `IF NOT EXISTS` なので、マイグレーション導入前に作った索引（`PRAGMA user_version` = 1、同じ表）もそのまま管理下に取り込む。SQLite では既存の表に NOT NULL の列を足すには既定値が要るため、後のマイグレーションで足す列に限り既定値を持たせてよい（設計方針の例外。アプリはこれまでどおり全列に値を書く）。索引はすべて原文から再構築できる派生データで、グループの状態（理由・詳細・再確認待ちを含む）と対応履歴と分析結果だけは索引の再構築時に引き継ぐ。
- 設計方針: 属性はすべて実列にし、JSON 列は `mailboxes.detail_info`（まとまった接続設定。`protocol` キーで種類を示し、現在は `imap` のみ。将来 `pop3` などを追加できる）の 1 列だけ。バウンスの抽出結果は `bounces` 表（メールと 1 対 1）に持ち、グループ統計はその列で集計する。グループの表示名は保存しない（組み立て方は [メール判定仕様](メール判定仕様.md) 4.3）。既定値は持たず（アプリが全列に値を書く）、長さを断定できる文字列は `VARCHAR(n)`、断定できない文字列（メール由来の値、外部のエラー文など）は `TEXT` とし、CHECK 制約は使わない（列挙値はアプリの定数で管理し、利用者の入力の長さは入力時に検査する。書き込み時の切り詰めは行わない）。日時は UTC で保存する。`tokens` と `settings` はテンプレートのまま。サービス起動パラメータ（待ち受けアドレス・ポート・同時実行数 `workers`・同期時刻 `check_times`・メールの保持日数 `mail_keep_days`）は既定値と異なる場合だけ `settings` に保存し、既定値になれば行を消す。
- 設定の書き込み（`settingslock.go`）: `settings` 表を書き換える経路はすべて、プロセス内の 1 つのロック（`settingsMu`）の中で「保存値を読む → 検証する → 書く」を行う。Web の設定（`PUT /api/v1/settings`）は `UpdateSettings(db, fill)` で、`fill` が `SettingsUpdate` に変更を集め（組み合わせの検証に要る保存値もここで読む）、1 つの要求の変更を 1 トランザクションで書く。CLI の `settings set`（`ApplySetting`）はキーごとの保存関数（多くは `UpdateSettings` を使う）で同じロックの中で書く。通知設定（`SaveNotificationSettings`）、エージェントの設定（プロバイダー・モデル・推論レベル）、確認メールの設定（Web の `PUT /api/v1/settings/probe` と CLI の `probe_*` はどちらも `SaveProbeSettings` = `UpdateSettings` で、パスワードの削除も `UpdateSettings`）、内部用の書き込み（確認メールの `probe_last_send_at` / `probe_next_check_at` / `probe_last_check_at` / `probe_last_check_error` / `probe_last_delete_error` / `probe_check_failures` / `probe_check_failing_since` / `probe_unreadable_notified_at` / `probe_wide_sweep_at`（`UpdateSettings`）、通知の最終送信日時 `notify_last_sent_at`、日次クリーンアップの日付 `cleanup_last_run_date`、利用上限の解除時刻 `agent_limited_until`、秘密鍵 `secret_key` の初回の保存、待ち受けアドレスとポート）も同じロックを取る。ロックが無いと、同時の 2 つの要求が互いの古い値を読んで組み合わせの検証（DNS 検証の有効・無効とリゾルバーとモード、エージェントのプロバイダー・モデル・推論レベル、SMTP の接続先と保存済みパスワード）を通り、検証が拒む組み合わせを保存しうる。DB を持つのは 1 つのプロセスだけ（サーバーの稼働中は CLI がコマンドをサーバーに依頼する）なので、ロックはプロセス内のものでよい。ロックは再入できない（ロックの中から設定を書く別の関数を呼ばない）。
- テーブル定義は [テーブル定義.md](テーブル定義.md) を参照。
