# システム設計書 - MailCare

本書は MailCare の設計を記述します。実装は本書の契約（パッケージ境界・関数シグネチャ・API 形状）に従います。システムの振る舞いを変更した場合は本書を更新してください。

## 1. 用語定義

| 用語（日本語） | English | 説明 |
| --- | --- | --- |
| 利用者 | User | Web 画面にログインして閲覧・操作する人（`users` テーブル） |
| 管理者 | Administrator | 役割 `admin` の利用者。利用者管理・設定・メールアドレス登録・ツール実行ができる |
| 一般利用者 | Member | 役割 `user` の利用者。閲覧専用（ダッシュボード、アラート、メール、ジョブ履歴の参照）と自分のプロファイルの変更だけができる |
| 運用者 | Operator | サーバーの起動・停止、CLI 操作、データディレクトリの管理をする人 |
| データディレクトリ | Data directory | 実行時データ（DB、メール原文、エージェント作業領域）を置くディレクトリ |
| マスター DB | Master database | `data/mailcare.db`。利用者・トークン・設定・メールアドレス・ジョブを保持する |
| 索引 DB | Mail index | `data/mails/<address>.sqlite`。メールアドレス単位の索引。原文ファイルから再生成できる派生データ |
| メールアドレス | Mailbox | 監視対象の 1 メールアドレスとその IMAP 接続設定（`mailboxes` テーブル） |
| 受信 | Fetch | IMAP から未取得メールを取り込み、原文を保存して索引に載せる処理（判定・纏めはしない） |
| 纏め | Grouping | 未処理のメールを判定し、カテゴリと対応単位でグループに束ねる処理 |
| 解析 | Analysis | エージェントで対応対象のグループを分析する処理 |
| 同期 | Sync | 1 アドレスについて受信 → 纏め → 解析投入を続けて行う処理。「全アドレス同期」は有効な全アドレスに 1 件ずつ投入する |
| 原文 | Raw message | `.eml` として保存した受信メールそのもの |
| メールキー | Message key | 1 メールを表すファイル名の基底（`YYYYMMDD-HHMMSS_<12桁hex>`） |
| バウンス | Bounce | メールデーモン（MAILER-DAEMON 等）が送る配信不能・遅延などの通知メール |
| 対象判定 | Classification | 受信メールがバウンスかどうか、どの種類かを判定する処理 |
| 纏めグループ | Bounce group | バウンスを「対応基準単位」で束ねたもの（`groups` テーブル）。対応対象のグループがアラートに載る |
| カテゴリ | Category | グループが表す問題の種類（IP ブロック、送信元拒否、認証失敗、宛先不明、容量超過 など）。対応単位・対応対象かどうかを決める |
| 対応単位 | Action unit | 管理者が対応する対象そのもの（送信サーバーの IP、送信元アドレス、送信ドメイン、当方の MTA。対象外なら宛先アドレス・宛先ドメイン）。`groups.unit_value` |
| 判断主体 | Authority | 結果を決めている相手（ブラックリストの提供元、宛先ドメイン）。登録先が違えば別グループになる。`groups.authority` |
| 対応対象 | Actionable | メールサーバー管理者が対応すべきグループ（`groups.actionable` = 1）。宛先側の問題（宛先不明・容量超過など）は対象外 |
| 対象外 | Excluded | 宛先側の問題のグループ（`groups.actionable` = 0）のうち未対応（`state = 'open'`）のもの。対応状態の区分も件数の管理も持たない。対応済・無視にすると対応対象の一覧に移り、未対応に戻すと対象外に戻る（`actionable` 列は変えない。下記「アラートの表示範囲」） |
| 診断テンプレート | Diagnostic template | 診断文からアドレス・IP・ID・数値などの揺れを除いた正規化文字列。カテゴリを判定できない場合の纏めの鍵になる |
| 対応者区分 | Responsible party | グループに対して対応すべき立場（`sender` 送信側のメール管理者 / `recipient` 宛先アドレスの所有者 / `domain` 宛先ドメインの管理者 / `unknown`。画面と解析報告はこの呼び名で統一する、6.3） |
| エージェント | Agent | 外部 CLI（Codex CLI 等）。纏めグループの原因分析と対応方法の提案を作成する |
| プロバイダー | Provider | エージェント CLI の種類（`codex` ほか、追加可能） |
| 分析報告 | Agent report | エージェントが作成した分析結果（`agent_reports` テーブルと `REPORT.md`） |
| ジョブ | Job | バックグラウンド処理の 1 単位（同期 / 受信 / 纏め / 解析 / 再索引 / 再判定 / 通知）。`jobs` テーブル |
| ワーカー | Worker | ジョブを実行する goroutine。数は設定 `workers`。同じ IMAP サーバー・同じ索引・エージェントを使うジョブは直列化される |
| スケジューラ | Scheduler | 設定されたチェック時刻に全アドレス同期を投入する常駐処理 |
| 通知 | Notification | 対応対象の纏めグループの要約を通知先の利用者へメールで送る機能。SMTP 設定と通知設定（時刻・間隔・通知先）から成る |
| 通知先 | Notification recipient | 通知メールを受け取る利用者。利用者に任意で登録したメールアドレス（`users.email`）へ送る |
| 公開 URL | Public base URL | 通知メール内のリンクの元になる、利用者がブラウザで開く MailCare の URL（設定 `public_base_url`） |
| トークン | Token | 将来の API 実装のために予約した秘密文字列（`mlc_` 接頭辞）。利用者とは無関係で、ログインには使わない |
| デフォルトトークン | Default token | `is_default` = 1 のトークン。サーバー起動時に無ければ識別子 `default` のトークンが自動作成（または既存の `default` が昇格）される |
| セッション | Session | Web ログイン後の Cookie（`mlc_session`）による認証状態 |
| コントロールエンドポイント | Control endpoint | ループバックからのみ使える停止・状態確認・ジョブ投入用 HTTP エンドポイント |
| SPA | Single Page Application | バイナリに埋め込まれて配信される React 製の Web 画面 |

## 2. 全体構成

```text
+---------------------------------------------------------------------------+
| mailcare (single binary)                                                  |
|                                                                           |
|  main.go -- kong CLI --> app/modules (commands, jobs, scheduler, auth)     |
|                              |                                            |
|            +-----------------+-----------------+                          |
|            v                 v                 v                          |
|   app/modules/mailengine  app/modules/agent   app/workers (HTTP server)   |
|   IMAP取得/解析/判定/纏め   エージェントCLI実行     Web :9790                  |
|            |                 |                   /api/v1/*  JSON (cookie) |
|            v                 v                   /web/*     login/logout  |
|         app/models  <-------+                    /control/* loopback only |
|            |                                     /*         embedded SPA  |
|   +--------+---------+                                                    |
|   v                  v                                                    |
| data/mailcare.db   data/mails/<address>.sqlite + <address>/<YYYY>/<MM>/*.eml .txt .html|
|                    data/agent/<address>/<group_key>/<report_id>/          |
|  embed.go: frontend/dist/**, templates/**                                |
+---------------------------------------------------------------------------+
```

- HTTP サーバーは Web サーバー 1 つ（既定ポート 9790）。外部公開 API は無く、`/api/v1/*` は Web 画面専用の内部 API（Cookie 認証）です。
- 依存方向は `main -> workers -> modules -> {mailengine, agent} -> models` の一方向です。`modules` から `workers` のサーバーを起動するため、`workers` が `init()` で `modules.StartServer` を登録します。
- `mailengine` と `agent` はマスター DB に触れません。必要な値（メールアドレス行、復号済みパスワード、パス）は `modules` が渡します。

## 3. データ配置

データディレクトリに作るのは SQLite ファイル、メールごとの `.eml` / `.txt` / `.html`、エージェントの実行ディレクトリだけである（SQLite が動作中に作る `-wal` / `-shm` と、書き込み中の一時ファイル `.<name>.<random>.tmp` を除く。中断で残った一時ファイルは日次の `cleanup` ジョブが削除する、5.6）。

```text
data/
  mailcare.db                 マスター DB（利用者、トークン、設定、メールアドレス、ジョブ）
  mails/
    user@example.com.sqlite   索引 DB（メール、バウンス詳細、纏めグループ、分析報告）
    user@example.com/         原文ディレクトリ（アドレスを安全化した名前）
      2026/                   メールキーの年（メールの日付、UTC）
        09/                   メールキーの月
          20260901-120000_ab12cd34ef56.eml       原文（受信したバイト列のまま。添付も含む）
          20260901-120000_ab12cd34ef56-1.txt     本文テキストの 1 つ目のセクション（UTF-8）
          20260901-120000_ab12cd34ef56-2.txt     2 つ目以降のセクション（-2, -3, ...）
          20260901-120000_ab12cd34ef56-1.html    HTML セクション（同じ規則。内容のある場合のみ）
  agent/
    user@example.com/
      <group_key>/
        <report_id>/            解析 1 回分の作業ディレクトリ（AGENTS.md, evidence/<message_key>.txt, PROMPT.md, RESULT.log, REPORT.md）
```

- 秘密鍵（パスワードの暗号化とセッション署名に使う 256 ビット鍵）はファイルではなく `settings.secret_key` に置く。
- メールは設定 `mail_keep_days`（既定 180 日、1〜3650）の保持日数を過ぎるまで残す。メールの日付（`messages.date`）が `now - mail_keep_days` より古いメールは、日付の変わり目に 1 回実行される `cleanup` ジョブ（7.1 / 7.3。ツール画面と CLI `cleanup` からも実行できる）が原文 `.eml`・本文セクションファイル・索引の行をまとめて削除する（`mailengine.PruneMailbox`、5.6）。所属していた纏めグループは件数を数え直し、メールが無くなったグループは分析報告ごと削除する。受信・再索引ではメールを削除しない。
- エージェントの作業ディレクトリは解析の実行ごとに作る（`report_id` は `agent_reports.id`）。設定 `agent_keep_days`（既定 30 日）より古い実行ディレクトリは同じ `cleanup` ジョブが削除する（6.2 の 5）。

### 3.1 アドレスの安全化（`mailengine.SanitizeAddress`）

- 使用可能文字は `A-Z a-z 0-9 . _ - @ +`。それ以外（`< > : " / \ | ? *`、制御文字、空白、非 ASCII）は `_` に置き換える。
- 末尾の `.` と空白は Windows で不可のため `_` に置き換える。
- Windows 予約名（`CON`, `PRN`, `AUX`, `NUL`, `COM1-9`, `LPT1-9`）に一致する場合は先頭に `_` を付ける。
- 結果が空なら `_`。大文字小文字は保持する（衝突検出のためアドレスは登録時に小文字化して保存する）。
- 安全化後の名前が他のメールアドレスの安全化後の名前と一致する登録・改名は拒否する（`a!b@example.com` と `a_b@example.com` は同じ `a_b@example.com` になる。`CreateMailbox` / `UpdateMailbox` が "mailbox %q conflicts with %q (same data directory name)" で拒否し、改名では自分自身は除外する）。

### 3.2 メールキーとファイル名

`<日付>_<hash>`。日付は `Date` ヘッダー（無ければ INTERNALDATE、無ければ取得時刻）の UTC を `YYYYMMDD-HHMMSS` で表し、hash は `sha1(folder + "\x00" + uidvalidity + "\x00" + uid)` の先頭 12 桁（hex）。同一メールは常に同じキーになる。UIDVALIDITY が変わるとキーも変わるため、チェック時は Message-ID が索引済みのメールを重複として取り込まない（`Skipped` に数える）。

メール 1 件のファイルはすべてキーから決まる（`mailengine.MessageDir` / `SectionFilePath`）。置き場所は原文ディレクトリの下の `<YYYY>/<MM>/`（キー先頭の年と月。つまりメールの日付の UTC の年月）で、ファイル名はキーそのままとする（DB の `message_key`・URL・原文のダウンロード名と一致させ、ファイル単体でも日時が分かるようにするため）。1 つのディレクトリに全メールを置くと、Windows ではファイル数の増加でファイル操作が大きく遅くなるため月単位に分ける。

原文ディレクトリを走査する処理（再索引の `.eml` 列挙、一時ファイルの削除）は `<YYYY>/<MM>/` の中だけを見る（`walkMailboxFiles`）。再索引は、キーが示す年/月ディレクトリ以外にある `.eml` を無視する。

| ファイル | 内容 |
| --- | --- |
| `<key>.eml` | 原文（受信したバイト列のまま） |
| `<key>-1.txt`, `<key>-2.txt`, ... | 内容のある `text/plain` セクションを MIME 順に 1 ファイルずつ（1 つしか無くても `-1`、以降連番）。UTF-8 |
| `<key>-1.html`, `<key>-2.html`, ... | 内容のある `text/html` セクション（同じ規則） |

- セクションファイルの数は索引の `messages.text_count` / `html_count` と常に一致する（受信・再索引でファイルと行を同時に書く）。空白だけ・骨組みだけのセクションはファイルにならず数えない。番号は欠けなく連続する。
- 索引行に無い情報（ヘッダー一覧、delivery-status の内容、埋め込み元メールのヘッダー）が必要なときは `.eml` を解析し直す。
- 受信も再索引も本文セクションのファイルは同名で上書きするだけで、削除は行わない（ファイルの整理は保持日数によるクリーンアップだけが行う）。
- IMAP 由来の識別情報（folder / uidvalidity / uid）と取得事実（size / received_at / fetched_at）はファイルではなく索引行だけが持つ。再索引はそれらを旧索引から引き継ぎ、旧索引に無いキー（手で複製した原文など）は uidvalidity 0、folder `INBOX`、uid = キーの FNV-32（既存行と衝突すれば +1 ずつ空きを探す）、received_at = `.eml` の更新日時で登録する（5.5）。

## 4. 認証と権限

- 利用者はユーザー名、表示名、任意の通知用メールアドレス（`users.email`。空なら通知先にならない）、画面の言語（`users.language`: `ja` / `en`、既定 `ja`）、表示用タイムゾーン（`users.timezone`、IANA 名、既定 `Asia/Tokyo`）、テーマ（`users.theme`: `auto` / `light` / `dark`、既定 `auto` = ブラウザの設定に従う）、役割を持つ。言語とテーマはブラウザから自動判別せず、利用者の設定に従う（ログイン前の画面は日本語・自動テーマ）。
- 利用者の入力項目の並びは全画面で統一する: ユーザー名 → 表示名 → メールアドレス → 言語 → タイムゾーン → テーマ →（管理者の利用者管理のみ）役割 → パスワード。
- 日時の扱い: データベースにはすべて UTC で保存する。Web 画面はログイン利用者のタイムゾーンで変換して表示し、API の応答は RFC 3339（UTC）のまま。CLI の表示はサーバーのローカル時刻。通知メールの日時は受信する利用者のタイムゾーン（通知メールの「言語とタイムゾーン」を参照）。同期時刻（`check_times`）と通知時刻（`notify_time`）はサーバーのローカル時刻で実行し、設定画面にその旨を表示する。
- 利用者はユーザー名とパスワード（bcrypt、コスト 12）でログインする（`POST /web/login`。JSON 本文のみ。フォーム形式・クエリ文字列は受け付けない）。メールアドレス（`users.email`）を設定している利用者は、ユーザー名の代わりにメールアドレスでもログインできる（`modules.AuthenticateUser`: 入力に `@` を含めばメールアドレスとして小文字化して照合し、含まなければユーザー名として照合する。ユーザー名には `@` を使えないため両者は衝突しない）。
- メールアドレスは利用者間で一意とする（保存時の小文字化後に比較し、空は対象外）。利用者の作成（初期設定・管理画面・CLI）、プロフィール変更、管理者による編集で、ほかの利用者が使っているアドレスを指定すると拒否する（`models.ErrEmailTaken`。Web API は 400 `{"key":"validation.user.emailTaken"}`）。
  - UNIQUE 制約は使わない。`models.InsertUser` / `UpdateUser` / `UpdateUserProfile` が書き込みの SQL 文そのものに「ほかの利用者が同じアドレスを持たない」条件（`NOT EXISTS`）を含め、影響行数 0 のときに `ErrEmailTaken` を返す。SQLite は 1 文を原子的に実行するため、確認と保存の間に別の書き込み（別プロセスの CLI を含む）が割り込むことはない。
  - 更新で現在のアドレスを変えない場合は条件を検査しない。一意化より前に同じアドレスを共有していた利用者も、アドレス以外の項目を変更できる。ただし一度外したアドレスを付け直すことはできない。このような重複がある場合、メールアドレスでのログインは最も古い利用者（id 最小）に対して照合する。
- トークン（`mlc_` + 40 桁 hex、有効期限任意）は利用者と無関係な将来の API 用の予約機能で、ログインには使えない。
- ログインの試行制限（`modules.LoginLimiter`。メモリ上のマップで、再起動で消える）: 送信元 IP（TCP の相手アドレス。転送ヘッダーは信用しない）とログイン名（入力されたユーザー名またはメールアドレス。小文字化・前後空白除去）の組ごとに連続失敗回数を数え、5 回連続で失敗すると 30 秒の待機に入り、待機後にさらに失敗するたびに待機を倍にする（上限 15 分）。待機中の要求はパスワードを検査せず 429 `{"key":"result.session.tooManyAttempts","params":{"seconds":N}}`（`Retry-After` ヘッダー付き）で拒否し、失敗回数には数えない。ログイン成功で記録を消す。失敗（`login failed for "<user>" from <ip>`）と拒否（`login refused for ...`）はサーバーログに残す。1 時間以上動きのない記録は破棄する。
- デフォルトトークン: サーバー起動時に `is_default` = 1 のトークンが無ければ、識別子 `default` のトークンがあればそれをデフォルトにし、無ければ識別子 `default`（無期限、`is_default` = 1）を作成して値をログに 1 度だけ出す。他のトークンの有無は問わず、`default` 以外のトークンを昇格させることはない。自動生成されるのは `default` だけで、利用者の作成や DB ファイルの作成とは連動しない。
- 初回起動で利用者が 0 人のときは Web が初期設定画面（`/setup`）を表示し、最初の管理者を作成する。CLI の `user create --role admin` でも作成できる。`POST /web/setup` はサーバー内のミューテックスで直列化し、ロック内で利用者数を再確認するため、同時に複数の要求が届いても管理者は 1 人しか作られない（残りは 403）。
- セッションは AES-256-GCM で封印した Cookie（`mlc_session`、HttpOnly、SameSite=Lax）。中身は `user_id`、`sha256(password_hash)`、有効期限、保持フラグ。パスワード変更で既存セッションが無効になる。サーバー側にセッション表は無いため、ログアウト（`POST /web/logout`）は Cookie を削除するだけで、複製された Cookie 値は有効期限まで（またはパスワード変更まで）使える。
- HTTPS の前提: サーバー自身は平文 HTTP だけを話す。ネットワーク越しに使うときは TLS 終端をリバースプロキシで行い、Cookie の `Secure` 属性はプロキシ側で付与する（`proxy_cookie_flags` 等）か、`web_listen` を `127.0.0.1` にしてプロキシ経由以外で到達できないようにする。プロキシは `Host` ヘッダーを書き換えずに渡すこと（9.1 の同一オリジン検査が `Host` と `Origin` を比べるため）。
- 秘密鍵: セッションの封印と保存パスワード（IMAP / SMTP）の暗号化に使う 256 ビットの鍵は `settings.secret_key`（16 進 64 桁）に置く。初回に必要になった時点で生成して保存し、以後どの経路でも再生成しない（読めない・壊れている場合は鍵を作り直さずエラーで止める。鍵を変えると保存済みパスワードが読めなくなるため）。鍵ファイルは作らず、`mailcare.db` のバックアップだけで鍵も保全される。`settings show` は鍵を表示せず、`settings set secret_key` は未知のキーとして拒否する。
- ログイン画面の「ログインを保持する」（`remember`）を付けると Max-Age 付きの永続 Cookie（既定 720 時間、スライド更新は 24 時間に 1 回）になる。付けない場合（既定）はブラウザを閉じると消えるセッション Cookie で、サーバー側の有効期限は 24 時間、更新はしない。初期設定でのログインは保持なし。

## 5. 受信・纏め（`app/modules/mailengine`）

受信（`FetchMailbox`）、纏め（`GroupMailbox`）、解析（`agent.AnalyzeGroup`）は互いに独立した関数で、制御側（`app/modules/jobs.go`）がジョブとして個別に、または同期ジョブとして順に呼び出す。受信は判定・纏めをせず `messages.classified = 0` で索引に載せるだけで、纏めは `classified = 0` のメールだけを処理する（全件やり直しは `full = true`）。

### 5.1 受信（`FetchMailbox`）

1. IMAP に接続（ポートの既定は 993。`imap_security`: `ssl` = IMAPS / `starttls` / `none`）、ログイン、`folder`（既定 `INBOX`）を SELECT。
2. 対象期間: 索引 DB にそのアドレスのメールが 1 件も無い（初回）なら `initial_days`（既定 90 日）、それ以外は `recent_days`（既定 30 日）。ただし制御側（`jobs.go` の `fetchOne`）が `mail_keep_days`（`ResolveMailKeepDays`）から `now - mail_keep_days` を `FetchOptions.NotBefore` として渡し、`FetchMailbox` は対象期間の開始日と `NotBefore` の遅い方を検索開始日にする（保持日数より前には遡らない。`mailengine` はマスター DB を見ないまま）。開始日が `NotBefore` で決まったときは進捗の "searching since ..." 行に "limited to the mail retention" を添える。`SEARCH SINCE <開始日>` で UID を列挙する（SINCE は INTERNALDATE で判定するため、到着が新しく `Date` ヘッダーだけ古いメールは取り込まれ、次の `cleanup` で削除される）。
3. UIDVALIDITY が前回と異なる場合も同じ手順で、索引に無い (uidvalidity, uid) のみを取り込む（重複はキーで排除される）。
4. 未取得の UID を `FETCH (UID RFC822.SIZE INTERNALDATE)` でサイズと INTERNALDATE を確認した後、`FETCH (UID INTERNALDATE RFC822.SIZE BODY.PEEK[])` で本文を取得する（`\Seen` を付けない）。大きさによる制限や切り詰めは無く、どのメールも丸ごと取り込む。
5. 原文を `.eml` に保存し、解析した本文セクションを `-1.txt` / `-2.txt` / ... と `-1.html` / `-2.html` / ...（3.2）に保存し、索引に `messages` 行（`classified = 0`）を追加する。行に入れるのはヘッダー（message_id、subject、from_address / from_name、to_address / to_name、date）、IMAP 由来の識別情報と取得事実（folder、uidvalidity、uid、size、received_at、fetched_at）、セクション数（`text_count` / `html_count`）と受信時点の `body_source`（優先本文の側）。それ以外の解析結果（ヘッダー一覧、delivery-status の内容、元メールのヘッダー）はファイルにも DB にも保存せず、必要な時に `.eml` を解析し直す。同じ Message-ID が索引済みなら取り込まず `Skipped` に数える。`FetchResult`（取得数・スキップ数・UIDVALIDITY）を返す。判定と纏めは行わない。
6. 受信では保持日数（`mail_keep_days`）による削除を行わない。取得したメールは `Date` ヘッダーに関係なく保存し、保持日数を過ぎたメールの削除は日次の `cleanup` ジョブだけが行う（5.6、7.1）。

### 5.2 解析（`ParsedMessage`、メモリ上のみ）

`go-message`（`charset` 登録で IANA / HTML の文字コード名を解決）で解析する。文字コードは次の順で扱う: (1) 別名表で正規化（`cp932` / `ms932` / `windows-31j` / `x-sjis` → Shift_JIS、`iso-2022-jp-ms` / `-1` / `-2` / `-3` → ISO-2022-JP、`x-euc-jp` → EUC-JP、`utf8` → UTF-8、`latin1` / `cp1252` → Windows-1252 など）、(2) 宣言どおりに UTF-8 へ変換、(3) 宣言が無い・未知・変換失敗のときは自動判定（正しい UTF-8 ならそのまま、ISO-2022-JP のエスケープ列があれば ISO-2022-JP、続いて Shift_JIS、EUC-JP の順に試し、どれも成立しなければ原文バイトを保持）。RFC 2047 のエンコード語（件名・差出人・宛先）と HTML の meta charset にも同じ規則を適用する。`.eml` は取得したバイト列をそのまま保存し、セクションファイル（`.txt` / `.html`）は UTF-8 で書く。ヘッダー: Message-ID、Subject（MIME デコード済み）、From（アドレス / 表示名）、To（アドレス / 表示名）、Date、Return-Path、Auto-Submitted、Content-Type、ヘッダー一覧。本文: 埋め込み元メール（`message/rfc822` / `text/rfc822-headers` 配下）と添付（`Content-Disposition: attachment`）を除く `text/plain` と `text/html` のパートを、種類ごとに MIME 順の**セクション配列**（`TextSections` / `HTMLSections`）として持つ（`Content-Disposition: inline; filename=...` の text/plain もセクションになる）。内容のあるセクション（plain は空白以外の文字がある、HTML はタグ・スタイル・スクリプト・コメントを除いた後に文字が残る。骨組みだけの HTML は無し）だけを数え、`text_count` / `html_count` に記録して 1 セクション 1 ファイル（3.2）で保存する。本文の大きさは制限しない（受信にも大きさの上限は無く、取り込んだメールの本文はすべて保存する）。`ParsedMessage` はメモリ上だけの構造体で、ファイルにも DB にも直列化しない（纏め・再索引は `.eml` から解析し直す）。

本文の採用規則（判定・抽出に使う本文）: 判定・抽出には連結ビューを使う。優先本文 = 全 text セクションを空行 1 つで区切って連結したもの（text セクションが無ければ全 HTML セクションをテキスト化して連結したもの。`<br>` / `<p>` / `<div>` / `<tr>` 等は改行、`&nbsp;` 等の実体参照は復元）、副本文 = text と HTML の両方があるときの HTML のテキスト。まず優先本文で対象判定を行い、対象にならなければ副本文でも判定し、どちらかで一致すれば対象とする。抽出は優先本文から行い、空のままの項目（宛先・状態コード・SMTP コード・診断文・相手ホスト・IP）を副本文から補う（delivery-status パートの値が最優先なのは変わらない）。`body_source`（`text` / `html` / 空）には判定・抽出に実際に使った本文を記録する: 優先本文で判定できた（または対象外だった）場合は優先本文の側（text セクションがあれば `text`）、text では対象にならず HTML だけで一致した場合は `html`、本文が無ければ空。受信直後は優先本文の側が入り、纏めフェーズで確定する。次の 5 パターンをすべて扱う: plain のみ、HTML のみ、plain + HTML、plain（パートはあるが空）+ HTML、plain + HTML（パートはあるが空）。元メール本文が先でバウンス通知が後の形式でも、その逆でも、セクションを MIME 順に連結するのでバウンス文面を失わない。壊れたメールでも panic せず、読めたヘッダーだけで索引する（本文はヘッダーブロック以降のバイト列を 1 セクションとして保持）。`multipart/report` の `message/delivery-status` パートは per-recipient フィールド（Final-Recipient、Original-Recipient、Action、Status、Diagnostic-Code、Remote-MTA）と per-message フィールド（Reporting-MTA、Arrival-Date）を構造化する。`message/rfc822` または `text/rfc822-headers` パートからは元メールの Message-ID、Subject、From、Date を取る（索引に保存する）。併せて To、Authentication-Results、Received-SPF、DKIM-Signature の署名ドメイン（`d=`）も取るが、これはエージェントの証拠（6.2）に使うだけで索引には保存しない。

### 5.3 対象判定（`classify.go`、纏めフェーズの第 1 段階）

ルールは Go のテーブル（`[]classifyRule`）として持ち、上から評価して最初に一致した結果を採用する。一致したルール名を `messages.rule` に記録する（対象外は空）。判定結果は `messages` 行の `is_bounce` / `bounce_kind` / `rule` / `body_source` に書き、`classified = 1` にする（`models.UpdateMessageClassification`。`bounces` 行を持たないメール（対象外・`auto_reply`・`other`）の古い `bounces` 行は同じトランザクションで削除される。5.4）。

| 6 | 本文（優先本文、次に HTML のテキスト）に配信不能通知に固有の文言がある（`Delivery has failed to these recipients` / `Undelivered Mail Returned to Sender` / `The following address(es) failed` / `could not be delivered to one or more` / `message wasn't delivered to` / `This is the mail system at host` / `Remote Server returned '5xx` / `Delivery Status Notification (Failure)` 等。通常メールが誤って一致しないよう厳密な語句に限る）（`body_pattern`） | バウンス（本文・件名で `delayed` / `failed` を判定。失敗・遅延の語が無ければ `other`） |
| - | いずれにも一致しない | 対象外（`is_bounce` = 0） |

判定した `failed` / `delayed` のバウンスからは `bounces` 表の 1 行（`id` = `messages.id`）を抽出する（`ExtractBounce` → `models.UpsertBounce`）: 配信できなかった宛先（`recipient`、`recipient_domain`）、`action`、状態コード（`status_code`）、SMTP 応答コード（`smtp_code`）、診断文（`diagnostic`）とそのテンプレート（`diagnostic_template`）、診断文を取った場所（`diagnostic_source`: delivery-status パートなら `dsn`、本文ならそのセクション `text:<n>` / `html:<n>`（セクションファイルと同じ番号）、診断文が無ければ空）、パターンキー（`pattern_key`、5.4）、相手 MTA（`remote_mta` / `remote_ip`）、通知元 MTA（`reporting_mta`）、元メールのヘッダー（`original_message_id` / `original_subject` / `original_from` / `original_date`）、所属グループ（`group_key`、5.4）。`auto_reply`、`other`（失敗の証拠が無いデーモンメール。成功 DSN を含む）と対象外メールには `bounces` 行を作らない（`is_bounce` と `bounce_kind` は記録するのでメール一覧・件数には現れる）。`smtp_code` は通知に 3 桁の応答コードが実際にある場合だけ入れる（無ければ空。プレースホルダーは合成しない）。delivery-status パートを優先し、無ければ本文（5.2 の優先本文、空のままの項目は副本文）から Postfix / Exim / qmail / Sendmail / Exchange / Gmail / 日本語 MTA 形式を正規表現で拾う（例: `<addr>: host <mta>[<ip>] said: <smtp> <status> <text>`、`550 5.1.1 <addr>...`、`The following address(es) failed:` の次行、`Final-Recipient:` 行）。監視アドレス自身と通知の差出人は宛先として採らない。

診断文を取った場所の決め方（`locateDiagnostic`）: 抽出は種類ごとに全セクションを連結した本文から行うので、診断文を最初に埋めたのが本文だった場合は、その種類（優先本文なら `text`、副本文なら `html`）のセクションを 1 つずつ（HTML はテキスト化して）調べ、一致した診断文を含むセクションを記録する。そのままの文字列で見つからなければ空白を畳んで比較し、それでも見つからなければその種類の 1 番目のセクションとする。text と HTML で内容が違う通知では、判定の根拠が入っている方のセクションがここに残り、エージェントにはそのセクションだけを見せる（6.2）。

`responsible`（対応者区分）は状態コードからではなく、5.4 のカテゴリから決め、グループにだけ持つ（`bounces` 行には持たない）。

### 5.4 纏め（`GroupMailbox`: `category.go` + `grouping.go`）

纏めは「管理者が何に対して動くか」の単位で束ねる。バウンス 1 件ごとに状態コードと診断文からカテゴリを判定し、カテゴリが対応単位（`unit_value`）と判断主体（`authority`）を決める。宛先アドレスや相手 IP が違っても対応単位が同じなら同じグループになり、ブラックリストの登録先が違えば別グループになる。

| カテゴリ | 対応対象 | 判定の手掛かり（診断文 / 状態コード） | unit_value | authority |
| --- | --- | --- | --- | --- |
| `ip_blocked` | 1 | `blocked` / `blacklist` / `block list` / `listed` / `rbl` / `dnsbl` / `spamhaus` / `barracuda` / `spamcop` / `sorbs` / `uceprotect` / `proofpoint` / `cloudmark` / `Our system has detected` / `unsolicited mail originating from your IP` / `poor reputation` / 5.7.1 や 4.7.0 で IP に言及 | 診断文中の当方の送信 IP（`[203.0.113.5]` 形式など。無ければ `reporting_mta`） | ブラックリストの提供元（診断文の URL / ホスト名から抽出した `spamhaus.org` 等）。無ければ宛先ドメイン |
| `rate_limited` | 1 | `too many` / `rate limit` / `try again later` / `throttl` / `temporarily rate limited` / 4.7.0 で IP ブロックの語が無い | 送信 IP（無ければ `reporting_mta`） | 宛先ドメイン |

| `content_rejected` | 1 | `spam` / `content` / `virus` / `malware` / `attachment` / `message rejected` / `rejected due to policy`（上記に該当しない） | 元メールの差出人アドレス | 宛先ドメイン |

| `delivery_delay` | 0 | `delayed` 種別、4.4.x / `connection timed out` / `greylist` | 宛先ドメイン | （空） |

- ルールは `category.go` の `[]categoryRule` テーブルで、上から評価して最初に一致したものを採用する。実装上の評価順: (1) 宛先側を明確に示す状態コード（5.1.1 / 5.1.0 / 5.1.3 / 5.1.6 / 5.1.10 → `user_unknown`、4.2.2 / 5.2.2 → `mailbox_full`、5.2.1 → `mailbox_disabled`、5.1.2 / 5.4.4 / 5.4.6 → `domain_not_found`）、(2) `ip_blocked`、(3) `rate_limited`、(4) 種別 `delayed` → `delivery_delay`、(5) `auth_failure`、(6) `sender_blocked`、(7) `message_too_large`、(8) `content_rejected`、(9) `server_config`、(10) 宛先側の文言（`user_unknown` / `mailbox_full` / `mailbox_disabled` / `domain_not_found` / `delivery_delay`）、(11) `unknown_failure`。`message_too_large` を `content_rejected` より先に置くのは "Message rejected: size exceeds" の誤判定を避けるため。
- カテゴリの定義（対応対象、対応者区分、対応単位、判断主体）は `categoryDefs` テーブルに持つ。`responsible` はカテゴリから決めて `groups.responsible` に書く（`bounces` 行には持たない。分析報告があればその対応者区分で上書きされる）: 対応対象のカテゴリ → `sender`（`unknown_failure` は `unknown`）、`user_unknown` / `mailbox_full` / `mailbox_disabled` → `recipient`、`domain_not_found` / `delivery_delay` → `domain`。
- 送信 IP の抽出: 診断文中の `[ip]` / `(ip)` → `ip` / `address` / `host` / `your` / `originating` / `client` などの直後の IP → 任意の IP リテラルの順で探し、相手 MTA の IP とループバックを除く。無ければ `reporting_mta`。
- ブラックリスト提供元の抽出: 既知の提供元テーブル（spamhaus.org、spamcop.net、sorbs.net、barracudacentral.org、uceprotect.net、proofpoint.com、cloudmark.com、invaluement.com、abuseat.org、mailspike.net、spamrats.com、senderscore.org、surbl.org、uribl.com、psbl.org、nixspam.org、blocklist.de、mail-abuse.com、lashback.com、junkemailfilter.com、trendmicro.com、mimecast.com、talosintelligence.com、spameatingmonkey.net）→ 無ければ listing の語があるときに文中の URL / ホスト名の登録可能ドメイン（宛先・送信・MTA のドメインと大手メールサービスのヘルプ URL は除外）→ 無ければ宛先ドメイン。
- 元メールの差出人が取れない場合、送信元アドレスは診断文中の宛先以外のアドレス → 送信ドメイン → `reporting_mta` の順で補う。
- どのカテゴリでも、上記の補完順が尽きて `unit_value` が空になるときは最終フォールバックとして宛先ドメイン → 相手側 MTA のホスト名（`remote_mta`）→ 固定値 `unknown` の順で埋める（ラベルや通知で対応単位が空欄にならない）。
- 診断テンプレート（アドレス → `<addr>`、IP → `<ip>`、ホスト → `<host>`、ID → `<id>`、日付 → `<date>`、数値 → `<n>`、SMTP コードと状態コードは保持。長さの上限は無い）は `bounces.diagnostic_template` に保存し、`unknown_failure` の authority と表示に使う。診断文が空のとき（宛先や応答文が取れない通知）は件名から診断テンプレートを作る。
- 一致したカテゴリ規則の名前（`Category.Reason`）は `bounces.category_rule` に保存する（そのバウンスが対応対象 / 対象外になった理由）。
- パターン: グループの中で「状態コード・診断テンプレート・相手 MTA・診断文を取った場所の種類（`dsn` / `text` / `html` / 空）」が同じバウンスを 1 パターンとし、`bounces.pattern_key` = `sha1(status_code|パターン用テンプレート|remote_mta|種類)` の先頭 16 桁（`mailengine.PatternKey`）。パターン用テンプレートは診断テンプレートのうち `<id>` の直後の区切り（`.` / `-`）に続く数字も `<n>` にしたもの（Gmail の `<id>-<id>.218` のようなキュー ID の末尾が SMTP コードと誤認されて残り、通知ごとに別パターンになるのを防ぐ。診断テンプレート自体とグループキーは変えない）。エージェントはパターンごとに 1 通だけ見本を読み（6.2）、解析の要否もパターンで決める（下記）。
- グループキー: `sha1(category + "|" + unit_value + "|" + authority)` の先頭 16 桁（hex）。`unit_value` と `authority` は小文字化・前後空白除去して比較する。所属は `bounces.group_key` に記録する（`messages` には無く、読み出し時に `bounces` を LEFT JOIN して `Message.GroupKey` に埋める）。
- 表示名は保存しない。CLI・ログ・通知メールでは `models.BounceGroup.Label()`（`<category>: <unit_value> @ <authority>`）、Web ではカテゴリから翻訳した見出しを組み立てる。
- 纏めフェーズの 1 メールの手順（`groupMessage`）: `.eml` を読んで解析（5.2）→ 対象判定（5.3）→ `failed` / `delayed` なら抽出（`ExtractBounce`）とカテゴリ判定 → 索引への書き込みを 1 つのトランザクションで行う: (1) グループを `UpsertGroup`（説明列のみ）、(2) `bounces` 行を `group_key` 付きで upsert（`bounces` 行を持たないメールは古い行を削除）、(3) そのグループの件数を数え直し（`RefreshGroupCounters`: 所属メール数、宛先アドレス（`bounces.recipient`）と相手側 IP（`bounces.remote_ip`）の空以外の種類数、最古 / 最新のメール日時）、対応対象で、そのバウンスのパターンをグループの最新の決着した報告（完了した報告、または解析不能で終わった報告）が扱っていなければ `needs_analysis = 1`（`models.PatternCovered`）、(4) `messages` 行の判定列を更新（`UpdateMessageClassification`。`classified = 1` になるのはここ）。順序が groups → bounces → messages なので、トランザクションが使えない状況で途中で止まっても「未分類のまま」に倒れ、判定済みなのに詳細が無いメールは生じない（`models` の関数は `*sql.DB` と `*sql.Tx` の両方を受ける `models.Execer` を取る）。`.eml` が読めないメールは飛ばして `classified = 0` のまま残す（次回再試行）。纏めは必ず原文から解析し直す（セクションファイルは書き換えない。再生成は再索引で行う）。
- 増分: `classified = 0` のメールだけ処理する。グループの件数はメールごとのトランザクション内で数え直す。解析の要否はパターンで決める: 完了した報告は解析時点のグループのパターンキーを `agent_report_patterns` に記録し（6.2）、新しいバウンスのパターンが最新の決着した報告（完了した報告、または解析不能で終わった報告）に無い対応対象グループにだけ `needs_analysis = 1` を立てる。完了報告の無いグループ（新規グループを含む）は最初のバウンスで立つ。既に扱ったパターンの通知が増えただけなら件数を更新するだけで再解析しない（同じ原因の通知が届き続けるグループを定時チェックのたびに解析し直さないため）。`RefreshGroupCounters` 自体は件数を数えるだけで旗を立てない。対象外グループ（`actionable` = 0）は `needs_analysis` = 0 のまま。`auto_reply`、`other` と対象外メール（`is_bounce` = 0）はグループに入れない（`bounces` 行を作らない）。処理済みは `classified = 1`。
- 全件（`full = true`）: `ClearMailClassification`（1 トランザクションで `bounces` を全削除し、`messages` の判定列（`is_bounce` / `bounce_kind` / `rule` / `body_source` / `classified`）を戻す）後に全メールを処理し、`DeleteEmptyGroups` で空グループを消す。既存グループの状態と解析報告は保持する（キーが同じ限り）。報告が扱ったパターンが変わらなければ再解析の旗は立たない（パターンを記録していない報告しか無いグループは立つ）。
- 戻り値 `GroupResult`: 処理したメール数、バウンス数、`GroupsTouched`（この実行で解析の旗が立った対応対象グループのキー）、グループ総数。

### 5.5 再索引・再判定

- `Reindex`（受信相当 + 全件纏め）: まず旧索引（`<address>.sqlite`。直接開く）から (a) `messages` の message_key ごとの IMAP 識別情報と取得事実（folder、uidvalidity、uid、size、received_at、fetched_at、server_deleted_at。`models.ListMessageSources`）、(b) `groups` の状態（state、state_updated_at、needs_analysis）、(c) `agent_reports` の全行と `agent_report_patterns` の全行を読み出し、`<address>.sqlite.rebuild` に新しい索引を構築する。旧索引は `models.OpenMailIndex` で開くので、読み出す前に最新のスキーマまでマイグレーションされる（古い版の索引からも引き継げる）。開けない・読めない場合だけ何も引き継がずに作り直す。ディレクトリの `.eml` を全件解析（本文セクションは 1 セクション 1 ファイルで同名のファイルを上書きする。ファイルの削除は行わない）→ 行挿入（(a) にあるキーは旧行の識別情報をそのまま、無いキーは合成 ID: uidvalidity 0、folder `INBOX`、uid = キーの FNV-32、received_at = `.eml` の更新日時。合成 ID の挿入が UNIQUE 違反になったときは uid を +1 して最大 1000 回まで再試行し、それでも入らなければ進捗に "error: skipping <key>: ..." を出して `ReindexResult.Skipped` に数え、他のメールの索引は続ける。読めない `.eml` も同様に数える）→ 判定 → 纏め。キーが再び現れたグループには状態と解析報告（扱ったパターンを含む）を引き継ぎ（`needs_analysis` は旧値 OR 対応対象で最新の決着した報告（完了した報告、または解析不能で終わった報告）が扱っていないパターンがある。`models.GroupHasUncoveredPattern`）、現れなかったグループの報告は捨てる。報告は元の `id` のまま挿入する（`models.RestoreAgentReport`。実行ディレクトリ `data/agent/<address>/<group_key>/<report_id>/` との対応を保つため。以後の新しい報告は引き継いだ最大 id より後の id を得る）。最新の決着した報告の対応者区分を再適用し（`reapplyReportResponsible`。6.2 と同じく確定値 `sender` / `recipient` / `domain` のときだけ。`unknown`・空・不正値は機械判定の値を残す）、成功したときだけ本体と入れ替える（`swapIndexFiles`: 旧索引の削除と `.rebuild` の改名は、Windows で開かれたままのファイルに対して失敗し得るため、100 ms 間隔で最大 5 秒再試行してからエラーにする）。失敗・中断（コンテキストのキャンセル）時は `.rebuild`（と `-wal` / `-shm` / `-journal`）を必ず削除し、旧索引はそのまま残る。
- 再判定は `GroupMailbox(full = true)`: `messages`・`groups`・`agent_reports` を残し、`ClearMailClassification`（`bounces` の全行と `messages` の判定列を消す）後に `.eml` を解析し直して判定と纏めをやり直す。グループは `UpsertGroup` で説明列だけ更新され（状態は保持）、最新の決着した報告（完了した報告、または解析不能で終わった報告）が扱っていないパターンのバウンスがあったときだけ `needs_analysis` が立つ。メールが 1 件も無くなったグループは `DeleteEmptyGroups` で削除され、その報告もカスケードで消える。最新の決着した報告の対応者区分を再適用する（再索引と同じく確定値のときだけ）。
- 再索引・再判定でも保持日数による削除は行わない。`.eml` があるメールは日付に関係なく索引に載せ直し、保持日数を過ぎたものは次の `cleanup` ジョブが削除する（5.6）。
- 索引 DB を開くと未適用のマイグレーションが当たる（11 章）。開くことで再索引が起きることはない。列を足した結果、既存の行に値を入れ直す必要があるときは再判定（または再索引）で行う。

### 5.6 保持日数による削除（`PruneMailbox`）

`cleanup` ジョブ（7.1）が対象アドレスごとに呼ぶ。`keep`（`mail_keep_days` を日数から換算。正の値のみ）を受け取り、次の順で処理する。

1. 索引の `messages.date`（`Date` ヘッダー、無ければ INTERNALDATE、無ければ取得時刻。すべて UTC）が `now - keep` より古い行を古い順に列挙する（`models.ListMessagesOlderThan`: id、message_key、text_count、html_count、bounces の group_key）。
2. 各行について、本文セクションファイル（`<key>-1.txt` 〜 `<key>-<text_count>.txt`、`<key>-1.html` 〜 `<key>-<html_count>.html`）を削除してから原文 `<key>.eml` を削除する（無いファイルは飛ばす。原文を最後に消すので、途中で失敗しても原文が残り再索引でセクションを作り直せる）。空になった月ディレクトリと年ディレクトリも削除する。ファイルを消せなかった行は残して次回に持ち越し、残りの行の処理は続ける。
3. 行を削除する（`models.DeleteMessage`。`bounces` 行は ON DELETE CASCADE で消える）。
4. 削除した bounces の `group_key` ごとに `RefreshGroupCounters` で件数・宛先数・IP 数・初回/最終日時を数え直す（`RefreshGroupCounters` は `needs_analysis` を立てない）。メールが 1 件も無くなったグループは `DeleteEmptyGroups` で削除し、その `agent_reports` はカスケードで消える（実行ディレクトリは `agent_keep_days` の規則で消える）。
5. `PruneResult`（削除したメール数 `Removed`、削除したグループ数 `RemovedGroups`）を返す。削除があったときだけ進捗に "removed N message(s) older than D days[, M group(s) left empty and removed]" の 1 行を出す。失敗は `errors.Join` でまとめ、途中までの結果と一緒に返す。コンテキストのキャンセルはその時点で打ち切り、消した分のグループは数え直す。

併せて `cleanup` ジョブは、原文ディレクトリ（年/月ディレクトリ）に残った書き込み中の一時ファイルの残骸（`.<name>.<random>.tmp`。原子的な書き込みが中断されたもの）のうち更新日時が 1 日より古いものを削除する（`RemoveStaleTempFiles`。削除があれば進捗に "removed N stale temporary file(s)" の 1 行を出し、結果行の件数には含めない）。

受信の検索開始日は保持日数より前に遡らない（5.1 の 2）ので、削除したメールが次のチェックで再取得されることはない（到着日が保持日数内で `Date` ヘッダーだけが古いメールを除く）。

### 5.6.1 サーバー上の保持日数による削除（`DeleteFromServer`、`serverdelete.go`）

`cleanup` ジョブ（7.1）が、有効なメールアドレスで `server_keep_days`（メールアドレスごとの設定。`mailboxes.detail_info`。0〜3650、0 は削除しない、新規登録の既定 60、設定の追加前に保存したアドレスは 0）が 1 以上のときだけ、手元の保持日数による削除（5.6）より**前に**呼ぶ（先に手元の行が消えると、そのメールはサーバーから削除できなくなるため）。

1. 索引から候補を選ぶ（`models.ListServerDeletionCandidates`）: 所属グループの状態が `resolved` / `ignored`、メールの日付（`messages.date`）が `now - server_keep_days` より古い、`server_deleted_at` が NULL、フォルダーがメールアドレスの監視フォルダー、`uidvalidity` が 0 でない（取得したことのない原文から索引した行は除く）。グループに属さないメール（自動返信、`other`、対象外メール）と未対応のグループ（対象外一覧の宛先側グループを含む）のメールは対象にしない。候補が無ければ接続しない。
2. 接続してフォルダーを選択する。サーバーが UIDPLUS（または IMAP4rev2）に対応していれば、手順 4 で指定した UID だけを `UID EXPUNGE` で消す。対応していないサーバー（通常の `EXPUNGE` しか無く、`\Deleted` の付いたメールをまとめて消す）では次の手順で消す: (a) `UID SEARCH DELETED` で、今回の対象以外に `\Deleted` の付いたメール（他のメールソフトが付けたもの）があれば何も消さず `ErrOtherDeletedFlags` を返す（次回のクリーンアップで再試行）、(b) 対象に `\Deleted` を付けた直後にもう一度調べ、対象以外が増えていれば付けた印を外して同じエラーにする、(c) 対象だけであれば `EXPUNGE` する。(b) と (c) の間のごく短い間に他のメールソフトが印を付けたメールは一緒に消えるが、それはそのメールソフトが削除しようとしたメールである。参考: Dovecot（Mailu も IMAP は Dovecot）、Cyrus、Gmail、Microsoft 365 は UIDPLUS に対応している。
3. 候補のうち `uidvalidity` が現在のフォルダーの UIDVALIDITY と違うものは飛ばす（フォルダーが作り直されて UID が別のメールを指している可能性があるため）。
4. 200 件ずつ、エンベロープの Message-ID を取得して索引の `message_id` と照合する（山括弧と前後の空白を除いて比較）。一致したものだけに `\Deleted` を付け（`STORE +FLAGS.SILENT`）、`UID EXPUNGE` でそれらの UID だけを完全に削除する（ゴミ箱への移動やアーカイブはしない）。索引に Message-ID が無い、または一致しないものはサーバーに残す。UID がサーバーに既に無いもの（他のメールソフトで削除済み）は削除済みとして扱う。
5. 削除した（または既に無かった）行に `server_deleted_at` を記録する。原文と行は手元の保持日数まで残り、メール詳細に「サーバーから削除」の日時を表示する。再索引では `server_deleted_at` を引き継ぐ（5.5 の (a)）。
6. `ServerDeleteResult`（削除数 `Deleted`、残した数 `Skipped`）を返し、進捗に対象件数・飛ばした件数・削除数を出す。

## 6. エージェント（`app/modules/agent`）

### 6.1 プロバイダー

`Provider` インターフェース（`Name` / `Label` / `Command`）を `provider_<name>.go` で実装し `init()` で登録する。次の任意インターフェースで機能を足せる（未実装なら使わない）。

| インターフェース | 役割 |
| --- | --- |
| `RateLimitDetector`（`DetectRateLimit(out) RateLimitOutcome`） | 利用上限・レート制限の判定をプロバイダー固有にする（未実装なら共通のマーカー判定） |
| `ModelSelector`（`ModelOption()` / `ModelArgs(model)` / `Models()`。`agent/model.go`） | 設定 `agent_model` のモデルを指定して起動する。未実装のプロバイダーは設定を無視し、設定画面のモデル入力は無効になる |
| `ReasoningSelector`（`ReasoningOption()` / `ReasoningArgs(level)` / `ReasoningLevels()`。`agent/reasoning.go`） | 設定 `agent_reasoning_effort` の推論レベルを指定して起動する。未実装のプロバイダーでは推論レベルを保存できず、設定画面の選択は無効になる |
| `UsageReporter`（`ParseUsage(raw, answer) models.AgentRunUsage`。`agent/usage.go`） | CLI の出力から実際のモデル・推論レベル・消費トークン数・実行コマンド数を読み、報告行に記録する。未実装なら記録しない（NULL / 空） |

起動引数は `Command()` の後に、モデルが設定されていれば `ModelArgs(model)`、推論レベルが設定されていれば `ReasoningArgs(level)` を足したもの（`providerCommand`）。どちらも空なら `Command()` のまま（CLI の既定・CLI 側の設定）。

- モデル名は `agent.ValidateModel`（英数字で始まり英数字と `. _ : / @ + -` のみ、100 文字以内。先頭が `-` の値はオプションと誤認されるため拒否）で検証し、保存値が不正なら未指定として扱う。
- 推論レベルは `agent.ValidateReasoningEffort`（英小文字のみ、20 文字以内）で形を検証し、保存時に `agent.CheckReasoningEffort` でモデルとの組み合わせを検証する: モデル指定ありでそのモデルの受け付ける値が分かっていれば、その一覧に無い値は拒否する。モデル未指定（CLI の既定のモデル）なら既知の全モデルの値の和集合で判定する。受け付ける値が分からない（キャッシュが無い、指定したモデルが載っていない）ときは形だけ検証する（モデル名は自由入力で、キャッシュは参考情報のため）。推論レベルに対応しないプロバイダーで空以外は拒否する。
- 検証は保存する組み合わせ全体に対して行い、拒否されたときは何も保存しない（`modules.CheckAgentSettings` / `SaveAgentSettings`）。モデルだけを変える場合も保存済みの推論レベルと合わなければ拒否する（CLI は先に推論レベルを変えるよう案内する）。プロバイダーを別のものに変えると `agent_model` と `agent_reasoning_effort` を削除する（名前も値もプロバイダーごとに違うため）。保存済みの値が実行時に使えなくなった場合（CLI の更新など）は、通常の解析失敗として理由が記録される。
- `codex`: 起動コマンドは `codex exec --sandbox read-only --skip-git-repo-check`（プロンプトは stdin）。モデル指定時は `--model <モデル>`、推論レベル指定時は `-c model_reasoning_effort="<値>"`（Codex に推論レベル専用のオプションは無く、設定の上書きで渡す。値は TOML として解釈されるので引用符付きの文字列にする）を足す。`Models()` と `ReasoningLevels()` は Codex CLI が自分のモデル選択用に保存しているキャッシュ `$CODEX_HOME/models_cache.json`（`CODEX_HOME` 未設定なら `~/.codex`）の `models[]` から読む: `Models()` は `visibility` が `list` のものを `priority` 順に（サインイン中のアカウントで使えるモデル）、`ReasoningLevels()` は非表示のモデルも含めて `slug` ごとの `supported_reasoning_levels[].effort`。このファイルは Codex の内部形式で公開仕様ではないため、無い・読めない・形式が違う場合は空とする。`ParseUsage()` は出力冒頭の `--------` で囲まれたヘッダーの `model:` / `reasoning effort:` 行、回答部分（エコーされたプロンプトより後）の `exec` 行の数（実行コマンド数）と `tokens used` の次の行（または同じ行）の数値（`54,394` の区切りは除く）を読む。ヘッダーが無い出力（Codex の出力でない）ではコマンド数も NULL にする。
- プロバイダーの有無は `exec.LookPath` で判定する。

解析は纏めフェーズの一部ではなく、纏め完了後に制御側が「対応対象かつ `needs_analysis = 1`（新規グループ、最新の決着した報告（完了した報告、または解析不能で終わった報告）が扱っていないパターンのバウンスが来たグループ、前回の解析が失敗したグループ）」のグループについて投入する。対象外（宛先側）のグループは自動では解析しない（グループ詳細の「解析」で個別に実行できる。9.2 の `.../analyze`）。

### 6.2 実行手順（`AnalyzeGroup`）

1. `agent_reports` に `running` 行を作る。その id を名前にした実行ごとの作業ディレクトリ `data/agent/<address>/<group_key>/<report_id>/`（`agent.RunDir`。`<address>` は 3.1 で安全化した名前）を作り、`templates/agent/<provider>/**`（codex では `AGENTS.md`）があれば複製する。1 回の解析の成果物（証拠、プロンプト、CLI の出力、報告）はこのディレクトリに閉じ、失敗した実行が前の実行のファイルに触れることはない。
2. 証拠を用意する（`agent/evidence.go`、`BuildEvidence`）。エージェントにはメールの保存先を読ませず、MailCare が判定の根拠を切り出して渡す。
   - グループの全バウンス（`models.ListGroupBounces`: バウンス行 + メールキー・日時・`body_source`）をパターン（5.4）ごとに集計する: 件数、宛先数、初回 / 最終日時。件数の多い順に並べ、`P1`、`P2`、... と呼ぶ。
   - パターンごとに最新の 1 通を見本（`S1`、`S2`、...。最大 `MaxEvidenceSamples` = 5）とし、`.eml` を解析し直して次を取り出す: 分類（カテゴリと `category_rule`）、診断文と取った場所、通知の From と件名、delivery-status の項目（そのバウンスの宛先のブロック。無ければ 1 つ目）、返送された元メールのヘッダー（From、To、Subject、Date、Message-ID、DKIM の `d=`、Authentication-Results、Received-SPF）、本文の抜粋。
   - 本文は判定の根拠が入っている方だけを使う: 診断文を本文から取った場合はそのセクション（`diagnostic_source`。HTML はテキスト化）、delivery-status から取った場合や診断文が無い場合は判定に使った本文（`body_source` の種類のうち状態コードを含むセクション、無ければ 1 番目）。text と HTML の両方がある通知では、もう一方の本文は「判定に使っておらず内容が違う可能性があるので使わない」と明記する。
   - 抜粋は空行の連続を 1 行に畳み、診断文（先頭 40 文字）→ 状態コード → 宛先を含む行を中心に最大 `MaxExcerptLines`（40）行（診断文を delivery-status から取った場合は本文は補足なので半分）。1 行は 300 文字まで。切った箇所には `[TRUNCATED: ... evidence/<key>.txt]` を付ける。通知に無い値は `(not found)` と明記する。
   - 見本ごとの証拠ファイル `evidence/<message_key>.txt` を作業ディレクトリに書く（delivery-status の全項目・全ブロック、返送された元メールのヘッダー、本文セクションの全文（2,000 行まで））。エージェントが読んでよいのはこのファイルだけで、条件（6.3）を満たすときに限る。
   - 前回との差分: 最新の完了報告が扱ったパターン（`agent_report_patterns`）があり、その一部だけが新しいとき（更新）は、新しいパターンだけを見本にし、プロンプトに前回の報告を載せる。新しいパターンが無い（手動の再解析）・全部が新しい・前回の報告がパターンを記録していない場合は全体を解析する。
3. プロンプト（6.3）を組み立てる。プロンプトは stdin で渡し、`PROMPT.md` は CLI の終了後に（成功・失敗・タイムアウト・中止のいずれでも）作業ディレクトリに書く（エージェントが実行中にプロンプトの写しを見つけて読み直さないようにしつつ、実行の履歴として残すため）。`{prompt_file}` でプロンプトをファイルから読むプロバイダーだけは実行前に書く。ジョブの進捗に出す作業ディレクトリは `workspace <group_key>/<report_id>` の相対名だけで、絶対パスは出さない（ジョブ履歴は一般利用者にも見えるため）。進捗には `running <Label> (model <モデル>, reasoning <推論レベル>) on N messages in P patterns, S samples`（指定したものだけ括弧内に出す）と、CLI が報告した `usage: model ..., reasoning ..., tokens ..., commands ...` を出す。
4. CLI を作業ディレクトリを cwd にして実行する（`AgentTimeout` 30 分）。終了コードは信頼せず、出力に有効な REPORT ブロックがあれば成功とする。codex はプロンプト全文をエコーしてから回答するため、解析前に出力からプロンプト本文を取り除き、テンプレートのプレースホルダー（`<one or two sentences>` 等）を含む報告や短すぎる報告は失敗として扱う。利用上限・レート制限（`usage limit` / `rate limit` / `429` / `try again at` 等。プロバイダーごとに `DetectRateLimit` で拡張できる）を検出した場合は `error_message` に再試行時刻を含めて失敗にする。成否にかかわらず `UsageReporter` の結果を報告行に記録する（`models.UpdateAgentReportUsage`）。
5. `RESULT.log`（`Result: Success` / `Result: Failure` と理由、抽出した要約・対応者区分・重大度・確度・報告、CLI が報告したモデル・推論レベル・トークン数・コマンド数、全出力）を毎回書き、成功時のみ `REPORT.md` を書く（失敗した実行のディレクトリには `REPORT.md` が無く、成功した実行のディレクトリはそのまま残る。DB も最新の完了報告を表示し続ける）。`CompleteAgentReport`（または `FailAgentReport`）で保存する。成功時は証拠に使ったグループの全パターンキーを `agent_report_patterns` に記録し、`needs_analysis` を「対応対象で、まだ扱っていないパターンがある」（解析中に新しいパターンのバウンスが届いた場合）に合わせる（通常は 0）。META の `responsible` が確定値（`sender` / `recipient` / `domain`）で現在値と異なれば `groups.responsible` を更新する（`models.UpdateGroupResponsible`）。`unknown`・空・不正値では機械判定の値を残す（報告行にはエージェントの回答をそのまま保存する）。失敗理由: プロバイダー未登録、CLI 起動失敗、タイムアウト、中止、REPORT ブロック無し、REPORT はあるが使えない（雛形のプレースホルダー行が残る / 見出しを除いた本文が 40 文字未満 / 要約がプレースホルダー / 報告本文または要約に秘密らしい文字列が含まれる: 64 桁の 16 進、`$2a$` / `$2b$` / `$2y$` で始まる bcrypt ハッシュ、`-----BEGIN`、`mlc_` + 40 桁 16 進、`AKIA` + 16 桁の英大文字数字。理由は "report contains secret-like content"）、利用上限・レート制限の検出。失敗のうち、利用上限（`agent.IsUsageLimitMessage`）と中止（コンテキストのキャンセル）はグループに関係が無いので `needs_analysis` に触れず（`agent_report_patterns` にも記録しない）、グループは解析待ちのまま次回に再試行される。それ以外の失敗（CLI の起動失敗、タイムアウト、REPORT 無し、使えない報告など）はそのグループを今のままでは解析できないとみなし、成功と同じくグループを決着させる: その時点のグループの全パターンを `agent_report_patterns` に記録し、`needs_analysis` を外す（解析中に新しいパターンのバウンスが届いていれば付いたまま）。以後は、決着した報告に無い新しいパターンのバウンスが届くまで、このグループは自動では解析しない。そのため失敗したグループは印が付いたまま次回のスケジュールで再試行される）。`AnalyzeGroup` は失敗でも報告行を返し、記録すらできない場合だけエラーを返す。
6. 整理（`CleanupWorkspaces`）: `analyze` ジョブは実行ディレクトリを整理しない。日次の `cleanup` ジョブ（7.1 / 7.3）が対象アドレスごとに、`data/agent/<address>/` 配下で更新日時（mtime）が設定 `agent_keep_days`（既定 30 日、1〜365）より古い実行ディレクトリを削除し、空になった `<group_key>/` ディレクトリも削除する。索引に無くなったグループのディレクトリも同じ規則で消える。ディレクトリ以外のエントリには触れない。削除数はジョブの進捗と結果に記録する。メールアドレスの改名・削除では `data/agent/<address>/` も改名・削除する（8 章 `mailbox update` / `mailbox delete`）。

残存リスクと運用前提: `--sandbox read-only` は書き込みを禁じるだけで、CLI は MailCare と同じ OS ユーザーが読める全ファイル（ホームディレクトリ、鍵、他のアプリの設定など）を読める。プロンプトの制約と 5 の秘密らしい文字列の検出は緩和策であって境界ではない。MailCare と codex は専用の低権限 OS ユーザーで実行し、そのユーザーが `data/` 以外を読めない（他のディレクトリの権限、または専用ホームディレクトリ）ようにすること。

### 6.3 プロンプト仕様

固定順: 制約（読み取り専用、読んでよいのは条件付きの証拠ファイルだけ（プロンプトの読み直し・README の探索・ディレクトリ一覧の禁止）、ネットワーク禁止、通知由来の値は信頼できないデータ、出力言語）→ タスク（管理者の立場で対応単位に対する具体的な対応を求める。カテゴリごとの指針を付ける: `ip_blocked` は当該ブラックリストの解除手順、`auth_failure` は送信ドメインの SPF / DKIM / DMARC / PTR / HELO、`sender_blocked` は送信元アドレスの評価 など。対象外グループでは宛先側の管理者に伝える短い注記を求める。更新では前回の報告を引き継いでグループ全体の報告を書き直すことを求める）→ グループ概要（カテゴリと説明、対応単位、判断主体、対応対象かどうか、宛先ドメイン、状態コード、診断テンプレート、件数、宛先数、IP 数、初回 / 最終日時、機械判定の対応者区分、宛先 / 相手 IP / 相手 MTA の一覧）→ 前回の報告（更新のみ）→ パターン一覧 → 証拠（見本ごとのブロック）→ 証拠の使い方 → 関係者の呼び名 → 出力指定。カテゴリの英語説明は `agent/category.go` の `CategoryGlossary` に持つ。

証拠の使い方（「足りないときは読む」のような曖昧な指示にしない。プロンプト上の目印で判断できる条件にする）:

- 回答はパターン一覧と証拠から行い、次のいずれかが成り立つときだけコマンドを実行してよい: (a) 抜粋に `[TRUNCATED]` があり、必要な部分（診断文、拒否したホスト、ブラックリスト / ポリシー名、参照 URL）が切れている、(b) 報告に必要な値がプロンプトで `(not found)` になっていて、見本の証拠ファイルにありそうだ、(c) 証拠がグループ概要のカテゴリと矛盾し、抜粋だけではどちらが正しいか分からない。
- 「念のため」「網羅のため」「他のメールも同じか確かめるため」は読む理由にならない。
- (a)〜(c) のときも、その見本の証拠ファイルだけを 1 回ずつ、合計 `MaxEvidenceReads`（3）ファイルまで、`cat` / `sed -n` で読む。スクリプトは書かない。
- それでも原因が確定できなければ推測で埋めず、推測を事実として書かない。原因の分析に、通知が示すこと・足りない情報・管理者が確かめる方法（どの照会・ログ・設定を見るか）を書き、担当が決まらなければ `unknown`、確度は `low` にする。
- 通知の記載（事実）と一般知識を分け、一般知識を通知に書いてあったかのように書かない。
- 機械判定のカテゴリは誤りうる。証拠と食い違えば証拠に従い、分類が誤っているようだと理由とともに書く。

プロンプト注入対策: グループ概要とパターン一覧の機械判定値（`unit_value`、`authority`、`recipient_domain`、`diagnostic_template`、状態コード、相手 MTA、宛先 / 相手 IP / 相手 MTA の各項目）と証拠の見出し行の値（診断文、From、件名、delivery-status と元メールのヘッダー）は、空白・改行の連続を 1 個の空白に畳んで必ず 1 行に収める。一覧は各 30 件（`agent.MaxPromptListItems`）、パターンは 20 件（`MaxPromptPatterns`）までとし超過分は件数で示す。本文の抜粋と前回の報告は各行の先頭に `| ` を付ける。通知の文字列に含まれる出力マーカー（`<<<MLC`）は `<<< MLC` に崩す。メール本文由来の文字列がプロンプトの行やセクションを増やしたり、REPORT / META ブロックを差し込んだりすることはできない。報告の秘密らしい文字列の検出は 6.2 の 5 を参照。

関係者の呼び名（`=== PARTIES ===`）: 報告が主語にできる関係者は次の 6 つで、それぞれ報告の言語で 1 つの呼び名だけを使わせる（同義語・略称は使わない）。日本語の呼び名は埋め込みテンプレート `templates/agent/party_names_ja.txt`（1 行 1 名、次の順）に置き、無い・6 行に満たないときは英語の呼び名を使う。あわせて、一人称・二人称（「当社」「当方」「弊社」「私たち」「貴社」など）を使わないよう指示する。MailCare の利用者は送信側の組織とは限らないため。プロンプトとカテゴリ用語集の英語の指示文も一人称（`our`）を使わず、同じ役割名で書く。

| 順 | 関係者 | 日本語の呼び名 | 英語の呼び名 |
| --- | --- | --- | --- |
| 1 | 送信側（送信サーバー・送信 IP・送信ドメインと DNS レコード・送信元アドレス）を管理する人 | 送信側のメール管理者 | the sending-side mail administrator |
| 2 | 宛先アドレスの所有者（宛先リストの管理者） | 宛先アドレスの所有者 | the recipient address owner |
| 3 | 宛先アドレスでメールを受け取る本人 | 受信者 | the recipient |
| 4 | 宛先ドメイン（メールサーバー・DNS・MX）を管理する人 | 宛先ドメインの管理者 | the recipient domain administrator |
| 5 | 送信 IP を登録しているブラックリストの提供元 | ブラックリストの提供元 | the blacklist provider |
| 6 | MailCare（機械判定） | MailCare | MailCare |

画面の対応者区分の表示（`sender` / `recipient` / `domain`）も 1・2・4 の呼び名に揃える。

報告の見出し: 英語の見出しは `prompt.go` に持つ。日本語の見出しは埋め込みテンプレート `templates/agent/report_headings_ja.txt`（1 行 1 見出し、原因 / 影響 / 対応 / 担当の順。`AnalyzeInput.TemplatesFS` から読む）に置き、Go のソースを ASCII のみに保つ。テンプレートが無い、または 4 行に満たないときは英語の既定見出しを使う（報告言語は日本語のまま）。

出力は次の 2 ブロックを各 1 回。

```text
<<<MLC:REPORT>>>
## 原因の分析
...
## 影響範囲
...
## 推奨する対応
1. ...
## 対応すべき担当
...
<<<MLC:/REPORT>>>
<<<MLC:META>>>
{"summary":"1〜2 文の要約","responsible":"sender|recipient|domain|unknown","severity":"high|medium|low","confidence":"high|medium|low"}
<<<MLC:/META>>>
```

`confidence` は原因をどこまで確定できたか: `high` = 通知が原因を直接示している、`medium` = 通知と一般知識から推定した、`low` = 証拠では確定できない（報告に足りない情報を書く）。`low` の報告はグループ詳細と通知メールで「要確認」と示す。

REPORT は最後のマーカー対を採用する。META はコードフェンスを除去し最初の `{` から最後の `}` を JSON として解釈する。解釈できない場合や列挙値が不正な場合は無視する（報告は完了扱い）。要約が空のときは報告本文の最初の見出し以外の段落（200 文字まで）を要約にする。プロンプトの全文と実例は [プロンプト仕様/バウンス分析 プロンプト仕様.md](プロンプト仕様/バウンス分析%20プロンプト仕様.md) を参照。

## 7. ジョブとスケジューラ（`app/modules/jobs.go`, `scheduler.go`）

### 7.1 種別

受信・纏め・解析は互いに独立したジョブで、制御側が個別にも、同期ジョブとして順にも呼び出す。

| kind | mailbox_id | target | 処理 |
| --- | --- | --- | --- |
| `sync` | 指定 | - | `FetchMailbox` → `GroupMailbox(full=false)` → 対応対象で `needs_analysis` のグループ（新規、最新の決着した報告（完了した報告、または解析不能で終わった報告）が扱っていないパターンのバウンスが来たもの、前回の解析が失敗したもの）があれば `analyze`（target 空）を投入 |
| `fetch` | 指定 | - | `FetchMailbox` のみ。結果を `mailboxes` に記録 |
| `group` | 指定 | - | `GroupMailbox(full=false)` → `analyze`（target 空）を投入 |
| `analyze` | 指定 | 空 = `needs_analysis` かつ対応対象のグループ / グループキー（対象外のグループも可。グループ詳細の「解析」）/ `*` = 対応対象の全グループ | `agent.AnalyzeGroup`（モデル `agent_model`、推論レベル `agent_reasoning_effort`）。解析待ちの印（`needs_analysis`）に触れるのは 3 箇所だけ: 纏めでの新規グループ・新しいパターン（付ける）、ツール・グループ詳細からの解析の指示（target が `*` またはグループキーのとき、開始時に対象の対応対象グループへ付ける）、解析の決着（成功、または利用上限・中止以外の失敗で外す、6.2 の 5）。利用上限での打ち切り・上限中の見送りでは触れないので、終わらなかったグループは印が付いたまま次回のスケジュールの解析（target 空）に持ち越される。既存のパターンの通知が加わっただけでは印は変わらない。あるグループの解析が利用上限・レート制限で失敗したら（`agent.IsUsageLimitMessage`）、残りのグループは起動せず（同じく拒否されるだけなので）、進捗に "stopped: N group(s) not analyzed because of the usage limit" を出してジョブをエラーで終える。CLI が解除時刻を示していれば（`try again at 7:22 PM` など。`agent.ParseRetryTime`: 時刻は次に来るその時刻、日付付きはその日時、`3 hours` などは今からの経過）設定 `agent_limited_until` に記録する。記録した解除時刻までは、解析ジョブは CLI を起動せずに見送る（スケジュールの解析（target 空）は結果 "skipped: the agent's usage limit lasts until ..." で成功扱い、ツール・グループ詳細からの明示の解析はその文でエラー）。解除時刻が分からない上限は記録せず、次のチェック時刻の同期でそのまま解析を試みる。受信と纏めは解析とは別のジョブなので、上限中も全アドレス分行う |
| `reindex` | 指定 | - | `Reindex` → `analyze`（target 空）を投入。結果は `messages N, bounces B, groups G[, skipped S]`（索引に載せられなかった原文の数、5.5） |
| `reclassify` | 指定 | - | `GroupMailbox(full=true)` → `analyze`（target 空）を投入 |
| `notify` | NULL | 空 = 通知先へ送信 / `test:<address>` = テスト送信 | 通知メールの組み立てと送信（7.5） |
| `cleanup` | 指定 | - | （有効なアドレスで `server_keep_days` > 0 のときだけ）`DeleteFromServer`（対応済・無視のグループのメールを IMAP サーバーから削除、5.6.1）→ `PruneMailbox`（`mail_keep_days` を過ぎたメールの削除、5.6）→ `RemoveStaleTempFiles`（原文ディレクトリに残った 1 日より古い書き込み中の一時ファイル `.<name>.<random>.tmp` の削除。件数は進捗の 1 行だけで結果行には含めない、5.6）→ `agent.CleanupWorkspaces`（`agent_keep_days` を過ぎた実行ディレクトリの削除、6.2 の 5）→ `DeleteOldJobs`（完了から 30 日より古い `jobs` 行の削除。ジョブ履歴は全体で 1 つなので毎子ジョブが試み、最初の子が実際に消す）。結果は `deleted D server mails, removed N messages, M groups, K agent workspaces, J jobs` |

- `mailbox_id` が NULL のジョブは「展開ジョブ」で、実行時に対象アドレス（`sync` / `fetch` は有効なアドレスのみ、それ以外（`cleanup` を含む）は無効なアドレスも含めた全アドレス）ごとに同種のジョブを 1 件ずつ投入して即終了する（結果は「queued N jobs」）。これにより全アドレス同期（全処理）は ワーカー数の範囲で並列に進む。
- 後続の `analyze` 投入は `agent_enabled` かつプロバイダーの CLI が PATH にあるときのみ行う。`requested_by` は `cli` / `scheduler` / `web:<username>`。展開で作られた子ジョブと後続の `analyze` は親の `requested_by` を引き継ぎ、`jobs.parent_id` 列に親ジョブの id を持つ（直接投入されたジョブは NULL）。
- ジョブの属性はすべて実列である: 進捗（`progress`。最新 100 行）、結果（`result`。完了時の 1 行）、失敗理由（`error_message`）、`parent_id`、3 つの日時（`created_at` / `started_at` / `finished_at`）。JSON 列は持たない。
- `cleanup` の子ジョブは `ResolveMailKeepDays` / `ResolveAgentKeepDays` の日数とジョブ履歴の保持期間（定数 `jobRetention` = 30 日）で 3 つの削除を順に行う。前の段階が失敗しても後の段階は行い、削除数を結果行に出したうえで失敗をジョブの失敗（`error_message`）にする（消せなかったものは次回に持ち越す）。メールアドレスが 1 件も無いときは展開ジョブ自身がジョブ履歴を削除する（結果 `queued 0 jobs (no mailbox), removed J jobs`）。スケジューラが日付の変わり目に投入するほか（7.3）、ツール画面と CLI `cleanup` からいつでも実行できる。
- 同じ種別・メールアドレス・対象の未完了ジョブがあれば重複投入しない（`HasActiveJob`）。
- 進捗は 500 ミリ秒に 1 回まで DB に書き、最新 100 行（`progressMaxLines`）を保持する。各行は `<追加時刻（UTC、RFC 3339）>\t<メッセージ>` の形で保存する（`stampProgressLine`）。1 件のジョブは 1 つのメールアドレスだけを扱い、アドレスはジョブの行に記録されているので、メッセージにはアドレスを付けない。Web はタブの前を利用者のタイムゾーンの `MM-dd HH:mm:ss` に整形して時刻列として表示し（`JobProgressLog`。ツール画面のジョブ履歴とグループ詳細の解析中表示）、CLI は端末のローカル時刻で `MM-dd HH:mm:ss <メッセージ>` と表示する（`FormatProgressLine`）。Web の進捗欄は高さを制限したスクロール領域で、最下部を見ている間は新しい行に合わせて自動でスクロールし、利用者が上へスクロールしている間は位置を保つ。サーバー起動時（`ResetStaleJobs`）は `running` のまま残ったジョブと分析報告を `error` にする復旧だけを行い（報告のエラー文は中止の形式 `analysis canceled: interrupted by a server restart` にするので、解析不能とは扱われず、グループは解析待ちのまま次回に再解析される）、完了から 30 日より古いジョブ行の削除は日次の `cleanup` ジョブが行う（7.3）。
- ジョブ履歴（`jobs` 表）はメールアドレスを削除しても残り、`mailbox_id` が NULL になる。削除時はそのアドレスの待機中（`queued`）のジョブを行の削除と同じトランザクションで `canceled`（`finished_at` 付き）にし（`models.CancelQueuedJobsForMailbox`）、実行中（`running`）のジョブがあるアドレスの削除と改名は `ErrMailboxBusy`（"a job is running for this mailbox"。HTTP は 409）で拒否する（`models.HasRunningJobForMailbox`）。`queued` のジョブの取消は Web（`DELETE /api/v1/jobs/{id}`）と CLI（`jobs cancel ID`）から行える（`running` 以降は取り消せない）。`mailbox_id` が NULL のジョブのうち、親ジョブがある（`parent_id` が 0 でない）もの、または `canceled` で結果が空のものは削除済みアドレスのジョブとみなし（`modules.JobOfDeletedMailbox`。`notify` は対象外）、CLI は "(deleted mailbox)"、Web は「削除済みのメールアドレス」と表示する（API は `mailbox_address` を空のまま `mailbox_deleted: true` を返す）。親の無い展開ジョブは従来どおり "(all)"（Web は「すべてのメールアドレス」）。

### 7.2 ワーカーと直列化

- ワーカー数は設定 `workers`（既定 2、1〜16。`service start --workers N`、`settings set workers N`、Web の一般設定）。ワーカーは同時に実行できるジョブ数であり、同時にアクセスするメールアカウント数の上限でもある。
- ジョブは実行時に「資源キー」の集合を占有する。占有中のキーを必要とするジョブは待機し（`queued` のまま）、キーが空いた時点で開始する。

| kind | 占有する資源キー |
| --- | --- |
| `sync`, `fetch` | `host:<imap_host 小文字>`、`mailbox:<address>` |
| `group`, `reclassify` | `mailbox:<address>` |
| `analyze` | `agent`、`analyze:<address>` |
| `reindex` | `mailbox:<address>`、`agent`（索引ファイルを入れ替えるため解析と同時に走らせない） |
| `cleanup` | `mailbox:<address>`、`agent`（解析中に同じアドレスのメールやグループを消さないため、解析と同時に走らせない）。サーバー上の削除を行うアドレス（有効で `server_keep_days` > 0）では `host:<imap_host 小文字>` も占有する（同じ IMAP サーバーの受信と重ねない） |
| `notify` | `notify` |
| 展開ジョブ（mailbox NULL） | なし |

- 同一 IMAP サーバーのアカウントは `host:` キーで直列化され、先行ジョブの完了を待って順に開始する。エージェント CLI は `agent` キーで常に 1 本ずつ実行する。
- ワーカーは `queued` を古い順に走査し、資源キーが空いている最初のジョブを取る（`ClaimNextRunnableJob`）。
- CLI のプロセス内実行（`RunJobInline`）は同じ実行器を使い、自分が投入したジョブ（展開で生じた子と後続の解析を含む）を順に実行する。自分のジョブかどうかは `parent_id` の連鎖で判定するので、別のターミナルから同時に投入された CLI ジョブは実行も待機もしない（サーバー稼働時の `--wait` も同じ判定）。

### 7.3 スケジューラ

`check_times`（`HH:MM` をカンマ区切り、ローカル時刻）を読み、`SchedulerTick` ごとに「直前 tick から現在までに到来した時刻」があれば全アドレス同期（`sync`、mailbox NULL）を投入する（同一分に二重投入しない）。`check_times` が空なら自動同期は行わない。全アドレスへの展開では、`sync` / `fetch` は無効（`mailboxes.enabled` = 0）のアドレスを除き、それ以外の種別（`cleanup` など）は無効なアドレスも含める。設定変更は即時反映（毎 tick で読み直す）。

利用上限後の解析（`queueAnalysisAfterLimit`）: 設定 `agent_limited_until`（7.1）の解除時刻から `AgentLimitResumeMargin`（10 分）過ぎた最初の tick で、解析待ちのグループの解析（`analyze`、mailbox NULL = 全アドレスに展開、target 空）を投入し、記録を消す。自動解析が無効（`agent_enabled` = 0）または CLI が無いときは投入せず記録だけ消す。投入できなかったときは記録を残して次の tick で再試行する。

日次のクリーンアップ（`CleanupDue`）: サーバーのローカル日付（`YYYY-MM-DD`）が設定 `cleanup_last_run_date`（前回 `cleanup` を投入した日付、内部用。未設定なら「一度も無し」）と異なる最初の tick で `cleanup`（mailbox NULL = 無効なアドレスも含む全アドレスに展開）を投入し、投入できたら `cleanup_last_run_date` に今日の日付を書く（同じプロセス内では投入した日付も覚えておき、設定の書き込みに失敗しても同日に繰り返さない）。サーバー起動時（`Scheduler.Start`）にも同じ判定を行い、`cleanup_last_run_date` が今日より前または未設定なら起動直後に 1 回投入する（停止していた日の分を補う。同じ日に再起動しただけなら投入しない）。チェック時刻と違い、日付が変われば必ず 1 回だけ実行する。この 1 日 1 回の `cleanup` が、メール・エージェントの実行ディレクトリ・ジョブ履歴（完了から 30 日）の 3 つの保持期間を適用する唯一の定期処理である。

### 7.4 通知（`notify.go`）

- SMTP 設定: `smtp_host`、`smtp_port`（既定 587）、`smtp_security`（`ssl` = SMTPS 465 / `starttls`（既定）/ `none`）、`smtp_username`（空なら認証しない）、`smtp_password_enc`（秘密鍵で暗号化）、`smtp_from`（送信元アドレス。表示名は `MailCare`）。認証は PLAIN、対応していなければ LOGIN。`none` は平文のため注意書きを表示する。
- 保存済みパスワードの保護: 保存済みパスワードは保存したときの接続先だけに使う。パスワードが保存されている間に接続設定（`smtp_host` / `smtp_port` / `smtp_security` / `smtp_username`）のいずれかを変える更新（`PUT /api/v1/settings/notifications`、CLI `settings set`）は、同じ要求に `smtp_password` が無ければ `smtp_password is required when the connection settings change`（Web API は `validation.connection.passwordRequiredOnChange`）で拒否し、何も保存しない（`modules.ErrSMTPPasswordRequired`）。CLI は 1 回に 1 キーしか設定できないため、先に `settings set smtp_password ""` で保存済みパスワードを消してから接続設定を変え、改めてパスワードを設定する（エラー文にその手順を添える）。テスト送信も同じ規則（下記）。パスワードが保存されていなければ制限しない。
- 通知設定: `notify_enabled`（既定 0）、`notify_time`（`HH:MM`、1 つ、既定 `09:00`。サーバーのローカル時刻）、`notify_interval_days`（1〜7、既定 1 = 毎日）、`notify_user_ids`（通知先の利用者 id をカンマ区切り）、`public_base_url`（例 `https://mailcare.example.com`。空なら `http://<web_listen または localhost>:<web_port>` を使う）、`notify_last_sent_at`（最終送信日時、内部用）。
- 送信条件: SMTP ホストと送信元がある、通知先に選ばれた利用者のうちメールアドレスが設定されている者が 1 人以上いる、対象グループが 1 件以上ある。いずれかを満たさなければ送信せず、理由をジョブ結果に記録する（`skipped: SMTP host or sender address is not set` / `no recipient is selected` / `none of the selected recipients has an email address` / `no open actionable group has a completed report`）。`notify_enabled` は定時送信だけを制御し、「今すぐ送信」（Web / CLI `notify`）は無効でも送る。成功時の結果は `sent N group(s) to <addresses>`。
- 送信タイミング: スケジューラが `SchedulerTick` ごとに評価し、`notify_enabled` のとき、直前 tick から現在までに `notify_time` が到来し、最終送信日から暦日で `notify_interval_days` 日以上経っていれば `notify` ジョブを投入する（同一分に二重投入しない。再起動後に過去分を遡って送らない。最終送信が無ければ最初の到来で送る）。
- 内容: 全メールアドレスの索引から「対応対象で状態が `open`、かつ完了した分析報告のあるグループ」を集め、メールアドレスごとの見出しの下に 1 グループ 1 ブロックで並べる。ブロックは「カテゴリ名と対応単位（判断主体）」「対象メール件数（宛先数・初回 / 最終日時）」「報告の要約（`agent_reports.summary`。無ければ報告本文の冒頭。報告の確度が `low` なら先頭に【要確認】）」「そのグループを開く URL（`<public_base_url>/alerts/<mailbox_id>/groups/<group_key>`）」。件名は日本語が `[MailCare] 対応が必要なアラート N 件 (YYYY-MM-DD)`、英語が `[MailCare] N alert(s) need attention (YYYY-MM-DD)`。本文は UTF-8 の text/plain。送信元は `MailCare <smtp_from>`、件名は RFC 2047、本文は 8bit（998 バイト超の行があれば base64）。
- 言語とタイムゾーン: 通知先の**利用者ごとに 1 通**送り、To にはその利用者だけを入れる（受信者どうしのアドレスは見えない）。文面はその利用者の言語（`users.language`）、日時（件名の日付、初回 / 最終日時）はその利用者のタイムゾーン（`users.timezone`。読めなければサーバーのローカル時刻）で組み立てる（`MailLocale` / `MailLocaleFor`）。テンプレートは `templates/mail/<種類>_<言語>.txt`（通知 `notification_`、テスト送信 `test_`。件名も同じファイルの `subject` テンプレート）。カテゴリ名は言語ファイルの `value.category.<カテゴリ>.label`（その言語のファイルが無ければ日本語）で、その言語のファイルが無ければ日本語（`_ja`）を使う（`mailTemplatePath`）。現在は `ja` と `en` がある。グループの収集は 1 回だけ行い、同じ言語・タイムゾーンの利用者には同じ文面を使い回す。解析報告の要約はエージェントが書いたまま（報告の言語。現在は日本語）で、利用者の言語には訳さない。確度 `low` の印は日本語が【要確認】、英語が `[Needs review]`。
- 一部の宛先だけ送信に失敗した場合は、1 人でも届けば送信済みとして `notify_last_sent_at` を更新し、ジョブの結果に `sent N group(s) to <届いたアドレス>; failed: <アドレス>: <理由>; ...` と失敗を残す（ジョブは成功扱い）。全員に失敗したときだけエラーにして、送信日時は更新しない。
- テスト送信: 通知設定画面の「テスト送信」（`POST /api/v1/notifications/test`、`{to?}` 省略時は自分のメールアドレス。接続設定を要求に含めて保存前の値を試すこともでき、保存済みパスワードを使えるのは接続設定が保存値と同じときだけ。9.2）は SMTP 設定だけを検証する短いメールを送る。言語とタイムゾーンは、宛先がいずれかの利用者の通知用アドレスならその利用者のもの（`MailLocaleForAddress`）、そうでなければ Web では操作した利用者のもの、CLI（`notify --test --to`）では既定（日本語・サーバーのローカル時刻）。「今すぐ送信」（`POST /api/v1/notifications/send`）は条件を満たせば通常の通知を送り、`notify_last_sent_at` を更新する。

### 7.5 CLI からの投入

CLI から `sync` / `fetch` / `group` / `analyze` / `reindex` / `reclassify` / `notify` を実行するとき、自分のデータディレクトリのサーバーが稼働中（設定 `web_port` の `/control/status` が応答し、その `data_dir` が CLI のデータディレクトリと一致する。`modules.LocalServer` + `ServerStatus.ServesDataDir`）なら `/control/jobs` に投入し、稼働していなければプロセス内で直接実行する。投入後、`sync` と `cleanup` は `--wait` 指定時のみ完了まで待ち、`fetch` / `group` / `reindex` / `reclassify` / `analyze` / `notify` は常に完了まで待って進捗を表示する（自分の投入したジョブとその子・後続の解析を `parent_id` の連鎖で追う、7.2）。これにより同じ索引 DB への同時書き込みを避ける。同じポートで別のデータディレクトリのサーバーが稼働している場合（CLI 側 DB で解決した mailbox_id はそのサーバーでは別のアドレスを指す）は投入せず、"A server is running on port N for another data directory; running in this process." と表示してサーバーが無いときと同じくプロセス内で実行する。

## 9. HTTP

### 9.1 共通

- `/api/v1/*` は Cookie 認証。未認証は 401 `{"key":"system.unauthorized"}`。権限不足は 403 `{"key":"system.forbidden"}`。入力の誤りは 400 `{"key":"<キー>","params":{...}}`。
- エラー応答の形（`/api/v1/*` と `/web/*`）: `{"key": "<キー>", "params": {...}}`（`params` は文言に差し込む値。無ければ省く）。キーは言語ファイルの完全なキー（例 `validation.user.emailTaken`）で、英語の文は返さない（10.1 の「言語ファイル」）。対象が無ければ 404 `system.notFound`、実行中のジョブがあるメールアドレスの変更・削除は 409 `result.mailbox.busy`、それ以外の入力の誤り・操作の拒否は 400、内部エラーは 500 `system.internal`（原因はサーバーログにだけ残す）。`/control/*`（CLI 用）は従来どおり `{"error": "<英語の文>"}` を返し、CLI がそのまま表示する。
- `/control/*` はループバック（127.0.0.1 / ::1）からのみ。
- CSRF 対策（状態を変える要求 = `/api/v1/*` と `/web/*` の GET / HEAD / OPTIONS 以外、`/control/*` の POST）: (a) `Content-Type` が `application/json`（`; charset=...` などのパラメータ付き可）でなければ 415（`/control/*` は `{"error":"Content-Type must be application/json"}`、それ以外は `{"key":"system.invalidRequest"}`。HTML フォームが送れる形式は届く前に拒否される。本文の無い POST / DELETE にも必要で、SPA と CLI は常に付ける）。(b) `Origin` ヘッダーがあれば、そのホスト（既定ポート 80 / 443 は無視。スキームは比べない: TLS 終端がプロキシの場合に備える）が `Host` と一致しなければ 403。`Origin` が無く `Sec-Fetch-Site` が `cross-site` / `same-site` なら 403（`same-origin` / `none` / 無しは許可）。検査は認証より前に行う。
- 防御ヘッダー: すべての応答に `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`（メール HTML 表示 `.../messages/{key}/html/{n}` だけは SPA の同一オリジン iframe に表示するため `SAMEORIGIN`。既存の CSP 等は維持）、`Referrer-Policy: no-referrer`。
- HTTP サーバーのタイムアウト: `ReadHeaderTimeout` 10 秒、`ReadTimeout` 30 秒、`WriteTimeout` 5 分（ジョブの完了を待つエンドポイントは無い）、`IdleTimeout` 2 分。
- DB ファイルの権限: `OpenDB` は `mailcare.db`（存在すれば `-wal` / `-shm` も）を 0600 にする。サーバー起動時にデータディレクトリの権限が 0700 でなければ警告をログに出す（Windows では判定しない）。
- 応答の日時は RFC 3339（UTC）文字列。`sql.NullTime` は `null` または文字列で返す（応答用の DTO を `dto.go` で組み立てる）。
- ジョブを投入するエンドポイント（`POST /api/v1/jobs`、`.../sync`、`.../analyze`、`POST /control/jobs`）は `{job: JobDTO, created: boolean}` を返す。新規なら 201、同一の未完了ジョブが既にあればそれを 200 `created: false` で返す。
- 未知の `/api/v1/*` は未認証なら 401、認証済みなら 404 の JSON を返す（認証の検査がルーティングより先）。未知の `/web/*` と `/control/*` は JSON の 404（`/control/*` はループバック以外なら 403）。`/api/v1`、`/web`、`/control` 以外の未知のパスは SPA のシェル（`index.html`）を返す。

言語ファイル（`src/i18n/ja.json` / `en.json`）:

- 読み手と言語: CLI のコンソール出力はサーバー管理者向けの英語で、Go のコードにだけ置き、言語ファイルには置かない（多言語化しない）。Web 画面は一般の利用者向けで、利用者の言語（`users.language`）で表示する。通知メールの本文は `templates/mail/` に置き、カテゴリ名だけ言語ファイルを使う。サーバーログは英語。
- 最上位の節は次の 10 個だけ。新しい文言は上から順に当てはめ、最初に当てはまった節に置く（1 画面でしか使わなくても、役割に当てはまれば役割の節を優先する）。

| 節 | 入れるもの | キーの形 |
| --- | --- | --- |
| `system` | 操作やデータに関係ない状態（通信できない、ログインが必要、権限がない、対象が無い、サーバーの準備中・内部エラー、不正な要求） | `system.<状態>` |

| `layout` | アプリの枠（アプリ名、ヘッダー、ナビゲーション、本文へ移動、ページが無いとき・描画に失敗したときの全画面表示） | `layout.<部位>.<語>` |
| `component` | 複数の画面で使う部品（`src/components/`）に固有の文言 | `component.<部品名>.<語>` |

- `<データ>` はアプリのデータの単位: `user`、`session`、`mailbox`、`connection`（IMAP と SMTP に共通する接続項目）、`mail`、`bounce`、`group`、`report`、`agent`、`job`、`setting`、`notification`、`token`。`<画面>` は画面のファイル名から決める（`login`、`setup`、`dashboard`、`alerts`、`groupDetail`、`mails`、`mailDetail`、`tools`、`settings`、`settingsGeneral`、`mailboxes`、`notifications`、`users`、`tokens`、`profile`）。
- 同じ節の中で同じ意味の文言は 1 キーだけにする。節が違って意味も違うもの（画面名とデータ項目の名前など）は、字面が同じでも別キーでよい。値の無いキー（空文字）と使われていないキーは置かない。
- CLI と Web の両方に出る文言（サーバーの検査・操作の結果）は、Go で `message.New("<言語ファイルの完全なキー>", "<CLI に出す英語の文>")` と 1 か所で定義する。英語の文はサーバー管理者向けの言い回しで書く（Web 画面の文言の訳ではない）。差し込む値は `.With("<名前>", 値)` で渡し、名前は言語ファイルの `{{名前}}` と同じにする。同じメッセージを複数の箇所で返すときはパッケージ変数に 1 度だけ定義する。
- Web API は `Key` と `Params` だけを返す（9 章のエラー応答の形）。画面は `ApiError`（`src/api/client.ts`。`key` と `params` を持つ）を受け取り、`t(err.key, err.params)` で表示するだけで、文言の変換や推測はしない。応答にキーが無い、または言語ファイルに無いキーのとき（プロキシのエラーページなど）は HTTP 状態から `system.unauthorized` / `system.forbidden` / `system.notFound` / `system.unavailable` / `system.internal` を使い、通信自体の失敗は `system.network` とする。

### 10.4 ユニバーサルデザイン

- 本文は 16px、補足情報（表の備考・ジョブ履歴の詳細など）は 14px。行間 1.5 以上、コントラスト比 4.5:1 以上。色だけに頼らず、状態はアイコン + 文字でも示す。
- すべての操作要素にフォーカスリング、`aria-label`、44px 以上のタップ領域。テーブルは幅が狭いときカード表示に切り替える。
- Markdown は `react-markdown` で表示し、`rehype` 系のサニタイズは使わず（内部生成のため）リンクは新規タブで開く。
- 纏めグループ一覧の並び替え（最終日時の昇降順 / 件数 / 重大度）はクライアント側で行い、状態・対応者区分・検索語は URL のクエリに保持する。

## 11. データベース

- マイグレーション: マスター DB と索引 DB のスキーマはどちらも goose のマイグレーションで管理する（`app/migrations/master/`、`app/migrations/index/`。パッケージ `app/migrations` が埋め込み、`migrations.Apply` が goose の Provider API（グローバルな状態を持たない）で未適用分を当てる）。各 DB は自分の `goose_db_version` 表に適用済みの版を番号で記録する。変更はディレクトリごとに連番のファイル（`0002_<説明>.sql`、...）を足して行い、適用済みのファイルは書き換えない。マスター DB は開くたび（`OpenDB`）、索引 DB も開くたび（`models.OpenMailIndex`）に適用する。
- マスター DB: SQLite（`modernc.org/sqlite`、CGO 不要）、初版は `master/0001_init.sql` の 1 本（適用したファイルのログはサーバー起動時だけ出し、CLI コマンドでは出さない）。DSN で `busy_timeout(5000)`、`journal_mode(WAL)`、`foreign_keys(1)`、`_time_format=sqlite` を設定する。
- 索引 DB: 同じドライバ。初版は `index/0001_init.sql`（`messages` / `bounces` / `groups` / `agent_reports` / `agent_report_patterns` の 5 表）。文は `IF NOT EXISTS` なので、マイグレーション導入前に作った索引（`PRAGMA user_version` = 1、同じ表）もそのまま管理下に取り込む。SQLite では既存の表に NOT NULL の列を足すには既定値が要るため、後のマイグレーションで足す列に限り既定値を持たせてよい（設計方針の例外。アプリはこれまでどおり全列に値を書く）。索引はすべて原文から再構築できる派生データで、グループの状態と分析報告だけは再索引時に引き継ぐ。
- 設計方針: 属性はすべて実列にし、JSON 列は `mailboxes.detail_info`（まとまった接続設定。`protocol` キーで種類を示し、現在は `imap` のみ。将来 `pop3` などを追加できる）の 1 列だけ。バウンスの抽出結果は `bounces` 表（メールと 1 対 1）に持ち、グループ統計はその列で集計する。グループの表示名は保存せず、カテゴリ・対応単位・判断主体から組み立てる。既定値は持たず（アプリが全列に値を書く）、長さを断定できる文字列は `VARCHAR(n)`、断定できない文字列（メール由来の値、外部のエラー文など）は `TEXT` とし、CHECK 制約は使わない（列挙値はアプリの定数で管理し、利用者の入力の長さは入力時に検査する。書き込み時の切り詰めは行わない）。日時は UTC で保存する。`tokens` と `settings` はテンプレートのまま。サービス起動パラメータ（待受アドレス・ポート・ワーカー数・チェック時刻・メールの保持日数 `mail_keep_days`）は既定値と異なる場合だけ `settings` に保存し、既定値になれば行を消す。
- テーブル定義は [テーブル定義.md](テーブル定義.md) を参照。
