# メール判定仕様 - MailCare

受信したメールを「自動通知」「迷惑メール」「一般のメール」に分け、自動通知から詳細を抽出し、カテゴリとグループを決める規則を定める。判定の実装は `app/modules/mailengine`（`classify.go`、`dmarc.go`、`junk.go`、`extract.go`、`category.go`、`grouping.go`、`serverdelete.go`）にある。受信・纏めの手順（トランザクション、増分と全件、再索引）は [システム仕様](システム仕様.md) の 5 章を参照。

## 1. 判定の区分

纏めフェーズ（`GroupMailbox`）が 1 通ごとに次のどれかに決め、`messages` 行の `is_bounce` / `bounce_kind` / `rule` に記録する。`is_bounce` = 1 のメール（メールシステムや自動応答が送るメール）を自動通知と呼ぶ。MailCare が利用者へ送るメール通知とは別のもの。

| 区分 | `is_bounce` | `bounce_kind` | グループ | 処理対象 | サーバーからの削除 | メール一覧のタブ |
| --- | --- | --- | --- | --- | --- | --- |
| 配信失敗・配信遅延 | 1 | `failed` / `delayed` | `bounces` 行を作り、1 通を 1 グループに入れる（3・4 章） | 確実な規則で判定したものは対象（5 章） | 処理対象なら削除 | バウンス |
| 自動返信・その他の自動通知 | 1 | `auto_reply` / `other` | 入れない | 確実な規則で判定したものは対象 | 処理対象なら削除 | バウンス |
| DMARC 集計レポート | 1 | `report` | 不合格の記録ごとに `dmarc_records` 行を作り、それぞれのグループに入れる（4.2） | 対象 | 削除 | バウンス |
| 迷惑 | 0 | `junk` | 入れない（アラートに載せない） | 含めない（別に数える） | 削除 | 迷惑 |
| 一般のメール | 0 | 空 | 入れない | 含めない | 削除しない | その他 |

- 処理対象と迷惑の定義、サーバーからの削除との関係は 5 章。
- メール画面のアドレスカードには、取得メール・処理対象・迷惑の件数を並べて表示する。

## 2. 対象判定（`classify.go`）

### 2.1 判定・抽出に使う本文

判定・抽出には連結ビューを使う。優先本文 = 全 text セクションを空行 1 つで区切って連結したもの（text セクションが無ければ全 HTML セクションをテキスト化して連結したもの。`<br>` / `<p>` / `<div>` / `<tr>` 等は改行、`&nbsp;` 等の実体参照は復元）、副本文 = text と HTML の両方があるときの HTML のテキスト。まず優先本文で対象判定を行い、どの規則にも一致しなければ副本文でも判定し、どちらかで一致した結果を採る。抽出は優先本文から行い、空のままの項目（宛先・状態コード・SMTP コード・診断文・相手ホスト・IP）を副本文から補う（delivery-status パートの値が最優先なのは変わらない）。`body_source`（`text` / `html` / 空）には判定・抽出に実際に使った本文を記録する: 優先本文で判定できた（またはどの規則にも一致しなかった）場合は優先本文の側（text セクションがあれば `text`）、text ではどの規則にも一致せず HTML だけで一致した場合は `html`、本文が無ければ空。受信直後は優先本文の側が入り、纏めフェーズで確定する。次の 5 パターンをすべて扱う: plain のみ、HTML のみ、plain + HTML、plain（パートはあるが空）+ HTML、plain + HTML（パートはあるが空）。元メール本文が先でバウンス通知が後の形式でも、その逆でも、セクションを MIME 順に連結するのでバウンス文面を失わない。壊れたメールでも panic せず、読めたヘッダーだけで索引する（本文はヘッダーブロック以降のバイト列を 1 セクションとして保持）。`multipart/report` の `message/delivery-status` パートは per-recipient フィールド（Final-Recipient、Original-Recipient、Action、Status、Diagnostic-Code、Remote-MTA）と per-message フィールド（Reporting-MTA、Arrival-Date）を構造化する。`message/rfc822` または `text/rfc822-headers` パートからは元メールの Message-ID、Subject、From、Date を取る（索引に保存する）。併せて To、Authentication-Results、Received-SPF、DKIM-Signature の署名ドメイン（`d=`）も取るが、これはエージェントの証拠（[システム仕様](システム仕様.md) 6.2）に使うだけで索引には保存しない。

### 2.2 ルール表

ルールは Go のテーブル（`[]classifyRule`）として持ち、上から評価して最初に一致した結果を採用する。一致したルール名を `messages.rule` に記録する（一般のメールは空）。判定には監視アドレス（そのメールを取得したアドレス）を渡す（`Classify(pm, mailbox)`。迷惑の規則が使う）。判定結果は `messages` 行の `is_bounce` / `bounce_kind` / `rule` / `body_source` に書き、`classified = 1` にする（`models.UpdateMessageClassification`）。同じトランザクションで、古い `bounces` 行は `models.DeleteBounce` が削除し、`dmarc_records` 行は `models.ReplaceDMARCRecords` が入れ替える（[システム仕様](システム仕様.md) 5.4）。

評価順の考え方:

1. 自動通知であることの確実な根拠を持つ規則（1、1'、2、3、3'）を最初に評価する。
2. 次に迷惑の規則（J1〜J4）を評価する。確実な根拠のある自動通知は先に決まるので、迷惑の規則に届かない（件名・表示名などの弱い規則でしか判定できない自動通知は、迷惑の規則に当たることがある）。たとえば監視ドメインのサーバー自身が出す配信エラー通知は、From が監視ドメインで DKIM 署名が無く DMARC に不合格になるが、1 または 2 で先に決まるので J2 には当たらない。受信サーバーがスパム判定ヘッダーを付けた DMARC レポートも 1' で先に決まる。
3. 最後に、件名・表示名だけ、または `Auto-Submitted: auto-generated` だけで判定する弱い規則（3''、3'''、4、5）と本文の文言（6）を評価する。件名を「Undeliverable」などにした迷惑メールが、件名だけでバウンスと判定されないようにするため。

| 順 | 条件 | 結果 |
| --- | --- | --- |
| 1 | `Content-Type: multipart/report; report-type=delivery-status`、または `message/delivery-status` パートを持つ（`dsn_report`） | バウンス。`Action` に `failed` があれば `failed`、`delayed` のみなら `delayed`、成功（`delivered` / `relayed` / `expanded`、または Action が無く状態コードが 2.x.x）のみなら `other`、Action も状態コードも無ければ文言で判定。`Action` は括弧内のコメントを除いて小文字化し、上記 5 値以外は空、`Status` は `[245].n.n` 形式の状態コードだけを採る（無ければ空） |
| 1' | 添付に DMARC 集計レポートがある（2.3）（`dmarc_report`） | `report`（`is_bounce` = 1）。不合格の記録を `dmarc_records` に保存し、記録ごとにグループに入れる（4.2） |
| 2 | From または Return-Path のローカル部が `mailer-daemon` / `postmaster` / `mail-daemon`（`+` / `-` の接尾辞も可、大文字小文字無視）（`daemon_sender`） | バウンス。件名・本文で `delayed` / `failed` を判定し、失敗・遅延の語が無ければ `other` |

| 3' | 件名が 3'' と同じ不在通知のパターンに一致し、機械が送った印がある: `Return-Path: <>`（空の送信者）、または `no` 以外の `Auto-Submitted`（Exchange の自動応答は `auto-generated` を付ける）（`auto_reply_marked`） | `auto_reply`（`is_bounce` = 1、`bounce_kind` = `auto_reply`）。3 と同じく確実な自動返信 |
| J1 | 迷惑: 表示名の偽装（2.4 の P1）（`phishing_display_name`） | `junk`（`is_bounce` = 0） |
| J2 | 迷惑: From の改ざん（2.4 の P2）（`phishing_forged_from`） | `junk`（`is_bounce` = 0） |
| J3 | 迷惑: 監視アドレスを埋め込んだ外部リンク（2.4 の P3）（`phishing_link`） | `junk`（`is_bounce` = 0） |
| J4 | 迷惑: スパム判定ヘッダー（2.4 の S1）（`spam_flag`） | `junk`（`is_bounce` = 0） |
| 3'' | 件名が `Out of Office` / `Automatic reply` / `自動返信` / `不在` / `休暇中` / `外出中` 等で、3 / 3' に一致しないもの（`auto_reply_subject`）。人が書いたメールの件名にも現れるため、ルール名で区別し、サーバー上の保持日数による削除（5 章）の対象にしない | `auto_reply`（`is_bounce` = 1、`bounce_kind` = `auto_reply`、`rule` = `auto_reply_subject`） |
| 3''' | `Auto-Submitted: auto-generated`（コメント付きも可）で、3 / 3' / 3'' に一致しないもの（`auto_generated`）。システムが自動生成したメール（通知、レポート、チケット受付など）。ルール名で自動返信と区別し、サーバー上の保持日数による削除（5 章）の対象にしない | `auto_reply`（`is_bounce` = 1、`bounce_kind` = `auto_reply`、`rule` = `auto_generated`） |

| 5 | From の表示名が `Mail Delivery System` / `Mail Delivery Subsystem` / `Mail Administrator` / `Postmaster` 等（`daemon_display_name`） | バウンス。件名・本文で `delayed` / `failed` を判定し、失敗・遅延の語が無ければ `other`（表示名が `Postmaster Team` の一般的な案内メールは `other` になりグループ化されない） |

### 2.3 DMARC 集計レポートの読み取り（`dmarc.go`）

- 受信側が送る DMARC 集計レポート（RFC 7489 7.2 節・付録 C）を、メールの添付から読む。`multipart/*`・`text/plain`・`text/html`（添付を含む）・`message/delivery-status`・`message/rfc822`・`message/global`・`text/rfc822-headers` 以外のパートを 1 つずつ調べ、中身で形式を見分ける: zip（先頭が `PK\x03\x04`。中のファイルを先頭から最大 16 個（`maxDMARCZipMembers`）まで順に試す）、gzip（先頭が `1f 8b`）、それ以外は XML としてそのまま。これらのパートであれば、宣言された Content-Type やファイル名は問わない（`application/octet-stream` で送る受信側もあるため）。埋め込み元メール（`message/rfc822` 配下）の中は見ない。
- 文書の大きさは 64 MiB まで（`maxDMARCReportSize`）。gzip は展開後、zip は試したファイルの展開後の合計がこれを超えたら、圧縮されていない XML はそのままの大きさがこれを超えたら、レポートとして扱わない（zip 爆弾の防止）。展開した先頭（BOM と空白を除く）が `<` でないファイルは全体を展開せずに飛ばす。メールそのものの大きさに上限を設けない（[システム仕様](システム仕様.md) 5.2）のとは別の扱い。
- ルート要素が `feedback` で、`report_metadata` と `policy_published` の両方がある XML だけをレポートとみなす（名前空間は問わない。DMARCbis の `urn:ietf:params:xml:ns:dmarc-2.0` も読む）。XML の文字コード宣言は本文と同じ文字コード解決（別名表と自動判定を含む）で読む。
- 読み取る項目: 報告元（`org_name`）、レポート ID、集計期間、公開ポリシーのドメインと `p=`、記録ごとの送信元 IP・件数・処置（`disposition`）・DMARC 評価の DKIM / SPF 結果（`policy_evaluated`）・`header_from`・`envelope_from`・DKIM と SPF の検証結果の一覧（`auth_results`）。
- 1 通につき最初のレポートだけを使う。
- 記録が DMARC に不合格（`policy_evaluated` の DKIM と SPF がどちらも `pass` でない）のものだけを `dmarc_records` に保存する。合格した記録は保存しない。

### 2.4 迷惑メール（`junk.go`）

フィッシングとスパムを迷惑（`bounce_kind` = `junk`、`is_bounce` = 0）とする。どれか 1 つに当たれば迷惑とし、グループには入れない（アラートに載せない）。サーバーからは処理対象と同じく保持日数を過ぎたら削除する（5 章）。

誤判定しても、サーバーから消えるのは保持日数（`server_keep_days`）を過ぎた後で、手元の索引と原文は `mail_keep_days` まで残る。この前提で、確実な根拠に限らず典型的な形で判定する。

監視アドレスから次の値を自動で求める（キーワードの表は持たない）:

- 監視ドメイン: 監視アドレスのドメインの組織ドメイン（公開サフィックス + 1 ラベル。`noreply@mail.example.co.jp` なら `example.co.jp`）。
- 監視ドメインの名前部分: 組織ドメインから公開サフィックスを除いたもの（`example.co.jp` なら `example`）。4 文字未満なら使わない（短い名前は無関係な語に一致するため）。

組織ドメインの判定は公開サフィックスリスト（`golang.org/x/net/publicsuffix`）で行う。

| 規則 | 条件 |
| --- | --- |
| P1 表示名の偽装（`phishing_display_name`） | From の表示名が次のどちらかに当たる。(a) 監視ドメインまたはその名前部分を含むのに、From のアドレスの組織ドメインが監視ドメインと違う（例: 表示名「example.co.jp Mail Administrator」、アドレス `x@other.example.net`）。(b) From のアドレスと別の組織のメールアドレスを含む（例: 表示名「support@bank.example.com」、アドレス `x@attacker.example.net`）。アドレスのドメインは ICANN の公開サフィックスで終わるものだけを数える。表示名の中のドメイン名だけ（アドレスでないもの）は見ない（「Acme Co.Ltd」のような社名がドメイン名に見えるため） |
| P2 From の改ざん（`phishing_forged_from`） | From のアドレスが監視ドメイン（サブドメインを含む）なのに、最上位の `Authentication-Results`（最後に受け取ったサーバーが付けたもの）が `dmarc=fail` |
| P3 監視アドレスを埋め込んだ外部リンク（`phishing_link`） | 本文（text と HTML の各セクション）の http(s) の URL に監視アドレスが含まれ（URL エンコードされたものを含む）、リンク先ホストの組織ドメインが監視ドメインとも From のアドレスの組織ドメインとも違う。正規のサービスはサブドメインが違っても自社の組織ドメインへリンクするので当たらない |
| S1 スパム判定ヘッダー（`spam_flag`） | `X-Spam` または `X-Spam-Flag` の値が `yes` / `true` で始まる。途中のどのサーバーが付けたヘッダーかは区別できないので確実な根拠ではないが、上記の前提で使う |

起こりうる誤判定（保持日数を過ぎるとサーバーから削除される。手元には `mail_keep_days` まで残る）:

- P1 (b): 表示名に投稿者のアドレスを入れて転送するメーリングリスト（例: Google グループの「'user@partner.example.com' via グループ名」）。
- P3: 宛先アドレスをそのまま URL に入れる、配信業者の計測用ドメイン経由のリンク（例: 送信元とは別組織のクリック計測ドメイン）。
- P1 (a): 監視ドメインの名前部分が一般的な単語（例: `delivery.co.jp` の `delivery`）のとき、その単語を単語として表示名に含む他組織のメール。名前部分は前後が英字・数字でない位置だけで照合する（`example` は `example-support` に当たり、`examples` には当たらない）。

判定できないもの: 人を装った一般的なスパム（文書共有を装うもの、詐欺など）でスパム判定ヘッダーの無いものは、形では正規のメールと見分けられないので一般のメールのままとする。

## 3. バウンスの抽出（`extract.go`）

判定した `failed` / `delayed` のバウンスからは `bounces` 表の 1 行（`id` = `messages.id`）を抽出する（`ExtractBounce` → `models.UpsertBounce`）: 配信できなかった宛先（`recipient`、`recipient_domain`）、`action`、状態コード（`status_code`）、SMTP 応答コード（`smtp_code`）、診断文（`diagnostic`）とそのテンプレート（`diagnostic_template`）、診断文を取った場所（`diagnostic_source`: delivery-status パートなら `dsn`、本文ならそのセクション `text:<n>` / `html:<n>`（セクションファイルと同じ番号）、診断文が無ければ空）、パターンキー（`pattern_key`、4.3）、相手 MTA（`remote_mta` / `remote_ip`）、通知元 MTA（`reporting_mta`）、元メールのヘッダー（`original_message_id` / `original_subject` / `original_from` / `original_date`）、所属グループ（`group_key`、4.3）。`auto_reply`、`other`（失敗の証拠が無いデーモンメール。成功 DSN を含む）、`report`（DMARC 集計レポート。不合格の記録は `dmarc_records` に持つ）、`junk` と一般のメールには `bounces` 行を作らない（`is_bounce` と `bounce_kind` は記録するのでメール一覧・件数には現れる）。`smtp_code` は通知に 3 桁の応答コードが実際にある場合だけ入れる（無ければ空。プレースホルダーは合成しない）。delivery-status パートを優先し、無ければ本文（2.1 の優先本文、空のままの項目は副本文）から Postfix / Exim / qmail / Sendmail / Exchange / Gmail / 日本語 MTA 形式を正規表現で拾う（例: `<addr>: host <mta>[<ip>] said: <smtp> <status> <text>`、`550 5.1.1 <addr>...`、`The following address(es) failed:` の次行、`Final-Recipient:` 行）。監視アドレス自身と通知の差出人は宛先として採らない。

診断文を取った場所の決め方（`locateDiagnostic`）: 抽出は種類ごとに全セクションを連結した本文から行うので、診断文を最初に埋めたのが本文だった場合は、その種類（優先本文なら `text`、副本文なら `html`）のセクションを 1 つずつ（HTML はテキスト化して）調べ、一致した診断文を含むセクションを記録する。そのままの文字列で見つからなければ空白を畳んで比較し、それでも見つからなければその種類の 1 番目のセクションとする。text と HTML で内容が違う通知では、判定の根拠が入っている方のセクションがここに残り、エージェントにはそのセクションだけを見せる（[システム仕様](システム仕様.md) 6.2）。

`responsible`（対応者区分）は状態コードからではなく、4 章のカテゴリから決め、グループにだけ持つ（`bounces` 行には持たない）。

## 4. カテゴリとグループ

### 4.1 バウンスのカテゴリ（`category.go`）

纏めは「管理者が何に対して動くか」の単位で束ねる。バウンス 1 件ごとに状態コードと診断文からカテゴリを判定し、カテゴリが対応単位（`unit_value`）と判断主体（`authority`）を決める。宛先アドレスや相手 IP が違っても対応単位が同じなら同じグループになり、ブラックリストの登録先が違えば別グループになる。

| カテゴリ | 対応対象 | 判定の手掛かり（診断文 / 状態コード） | unit_value | authority |
| --- | --- | --- | --- | --- |
| `ip_blocked` | 1 | `blocked` / `blacklist` / `block list` / `listed` / `rbl` / `dnsbl` / `spamhaus` / `barracuda` / `spamcop` / `sorbs` / `uceprotect` / `proofpoint` / `cloudmark` / `Our system has detected` / `unsolicited mail originating from your IP` / `poor reputation` / 5.7.1 や 4.7.0 で IP に言及 | 診断文中の当方の送信 IP（`[203.0.113.5]` 形式など。無ければ `reporting_mta`） | ブラックリストの提供元（診断文の URL / ホスト名から抽出した `spamhaus.org` 等）。無ければ宛先ドメイン |
| `rate_limited` | 1 | `too many` / `rate limit` / `try again later` / `throttl` / `temporarily rate limited` / 4.7.0 で IP ブロックの語が無い | 送信 IP（無ければ `reporting_mta`） | 宛先ドメイン |
| `auth_failure` | 1 | `spf` / `dkim` / `dmarc` / `not authorized` / `unauthenticated` / `reverse dns` / `ptr` / `helo` / 5.7.23〜5.7.27 | 送信ドメイン（元メールの差出人のドメイン。無ければ `reporting_mta`） | 宛先ドメイン |
| `sender_blocked` | 1 | `sender address rejected` / `sender ... blocked` / `sender ... denied` / `blocked using` が送信元アドレスを指す / 5.7.1 で送信元アドレスに言及 | 元メールの差出人アドレス（無ければ送信ドメイン） | 宛先ドメイン |
| `content_rejected` | 1 | `spam` / `content` / `virus` / `malware` / `attachment` / `message rejected` / `rejected due to policy`（上記に該当しない） | 元メールの差出人アドレス | 宛先ドメイン |
| `message_too_large` | 1 | `too large` / `message size` / `exceeds` / 5.2.3 / 5.3.4 | 元メールの差出人アドレス | 宛先ドメイン |
| `server_config` | 1 | `relay` / `tls` / `starttls` / `encryption required` / `helo command rejected` / 5.5.x / 5.3.0 / 5.6.x | `reporting_mta`（当方の MTA） | 宛先ドメイン |
| `unknown_failure` | 1 | 上記のどれにも該当しない `failed` / `other` | 宛先ドメイン | `<状態コード> <診断テンプレート>` |
| `user_unknown` | 0 | 5.1.1 / 5.1.0 / 5.1.3 / 5.1.6 / 5.1.10 / `user unknown` / `no such user` / `recipient not found` / `recipnotfound` / `does not exist` | 宛先アドレス | （空） |
| `mailbox_full` | 0 | 4.2.2 / 5.2.2 / `over quota` / `out of storage` / `mailbox full` | 宛先アドレス | （空） |
| `mailbox_disabled` | 0 | 5.2.1 / `disabled` / `inactive` / `suspended` | 宛先アドレス | （空） |
| `domain_not_found` | 0 | 5.1.2 / 5.4.4 / 5.4.6 / `domain not found` / `no mx` / `unrouteable` / `name service error` | 宛先ドメイン | （空） |
| `delivery_delay` | 0 | `delayed` 種別、4.4.x / `connection timed out` / `greylist` | 宛先ドメイン | （空） |

- ルールは `category.go` の `[]categoryRule` テーブルで、上から評価して最初に一致したものを採用する。実装上の評価順: (1) 宛先側を明確に示す状態コード（5.1.1 / 5.1.0 / 5.1.3 / 5.1.6 / 5.1.10 → `user_unknown`、4.2.2 / 5.2.2 → `mailbox_full`、5.2.1 → `mailbox_disabled`、5.1.2 / 5.4.4 / 5.4.6 → `domain_not_found`）、(2) `ip_blocked`、(3) `rate_limited`、(4) 種別 `delayed` → `delivery_delay`、(5) `auth_failure`、(6) `sender_blocked`、(7) `message_too_large`、(8) `content_rejected`、(9) `server_config`、(10) 宛先側の文言（`user_unknown` / `mailbox_full` / `mailbox_disabled` / `domain_not_found` / `delivery_delay`）、(11) `unknown_failure`。`message_too_large` を `content_rejected` より先に置くのは "Message rejected: size exceeds" の誤判定を避けるため。
- カテゴリの定義（対応対象、対応者区分、対応単位、判断主体）は `categoryDefs` テーブルに持つ。`responsible` はカテゴリから決めて `groups.responsible` に書く（`bounces` 行には持たない。分析報告があればその対応者区分で上書きされる）: 対応対象のカテゴリ → `sender`（`unknown_failure` は `unknown`）、`user_unknown` / `mailbox_full` / `mailbox_disabled` → `recipient`、`domain_not_found` / `delivery_delay` → `domain`。DMARC のカテゴリも同じテーブルに持つ（4.2）。
- 送信 IP の抽出: 診断文中の `[ip]` / `(ip)` → `ip` / `address` / `host` / `your` / `originating` / `client` などの直後の IP → 任意の IP リテラルの順で探し、相手 MTA の IP とループバックを除く。無ければ `reporting_mta`。
- ブラックリスト提供元の抽出: 既知の提供元テーブル（spamhaus.org、spamcop.net、sorbs.net、barracudacentral.org、uceprotect.net、proofpoint.com、cloudmark.com、invaluement.com、abuseat.org、mailspike.net、spamrats.com、senderscore.org、surbl.org、uribl.com、psbl.org、nixspam.org、blocklist.de、mail-abuse.com、lashback.com、junkemailfilter.com、trendmicro.com、mimecast.com、talosintelligence.com、spameatingmonkey.net）→ 無ければ listing の語があるときに文中の URL / ホスト名の登録可能ドメイン（宛先・送信・MTA のドメインと大手メールサービスのヘルプ URL は除外）→ 無ければ宛先ドメイン。
- 元メールの差出人が取れない場合、送信元アドレスは診断文中の宛先以外のアドレス → 送信ドメイン → `reporting_mta` の順で補う。
- どのカテゴリでも、上記の補完順が尽きて `unit_value` が空になるときは最終フォールバックとして宛先ドメイン → 相手側 MTA のホスト名（`remote_mta`）→ 固定値 `unknown` の順で埋める（ラベルや通知で対応単位が空欄にならない）。
- 診断テンプレート（アドレス → `<addr>`、IP → `<ip>`、ホスト → `<host>`、ID → `<id>`、日付 → `<date>`、数値 → `<n>`、SMTP コードと状態コードは保持。長さの上限は無い）は `bounces.diagnostic_template` に保存し、`unknown_failure` の authority と表示に使う。診断文が空のとき（宛先や応答文が取れない通知）は件名から診断テンプレートを作る。
- 一致したカテゴリ規則の名前（`Category.Reason`）は `bounces.category_rule` に保存する（そのバウンスが対応対象 / 対象外になった理由）。

### 4.2 DMARC の不合格記録のカテゴリ（`dmarc.go`）

DMARC 集計レポートの不合格の記録は、1 件ずつカテゴリを決めてグループに入れる（`CategorizeDMARCRecord`）。送信元が記録のドメインの持ち主のサーバーか、転送した受信側か、なりすましかはレポートからは機械的に判断できない。このため 3 カテゴリとも対応対象とし、カテゴリは「記録が何を示しているか」を表す（どれに当たるかの見立てはエージェントの解析が行う）。

記録のドメインは `header_from`（無ければ公開ポリシーのドメイン）。「揃っている」は relaxed アラインメント（組織ドメインが同じ）で判定する。

| カテゴリ | 対応者区分 | 条件（上から評価） | category_rule |
| --- | --- | --- | --- |
| `dmarc_not_authenticated` | `unknown` | 揃った DKIM または SPF が単独では `pass` なのに DMARC に不合格（strict アラインメント） | `dmarc_strict_alignment` |
| `dmarc_spf_missing` | `sender` | 揃った SPF ドメイン（記録のドメインと組織ドメインが同じもの。送信サーバーの HELO 名など）の SPF 結果が `none` / `neutral` / `temperror` / `permerror`（使える SPF レコードが無い） | `dmarc_spf_missing` |
| `dmarc_dkim_failed` | `unknown` | 揃った DKIM 署名があるが検証に失敗（受信側の転送やセキュリティゲートウェイによる書き換え、または送信側の DKIM 設定の誤り） | `dmarc_dkim_failed` |
| `dmarc_not_authenticated` | `unknown` | 揃った SPF ドメインが送信元 IP を許可していない（`fail` / `softfail`）うえ、揃った DKIM 署名も無い（SPF に登録していない正規のサービス、またはなりすまし） | `dmarc_not_authorized` |
| `dmarc_not_authenticated` | `unknown` | DKIM も SPF も揃ったドメインを検証していない | `dmarc_unaligned` |

- 対応単位（`unit_value`）は記録のドメイン（空なら `unknown`）、判断主体（`authority`）は空。グループは「カテゴリ × ドメイン」になり、送信元 IP ごとには分けない（IP は記録とグループの一覧に残る）。
- 記録の形（`diagnostic_template`、`DMARCTemplate`）: `dmarc fail: dkim <DKIM>; spf <SPF>; disposition <処置>`。`<DKIM>` / `<SPF>` には、揃ったドメインの結果を `aligned <結果>` で、揃っていないドメインの検証があれば `unaligned` を、何も無ければ `none` を書く。送信元 IP・件数・日付・報告元・揃っていないドメインの名前は含めない。なりすましの送信元が日々変わっても同じパターンのままにし、そのたびに再解析しないため。
- パターンキーは `PatternKey("", diagnostic_template, "", "dmarc")`（4.3）。
- グループの件数: 所属メール数はレポートのメールの数（同じグループの記録が複数あっても 1 通と数える）。相手側 IP の種類数には送信元 IP を含め、宛先アドレスの種類数には数えない。
- エージェントの解析では、見本はメール本文ではなく、レポートの情報と記録の全項目になる（[バウンス分析 プロンプト仕様](プロンプト仕様/バウンス分析%20プロンプト仕様.md)）。

### 4.3 パターン・グループキー・表示

- パターン: グループの中で「状態コード・診断テンプレート・相手 MTA・診断文を取った場所の種類（`dsn` / `text` / `html` / 空）」が同じバウンスを 1 パターンとし（DMARC の記録は種類 `dmarc` で、記録の形だけで分ける。4.2）、`bounces.pattern_key` = `sha1(status_code|パターン用テンプレート|remote_mta|種類)` の先頭 16 桁（`mailengine.PatternKey`）。パターン用テンプレートは診断テンプレートのうち `<id>` の直後の区切り（`.` / `-`）に続く数字も `<n>` にしたもの（Gmail の `<id>-<id>.218` のようなキュー ID の末尾が SMTP コードと誤認されて残り、通知ごとに別パターンになるのを防ぐ。診断テンプレート自体とグループキーは変えない）。エージェントはパターンごとに 1 通だけ見本を読み（[システム仕様](システム仕様.md) 6.2）、解析の要否もパターンで決める（[システム仕様](システム仕様.md) 5.4 の増分）。
- グループキー: `sha1(category + "|" + unit_value + "|" + authority)` の先頭 16 桁（hex）。`unit_value` と `authority` は小文字化・前後空白除去して比較する。所属はバウンスなら `bounces.group_key`、DMARC の記録なら `dmarc_records.group_key` に記録する（`messages` には無い。読み出し時に `bounces` を LEFT JOIN して `Message.GroupKey` に埋めるので、`Message.GroupKey` はバウンスのグループだけを表す）。グループの所属メールの一覧は、`bounces` と `dmarc_records` をそれぞれ `group_key` で絞って求める。
- 表示名は保存しない。CLI・ログ・メール通知（[システム仕様](システム仕様.md) 7.4）では `models.BounceGroup.Label()`（`<category>: <unit_value> @ <authority>`）、Web ではカテゴリから翻訳した見出しを組み立てる。

## 5. 処理対象と迷惑（サーバーからの削除対象）

- 処理対象（`mailengine.serverDeletableRules`）: 確実な根拠で自動通知と判定したメール。`rule` が `dsn_report` / `dmarc_report` / `daemon_sender` / `auto_reply` / `auto_reply_marked` / `body_pattern` のもの。件名や表示名だけで判定したもの（`auto_reply_subject` / `subject_pattern` / `daemon_display_name`）と自動生成メール（`auto_generated`）は、人が書いたメールも一致しうるので含めない。
- 迷惑（`mailengine.junkRules`）: `rule` が `phishing_display_name` / `phishing_forged_from` / `phishing_link` / `spam_flag` のもの。処理対象とは別に数える。
- サーバーからの削除の対象（`mailengine.serverDeletionRules`）: 処理対象と迷惑の両方。手順は [システム仕様](システム仕様.md) 5.6.1。
- 件数: 処理対象は `mailengine.CountTargetMessages`（API の `stats.target_messages`）、迷惑は `mailengine.CountJunkMessages`（`stats.junk_messages`）。どちらも判定済み（`classified` = 1）の行を、日付と `server_deleted_at` を問わず数える（サーバーから削除済みでも、`mail_keep_days` を過ぎて手元から消えるまでは数える）。
- 件数と削除の候補は同じ規則の一覧を参照し、片方だけを変えてはならない。
