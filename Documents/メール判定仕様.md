# メール判定仕様 - MailCare

受信したメールを「自動通知」「迷惑メール」「一般のメール」に分け、自動通知から詳細を抽出し、カテゴリとグループを決め、対応済・無視のグループを再確認待ちにする規則を定める。判定の実装は `app/modules/mailengine`（`classify.go`、`dmarc.go`、`junk.go`、`extract.go`、`category.go`、`grouping.go`、`serverdelete.go`、`dnsfailure.go`、`dnsverify.go`、`sendingsources.go`、`sourcelookups.go`、`recheck.go`）と DNS の検証（`app/modules/dnscheck`）にある。受信・グループ化の手順（トランザクション、増分と全件、索引の再構築）は [システム仕様](システム仕様.md) の 5 章、判定の結果の画面での表示は [画面仕様](画面仕様.md) を参照。

## 1. 判定の区分

グループ化（`GroupMailbox`）が 1 通ごとに次のどれかに決め、`messages` 行の `is_bounce` / `bounce_kind` / `rule` に記録する。`is_bounce` = 1 のメール（メールシステムや自動応答が送るメール）を自動通知と呼ぶ。MailCare が利用者へ送る通知メールとは別のもの。

| 区分 | `is_bounce` | `bounce_kind` | グループ | 処理対象 | サーバーからの削除 | メール一覧のタブ |
| --- | --- | --- | --- | --- | --- | --- |
| 配信失敗・配信遅延 | 1 | `failed` / `delayed` | `bounces` 行を作り、1 通を 1 グループに入れる（3・4 章） | 確実な規則で判定したものは対象（5 章） | 処理対象なら削除 | 処理対象（処理対象の規則で判定したもの。件名・表示名だけで判定したものは「その他」） |
| 自動返信・その他の自動通知 | 1 | `auto_reply` / `other` | 入れない | 確実な規則で判定したものは対象 | 処理対象なら削除 | 処理対象（同上。件名だけ・`Auto-Submitted: auto-generated` だけで判定したものは「その他」） |
| DMARC 集計レポート | 1 | `report` | 不合格の記録ごとに `dmarc_records` 行を作り、それぞれのグループに入れる（4.2） | 対象 | 削除 | 処理対象 |
| 迷惑 | 0 | `junk` | 入れない（アラートに載せない） | 含めない（別に数える） | 削除 | 迷惑 |
| 一般のメール | 0 | 空 | 入れない | 含めない | 削除しない | その他 |

- 処理対象と迷惑の定義、サーバーからの削除との関係は 5 章。メール一覧のタブは「すべて / 処理対象 / 迷惑 / その他」で、「処理対象」には規則が処理対象の規則（`mailengine.TargetRules()`。5 章）のメールだけが載り、迷惑でないそれ以外のメール（件名・表示名だけで判定した自動通知、自動生成メール、一般のメール、まだ判定していないメール）は「その他」に載る。件数のカードとタブの画面は [画面仕様](画面仕様.md) 6.1。

## 2. 対象判定（`classify.go`）

### 2.1 判定・抽出に使う本文

判定・抽出には連結ビューを使う。優先本文 = 全 text セクションを空行 1 つで区切って連結したもの（text セクションが無ければ全 HTML セクションをテキスト化して連結したもの。`<br>` / `<p>` / `<div>` / `<tr>` 等は改行、`&nbsp;` 等の実体参照は復元）、副本文 = text と HTML の両方があるときの HTML のテキスト。まず優先本文で対象判定を行い、どの規則にも一致しなければ副本文でも判定し、どちらかで一致した結果を採る。抽出は優先本文から行い、空のままの項目（宛先・状態コード・SMTP コード・診断文・相手ホスト・IP）を副本文から補う（delivery-status パートの値が最優先なのは変わらない）。`body_source`（`text` / `html` / 空）には判定・抽出に実際に使った本文を記録する: 優先本文で判定できた（またはどの規則にも一致しなかった）場合は優先本文の側（text セクションがあれば `text`）、text ではどの規則にも一致せず HTML だけで一致した場合は `html`、本文が無ければ空。受信直後は優先本文の側が入り、グループ化で確定する。次の 5 パターンをすべて扱う: plain のみ、HTML のみ、plain + HTML、plain（パートはあるが空）+ HTML、plain + HTML（パートはあるが空）。元メール本文が先でバウンス通知が後の形式でも、その逆でも、セクションを MIME 順に連結するのでバウンス文面を失わない。壊れたメールでも panic せず、読めたヘッダーだけで索引する（本文はヘッダーブロック以降のバイト列を 1 セクションとして保持）。`multipart/report` の `message/delivery-status` パートは per-recipient フィールド（Final-Recipient、Original-Recipient、Action、Status、Diagnostic-Code、Remote-MTA）と per-message フィールド（Reporting-MTA、Arrival-Date）を構造化する。`message/rfc822`、`message/global`（国際化メールの元メール。`message/rfc822` と同じに扱う）または `text/rfc822-headers` パート（最初の 1 つ）からは元メールの Message-ID、Subject、From、Date を取る（索引に保存する）。併せて To、Authentication-Results、Received-SPF、DKIM-Signature の署名ドメイン（`d=`）、Received を取る。Authentication-Results・Received-SPF はエージェントの証拠（[システム仕様](システム仕様.md) 6.2）に使い、DKIM の署名ドメインと Received は送信元以外から送信されたメールのバウンスの判定（2.6）にも使う。どれも索引には保存しない。

### 2.2 ルール表

ルールは Go のテーブル（`[]classifyRule`）として持ち、上から評価して最初に一致した結果を採用する。一致したルール名を `messages.rule` に記録する（一般のメールは空）。判定には監視アドレス（そのメールを受信したアドレス）を渡す（`ClassifyWith(pm, mailbox, sources)`。迷惑の規則と 2.6 が使う。`Classify(pm, mailbox)` は送信元の設定を渡さない形で、2.6 の規則は働かない）。判定結果は `messages` 行の `is_bounce` / `bounce_kind` / `rule` / `body_source` に書く（`bounces` 行・`dmarc_records` 行とともに 1 つのトランザクションで書く手順は [システム仕様](システム仕様.md) 5.4）。

評価順の考え方:

0. 最初に、送信元以外から送信されたメールのバウンス（B0。2.6）を迷惑にする（その監視アドレスにホスト名があるときだけ）。本物の構造を持つ通知（規則 1）の中から、送信元から送っていないメールの返送を取り除くので、規則 1 より前に置く。
0'. 本物の配信不能通知の構造（`message/delivery-status`）を持つもの（1）と DMARC 集計レポート（1'）を決める。その直後に、構造を持たないのに配信不能通知を装うもの（F1、F2。2.5）を迷惑にする。偽の通知は `mailer-daemon@...` を名乗るため、2 より後ろに置くと先にバウンスと判定されてしまう。
1. 自動通知であることの確実な根拠を持つ規則（2、3、3'）を評価する。
2. 次に迷惑の規則（J1〜J4）を評価する。確実な根拠のある自動通知は先に決まるので、迷惑の規則に届かない（件名・表示名などの弱い規則でしか判定できない自動通知は、迷惑の規則に当たることがある）。たとえば監視ドメインのサーバーが出す配信エラー通知は、From が監視ドメインで DKIM 署名が無く DMARC に不合格になるが、1 または 2 で先に決まるので J2 には当たらない。受信サーバーがスパム判定ヘッダーを付けた DMARC レポートも 1' で先に決まる。
3. 最後に、件名・表示名だけ、または `Auto-Submitted: auto-generated` だけで判定する弱い規則（3''、3'''、4、5）と本文の文言（6）を評価する。件名を「Undeliverable」などにした迷惑メールが、件名だけでバウンスと判定されないようにするため。

| --- | --- | --- |

### 2.3 DMARC 集計レポートの読み取り（`dmarc.go`）

- 受信側が送る DMARC 集計レポート（RFC 7489 7.2 節・付録 C）を、メールの添付から読む。`multipart/*`・`text/plain`・`text/html`（添付を含む）・`message/delivery-status`・`message/rfc822`・`message/global`・`text/rfc822-headers` 以外のパートを 1 つずつ調べ、中身で形式を見分ける: zip（先頭が `PK\x03\x04`。中のファイルを先頭から順にすべて試す）、gzip（先頭が `1f 8b`）、それ以外は XML としてそのまま。これらのパートであれば、宣言された Content-Type やファイル名は問わない（`application/octet-stream` で送る受信側もあるため）。埋め込み元メール（`message/rfc822` 配下）の中は見ない。
- 文書の大きさは 64 MiB まで（`maxDMARCReportSize`。zip 爆弾の防止。規格に値の定めは無い）。gzip は展開後、zip は展開した量の合計（レポートでないファイルを見分けるために読んだ先頭を含む）、圧縮されていない XML はそのままの大きさがこれを超えたら、レポートとして扱わない。展開した先頭（BOM と空白を除く）が `<` でないファイルは全体を展開せずに飛ばす。メールそのものの大きさに上限を設けない（[システム仕様](システム仕様.md) 5.2）のとは別の扱い。
- ルート要素が `feedback` で、`report_metadata` と `policy_published` の両方がある XML だけをレポートとみなす（名前空間は問わない。DMARCbis の `urn:ietf:params:xml:ns:dmarc-2.0` も読む）。XML の文字コード宣言は本文と同じ文字コード解決（別名表と自動判定を含む）で読む。
- 読み取る項目: 報告元（`org_name`）、レポート ID、集計期間、公開ポリシーのドメインと `p=`、記録ごとの送信 IP・件数・処置（`disposition`）・DMARC 評価の DKIM / SPF 結果（`policy_evaluated`）・`header_from`・`envelope_from`・DKIM と SPF の検証結果の一覧（`auth_results`）。
- 1 通につき最初のレポートだけを使う。
- 記録が DMARC に不合格（`policy_evaluated` の DKIM と SPF がどちらも `pass` でない）のものだけを `dmarc_records` に保存する。合格した記録は保存しない。

### 2.4 迷惑メール（`junk.go`）

フィッシングとスパムを迷惑（`bounce_kind` = `junk`、`is_bounce` = 0）とする。どれか 1 つに当たれば迷惑とし、グループには入れない（アラートに載せない）。IMAP サーバーからは処理対象と同じくサーバーでの保持日数を過ぎたら削除する（5 章）。

誤判定しても、IMAP サーバーから消えるのはサーバーでの保持日数（`server_keep_days`）を過ぎた後で、手元の索引と原文は `mail_keep_days` まで残る。この前提で、確実な根拠に限らず典型的な形で判定する。

監視アドレスから次の値を自動で求める（キーワードの表は持たない）:

- 監視ドメイン: 監視アドレスのドメインの組織ドメイン（公開サフィックス + 1 ラベル。`noreply@mail.example.co.jp` なら `example.co.jp`）。
- 監視ドメインの名前部分: 組織ドメインから公開サフィックスを除いたもの（`example.co.jp` なら `example`）。4 文字未満なら使わない（短い名前は無関係な語に一致するため）。

組織ドメインの判定は公開サフィックスリスト（`golang.org/x/net/publicsuffix`）で行う。

| 規則 | 条件 |
| --- | --- |
| P1 表示名の偽装（`phishing_display_name`） | From の表示名が次のどちらかに当たる。(a) 監視ドメインまたはその名前部分を含むのに、From のアドレスの組織ドメインが監視ドメインと違う（例: 表示名「example.co.jp Mail Administrator」、アドレス `x@other.example.net`）。(b) From のアドレスと別の組織のメールアドレスを含む（例: 表示名「support@bank.example.com」、アドレス `x@attacker.example.net`）。アドレスのドメインは ICANN の公開サフィックスで終わるものだけを数える。表示名の中のドメイン名だけ（アドレスでないもの）は見ない（「Acme Co.Ltd」のような社名がドメイン名に見えるため） |
| P2 From の改ざん（`phishing_forged_from`） | From のアドレスが監視ドメイン（サブドメインを含む）なのに、最上位の `Authentication-Results`（最後に受け取ったサーバーが付けたもの）が `dmarc=fail` |
| P3 監視アドレスを埋め込んだ外部リンク（`phishing_link`） | 本文（text と HTML の各セクション）の http(s) の URL に監視アドレスが含まれ（URL エンコードされたものを含む）、リンク先ホストの組織ドメインが監視ドメインとも From のアドレスの組織ドメインとも違う。正規のサービスはサブドメインが違ってもそのサービスの組織ドメインへリンクするので当たらない |
| S1 スパム判定ヘッダー（`spam_flag`） | `X-Spam` または `X-Spam-Flag` の値が `yes` / `true` で始まる。途中のどのサーバーが付けたヘッダーかは区別できないので確実な根拠ではないが、上記の前提で使う |

起こりうる誤判定（サーバーでの保持日数を過ぎると IMAP サーバーから削除される。手元には `mail_keep_days` まで残る）:

- P1 (b): 表示名に投稿者のアドレスを入れて転送するメーリングリスト（例: Google グループの「'user@partner.example.com' via グループ名」）。
- P3: 宛先アドレスをそのまま URL に入れる、配信業者の計測用ドメイン経由のリンク（例: 差出人とは別組織のクリック計測ドメイン）。
- P1 (a): 監視ドメインの名前部分が一般的な単語（例: `delivery.co.jp` の `delivery`）のとき、その単語を単語として表示名に含む他組織のメール。名前部分は前後が英字・数字でない位置だけで照合する（`example` は `example-support` に当たり、`examples` には当たらない）。

判定できないもの: 人を装った一般的なスパム（文書共有を装うもの、詐欺など）でスパム判定ヘッダーの無いものは、形では正規のメールと見分けられないので一般のメールのままとする。

### 2.5 偽装された通知（`fake_notice_link` / `fake_notice_auth`、`junk.go`）

配信不能通知を装うフィッシングを、構造の有無を手掛かりに迷惑にする。本物の配信不能通知のほぼすべては `message/delivery-status` パートか元メールの添付を持つが、偽の通知はどちらも持たない。評価は 2.2 の表の F1・F2（規則 1・1' の直後、規則 2 の前）。

用語:

- 配信不能通知らしい: 次のどれかに当たる。(a) From または Return-Path のローカル部が `mailer-daemon` / `postmaster` / `mail-daemon`（規則 2 と同じ）、(d) 本文（text と HTML のテキスト）に配信不能通知に固有の文言がある（規則 6）、(b)(c) 件名が配信不能通知の既知パターン（規則 4）で、かつ From の表示名が `Mail Delivery System` 等（規則 5）。表示名だけ、件名だけでは「らしい」とみなさない（ホスティング会社や運送会社のお知らせ、保守の案内を迷惑にして、サーバーから削除してしまわないため）。
- 本物の構造: `message/delivery-status` パート（受信者が無いものを含む。規則 1 に一致したものは F1・F2 に届かない）、`multipart/report`、または元メールの添付（`message/rfc822` / `message/global` / `text/rfc822-headers`。`ParsedMessage.OriginalMessage` が取れる）のどれか。

| 規則 | 条件（すべて満たす） |
| --- | --- |
| F1 `fake_notice_link` | 配信不能通知らしい。本物の構造が無い。`Auto-Submitted` が無い、または `no`（自動返信を巻き込まないため）。本文（text と HTML の各セクション）の http(s) の URL のうち、リンク先ホストの組織ドメインが、From のアドレスの組織ドメイン・Return-Path の組織ドメイン（`<>` は無いものとして飛ばす）・監視ドメインのどれとも違うものがある（リンクは通知の著者が読み手に押させるために置いたものだけを数える。HTML のセクションは、コメント・script・style・head・title を除き、`<a>` と `<area>` の `href`（引用符あり・なし。ブラウザと同じく、`&amp;` や文字参照を復元し、前後の空白と、値の中のタブ・CR・LF を除いて読む。`//host/path` のようなスキームの無いネットワークパス参照は https として数える。http(s) で読めるホストを持つものだけ）だけを数える。生のマークアップの中の URL（`xmlns`、DOCTYPE の DTD、`img` / `script` / `link` の `src`、CSS の `url()`）と、HTML の中に文字で書かれた URL、相対リンク、`mailto:`、`javascript:` は数えない。text のセクションは行ごとに読み、リモートサーバーの SMTP 応答を引用している行の URL は数えない。SMTP 応答の行とは、次のどれかを含む行（大文字小文字を区別しない。行の中の URL を空白に置き換えてから調べるので、URL 自体が行を応答に見せることはない）: `said:`、`smtp error from remote`、`remote host said`、`response:`、`reply:`、拡張状態コード付きの 4xx / 5xx の応答コード（`554 5.7.1`、`550-5.1.1`）、単独の拡張状態コード（`5.7.1`、`4.4.1`、`2.0.0`）、行頭（前の空白と、Sendmail の記録の `<<<` を除いた位置）の 4xx / 5xx の応答コードで、その後に空白かハイフンが続くもの（`<<< 550-5.7.1 ...`、`421 Service not available`）。P3 の URL の取り出しとは別。ただし各セクションは、元メールの複製の開始を示す次の語句（大文字小文字を区別しない）が最初に現れる位置で打ち切り、その手前のリンクだけを数える: `below this line is a copy of the message`（qmail）、`this is a copy of the message, including all the headers`（Exim）、`original message follows`（Sendmail など）、`-----Original Message-----`（Outlook）） |
| F2 `fake_notice_auth` | 配信不能通知らしい。本物の構造が無い。`Auto-Submitted` が無い、または `no`。最上位の `Authentication-Results`（最後に受け取ったサーバーが付けたもの）が `dmarc=fail`。From のアドレスのドメインが監視ドメイン（サブドメインを含む）でない。本文（text と HTML のテキストの両方）が、規則 6 の語句に次を加えた「本物の通知の文言」に一致しない |

- F1・F2 共通の条件（表の条件に加えて）: 件名が返信・転送の接頭辞（`re:` / `fw:` / `fwd:`。大文字小文字を区別せず、重ねたもの、`Re[2]:`、全角のコロン `：`、`返信:` / `転送:`、角括弧の `[返信]` / `[転送]`、隅付き括弧の `【返信】` / `【転送】` を含む）で始まらず、不在通知の件名（規則 `auto_reply_subject` と同じ語）でもない。人が配信不能通知を転送したもの（引用にサポート用のリンクがある）や、Auto-Submitted ヘッダーの無い不在通知の自動返信を迷惑にしないため。ただし From または Return-Path が `mailer-daemon` 系のアドレスのときは、この件名の除外を使わない（人の転送や自動返信ではなく、偽の通知が接頭辞を付けるだけで免れるのを避けるため）。
- F2 が除く「本物の通知の文言」は、規則 6 の語句と、次の語句（大文字小文字を区別しない部分文字列）。(1) `this is the qmail-send program at`、(2) `i'm afraid i wasn't able to deliver your message to the following addresses`（ここまで qmail）、(3) `(宛先|受信者|アドレス)(に|へ)(メッセージを|メールを)?(配信|送信)できませんでした`（日本語の MTA の通知）、(4) `(宛先|受信者|グループ)への(メッセージの)?配信に失敗しました`（Exchange の日本語版）。日本語の語句はどれも受信者に対する失敗を述べる文に限る。「配信不能」「不達」「配信に失敗」だけの語は、偽の通知が誘い文句に使うので含めない。規則 6 は広げない（規則 6 に当たると処理対象としてサーバーからの削除の対象になるため）。
- F2 を F1 と別の規則にしたのは、`messages.rule` が 1 通につき 1 つで、迷惑にした理由を規則名で示すため。
- F2 が (d) を除くのは、DKIM を付けない小規模サーバーや qmail 系の本物の通知が DMARC 不合格になりうるため。監視ドメインのメールサーバーが出す通知は From が監視ドメインなので F2 に当たらない（2.2 の評価順の説明のとおり、J2 にも当たらない）。
- 弱い理由（構造が無いだけ、など）だけでは迷惑にしない。印も付けない（`messages` に疑いの列は持たない）。
- 迷惑にした通知は 2.4 の迷惑と同じ扱い（グループに入れない、別に数える、IMAP サーバーからはサーバーでの保持日数を過ぎたら削除する。5 章）。個別に戻す操作は無く、誤判定は規則を調整して直す。

起こりうる誤判定と限界:

- 構造を持たない独自形式の本物の通知が、通知の著者によるサポート用の別組織のリンクを複製の開始の語句より前に持つ場合（F1）。
- 構造を持たず、上の語句にも当たらない日本語の本物の通知が、DMARC に不合格で届く場合（F2）。
- 偽の通知の作り手が、複製の開始の語句やF2が除く語句をそのまま写した場合は、それぞれ F1・F2 を免れる（F1 を免れても、DMARC に不合格なら F2 に当たる）。
- 偽の通知が、リンクを「SMTP 応答を引用している行」に見える行に置いた場合は F1 を免れる（HTML の中に文字で書いた URL、`<a>` を使わない手法も同じ）。
- 表示名だけ、または件名だけで配信不能通知を装い、`mailer-daemon` 系のアドレスも本物らしい文言も使わない偽の通知は、F1・F2 の対象にならない（誤判定を避けるための選択）。
- 偽の通知が、差出人の組織ドメイン（または Return-Path の組織ドメイン）へのリンクだけを持つ場合は F1 を免れる（Return-Path は送信側が決めるので、除外の根拠として強いものではない）。
- 偽の通知が、`message/rfc822` の添付を付ける、または `multipart/report` を宣言して本物の構造を装う場合は、F1・F2 のどちらも免れる。このとき `mailer-daemon@...` を名乗れば規則 2 でバウンスと判定され、グループに入る（診断文に `Name service error` の行を入れれば検証の対象にもなる。検証は 4.4 の条件の範囲に限られる）。
- 差出人が `mailer-daemon` 系でない偽の通知が、返信・転送の接頭辞を件名に付けた場合は F1・F2 を免れる。

### 2.6 送信元以外から送信されたメールのバウンス（`backscatter`、`classify.go`）

監視アドレスを差出人に詐称したメール（スパムなど）が宛先で拒否されると、そのバウンスが詐称された監視アドレスに届く。通知は本物の MTA が出すが、元のメールは送信元から送ったものではないので、送信側のメール管理者が対応することはない。元メールの `Received` に送信元が 1 つも出てこないバウンスを迷惑にする。

前提（監視アドレスごとに判定する）: そのメールを受信した監視アドレスについて、管理者が書いたホスト名が 1 つ以上ある。その監視アドレスのホスト名は、全体設定 `sending_source_hosts`（どの監視アドレスにも効く）と、そのアドレスの SMTP サーバー（メールアドレスの設定「SMTP サーバー」）。他の監視アドレスの SMTP サーバーは、このアドレスの規則を有効にしない（一致の対象と、アドレスの取得の対象には含める。2.7）。IP だけがあってその監視アドレスのホスト名が無いときは判定しない。送信側のメールサーバーは、そのメールの `Received` に（`by mx1.example.jp` のように）名前でしか現れず、IP が現れるのは通信相手の側だからで、SMTP サーバーの名前が無いと、送信側のメールサーバーが出した通知まで送信元以外のものになってしまう。自動で取得したもの（名前から引いた IP、SPF の範囲と名前）はホスト名の有無に数えない。その監視アドレスの送信元がすべて空のときも判定しない（名前解決の失敗の通知元の判定（4.4）では空を「送信側のメールサーバー」とみなすのとは逆に、ここでは「判定しない」）。ホスト名が無いためにこの規則が働かない監視アドレスは、一般設定の画面に一覧で示す（設定 API の `sending_source_mailboxes_without_host`。[システム仕様](システム仕様.md) 9.2、[画面仕様](画面仕様.md) 9.2）。DNS 検証が無効のときは、SPF を使わずに判定する（ホスト名のアドレスは OS のリゾルバーだけで引く。2.7）。

条件（すべて満たす）:

- 配信不能通知である: `message/delivery-status` パートを持つか、`multipart/report`（`report-type=delivery-status`）である。または、`delivery-status` 以外の種類の `multipart/report` でなく（`report-type` が無い `multipart/report` は他の種類とはみなさない）、2.5 の「配信不能通知らしい」に当たる。DMARC 集計レポートと、`delivery-status` 以外の種類の `multipart/report`（既読通知、不正利用の報告など。`report-type` が書かれていないものは他の種類とはみなさない）は対象外。
- 件名が返信・転送の接頭辞で始まらず、不在通知の件名でもない（2.5 の F1・F2 と同じ除外。人が配信不能通知を添付して転送したものや、不在通知の自動返信を巻き込まないため）。From または Return-Path が `mailer-daemon` 系のアドレスのときは、この除外を使わない。
- 通知を出した MTA（`message/delivery-status` パートの `Reporting-MTA`）が送信元でない。ホスト名が送信元のホスト名（2.7。他の監視アドレスの SMTP サーバーを含む）のどれかに文字列で一致する、または IP リテラルが送信元の IP の範囲（2.7）に含まれるなら、送信側のメールサーバーが扱ったメールの通知なので、対象外（送信側のメール管理者が対応すべき問題）。通知元の名前自体を引くことはしない。
- 元メールの添付（`ParsedMessage.OriginalMessage`）があり、その `Received` ヘッダーが 1 つ以上ある。
- どの `Received` も送信元に一致しない。一致の判定は、行に現れる IP（`[203.0.113.5]`、`(IPv6:2001:db8::25)` などの括弧内の IP リテラル、`from`・`by` の直後のホスト名の IP リテラル）が送信元の IP の範囲（2.7。全体設定、名前から引いた IP、SPF の範囲）に含まれる（IPv4 射影アドレスは IPv4 に戻す）か、`from` / `by` のホスト名が送信元のホスト名（2.7。全体設定、全監視アドレスの SMTP サーバー、SPF の `a` / `mx` が指す名前）のどれかに文字列で一致する（小文字、末尾のドットなし）こと。判定そのものはネットワークを使わない。まず設定した値だけで判定し、この規則に当たったときだけ、その実行の取得（2.7。名前から引いた IP と SPF。1 回の実行で 1 度）をして、取得した値を加えて判定し直す（取得した値は一致を増やすだけなので、設定した値だけで当たらないメールには取得が要らない）。`Received` は件数・長さ・IP の数にかかわらずすべて調べる。1 行は 1 度だけ先頭から読み（正規表現を使わない）、IP は重複を除いて 1 つにつき 1 度、送信元の範囲を範囲の長さごとの表で引く（範囲がいくつあっても IPv4 は 33 回、IPv6 は 129 回までの表引き。`addrIndex`）ので、処理時間はヘッダーの長さに比例し、巨大なヘッダーでも範囲の数との積にはならない。
- 送信元の取得が不完全でない（2.7）。その実行で、管理者が書いたホスト名（全体設定のホスト名と、他の監視アドレスのものを含む全監視アドレスの SMTP サーバー）のどれかのアドレスの取得に応答が無く（A / AAAA の片方だけの答えを含む）保存結果も無いとき、DNS 検証が有効でどれかのドメインの SPF を完全に読めず（範囲が広すぎる場合を含む）保存結果も無いときは、その実行ではこの規則を働かせない（一時的な取得の失敗で、本物の通知を迷惑にしないため）。その通知は、送信元の設定を空とした判定（B0 を除いた規則）で決める。ホスト名は、DNS 検証の有効・無効にかかわらず、すべてを 1 件ずつ順に引く（2.7）。
- 元メールに、`d=` が監視ドメインの組織ドメインである `DKIM-Signature` ヘッダーが無い。外部の配信サービスが監視ドメインで署名して送った本物のメールの返送を、迷惑にしないため。署名の検証はしない。

評価の位置は 2.2 の表の B0（すべての規則より前）。結果は `junk`（`is_bounce` = 0）、規則名 `backscatter`。2.4 の迷惑と同じ扱い（グループに入れない、別に数える、IMAP サーバーからはサーバーでの保持日数を過ぎたら削除する。5 章）。判定が送信元の設定に依存するので、設定を変えたら全件再判定（`reclassify`）で既存のメールに適用する（4.4 の「通知のグループが変わるとき」）。

限界と起こりうる誤判定:

- 登録していない送信経路（外部の配信サービス、別のサーバー、個別の配信アプリ）から送ったメールの配信エラーは、監視ドメインの DKIM 署名が無ければ、送信元以外から送信されたメールのバウンスとして迷惑になり、アラートに載らない。設定画面に、その旨の注意を出す（[画面仕様](画面仕様.md) 9.2）。
- 元メールの `Received` を返さない MTA の通知は判定しない（そのまま本物として扱う）。
- 偽の元メールが、監視ドメインの `DKIM-Signature` ヘッダーを書き写した場合は免れる（署名を検証しないため）。
- 送信側のメールサーバーを経由した詐称メール（踏み台にされた場合）は、`Received` に送信元のホストが出るので判定されず、通常のバウンスとして残る（送信側のメール管理者が対応すべき問題のため）。
- 名前から引いた IP は、そのサーバーが待ち受けている IP で、相手のサーバーから見える送信元の IP と同じとは限らない（NAT、中継）。違うときは、全体設定の IP にも登録する。
- 送信元のホスト名を引けない環境（OS のリゾルバーも、DNS 検証が有効なときの設定のリゾルバーも答えない）では、ホスト名のアドレスの取得が完全にならず、保存結果が無ければこの規則は働かない（進捗の `sending sources:` の行が手掛かり。2.7）。DNS 検証が有効なときは SPF も同じ。
- SPF の `include:` が指す、他の利用者と共有する範囲（大手のメールサービスなど）も、送信元とみなす（pass の修飾子で参照されたものだけ。2.7）。その経由で詐称されたメールのバウンスは、迷惑にならず、通常のバウンスとして残る。ただし /8（IPv4）や /16（IPv6）より広い範囲を取り込む SPF は不完全として扱い、この規則を働かせない（`0.0.0.0/0` などで、すべての IP を送信元にしてしまうため）。範囲の数と合計には上限を設けない（RFC 7208 の問い合わせの上限の中で書かれた範囲は、そのドメインが送信元と宣言したもの）。
- 一致の対象は `from` / `by` のホスト名、その直後の括弧内の逆引き名、`helo=` / `HELO` の名前。IP は、行の中の括弧・角括弧の中、コメント内の IP リテラル、`from` / `by` の直後の語を見る。
- バウンスが元メールを添付でなく本文の中に複製する形（Exim、qmail）の場合は判定しない。

### 2.7 送信元（`sendingsources.go`、`sourcelookups.go`、`app/modules/dnscheck`）

送信元以外から送信されたメールのバウンスの判定（2.6）と、名前解決の失敗の通知元の判定と直接の問い合わせの可否（4.4）が使う。次の合計。一致の対象はどの監視アドレスでもこの合計全体だが、「設定されている」かどうか（2.6 の前提、4.4 の「未設定」）は監視アドレスごとに数える（下の「設定されている」の数え方）。

| 出どころ | 内容 |
| --- | --- |
| 全体設定 | `sending_source_ipv4` / `sending_source_ipv6`（IP と CIDR）、`sending_source_hosts`（ホスト名）。SMTP サーバーを通さず直接送るアプリ、別の中継、外部の配信サービスなど、監視アドレスに紐づかない送信元用。どの監視アドレスにも効く |
| 監視アドレスごと | SMTP サーバーのホスト名（`mailboxes.detail_info.smtp_host`）。登録した全アドレスのもの（有効・無効を問わない）を一致の対象にするが、「設定」として数えるのはそのアドレスのものだけ（他の監視アドレスのものは、一致とアドレスの取得にだけ使う。`SendingSources.WithOtherHosts`） |
| 自動（名前から） | 上の 2 種類のホスト名（他の監視アドレスの SMTP サーバーを含む）の A / AAAA。管理者が書いた名前なので信用して引く。どのモードでも、まず OS のリゾルバーに問い合わせる（2 ラベル以上の名前は末尾にドットを付けた絶対名で検索ドメインを付けずに、ドットの無い 1 ラベルの名前は OS の検索リストと hosts ファイルが効くよう書かれたまま。A と AAAA を別々に、それぞれ 10 秒（問い合わせ 1 回 5 秒・再送 1 回。OS のリゾルバーの既定）まで）。OS のリゾルバーがアドレスを 1 つも返さず、名前が 2 ラベル以上で、DNS 検証が有効で `dns_check_system_resolver_only` が無効のときだけ、設定のリゾルバー（`dns_check_resolvers`。対照クエリに通ったものを順に、A と AAAA の両方に答えた最初のもの）にも問い合わせる（内部の DNS だけで引ける名前と、公開リゾルバーが知らない 1 ラベルの名前があるため）。DNS 検証が無効なら OS のリゾルバーだけ（公開リゾルバーには問い合わせない） |
| 自動（SPF） | DNS 検証が有効なときだけ。全監視アドレスのドメイン（2 ラベル以上のもの。重複を除き、すべて）の SPF レコード（TXT）の `ip4:` / `ip6:` / `a` / `mx`（`:ドメイン` と CIDR 長を含む）/ `include:` / `redirect=`。pass の修飾子（付けない、または `+`）の項目だけを取り込み、`-` / `~` / `?` の項目は（`include:` は参照先の全体ごと）読み飛ばす。`a` / `mx` が指すホスト名はホスト名として、アドレスは IP の範囲として加える |

- SPF の読み方: 先頭が `v=spf1` のレコード 1 つだけを使う（複数の文字列は空白なしでつなぐ）。`all`、`exists`、`ptr`、`exp=`、マクロ（`%` を含むドメイン指定）は無視する（失敗にしない）。ただし `all` は、修飾子にかかわらず、同じレコードの `redirect=` を無効にする。未知の項目は、修飾子にかかわらず書式の誤りとして不完全にする。`ip6:::ffff:a.b.c.d/n` は、n が 96 以上なら IPv4 の /(n-96) として取り込み、それ未満なら無視する。上限は RFC 7208 4.6.4 のとおり: DNS の問い合わせを伴う項目（`include`、`a`、`mx`、`ptr`、`exists`、`redirect`。入れ子の中を含み、修飾子を問わない）が 10 個まで、そのうち答えが NXDOMAIN かデータなしだったもの（空の問い合わせ。アドレスの無い `a`、MX の無い `mx`、SPF レコードの無い `include` / `redirect` の先）が 2 個まで、1 つの `mx` の向き先が 10 件まで（超えると受信側でもその SPF は permerror になる）。入れ子の深さは 10 まで（再帰の歯止め。10 個の上限の中ではこれに届かない）。同じドメインを連鎖の中で 2 度たどることはしない（ループの歯止め）。範囲の数には上限を設けない。問い合わせは、設定のリゾルバー（`dns_check_system_resolver_only` が有効なら OS のリゾルバー）のうち対照クエリに通り、答えた最初のものの答えで決める（監視アドレスのドメインなので、投票はしない。通知が選んだ名前は SPF としては読まない）。
- 「完全」と「不完全」: 存在しない（NXDOMAIN）、TXT が無い、`v=spf1` のレコードが無い、は「完全で、加えるものが無い」。未知の項目、SPF レコードが 2 つ、書式の誤り、SERVFAIL・タイムアウト、上の上限を超えた、実行の取り消し、/8（IPv4）や /16（IPv6）より広い範囲を実際に取り込む項目（`0.0.0.0/0` など。すべての IP を送信元にして判定を無効にしてしまうため。範囲が見つからない `a/0` は完全）、は「不完全」。管理者が書いたホスト名（他の監視アドレスの SMTP サーバーを含む）のアドレスの取得も、応答が無かった（SERVFAIL、タイムアウト、リゾルバーに届かない、A / AAAA の片方だけ答えた、実行の取り消し）ときは「不完全」。名前が存在しない・データが無いという答えは「完全で、加えるものが無い」（名前は文字列としては一致の対象のまま）。全ドメインの範囲を合わせた数や合計にも上限は無い。
- 「設定されている」の数え方（監視アドレスごと）: 全体設定の 3 つの欄と、その監視アドレスの SMTP サーバーが、すべて空なら、その監視アドレスでは「未設定」。他の監視アドレスの SMTP サーバーと、自動で取得したもの（名前から引いた IP、SPF の範囲と名前）は、「設定」にも、2.6 の「管理者が書いたホスト名」にも数えない（一致の対象にはなる）。保存値がホスト名として正しくない SMTP サーバー（データベースを手で書き換えたもの）は無いものとして扱う。
- キャッシュ（マスター DB の `sending_source_lookups`。[テーブル定義](テーブル定義.md)）: 取得は種類（`smtp_host` / `spf` / `global_host`）と名前（ホスト名または SPF のドメイン）ごとに 1 行で、監視アドレスをまたいで共有する。ホスト名の取得結果は、その名前の種類（全体設定のホスト名、監視アドレスの SMTP サーバー。両方なら両方）の行に保存し、読むときはそのうち最も新しい行を使う。同じ表には通知元のアドレスも保存する（`reporter`。4.4）。
  - 保存した結果を問い合わせずに使う期間（鮮度）は 12 時間（`dnscheck.CacheFreshAge`。DNS の保存結果すべてに共通の 1 つの値。4.4 の `dns_checks` も同じ）。多くのレコードの TTL は 3600 秒だが、1 時間で取り直すと問い合わせが何倍にも増えるため、問い合わせの量を抑える実用の値として所有者が決めた（同じ用途の規格は無い）。この間の行は、別の監視アドレス、別の実行でも問い合わせずに使う。取得日時が現在より後の行（時計が戻ったとき）は鮮度の内とは扱わない。
  - 鮮度を過ぎたものは取り直し、完全に取れたら行を置き換える（アドレスの無い答え、たとえば存在しない名前（NXDOMAIN）は、アドレスの無い行になる）。ただし、何も見つからなかった完全な答え（アドレスもホスト名も無い）は、何かを載せた行（古さを問わない。取得日時が現在より後の行を含む）を置き換えず、その行をそのまま使う（取得日時は更新しない。1 度の空の答えや偽装された答えで送信元が減らないようにするため）。
  - 取れなかった（不完全な）ときは、保存済みの行を古さを問わず（取得日時が現在より後の行を含む）完全なものとして使い、行が無ければ不完全とする（SPF にも、ホスト名にも同じ。DNS の障害が続いても、送信側のメールサーバーのアドレスを失わず、2.6 も止めないため）。ホスト名の行は、A と AAAA の両方に答えがあったときだけ「完全」として保存し、片方だけの答えで保存済みの行を置き換えることはしない。
  - SPF の行のうち、/8・/16 より広い範囲を含むもの（その制限を設ける前に保存された行）は、新しくても、空の答えの代わりにも、取れなかったときの代わりにも使わない。
  - どの設定（全監視アドレスの SMTP サーバー、監視アドレスのドメイン、全体設定のホスト名）からも参照されなくなった行は、実行の最初の取得の前に、そのときの設定（監視アドレスの一覧と `sending_source_hosts`）を読み直して削除する（並行して動く別のジョブが追加した設定の行を消さないため。通知元の行は対象外）。送信元の行は古さでは削除しない。取得日時が現在より後の行（古さが分からない）は、日次のクリーンアップが削除する（進捗は [システム仕様](システム仕様.md) 7.1 の `cleanup`）。
  - DNS 検証が無効のときは、SPF は読まず、SPF の保存行も使わない。ホスト名は、鮮度の内の保存行があればそれを使い、無ければ OS のリゾルバーだけで引き、引けなかったときは保存行を古さを問わず代わりに使う（有効のときと同じ規則。答えが得られれば行を保存する）。
- 取得のタイミング: 判定が必要になったときだけ、1 回の実行につき同じ（種類, 名前）を 1 度だけ取得する。必要になった最初のときに、全ホスト名のアドレスと全ドメインの SPF をまとめて取得し、その実行の間は覚えておく（実行が取り消されたときは覚えない）。送信元以外から送信されたメールのバウンスの候補は、まず取得前の値で判定し、2.6 の規則に当たるときだけ、取得した値で判定し直す。名前解決の失敗の検証では、通知元が送信側のメールサーバーかを判定するのに IP の照合が要るときと、直接の問い合わせの可否を決める通知の接続元の IP が設定した IP の範囲に無いとき（4.4）に取得する。どちらにも必要なメールが無い実行では何も引かない。ホスト名は 1 件ずつ順に引く（並行させない。[システム仕様](システム仕様.md) 2.2。引かない名前は無い）。1 回の実行で引く数と時間の合計に上限は無く、各問い合わせのタイムアウト（5 秒、応答が無ければ 1 回再送）だけで区切る。
- 進捗: 取得した実行では `sending sources: <a> address(es) of <h> host name(s), <p> SPF prefix(es) and <s> SPF host name(s) of <d> domain(s)` の 1 行を出す（`<h>` は他の監視アドレスの SMTP サーバーを含むホスト名の数）。アドレスの取得に応答が無かったホスト名や、SPF を完全に読めなかったドメインがあれば、`no answer for the addresses of <名前>, ...` と `SPF not read completely for <ドメイン>, ...` を添える（複数あればセミコロンで区切る）。その実行の監視アドレスに 2.6 の規則が働く（ホスト名がある）ときは `; backscatter detection was skipped for this run: ` に続けて、働かないときは `; ` に続けて添える（働かない監視アドレスでは、取得の不足は通知元の判定を未検証にするだけのため）。

## 3. バウンスの抽出（`extract.go`）

判定した `failed` / `delayed` のバウンスからは、配信できなかった宛先ごとに `bounces` 表の 1 行（`message_id` = `messages.id`、`recipient_index` = 0, 1, ...）を抽出する（`ExtractBounces` → `models.ReplaceBounces`）: 配信できなかった宛先（`recipient`、`recipient_domain`）、`action`、状態コード（`status_code`）、SMTP 応答コード（`smtp_code`）、診断文（`diagnostic`）とそのテンプレート（`diagnostic_template`）、診断文を取った場所（`diagnostic_source`: delivery-status パートなら `dsn`、本文ならそのセクション `text:<n>` / `html:<n>`（セクションファイルと同じ番号）、診断文が無ければ空）、パターンキー（`pattern_key`、4.3）、相手 MTA（`remote_mta` / `remote_ip`）、通知元 MTA（`reporting_mta`）、元メールのヘッダー（`original_message_id` / `original_subject` / `original_from` / `original_date`）、所属グループ（`group_key`、4.3）。`auto_reply`、`other`（失敗の証拠が無いデーモンメール。成功 DSN を含む）、`report`（DMARC 集計レポート。不合格の記録は `dmarc_records` に持つ）、`junk` と一般のメールには `bounces` 行を作らない（`is_bounce` と `bounce_kind` は記録するのでメール一覧・件数には現れる）。`smtp_code` は通知に 3 桁の応答コードが実際にある場合だけ入れる（無ければ空。プレースホルダーは合成しない）。delivery-status パートを優先し、無ければ本文（2.1 の優先本文、空のままの項目は副本文）から Postfix / Exim / qmail / Sendmail / Exchange / Gmail / 日本語 MTA 形式を正規表現で拾う（例: `<addr>: host <mta>[<ip>] said: <smtp> <status> <text>`、`550 5.1.1 <addr>...`、`The following address(es) failed:` の次行、`Final-Recipient:` 行）。監視アドレスと通知の差出人は宛先として採らない。

宛先ごとの行（`ExtractBounces`）: 1 通の配信状態通知が複数の宛先を報告するとき、delivery-status パートの宛先ブロックのうち失敗か遅延を報告するもの（`Action` が `failed` / `delayed`。`Action` が無いか読めなければ `Status` の 5.x.x / 4.x.x。2.2 の規則 1 で種別を決めるのと同じ数え方。`blockKind`）をすべて行にする。1 行目は、通知の種別を報告する最初のブロック（無ければ成功を報告しない最初のブロック）を本文で補ったもの（1 宛先の通知と同じ）。2 行目以降は、そのブロックの値だけで作る（本文は宛先ごとに分けられないため）。成功（`delivered` / `relayed` / `expanded`、2.x.x）や何も報告しないブロック、監視アドレスと通知の差出人の宛先は行にしない。各行はその宛先の `Action` の種別でカテゴリを判定し（1 通に失敗と遅延が混ざることがある）、4.4 の検証も行ごとに行って、それぞれのグループに入る（4.3 の件数）。delivery-status パートが無い通知と、失敗・遅延のブロックが 1 つの通知は 1 行。0.3.0 の索引の行は 1 行目（`recipient_index` = 0）として残り、2 行目以降は全件再判定で作られる（索引の移行 0005。[テーブル定義](テーブル定義.md)）。

診断文を取った場所の決め方（`locateDiagnostic`）: 抽出は種類ごとに全セクションを連結した本文から行うので、診断文を最初に埋めたのが本文だった場合は、その種類（優先本文なら `text`、副本文なら `html`）のセクションを 1 つずつ（HTML はテキスト化して）調べ、一致した診断文を含むセクションを記録する。そのままの文字列で見つからなければ空白を畳んで比較し、それでも見つからなければその種類の 1 番目のセクションとする。text と HTML で内容が違う通知では、判定の根拠が入っている方のセクションがここに残り、エージェントにはそのセクションだけを見せる（[システム仕様](システム仕様.md) 6.2）。

`responsible`（対応者区分）は状態コードからではなく、4 章のカテゴリから決め、グループにだけ持つ（`bounces` 行には持たない）。

## 4. カテゴリとグループ

### 4.1 バウンスのカテゴリ（`category.go`）

グループ化は「送信側のメール管理者が何に対して動くか」の単位で束ねる。バウンス 1 件ごとに状態コードと診断文からカテゴリを判定し、カテゴリが対応単位（`unit_value`）と判定元（`authority`）を決める。宛先アドレスや相手 IP が違っても対応単位が同じなら同じグループになり、ブラックリストの登録先が違えば別グループになる。

- ルールは `category.go` の `[]categoryRule` テーブルで、上から評価して最初に一致したものを採用する。実装上の評価順: (1) 宛先側を明確に示す状態コード（5.1.1 / 5.1.0 / 5.1.3 / 5.1.6 / 5.1.10 → `user_unknown`、4.2.2 / 5.2.2 → `mailbox_full`、5.2.1 → `mailbox_disabled`）、(1') 名前解決の失敗（4.4。恒久的な名前解決の失敗の通知は 5.4.4（Postfix）や 5.1.2（Sendmail）を伴うので、次の 5.1.2 / 5.4.4 / 5.4.6 → `domain_not_found` の状態コードの規則より前に置く。そうしないと、実在する名前に NXDOMAIN を返された通知が検証の対象にならない。`ip_blocked` / `rate_limited` より前に置くのは `Host not found, try again later` のような文面が `rate_limited` の `try again later` に先に当たるのを避けるため、種別 `delayed` の判定より前に置くのは遅延の警告として届く名前解決の失敗の通知を検証の対象にするため）、(1'') 5.1.2 / 5.4.4 / 5.4.6 → `domain_not_found`（名前解決の失敗を検出していない通知に対する状態コードの規則）、(2) `ip_blocked`、(3) `rate_limited`、(4) `auth_failure`、(5) `sender_blocked`、(6) `message_too_large`、(7) `content_rejected`、(8) `server_config`、(9) 種別 `delayed` → `delivery_delay`（`delayed_kind`。遅延の通知でも、理由が送信側の問題（認証、差出人、サイズ、内容、TLS などの設定）ならそのカテゴリにする。そうでない遅延は、宛先側の文言があっても遅延）、(10) 宛先側の文言（`user_unknown` / `mailbox_full` / `mailbox_disabled` / `domain_not_found` / `delivery_delay`）、(11) `unknown_failure`。`message_too_large` を `content_rejected` より先に置くのは "Message rejected: size exceeds" の誤判定を避けるため。
- カテゴリの定義（対応対象、対応者区分、対応単位、判定元）は `categoryDefs` テーブルに持つ。`responsible` はカテゴリから決めて `groups.responsible` に書く（`bounces` 行には持たない。分析結果があればその対応者区分で上書きされる）: 対応対象のカテゴリ → `sender`（`unknown_failure` と `dns_lookup_failure` は `unknown`）、`user_unknown` / `mailbox_full` / `mailbox_disabled` → `recipient`、`dns_resolver_failure` → `sender`、`domain_not_found` / `delivery_delay` / `dns_failure_external` → `domain`。DMARC のカテゴリも同じテーブルに持つ（4.2）。
- 送信 IP の抽出: 診断文中の `[ip]` / `(ip)` → `ip` / `address` / `host` / `your` / `originating` / `client` などの直後の IP → 任意の IP リテラルの順で探し、相手 MTA の IP とループバックを除く。無ければ `reporting_mta`。
- ブラックリストの提供元の抽出: 既知の提供元テーブル（spamhaus.org、spamcop.net、sorbs.net、barracudacentral.org、uceprotect.net、proofpoint.com、cloudmark.com、invaluement.com、abuseat.org、mailspike.net、spamrats.com、senderscore.org、surbl.org、uribl.com、psbl.org、nixspam.org、blocklist.de、mail-abuse.com、lashback.com、junkemailfilter.com、trendmicro.com、mimecast.com、talosintelligence.com、spameatingmonkey.net）→ 無ければ listing の語があるときに文中の URL / ホスト名の登録可能ドメイン（宛先・送信・MTA のドメインと大手メールサービスのヘルプ URL は除外）→ 無ければ宛先ドメイン。
- 元メールの差出人が取れない場合、差出人アドレスは診断文中の宛先以外のアドレス → 送信ドメイン → `reporting_mta` の順で補う。
- どのカテゴリでも、上記の補完順が尽きて `unit_value` が空になるときは最終フォールバックとして宛先ドメイン → 相手側 MTA のホスト名（`remote_mta`）→ 固定値 `unknown` の順で埋める（ラベルや通知で対応単位が空欄にならない）。
- 診断テンプレート（アドレス → `<addr>`、IP → `<ip>`、ホスト → `<host>`、ID → `<id>`、日付 → `<date>`、数値 → `<n>`、SMTP コードと状態コードは保持。長さの上限は無い）は `bounces.diagnostic_template` に保存し、`unknown_failure` の authority と表示に使う。診断文が空のとき（宛先や応答文が取れない通知）は件名から診断テンプレートを作る。
- 一致したカテゴリ規則の名前（`Category.Reason`）は `bounces.category_rule` に保存する（そのバウンスが対応対象 / 対象外になった理由）。

### 4.2 DMARC の不合格記録のカテゴリ（`dmarc.go`）

DMARC 集計レポートの不合格の記録は、1 件ずつカテゴリを決めてグループに入れる（`CategorizeDMARCRecord`）。送信 IP が記録のドメインの持ち主のサーバーか、転送した受信側か、なりすましかはレポートからは機械的に判断できない。このため 3 カテゴリとも対応対象とし、カテゴリは「記録が何を示しているか」を表す（どれに当たるかの見立てはエージェントの分析が行う）。

記録のドメインは `header_from`（無ければ公開ポリシーのドメイン）。「揃っている」は relaxed アラインメント（組織ドメインが同じ）で判定する。

| カテゴリ | 対応者区分 | 条件（上から評価） | category_rule |
| --- | --- | --- | --- |
| `dmarc_not_authenticated` | `unknown` | 揃った DKIM または SPF が単独では `pass` なのに DMARC に不合格（strict アラインメント） | `dmarc_strict_alignment` |
| `dmarc_spf_missing` | `sender` | 揃った SPF ドメイン（記録のドメインと組織ドメインが同じもの。送信サーバーの HELO 名など）の SPF 結果が `none` / `neutral` / `temperror` / `permerror`（使える SPF レコードが無い） | `dmarc_spf_missing` |
| `dmarc_dkim_failed` | `unknown` | 揃った DKIM 署名があるが検証に失敗（受信側の転送やセキュリティゲートウェイによる書き換え、または送信側の DKIM 設定の誤り） | `dmarc_dkim_failed` |
| `dmarc_not_authenticated` | `unknown` | 揃った SPF ドメインが送信 IP を許可していない（`fail` / `softfail`）うえ、揃った DKIM 署名も無い（SPF に登録していない正規のサービス、またはなりすまし） | `dmarc_not_authorized` |
| `dmarc_not_authenticated` | `unknown` | DKIM も SPF も揃ったドメインを検証していない | `dmarc_unaligned` |

- 対応単位（`unit_value`）は記録のドメイン（空なら `unknown`）、判定元（`authority`）は空。グループは「カテゴリ × ドメイン」になり、送信 IP ごとには分けない（IP は記録とグループの一覧に残る）。
- 記録の形（`diagnostic_template`、`DMARCTemplate`）: `dmarc fail: dkim <DKIM>; spf <SPF>; disposition <処置>`。`<DKIM>` / `<SPF>` には、揃ったドメインの結果を `aligned <結果>` で、揃っていないドメインの検証があれば `unaligned` を、何も無ければ `none` を書く。送信 IP・件数・日付・報告元・揃っていないドメインの名前は含めない。なりすましの送信 IP が日々変わっても同じパターンのままにし、そのたびに再分析しないため。
- パターンキーは `PatternKey("", diagnostic_template, "", "dmarc")`（4.3）。
- グループの件数: 所属メール数はレポートのメールの数（同じグループの記録が複数あっても 1 通と数える）。相手側 IP の種類数には送信 IP を含め、宛先アドレスの種類数には数えない。
- エージェントの分析では、見本はメール本文ではなく、レポートの情報と記録の全項目になる（[バウンス分析 プロンプト仕様](プロンプト仕様/バウンス分析%20プロンプト仕様.md)）。

### 4.3 パターン・グループキー・表示

- パターン: グループの中で「状態コード・診断テンプレート・相手 MTA・診断文を取った場所の種類（`dsn` / `text` / `html` / 空）」が同じバウンスを 1 パターンとし（DMARC の記録は種類 `dmarc` で、記録の形だけで分ける。4.2）、`bounces.pattern_key` = `sha1(status_code|パターン用テンプレート|remote_mta|種類)` の先頭 16 桁（`mailengine.PatternKey`）。パターン用テンプレートは診断テンプレートのうち `<id>` の直後の区切り（`.` / `-`）に続く数字も `<n>` にしたもの（Gmail の `<id>-<id>.218` のようなキュー ID の末尾が SMTP コードと誤認されて残り、通知ごとに別パターンになるのを防ぐ。診断テンプレート自体とグループキーは変えない）。エージェントはパターンごとに 1 通だけ見本を読み（[システム仕様](システム仕様.md) 6.2）、分析の要否もパターンで決める（[システム仕様](システム仕様.md) 5.4 の増分）。再確認の判定は、パターンから作る再確認キーで比べる（4.5）。
- グループキー: `sha1(category + "|" + unit_value + "|" + authority)` の先頭 16 桁（hex）。`unit_value` と `authority` は小文字化・前後空白除去して比較する。所属はバウンスなら宛先ごとの `bounces.group_key`、DMARC の記録なら `dmarc_records.group_key` に記録する（`messages` には無い。読み出し時に最初の宛先の `bounces` 行（`recipient_index` = 0）を LEFT JOIN して `Message.GroupKey` に埋めるので、`Message.GroupKey` は最初の宛先のグループを表す）。グループの所属メールの一覧は、`bounces`（どの宛先の行でも）と `dmarc_records` をそれぞれ `group_key` で絞って求める（宛先ごとに別のグループに入った通知は、それぞれのグループに現れる）。
- グループの件数（`RefreshGroupCounters`）: 所属メール数は通知の数（同じ通知の宛先がいくつ同じグループに入っても 1 通）、宛先アドレスの種類数は所属するすべての宛先の行（3 章）、相手側 IP の種類数はその行と DMARC の記録の送信 IP から数える。グループの宛先・相手側 IP・相手側 MTA の一覧（`GroupStats`）も同じ行から作る。日次・保持期間によるメールの削除（`PruneMailbox`）は、削除したメールのすべての宛先のグループを数え直す。
- 表示名は保存しない。CLI とログでは `models.BounceGroup.Label()`（`<category>: <unit_value> @ <authority>`）、Web・PDF レポート・通知メール（[システム仕様](システム仕様.md) 7.4）ではカテゴリの表示名（言語ファイルの `value.category.<カテゴリ>.label`）と対応単位・判定元から見出しを組み立てる。

### 4.4 名前解決の失敗の検出と検証（`dnsfailure.go`、`app/modules/dnscheck`）

`Name service error for name=infoseek.jp type=MX: Host not found, try again` のような通知は、宛先ドメインが実在しないのか、通知を出したサーバー（多くは送信側のメールサーバー）のリゾルバーが不調なのかを、通知の文面だけでは区別できない。名前を実際に引いて確かめ、確かめた結果でカテゴリを決める。

**検出**（`ParseDNSFailure(診断文, 相手側の MTA)`。ネットワークを使わない）: 次の形式から名前（`Name`）、通知が書いた種別（`QType`。情報として証拠に残すだけで、検証は種別によらない）、一時的か（`Temporary`）を取り出す。名前を書かない形式は宛先ドメインの失敗とみなす（`Name` は空。検証では宛先ドメインを引く）。種別を書く形式は、配送で引く種別（MX / A / AAAA）のときだけ検出する（SPF の確認で引く TXT などの失敗は配送の失敗ではない）。

| MTA | 形式（名前の無いものは「名前なし」） | 一時 / 恒久 |
| --- | --- | --- |
| Postfix | `Name service error for name=<名前> type=<種別>: <理由>`。理由が `Host not found, try again` / `Server failure` / `Temporary failure` / `timed out` / `Malformed or unexpected name server reply` | 一時 |
| Postfix | 同上で理由が `Host not found` / `Host found but no data record of requested type` / `Non-recoverable error`。`Domain <名前> does not accept mail (nullMX)` | 恒久 |
| Sendmail | `Name server: <名前>: host not found` / `non-recoverable error` / `no data known`（`Host unknown (...)` の中）。`Host does not accept mail: MX 0 .`（名前なし） | 恒久 |
| Sendmail | `Name server: <名前>: host name lookup failure`（`Deferred:` の後） | 一時 |
| Exim | `all relevant MX records point to non-existent hosts`、`an MX or SRV record indicated no SMTP service`（いずれも名前なし） | 恒久 |
| Exim | `host lookup did not complete`、`missing MX, or all MXs point to missing A records`（名前なし） | 一時 |
| qmail | `Sorry, I couldn't find any host named <名前>. (#5.1.2)` | 恒久 |
| qmail | `Sorry, I couldn't find any host by that name. (#4.1.2)`、`CNAME lookup failed temporarily. (#4.4.3)`（名前なし） | 一時 |
| Exchange / Microsoft 365 | `DNS domain <名前> does not exist`（5.4.310）、`SMTPSEND.DNS.NonExistentDomain`（名前なし） | 恒久 |
| Exchange / Microsoft 365 | `DNS query failed`（4.4.312。名前なし）。通知が相手側の MTA（`Remote-MTA`）を書いているとき、または文面が相手のサーバーの応答の引用（`said:`、`SMTP error from remote`）のときは検出しない（相手のサーバーの中の失敗で、送信側の名前解決の失敗ではないため） | 一時 |
| Gmail | `DNS type '<種別>' lookup of <名前> responded with code <コード>`。コードが NXDOMAIN / NOERROR なら恒久、それ以外（SERVFAIL など）は一時。`DNS Error: Domain name not found`、`DNS Error: DNS server returned answer with no data`（名前なし）は恒久、`DNS Error: Could not contact DNS servers`（名前なし）は一時 | 左に記載 |

文面の出典: Postfix のソース（`src/dns/dns_lookup.c`、`dns_strerror.c` と SMTP クライアント）、Sendmail のソース（`sendmail/err.c`）、Exim のソース（`src/routers/dnslookup.c`）とマニュアル、qmail のソース（`qmail-remote.c`）、Microsoft の配信不能レポートの資料（5.4.310、4.4.312）、Gmail の配信不能通知の文面。Exchange の 4.4.316 は接続の拒否（DNS ではない）なので含めない。Exim の `Unrouteable address` はルーターが宛先を扱えないときの一般の文面で、名前解決の失敗に限らないので含めない。Courier は文面の出典を確認できなかったので含めない。

**検証する条件**: 診断文の名前は、偽の通知なら作り手が書けるため、引く範囲を絞る。検証の部品に渡すのは、迷惑（2.4・2.5・2.6）でない `failed` / `delayed` のバウンスで、診断文に名前解決の失敗を検出したものだけ（宛先ごとの行。3 章）。名前ごとに、次の順に評価し、最初に決まったものを採る（括弧内は進捗の `dns:` の行で数える区分）。通知の古さ、1 回の実行で検証する数、時間の合計には上限を設けない（どの通知も検証する）:

1. 名前（名前の無い形式は宛先ドメイン）が 2 ラベル以上の正しいホスト名でない → 検証しない（`not applicable`）。
2. DNS 検証が無効 → 問い合わせず、保存済みの結果を通知の期間（下の「結果の保存と再利用」）でそのまま使う（`reused`）。無ければ検証しない（`not checked (the DNS check is off)`）。
3. 鮮度（12 時間。下の「結果の保存と再利用」）の内の保存済みの結果がある → それを使う（`reused`）。問い合わせず、MX の向き先の確認より前に使う。直接の問い合わせの対象の通知（下の「直接の問い合わせ」）がここで使うのは `direct` = 1 の行だけ。
4. 名前が宛先ドメインそのもの、宛先ドメインの MX の向き先、または宛先ドメインと組織ドメインが同じ名前であること。どれでもなければ検証しない（`not applicable`。宛先ドメインが無いときも）。MX の向き先は宛先ドメインごとに 1 回の実行で 1 度引いて記憶する（答えが無かったことも）。どのリゾルバーも答えなかったら `inconclusive`。
5. 検証する（下の「検証」）。結果を保存して使う（`verified`）。
6. 4 で検証できない（条件外）か、5 で結果が出ない（保留）とき → 保存済みの最新の結果（古さ・種類を問わない）があればそれを使う（`reused`）。無ければ未検証のまま（`not applicable` / `inconclusive`）。

**検証**: 通知が書いた種別にかかわらず、その名前にメールを届けられるかを、MTA と同じ引き方で確かめる（`Checker.resolveName`）。

- 宛先ドメインの MX の向き先の名前は、ホストとして引く: A と AAAA の両方。
- それ以外の名前（宛先ドメイン、同じ組織ドメインの名前）は、メールのドメインとして引く: MX を引き、すべての向き先について A と AAAA の両方を引く（向き先の数に上限は無い。1 件ずつ順に引き、引かない向き先は無い）。MX が無い（データなし）ときは、その名前そのものの A と AAAA を引く（RFC 5321 5.1 の暗黙の MX）。null MX（`MX 0 .`、RFC 7505）は「メールを受け付けない」（届け先なし）。
- リゾルバーごとの答え: アドレス（A か AAAA）が 1 つでも得られた → 届け先あり。MX（ホストは A と AAAA の両方）が NXDOMAIN → 存在しない。存在するが届け先のアドレスが無い（どの向き先にもアドレスが無い、向き先が存在しない、null MX、MX もその名前のアドレスも無い）→ 届け先なし。必要な問い合わせがエラー応答（SERVFAIL・REFUSED など）でアドレスも得られない → 失敗。応答が無い（再送しても無応答）→ 無応答。

設定のリゾルバー（`dns_check_resolvers`。`dns_check_system_resolver_only` が有効なら OS のリゾルバーだけ）で引く。名前の組織ドメインの権威 DNS（NS を引いて各サーバーへ直接）にも、名前が存在するかを尋ねる（ドメインは MX、ホストは A。データ、データなし、その名前の CNAME は「存在する」、NXDOMAIN は「存在しない」）のは、通知が送信元から届いたものだと監視アドレスの受信サーバーが記録した `Received` から分かるとき（下の「直接の問い合わせ」）で、かつ OS のリゾルバーだけを使う設定でないときに限る（NS の問い合わせもこのときだけ）。設定のリゾルバーへの問い合わせ（対照クエリ、送信元のホスト名と SPF の問い合わせを含む）には、すべて EDNS0 の Client Subnet オプション（オプション番号 8。アドレスファミリー 1、送信元プレフィックス長 0、アドレスなし）を付け、このサーバーのアドレスの一部（サブネット）を権威 DNS へ伝えないようリゾルバーに求める（RFC 7871 7.1.2。既定のリゾルバーのうち Google Public DNS は、付けなければ問い合わせ元の /24 を、通知が選んだ名前の権威 DNS へ伝える）。権威 DNS への直接の問い合わせには付けない（このサーバーから直接届くため）。OS のリゾルバーを使う問い合わせは OS の仕組みで送るので、このオプションを付けない。問い合わせなかったときは、証拠に `authoritative: not asked (only the OS resolver is used)` または `authoritative: not asked (the notice does not show mail sent from the sending sources)` の行を加え、リゾルバーだけで投票する。

各問い合わせは 5 秒待ち、応答が無ければ 1 回だけ送り直す（`DefaultTimeout`・`queryAttempts`。値は所有者が決めたもので、同じ用途の規格は無い。OS のリゾルバーの既定 `timeout:5` `attempts:2` と同じ値）。切り詰められた（TC）UDP の応答は TCP で問い合わせ直す（同じく 5 秒）。1 つの名前の検証や 1 回の実行の全体には時間の制限を設けない。どのリゾルバーからも答えが無い（すべて無応答）名前は保留とし（保存しない）、保存済みの結果があればそれを代わりに使い（上の 6）、無ければ次のグループ化で改めて検証する（下の「未検証の通知の再判定」。同じ実行の次の通知でも引き直す）。実行が取り消されたときも保留（取り消された問い合わせは名前についても、サーバーについても何も語らない）。リゾルバーごとに既知の安定した名前（`example.com` の A）を引く対照クエリを、その実行で初めて使うときに 1 度だけ付け、応答のないリゾルバーは投票から除き、同じ実行の間は二度と問い合わせない。本文中のリンクのホストは引かない。権威 DNS は、NS レコードのすべてのサーバーを名前順に、それぞれ使えるすべてのアドレス（IPv4 を先に。応答があればそのサーバーの残りのアドレスは引かない）で、NS を答えたリゾルバーで引いて使う。権威 DNS への問い合わせは、権威の応答（AA ビット付き。問い合わせた名前そのものの CNAME はデータとして数える）だけを数える（AA の無い応答、委任の応答、無応答は「届かなかった」扱い。SERVFAIL・REFUSED は失敗。どちらも投票しない）。権威 DNS のアドレスは、グローバルなユニキャストで特殊用途の範囲に入らないものだけを引く。除外するのは（IPv4 射影アドレスは IPv4 に戻して判定）ループバック、プライベート、リンクローカル、マルチキャスト、未指定のアドレスに加えて、0.0.0.0/8、100.64.0.0/10、192.0.0.0/24、192.0.2.0/24、198.18.0.0/15、198.51.100.0/24、203.0.113.0/24、240.0.0.0/4、255.255.255.255/32、fc00::/7、fe80::/10、64:ff9b::/96、64:ff9b:1::/48、2002::/16、2001::/32、2001:db8::/32、100::/64、fec0::/10、::/96、3fff::/20、5f00::/16。応答の無かった権威 DNS のアドレスは 5 分（`failureTTL`。RFC 2308 7.2 が応答の無いサーバーを覚えてよい上限。リゾルバーとして権威 DNS に問い合わせる同じ役割）の間は引かない（証拠は `authoritative <ホスト> (<アドレス>): no response in the last 5 minutes`。応答があればすぐに戻す）。権威 DNS の確認を実行の途中で止めることはしない。リゾルバーの間も、権威 DNS の間も、問い合わせは 1 件ずつ順に行う（並行させない。[システム仕様](システム仕様.md) 2.2）。

結果（`DNSOutcome`、`vote`）は次の順に評価して最初に当たるもの。失敗（エラー応答）や無応答のリゾルバーは、他に答えたリゾルバーがあれば投票から除く（1 つのリゾルバーの不調は名前について何も語らない）:

| 結果 | 条件 |
| --- | --- |
| 保留 | 届くリゾルバーが無い（対照クエリがすべて失敗する閉域網など）、どのリゾルバーからも答えが無い（すべて無応答）、または実行の取り消しでリゾルバーの答えが揃わない。結果は保存しない。保存済みの結果があればそれを使い（取り消しを除く）、無ければ次のグループ化で検証し直す |
| `broken` | 答えたリゾルバーがすべて失敗（エラー応答）を返した（DNS がその名前に正常に答えない） |
| `not_found` | 答えたリゾルバーがすべて「存在しない」で、存在すると答えた権威 DNS が無い |
| `exists` | 答えたリゾルバーがすべて「届け先あり」で、NXDOMAIN を返した権威 DNS が無い |
| `broken` | それ以外: 名前は存在するが届け先が無い（受信側の設定）、またはリゾルバーや権威 DNS の答えが食い違う |

結果の証拠（`dns_checks.detail`）は、1 行目が `name=<名前> outcome=<結果>`、2 行目が引き方（`checked as a mail domain: MX, then the A and AAAA of every MX target (or of the name itself without MX)` / `checked as a host (an MX target of the recipient domain): A and AAAA`）、続けてリゾルバーごとに 1 行で、行った問い合わせとその答え（例: `resolver 1.1.1.1: control ok; MX ok (mx1.example.jp, mx2.example.jp); mx1.example.jp: A ok (192.0.2.1), AAAA no data; mx2.example.jp: A NXDOMAIN, AAAA NXDOMAIN`、`MX none (the name itself is the mail host); A ok (192.0.2.9), AAAA no data`、`MX ok (.) (null MX: the domain accepts no mail)`、`resolver 9.9.9.9: control failed (timeout); not asked`）、権威 DNS ごとに 1 行（例: `authoritative ns1.example.jp (203.0.113.1): MX NXDOMAIN`。問い合わせなかったときは上の `authoritative: not asked (...)` の行、NS が引けなければ `authoritative: NS lookup of <ドメイン> failed` / `authoritative: no NS records for <ドメイン>`）。1 つの答えから引用するレコードは 5 つまでで、残りは `, +<n> more` と数だけを書く（表示だけの省略。どのレコードも結果に数え、MX の向き先は各向き先の行にすべて現れる）。通知が書いた種別は、分析の根拠に情報として渡す（`dns_checks` は種別をまたいで共有するので持たない）。`SystemOnly` では Go の標準リゾルバーが NXDOMAIN とデータなしを区別できず、どちらも「存在しない」扱いになる（届け先の無いドメインは `broken` でなく `not_found` になる）。この場合の行は `resolver system: control ok; MX ok (...); <向き先>: address ok (...)`、`MX not found (NXDOMAIN or no data); address of the name itself ok (...)` のようになる。OS のリゾルバーへの問い合わせは、検索ドメインを順に付けて試されないよう、すべて絶対名（末尾にドット）で行う（検索ドメインにワイルドカードがあると NXDOMAIN が存在に変わるため）。管理者が登録した単一ラベルのホスト名だけは、OS の検索リストと hosts を使う相対名で引く。

**直接の問い合わせ**（`direct`。`dnsVerification.aboutSentMail`）: 権威 DNS に直接問い合わせてよいのは、通知が送信元から届いたものだと、通知の送り手が偽れない手掛かりから分かるときに限る。偽の通知は名前も宛先ドメインも選べるので、その作り手のドメインのネームサーバーへこのサーバーから問い合わせると、このサーバーの IP アドレスを知らせ、問い合わせ先を通知に選ばせることになるため。手掛かりは、監視アドレスの受信サーバーが通知を受け取ったときに付けた、通知そのものの `Received` ヘッダーだけ（上が新しい。通知の送り手が足せるのはそれより下の行だけ）:

- 通知の `Received` を上から読み、各行の `from` 句に記録された接続元の IP を取る。`from` 句（`by` / `via` / `with` / `id` / `for` の前まで）のコメントの中の IP リテラル（`(mail.example.jp [192.0.2.5])`、`([192.0.2.5]:25 helo=...)`、`(192.0.2.5)`、`(IPv6:2001:db8::5)` など）、コメントに無ければ `from` の直後の IP リテラル（`from [192.0.2.5]`）。IPv4 射影アドレスは IPv4 に戻す。`helo=` の値と、コメント中の `HELO` / `EHLO` に続く語は使わない（接続元が名乗った値のため）。行の長さや件数に上限は無い（最初の外部の接続元の行で読むのを止める。それより下は通知が届く前に書かれた行のため）。
- 接続元の IP の無い行と、接続元が内部の IP（ループバック、プライベート（RFC 1918、IPv6 のユニークローカル）、100.64.0.0/10、リンクローカル）の行は飛ばす（内部の中継。件数を問わない）。
- それ以外の IP が現れた最初の行で決める。その IP が設定した IP の範囲（`sending_source_ipv4` / `sending_source_ipv6`）に含まれるか、その実行の取得（2.7。名前から引いた IP と SPF の範囲。必要になった最初のときに取得する）が完全でそのどれかに含まれれば、直接の問い合わせの対象とする（送信元がその通知を作ったか、監視アドレスの受信サーバーへ中継した。ホスティングの監視アドレスでは、送信側のメールサーバーが接続元として記録される）。
- 次のときは対象にしない: その監視アドレスに送信元が設定されていない（2.7 の「設定されている」。未設定の監視アドレスでは、通知元の判定がどの通知元も送信側のメールサーバーとみなすのとは別に、直接の問い合わせはしない）。そのような行が無い。それより前の行を判定できない（`from` 句のコメントに異なる IP が 2 つある）。IP がどれにも含まれない。IP が設定した範囲に無く、その実行の取得が不完全。
- ホスト名は文字列で比べない。通知の中身（通知元 `reporting_mta`、返送された元メールの `Received`、`DKIM-Signature` の `d=`）は見ない。送信元からメールを受け取ったことのある者なら誰でも書き写せるため。
- 対象の通知でも、DNS 検証が有効で OS のリゾルバーだけを使う設定のときは、権威 DNS に問い合わせず、保存済みの結果もどちらの種類も同じに扱う（下の「結果の保存と再利用」）。

限界:

- 他の利用者と共有する SPF の範囲（2.6 の限界と同じ。`include:` が指す大手のメールサービスなど）から届いた通知も、対象になる。
- 監視アドレスの受信サーバーの前にあるプロキシや NAT が、接続元をプライベートの IP として記録すると、その行は飛ばされ、それより下の行（通知の送り手が書ける行）で決まる。
- 監視アドレスの受信サーバー（MX）自体が送信元でもあり、グローバルな IP で次のサーバーへ中継する構成では、その中継の行で決まるので、どの通知も対象になる。
- 監視アドレスのサーバーの中で作られた通知は、接続元の IP を持たないので対象にならない（リゾルバーだけで検証する）。

**通知元が送信側のメールサーバーか**（`FromSendingSource`。検証結果が `exists` のときだけ判定する。他の結果ではカテゴリを変えないため、名前の解決もしない）。送信元は 2.7:

- その監視アドレスが「未設定」（全体設定の 3 つの欄とそのアドレスの SMTP サーバーがすべて空。他の監視アドレスの SMTP サーバーと自動で取得したものは数えない）なら、どの通知元も送信側のメールサーバーとみなす（名前を引かない）。
- `reporting_mta` が IP リテラル（`1.2.3.4`、`[IPv6:...]` など。IPv4 射影アドレスは IPv4 に戻す）なら、設定した IP の範囲に含まれれば送信側のもの。含まれなければ、その実行の取得（2.7。名前から引いた IP と SPF の範囲）に照らし、含まれれば送信側のもの。どれにも含まれず、その実行の取得が完全なら外部のサーバー。
- `reporting_mta` がホスト名なら、まず送信元のホスト名（全体設定、全監視アドレスの SMTP サーバー。SPF を読む実行では SPF の `a` / `mx` が指す名前も。このとき 2.7 の取得をする）と文字列（小文字、末尾のドットなし）で比べ、一致すれば送信側のもの。一致しなければ、通知の古さにかかわらず、検証の部品でそのホスト名の A と AAAA を引いて（診断文の名前と同じく通知に書かれた信用できない名前なので、2 ラベル以上の名前だけ、各問い合わせ 5 秒・再送 1 回）得た IP（IPv4 射影アドレスは IPv4 に戻す）を、IP リテラルと同じく照らす。引いたアドレスは `sending_source_lookups`（`kind` = `reporter`。判定ではなくアドレスだけ）に保存し、鮮度（12 時間。4.4 の `dns_checks`、2.7 と同じ値）の間は、別の実行でも問い合わせずに使う。鮮度を過ぎたら引き直し、答えがあれば行を置き換える（アドレスの無い答えも答えとして）。どのリゾルバーも答えないときは保存済みのアドレスを古さを問わず使う。DNS 検証が無効なら引かず、保存済みのアドレスがあればそのまま使う。送信側のものかどうかは、保存したアドレスを使うときも、毎回その時点の設定と取得結果で判定する。その実行の間は結果を記憶する（答えの無かったものも）。Postfix・Exim・Sendmail は通知元をホスト名で報告するので、IP だけを登録した場合もこれで一致する。
- 次の場合は、送信側のメールサーバーかどうかを判定できないので、その通知は未検証として扱う（`dns_unverified_*`。進捗では `inconclusive`）。判定できなかったものを「外部のサーバー」にはしない（応答の無さや通知の順序で通知が外部のサーバー扱いになるのを防ぎ、変わった名前で送信側のリゾルバーの不調を隠させないため）。未検証の通知は次のグループ化で改めて調べる（下の「未検証の通知の再判定」）:
  - `reporting_mta` が空、または読めない形。
  - ホスト名のアドレスが得られなかった: 1 ラベルの名前（引かない）、どのリゾルバーも答えず保存済みのアドレスも無い、実行が取り消された、DNS 検証が無効で保存済みのアドレスが無い（保存済みの結果だけを使う部品は名前を引かない。このとき、保存済みの結果が `exists` で照合で決まらない通知は、`not checked` ではなく `inconclusive` に数える）。
  - 引いた答えにアドレスが無い（NXDOMAIN、データなし。引けない名前は、どのサーバーが通知を書いたかを示さない）。
  - アドレス（または IP リテラル）がどれにも一致しないのに、その実行の取得が不完全（2.7。送信元のホスト名のどれかのアドレスの取得に応答が無く保存結果も無い、SPF を完全に読めない）。文字列の一致で決まるときは影響しない。
- OS のリゾルバーだけを使うときは、hosts ファイルの「その種類のアドレスが無い」は存在しない扱いにする。
- 送信側のメールサーバーかどうかはグループ化の時点の設定と取得結果で決まり、保存しない（保存するのは通知元のアドレスだけ）（グループが変わる場合は下の「通知のグループが変わるとき」）。

**カテゴリ規則**（4.1 の評価順 (1') に置く。上から評価して最初に一致したもの。「宛先ドメインの名前」は、名前が宛先ドメインと同じか、名前の無い形式）:

| 規則名 | 条件 | カテゴリ |
| --- | --- | --- |
| `dns_verified_not_found` | 検証結果が `not_found` で、宛先ドメインの名前 | `domain_not_found` |
| `dns_verified_name_not_found` | 検証結果が `not_found` で、宛先ドメイン以外の名前（MX の向き先のホストなど） | `dns_failure_external` |
| `dns_resolver_failure` | `exists` で、通知元が送信側のメールサーバー | `dns_resolver_failure` |
| `dns_failure_external` | `exists` で通知元が外部のサーバー、または `broken` | `dns_failure_external` |
| `dns_unverified_temporary` | 検出したが検証していない（無効・条件外・保留、または `exists` で通知元を判定できない）。種別が `delayed`、または一時 | `dns_lookup_failure` |
| `dns_unverified_not_found` | 検出したが検証していない。種別が `failed` で恒久、宛先ドメインの名前 | `domain_not_found` |
| `dns_unverified_name_not_found` | 検出したが検証していない。種別が `failed` で恒久、宛先ドメイン以外の名前 | `dns_failure_external` |

検証していない一時的な失敗（と遅延の警告）は、送信側と宛先側のどちらの問題か分からないので、対応対象のカテゴリ `dns_lookup_failure`（対応者区分 `unknown`、対応単位は宛先ドメイン）に入れて知らせる（遅延に紛れさせない）。検証していない恒久的な失敗は、宛先ドメインなら `domain_not_found`、宛先ドメイン以外の名前（宛先ドメインの MX が指すホストなど）なら宛先側の DNS の問題として `dns_failure_external` にする。`bounces.category_rule` の規則名（`dns_unverified_*`）で検証していないことが分かる。`try again` の有無（一時 / 恒久）は検証結果とともに証拠としてエージェントに渡す。

**未検証の通知の再判定**: 規則名が `dns_unverified_` で始まる通知は、全件再判定だけでなく、DNS 検証が有効なときは毎回のグループ化（増分を含む）で改めてグループ化する（無効なときは増分のグループ化では改めない。保存済みの結果だけでは結果が変わらないため）（`GroupMailbox`、`models.ListMessagesByBounceRulePrefix`。進捗 `verifying again <n> notice(s) whose DNS lookup failure was not verified`）。検証できたら検証結果のグループへ移り、それまでのグループは件数を数え直し、所属が無くなれば状態・対応履歴・分析結果ごと削除する（`models.DeleteGroupIfEmpty`）。0.3.0 で未検証として `delivery_delay` に入れた通知（規則名 `dns_unverified_delay`）も対象になり、次のグループ化で検証されるか `dns_lookup_failure` に移る。

**結果の保存と再利用**: 検証した結果はマスター DB の `dns_checks` に保存する（`qtype` = `NAME`。[テーブル定義](テーブル定義.md)）。保存した結果を問い合わせずに使う期間（鮮度）は 12 時間（`dnscheck.CacheFreshAge`）で、DNS の保存結果すべてに共通の 1 つの値とする（2.7 の送信元の取得結果と、上の通知元の取得結果も同じ）。多くのレコードの TTL は 3600 秒だが、1 時間で引き直すと問い合わせが何倍にも増えるため、問い合わせの量を抑える実用の値として所有者が決めた（同じ用途の規格は無い）。

- DNS 検証が有効なとき: 名前が同じで（通知が書いた種別は問わない）、検証日時が現在から鮮度の内のものがあれば、通知の古さにかかわらず、そのうち最も早いものを使う（同時に検証した複数のジョブが同じ結果を使うため）。鮮度の内のものが無ければ今検証し、その結果を保存して使う（鮮度を過ぎた行も消さない）。検証の条件に合わないとき（条件外）と、検証しても結果が出ないとき（保留）は、保存済みの最新の結果（古さを問わない）を代わりに使う（「検証する条件」の 6）。
- DNS 検証が無効なとき（問い合わせない部品）: 保存済みの結果をそのまま使う。通知の時刻（IMAP の受信日時。無ければメールの日付。無い・未来なら現在）の 24 時間前（`dnscheck.ReuseWindow`）から現在までの期間（両端を含む。`dnscheck.ReuseRange`）に検証したもののうち最も早いもの（無効にしても、既に検証した通知のグループが変わらないように）。
- 検証が通知より 1 日（`mailengine.DNSLateCheckAfter`）を超えて後のときは、分析の根拠にその日数（`checked N days after the notice`）を書き、その間に DNS が変わりうることを示す（[バウンス分析 プロンプト仕様](プロンプト仕様/バウンス分析%20プロンプト仕様.md)）。0.3.0 までの種別ごとの行（`qtype` = MX / A / AAAA）は使わず、日次のクリーンアップで消える。
- 種類（`dns_checks.direct`）: 直接の問い合わせの対象の通知（上の「直接の問い合わせ」）は、鮮度の内の `direct` = 1 の行（権威 DNS にも問い合わせた検証）を使う。無ければ、権威 DNS にも問い合わせて検証し、`direct` = 1 の行を保存する（鮮度の内に `direct` = 0 の行があっても、それでは決めない。直接の問い合わせの対象でない通知のために保存された、リゾルバーだけの結果で決めないため）。条件外と保留のときは、上の代わりの規則で保存済みの最新の行（どちらの種類も）を使う。DNS 検証が無効なときは、通知の期間の `direct` = 1 の行を先に、無ければ `direct` = 0 の行を使う。それ以外の通知は、どちらの種類も使う。DNS 検証が有効で OS のリゾルバーだけを使う設定のときは、この優先をしない（どの通知もどちらの種類も使う）。
- 保存は「その通知が使う行が無ければ追加する」を 1 つの SQL 文で行う。`direct` = 1 の行は `direct` = 1 の行が無ければ、`direct` = 0 の行はどちらの種類の行も無ければ追加する。調べる期間は鮮度の始め（検証を始めた時点の 12 時間前）から保存する時点まで（検証中に別のジョブが保存した行も見つける）。複数のジョブが同時に同じ名前を検証しても、同じ種類の行は 1 つになる（先に入った行が採られ、後のジョブはそれを再利用したものとして数える）。保存する種類は、権威 DNS の段階を実際に行ったか（NS を引いた。何が答えたかは問わない）で決める。

検証日時は、検証を始めた時点とする。全件再判定や索引の再構築も同じ規則で、鮮度を過ぎた名前は引き直す（DNS が変わっていれば、通知は別のグループへ移る。下の「通知のグループが変わるとき」）。検証していない通知（無効・条件外・保留で、代わりの結果も無いもの）は、次のグループ化（増分を含む。DNS 検証が有効なとき）や全件再判定のときに、その時点の条件で改めて調べる。保存した結果は、保持中の通知が使い終わるまで残し、日次のクリーンアップが削除する（`mail_keep_days` + 24 時間。進捗は [システム仕様](システム仕様.md) 7.1 の `cleanup`）。

**実行場所**: グループ化の 1 通ごとの処理で、判定・抽出の後に検証し、通知元の名前と登録したホスト名も解決する（どれもトランザクションを開く前。取り消されたときの扱いとともに [システム仕様](システム仕様.md) 5.4）。`Categorize` は純粋な関数のままで、検証結果と通知元の判定を入力として受け取る（`CategorizeWith`）。`GroupMailbox` と `Reindex` は検証の部品（`DNSVerifier`。実装は `app/modules/dnscheck` の `Checker`）を `WithDNS` で受け取り、テストでは差し替える。部品とキャッシュ（取得した送信元の記憶）は実行（`GroupMailbox` / `Reindex` の 1 回）ごとに作り直す（応答のないリゾルバーを同じ実行では二度と引かない規則と、取得の記憶が、実行ごとに働くように。応答の無い権威 DNS は実行の中でも 5 分で忘れる）。制御側が実行ごとに行う設定からの部品の組み立て（`modules.groupOptions(mb)`。`groupdns.go`）では何も解決しない:

- 送信元（`WithSendingSources`）は監視アドレスごとに作り（全体設定とそのアドレスの SMTP サーバーを「設定」、他の監視アドレスの SMTP サーバーを一致だけの名前として。`SendingSources.WithOtherHosts`）、DNS 検証の有効・無効とは無関係に常に渡す（2.6 の判定が使う）。`WithDNS` の部品は、通知元の判定にもこの送信元を使う。
- DNS 検証が有効なら、設定のリゾルバーを使う `Checker` を `WithDNS` に渡す。送信元のホスト名のアドレス（`WithSourceHostResolver`）と監視アドレスのドメインの SPF（`WithSourceSPF`。すべてのドメイン、2.7）も同じ部品で引き、その前に保存済みの取得結果（2.7 のキャッシュ。`sourceCache`、マスター DB の `sending_source_lookups`）を置く。
- DNS 検証が無効なら、問い合わせをしない `Checker`（`dnscheck.Config.StoredOnly`。保存済みの結果だけで通知を振り分け、名前の検証も、通知元の名前の問い合わせも、SPF も行わない。通知元は保存済みのアドレスがあればそれで判定する）を `WithDNS` に渡す。こうして、無効にしても既に検証した通知のグループは変わらない。送信元のホスト名は OS のリゾルバーだけで引き（`dnscheck.SystemHostResolver`。保存済みの取得結果を前に置く）、SPF は読まない（`WithSourceSPF` を渡さない）。
- 監視アドレスの一覧を読めないときは、ホスト名を欠いたままグループ化することはせず、そのジョブ（同期・グループ化・再判定・索引の再構築）をエラーで終える。

進捗（その実行で該当があったときだけ、グループ化の終わりに出す）:

- `dns: <n> notice(s): <a> verified, <b> reused from stored results, <c> not applicable, <d> inconclusive`。DNS 検証が無効で検証しなかった通知があれば `, <e> not checked (the DNS check is off)` を続ける（0 なら出さない）。`<n>` は名前解決の失敗を検出して検証の部品に渡した通知の宛先の数で、各通知は上の「検証する条件」と「通知元が送信側のメールサーバーか」で決まった区分のどれか 1 つに数える（`exists` で通知元を判定できなかったものは `inconclusive`）。
- `verifying again <n> notice(s) whose DNS lookup failure was not verified`（増分のグループ化で、未検証の通知を改めてグループ化するとき。グループ化の始め）。
- `junk: <n> backscatter, <m> fake_notice_link, <k> fake_notice_auth`（2.5・2.6 の規則で迷惑にした通知の数。どれかが 1 以上のとき）。
- `sending sources: ...`（2.7。取得した実行だけ）。

**通知のグループが変わるとき**: カテゴリと対応単位がグループキーを決めるので、検証の結果や通知元の判定が変わると、通知は別のグループへ移る。既にグループ化した通知が移るのは、次のグループ化（未検証の通知だけ）・全件再判定（`reclassify`）・索引の再構築のときで、主に次の場合:

- 設定を変えたとき: 送信元（全体設定、監視アドレスの SMTP サーバー）を変えると、送信元以外から送信されたメールのバウンスの判定（2.6）、通知元の判定、直接の問い合わせの可否が変わる。DNS 検証のリゾルバーやモードを変えたときも、未検証の通知の結果が変わりうる。検証済みの既存のメールに反映するには全件再判定を実行する。
- DNS 検証の有効・無効を切り替えたとき: 保存済みの結果は無効の間も使うので、検証済みの通知はそのまま。無効の間に届いた通知は未検証（`dns_unverified_*`）になり、有効に戻した後のグループ化で検証される。無効の間は SPF を読まないので、SPF にだけ載る送信元による一致（2.6 の除外、通知元の判定）が無くなる。
- 鮮度を過ぎた後の検証: 同じ名前を鮮度（12 時間）を過ぎてから検証し直したとき、全件再判定・索引の再構築でその時点の結果に従う（DNS が変わっていれば別のグループへ移る）。通知元の取得結果も同じ。
- 別の通知による最初の検証: 未検証だった通知の名前について、同じ名前の結果が別の通知のために保存されたとき（保存済みの結果は検証の条件より前に使われ、条件外のときも代わりに使われるので、宛先との関係を確かめられなかった通知にも使われる）、次のグループ化でその結果に従う。
- 直接の問い合わせの可否の入力が変わったとき: 送信元の設定（IP の範囲、ホスト名）、その実行の取得（名前から引いた IP、SPF の範囲とその完全さ。2.7）、OS のリゾルバーだけを使う設定、その実行で権威 DNS の確認を省くようになったかどうかで、通知が直接の問い合わせの対象かどうかと、`direct` = 1 の行を優先するかどうかが変わり、使う結果も変わりうる。
- 後から保存された `direct` = 1 の行: 直接の問い合わせの対象の通知が `direct` = 0 の行を代わりに使った後、その後に同じ名前の `direct` = 1 の行が別の通知のために保存されると、次の全件再判定でその行に従う（その行が無くても、全件再判定で改めて権威 DNS にも問い合わせて検証する）。
- 取得の完全さ: 送信元の取得が不完全な実行（2.7）では、送信元以外から送信されたメールのバウンスの判定が働かず、IP の照合が要る通知元は判定できない（未検証として、次のグループ化で改めて調べる）。
- 未検証から検証済みへ: 未検証だった通知が後のグループ化・全件再判定で検証されると、`dns_unverified_*` のグループから検証結果のグループへ移る（移った先が新しい対応対象のグループなら分析の対象になる。元のグループは空になれば削除する）。
- 空になったグループ: 全件再判定で所属メールが無くなったグループは、状態・対応履歴・分析結果ごと削除する（`DeleteEmptyGroups`。[システム仕様](システム仕様.md) 5.5）。同じキーのグループが後で再びできても、前の状態と履歴は戻らない。
- 索引を失って作り直したとき: 索引の再構築は、旧索引に無いメール（索引ファイルを失ったときは全メール）の受信日時に `.eml` の更新日時を使う（[システム仕様](システム仕様.md) 3.2）。通知の時刻が変わると、DNS 検証が無効のときに保存済みの結果を使う期間もずれ、別の結果を使うことがある。

### 4.5 再確認（`recheck.go`）

対応済・無視のグループに、その判断で片付いていないことを示すメンバー（バウンスまたは DMARC の記録）が入ったとき、グループを再確認待ち（`groups.needs_recheck` = 1）にする。状態の変更と対応履歴は [システム仕様](システム仕様.md) 5.9、画面の表示は [画面仕様](画面仕様.md) 5.3。

- 判定する時点: グループ化で、対応済・無視で再確認待ちでないグループにメンバーを入れたとき（[システム仕様](システム仕様.md) 5.4）と、索引の再構築で状態を引き継いだそのようなグループのメンバーを調べるとき（`groupSentBack`。[システム仕様](システム仕様.md) 5.5）。比べる相手は最新の状態変更と、そのとき記録した再確認キー（`group_state_change_patterns`）。状態変更の記録が無いグループは対象外。
- メンバーは宛先ごとの行（1 通の通知が複数の宛先を報告していれば、グループに入った宛先それぞれ。3 章）と DMARC の記録。
- 再確認キー（`mailengine.RecheckKey`）: バウンスはパターン（4.3）から相手側 MTA を除いたもの（`PatternKey(状態コード, 診断テンプレート, "", 診断文を取った場所)`。同じ拒否を別の受信サーバーが伝えても同じキーになる）、DMARC の記録はパターンそのもの（サーバーを含まない）。
- 条件（`recheckBasis.sendsBack`。どちらかに当たれば再確認待ちにする）:
  - 新しいパターン（対応済・無視の両方）: メンバーの再確認キーが最新の状態変更の記録に無い。ただし調べるのは、同じグループに別の原因が入りうるカテゴリ（`auth_failure`、`server_config`、DMARC の 3 カテゴリ。`recheckByPattern`）だけ。他のカテゴリは対応単位と判定元で問題が決まっており、文言が違っても別の受信サーバーの言い回しにすぎないため調べない。
  - 反映の期間を過ぎた送信（対応済だけ）: メンバーの送信日時（`mailengine.SentAt`: バウンスは返送された元メールの日時、DMARC の記録はレポート期間の終わり、どちらも無ければ通知の日時）が「最新の状態変更の日時 + カテゴリの再確認までの日数」より後。変更前に送ったメールの遅れた通知や、解除などが反映されるまでの通知では再確認にならない。無視は「来続けても対応しない」判断なので、この条件を使わない。
- 再確認までの日数（設定 `recheck_days`、カテゴリごと 1〜365。`modules.ResolveRecheckDays`、`mailengine.DefaultRecheckDays`。未知のカテゴリは 7 日）の既定値: 14 日 = `ip_blocked`・`sender_blocked`（ブラックリストの提供元や宛先ドメインの管理者の対応待ち。解除に 1 週間以上かかることがある）、7 日 = `rate_limited`・`unknown_failure`・DMARC の 3 カテゴリ・宛先側の 6 カテゴリ（`dns_failure_external` を含む。評価の回復、翌日以降に届くレポート、宛先リストの修正の反映）、3 日 = `auth_failure`・`content_rejected`・`message_too_large`・`server_config`・`dns_resolver_failure`・`dns_lookup_failure`（送信側を直せば効く。DNS の反映を見込む）。
- 再確認待ちにしたとき: `needs_recheck = 1` と、対応対象なら `needs_analysis = 1` を立てる（`models.SetGroupNeedsRecheck`）。状態は変えない（以後の分析フラグの立て方は [システム仕様](システム仕様.md) 5.4）。`needs_recheck` を外すのは利用者の次の状態変更だけ。

## 5. 処理対象と迷惑（サーバーからの削除対象）

- 処理対象（`mailengine.serverDeletableRules`）: 確実な根拠で自動通知と判定したメール。`rule` が `dsn_report` / `dmarc_report` / `daemon_sender` / `auto_reply` / `auto_reply_marked` / `body_pattern` のもの。件名や表示名だけで判定したもの（`auto_reply_subject` / `subject_pattern` / `daemon_display_name`）と自動生成メール（`auto_generated`）は、人が書いたメールも一致しうるので含めない。
- 迷惑（`mailengine.junkRules`）: `rule` が `phishing_display_name` / `phishing_forged_from` / `phishing_link` / `spam_flag` / `fake_notice_link` / `fake_notice_auth` / `backscatter` のもの。処理対象とは別に数える。
- サーバーからの削除の対象（`mailengine.serverDeletionRules`）: 処理対象と迷惑の両方。手順は [システム仕様](システム仕様.md) 5.6.1。
- 件数: 処理対象は `mailengine.CountTargetMessages`（API の `stats.target_messages`。メール一覧の「処理対象」タブも同じ規則 `mailengine.TargetRules()` で絞る）、迷惑は `mailengine.CountJunkMessages`（`stats.junk_messages`）。どちらも判定済み（`classified` = 1）の行を、日付と `server_deleted_at` を問わず数える（サーバーから削除済みでも、`mail_keep_days` を過ぎて手元から消えるまでは数える）。
- 件数と削除の候補は同じ規則の一覧を参照し、片方だけを変えてはならない。
