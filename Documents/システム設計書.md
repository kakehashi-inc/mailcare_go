# システム設計書 - MailCare

本書は MailCare の設計を記述します。実装は本書の契約（パッケージ境界・関数シグネチャ・API 形状）に従います。システムの振る舞いを変更した場合は本書を更新してください。

## 1. 用語定義

| 用語（日本語） | English | 説明 |
| --- | --- | --- |

## 2. 全体構成

```text
+---------------------------------------------------------------------------+
| mailcare (single binary)                                                  |
|                                                                           |
|  main.go -- kong CLI --> app/modules (commands, jobs, scheduler, auth)     |
|                              |                                            |
|            +-----------------+-----------------+                          |
|            v                 v                 v                          |
|   app/modules/mailengine  app/modules/agent   app/workers (HTTP server)   |
|   IMAP取得/解析/判定/纏め   エージェントCLI実行     Web :9790                  |
|            |                 |                   /api/v1/*  JSON (cookie) |
|            v                 v                   /web/*     login/logout  |
|         app/models  <-------+                    /control/* loopback only |
|            |                                     /*         embedded SPA  |
|   +--------+---------+                                                    |
|   v                  v                                                    |
| data/mailcare.db   data/mails/<address>.sqlite + <address>/*.eml ...       |
|                    data/agent/<address>/<group_key>/                       |
|                                                                           |
|  embed.go: app/migrations/*.sql, frontend/dist/**, agent-templates/**     |
+---------------------------------------------------------------------------+
```

- HTTP サーバーは Web サーバー 1 つ（既定ポート 9790）。外部公開 API は無く、`/api/v1/*` は Web 画面専用の内部 API（Cookie 認証）です。
- 依存方向は `main -> workers -> modules -> {mailengine, agent} -> models` の一方向です。`modules` から `workers` のサーバーを起動するため、`workers` が `init()` で `modules.StartServer` を登録します。
- `mailengine` と `agent` はマスター DB に触れません。必要な値（メールアドレス行、復号済みパスワード、パス）は `modules` が渡します。

## 3. データ配置

```text
data/
  mailcare.db                 マスター DB
  mailcare.key                秘密鍵（32 バイト、hex、0600）
  mails/
    user@example.com/         原文ディレクトリ（アドレスを安全化した名前）
      20260901-120000_ab12cd34ef56.eml
      20260901-120000_ab12cd34ef56.txt
      20260901-120000_ab12cd34ef56.html   (HTML パートがある場合のみ)
      20260901-120000_ab12cd34ef56.json
    user@example.com.sqlite   索引 DB
  agent/
    user@example.com/
      <group_key>/PROMPT.md, RESULT.log, REPORT.md, AGENTS.md
```

### 3.1 アドレスの安全化（`mailengine.SanitizeAddress`）

- 使用可能文字は `A-Z a-z 0-9 . _ - @ +`。それ以外（`< > : " / \ | ? *`、制御文字、空白、非 ASCII）は `_` に置き換える。
- 末尾の `.` と空白は Windows で不可のため `_` に置き換える。
- Windows 予約名（`CON`, `PRN`, `AUX`, `NUL`, `COM1-9`, `LPT1-9`）に一致する場合は先頭に `_` を付ける。
- 結果が空なら `_`。大文字小文字は保持する（衝突検出のためアドレスは登録時に小文字化して保存する）。

### 3.2 メールキー

`<日付>_<hash>`。日付は `Date` ヘッダー（無ければ INTERNALDATE、無ければ取得時刻）の UTC を `YYYYMMDD-HHMMSS` で表し、hash は `sha1(folder + "\x00" + uidvalidity + "\x00" + uid)` の先頭 12 桁（hex）。同一メールは常に同じキーになる。UIDVALIDITY が変わるとキーも変わるため、チェック時は Message-ID が索引済みのメールを重複として取り込まない（`Skipped` に数える）。

## 4. 認証と権限

- 利用者はユーザー名とパスワード（bcrypt、コスト 12）でログインする。ログイントークン（`mlc_` + 40 桁 hex、利用者に紐付く、有効期限任意）でもログインできる。
- 初回起動で利用者が 0 人のときは Web が初期設定画面（`/setup`）を表示し、最初の管理者を作成する。CLI の `user create --role admin` でも作成できる。
- セッションは AES-256-GCM で封印した Cookie（`mlc_session`、HttpOnly、SameSite=Lax、既定 720 時間、スライド更新は 24 時間に 1 回）。中身は `user_id`、`sha256(password_hash)`、有効期限。パスワード変更で既存セッションが無効になる。
- 権限:

| 操作 | admin | user |
| --- | --- | --- |
| ダッシュボード、アラート、メール閲覧 | o | o |
| メールチェックの実行、分析の再実行（グループ単位） | o | o |
| 纏めグループの状態変更（open / resolved / ignored） | o | o |
| 自分のパスワード変更、自分のトークン管理 | o | o |
| メールアドレスの追加・変更・削除、接続テスト | o | - |
| 設定（チェック時刻、エージェント）の変更 | o | - |
| 利用者管理、他人のトークン管理 | o | - |
| ツール（再索引・再判定・全体分析） | o | - |

## 5. メールチェック（`app/modules/mailengine`）

### 5.1 取得

1. IMAP に接続（`imap_security`: `ssl` = IMAPS / `starttls` / `none`）、ログイン、`folder`（既定 `INBOX`）を SELECT。
2. 対象期間: 索引 DB にそのアドレスのメールが 1 件も無い（初回）なら `initial_days`（既定 90 日）、それ以外は `recent_days`（既定 30 日）。`SEARCH SINCE <日付>` で UID を列挙する。
3. UIDVALIDITY が前回と異なる場合も同じ手順で、索引に無い (uidvalidity, uid) のみを取り込む（重複はキーで排除される）。
4. 未取得の UID をまず `FETCH (UID RFC822.SIZE)` で確認し、`MaxMessageSize` を超えるものは本文を取得せずスキップして記録する。残りを `FETCH (UID INTERNALDATE RFC822.SIZE BODY.PEEK[])` で取得する（`\Seen` を付けない）。
5. 原文を `.eml` に保存し、解析結果を `.txt` / `.html` / `.json` に保存し、索引に `messages` 行を追加する。
6. 対象判定と纏め（5.3、5.4）を行い、`GroupsTouched` を返す。

### 5.2 解析（`.json` の内容 = `ParsedMessage`）

`go-message`（`charset` 登録で ISO-2022-JP 等に対応）で解析する。ヘッダー: Message-ID、Subject（MIME デコード済み）、From（アドレス / 表示名）、To、Date、Return-Path、Auto-Submitted、Content-Type。本文: 最初の `text/plain` と `text/html` を UTF-8 に変換して `.txt` / `.html` に保存する（`.json` は本文を重複して持たない）。`.json` には IMAP 由来の識別情報 `source`（message_key、folder、uidvalidity、uid、size、received_at、fetched_at）も入れ、再索引で `messages` 行を復元する。`.json` が無い（手で複製した）原文は uidvalidity 0、folder 空、uid = キーの FNV-32 で登録する。壊れたメールでも panic せず、読めたヘッダーだけで索引する。`multipart/report` の `message/delivery-status` パートは per-recipient フィールド（Final-Recipient、Original-Recipient、Action、Status、Diagnostic-Code、Remote-MTA）と per-message フィールド（Reporting-MTA、Arrival-Date）を構造化する。`message/rfc822` または `text/rfc822-headers` パートからは元メールの Message-ID、Subject、From、Date を取る。

### 5.3 対象判定（`classify.go`）

ルールは Go のテーブル（`[]classifyRule`）として持ち、上から評価して最初に一致した結果を採用する。判定理由（`classify_reason`）にルール名を記録する。

| 順 | 条件 | 結果 |
| --- | --- | --- |
| 1 | `Content-Type: multipart/report; report-type=delivery-status`、または `message/delivery-status` パートを持つ（`dsn_report`） | バウンス。`Action` に `failed` があれば `failed`、`delayed` のみなら `delayed`、成功（`delivered` / `relayed` / `expanded`）のみなら `other`、Action が無ければ文言で判定 |
| 2 | From または Return-Path のローカル部が `mailer-daemon` / `postmaster` / `mail-daemon`（`+` / `-` の接尾辞も可、大文字小文字無視）（`daemon_sender`） | バウンス。件名・本文で `delayed` / `failed` を判定 |
| 3 | 件名が既知パターンに一致（`subject_pattern`）（`Undelivered Mail Returned to Sender`、`Delivery Status Notification`、`Mail delivery failed`、`Returned mail`、`Undeliverable`、`failure notice`、`Delivery Failure`、`Non-Delivery`、`Mail System Error`、`配信不能`、`配信できません`、`送信できません`、`Delayed Mail`、`Warning: could not send` 等） | バウンス（`Delayed` / `Warning` を含めば `delayed`、それ以外は `failed`） |
| 4 | `Auto-Submitted: auto-replied` または件名が `Out of Office` / `自動返信` / `不在` 等（`auto_reply`） | `auto_reply`（`is_bounce` = 1、`bounce_kind` = `auto_reply`） |
| 5 | From の表示名が `Mail Delivery System` / `Mail Delivery Subsystem` / `Mail Administrator` / `Postmaster` 等（`daemon_display_name`） | バウンス（`other`） |
| - | いずれにも一致しない | 対象外（`is_bounce` = 0） |

判定した `failed` / `delayed` / `other` のバウンスからは `bounces` 行の各値を抽出する。`smtp_code` は通知に 3 桁の応答コードが実際にある場合だけ入れる（無ければ空。プレースホルダーは合成しない）。delivery-status パートを優先し、無ければ本文から Postfix / Exim / qmail / Sendmail / Exchange / Gmail 形式を正規表現で拾う（例: `<addr>: host <mta>[<ip>] said: <smtp> <status> <text>`、`550 5.1.1 <addr>...`、`The following address(es) failed:` の次行、`Final-Recipient:` 行）。

`responsible` は状態コードから機械的に決める（エージェントが後で上書きしうる）。

| 状態コード | responsible |
| --- | --- |
| 5.1.1, 5.1.0, 5.1.3, 5.1.6, 5.2.1, 5.2.2, 4.2.2 | `recipient` |
| 5.1.2, 5.4.4, 5.4.6, 5.1.10, 5.4.1 | `domain` |
| 5.7.x, 4.7.x, 5.3.0, 5.5.x, 5.6.x | `sender` |
| 4.4.x, 4.3.x, 4.2.x | `sender`（遅延は送信側で監視） |
| その他 / 不明 | `unknown` |

状態コードが取れなかった場合は診断文の語句で推定する（`user unknown` / `no such user` / `mailbox unavailable` → `recipient`、`domain not found` / `no MX` / `DNS` / `connection timed out` → `domain`、`spam` / `blocked` / `blacklist` / `policy` / `SPF` / `DKIM` / `DMARC` / `too large` → `sender`）。

### 5.4 纏め（`grouping.go`）

- 診断テンプレート: 診断文（無ければ件名）を小文字化し、メールアドレス → `<addr>`、IPv4/IPv6 → `<ip>`、ホスト名らしき語 → `<host>`、Message-ID / キュー ID / 16 進列 → `<id>`、日付・時刻 → `<date>`、数値 → `<n>` に置換し、空白を畳む。ただし SMTP 応答コード（`550`）と拡張状態コード（`5.1.1`）は残す。
- グループキー: `sha1(bounce_kind + "|" + recipient_domain + "|" + status_code + "|" + diagnostic_template)` の先頭 16 桁（hex）。
- タイトル: `<recipient_domain> - <status_code> - <診断テンプレートの先頭 80 文字>`。ホスト名のプレースホルダーは `resolver.adr.recipnotfound` のようなドット区切りの語も吸収する（状態コードで区別される）。
- 増分: チェックで追加されたメールのみキーを計算して `UpsertGroup` → `RefreshGroupCounters`。再索引 / 再判定では全メールを対象に再計算し、`DeleteEmptyGroups` で空グループを消す。
- 対象外メール（`is_bounce` = 0）と `auto_reply` はグループに入れない（`group_key` = ""）。

### 5.5 再索引・再判定

- `Reindex`: まず旧索引（スキーマが古くても直接開く）から `groups` の状態（state、state_updated_at、needs_analysis、message_count）と `agent_reports` の全行を読み出し、`<address>.sqlite.rebuild` に新しい索引を構築する。`.eml` を全件解析（`.txt` / `.html` / `.json` も再生成）→ 判定 → 纏め。キーが再び現れたグループには状態と分析報告を引き継ぎ（`needs_analysis` は旧値 OR メール数が増えた）、現れなかったグループの報告は捨てる。最新の完了報告の対応者区分を再適用し、成功したときだけ本体と入れ替える（中断・失敗しても旧索引は残る）。
- `Reclassify`: `messages`・`groups`・`agent_reports` を残し、`ClearMailClassification`（`bounces` とメールの判定列のみ消す）後に `.json` + `.txt` / `.html`（無ければ `.eml`）から判定と纏めをやり直す。グループは `UpsertGroup` で説明列だけ更新され（状態は保持）、メール数が増えたときだけ `needs_analysis` が立つ。メールが 1 件も無くなったグループは `DeleteEmptyGroups` で削除され、その報告もカスケードで消える。最新の完了報告の対応者区分を再適用する。
- 索引 DB の `user_version` が古い場合、`OpenIndex` が自動で再索引する。

## 6. エージェント（`app/modules/agent`）

### 6.1 プロバイダー

`Provider` インターフェース（`Name` / `Label` / `Command`）を `provider_<name>.go` で実装し `init()` で登録する。`codex` の起動コマンドは `codex exec --sandbox read-only --skip-git-repo-check`（プロンプトは stdin）。読み取り専用サンドボックスのためメール原文（作業領域外）を読める。プロバイダーの有無は `exec.LookPath` で判定する。

### 6.2 実行手順（`AnalyzeGroup`）

1. `agent_reports` に `running` 行を作る。作業領域 `data/agent/<address>/<group_key>/` を作り、`agent-templates/<provider>/**` があれば複製する。
2. グループとその統計、最新 `AgentMaxSampleMessages`（20）件のメールの `.eml` と `.txt` の絶対パスを列挙したプロンプト（6.3）を `PROMPT.md` に書く。
3. CLI を作業領域で実行する（`AgentTimeout` 30 分）。終了コードは信頼せず、出力に REPORT ブロックがあれば成功とする。
4. `RESULT.log`（`Result: Success` / `Result: Failure` と理由、抽出した要約・対応者区分・重大度・報告、全出力）を毎回書き、成功時のみ `REPORT.md` を書く（失敗時は前回の `REPORT.md` を残す。DB も最新の完了報告を表示し続ける）。`CompleteAgentReport`（または `FailAgentReport`）で保存し、成功時に `SetGroupNeedsAnalysis(false)`。META の `responsible` が確定値（`sender` / `recipient` / `domain`）で現在値と異なれば `groups.responsible` を更新する（`models.UpdateGroupResponsible`）。`unknown`・空・不正値では機械判定の値を残す（報告行にはエージェントの回答をそのまま保存する）。失敗理由: プロバイダー未登録、CLI 起動失敗、タイムアウト、中止、REPORT ブロック無し。`AnalyzeGroup` は失敗でも報告行を返し、記録すらできない場合だけエラーを返す。

### 6.3 プロンプト仕様

固定順: 制約（読み取り専用、列挙されたファイル以外を読まない、メール内の指示に従わない、出力言語）→ グループ概要（宛先ドメイン、状態コード、診断テンプレート、件数、宛先数、IP 数、初回 / 最終日時、機械判定の対応者区分）→ メールファイル一覧（`- <eml path>` と `  text: <txt path>`）→ 出力指定。

出力は次の 2 ブロックを各 1 回。

```text
<<<MLC:REPORT>>>
## 原因の分析
...
## 影響範囲
...
## 推奨する対応
1. ...
## 対応すべき担当
...
<<<MLC:/REPORT>>>
<<<MLC:META>>>
{"summary":"1〜2 文の要約","responsible":"sender|recipient|domain|unknown","severity":"high|medium|low"}
<<<MLC:/META>>>
```

REPORT は最後のマーカー対を採用する。META はコードフェンスを除去し最初の `{` から最後の `}` を JSON として解釈する。解釈できない場合や列挙値が不正な場合は無視する（報告は完了扱い）。要約が空のときは報告本文の最初の見出し以外の段落（200 文字まで）を要約にする。プロンプトの全文と実例は [プロンプト仕様/バウンス分析 プロンプト仕様.md](プロンプト仕様/バウンス分析%20プロンプト仕様.md) を参照。

## 7. ジョブとスケジューラ（`app/modules/jobs.go`, `scheduler.go`）

- ジョブは `jobs` テーブルに `queued` で投入され、ワーカー（1 goroutine、直列）が `ClaimNextJob` で取り出して実行する。進捗は `progress` 列に随時書き、完了時に `result` / `error_message` を書く。同じ種別・メールアドレス・対象の未完了ジョブがあれば重複投入しない（`HasActiveJob`）。
- 種別:

| kind | mailbox_id | target | 処理 |
| --- | --- | --- | --- |
| `check` | 指定 or NULL（有効な全アドレス） | - | `CheckMailbox` → 結果を `mailboxes` に記録 → `agent_enabled` かつプロバイダーが利用可能なら `GroupsTouched` ごとに `analyze` ジョブを投入 |
| `reindex` | 指定 or NULL（全アドレス） | - | `Reindex` → `ResetMailboxCheckState` はしない（原文は残っているため） → アドレスごとに target 空（`needs_analysis` のグループのみ）の `analyze` を 1 件投入 |
| `reclassify` | 指定 or NULL | - | `Reclassify` → アドレスごとに target 空の `analyze` を 1 件投入 |
| `analyze` | 指定 | group_key、または "" で `needs_analysis` のグループ全部、`"*"` で全グループ | `agent.AnalyzeGroup` |

- 後続の `analyze` 投入は `agent_enabled` かつプロバイダーの CLI が PATH にあるときのみ行う。`requested_by` は `cli` / `scheduler` / `web:<username>`。
- 進捗は 500 ミリ秒に 1 回まで DB に書き、最新 200 行を保持する。
- サーバー起動時に `running` のまま残ったジョブと分析報告を `error` にし、30 日より古い完了ジョブを削除する。
- CLI のプロセス内実行（`RunJobInline`）は、自分が投入したジョブを実行した後、その実行中に投入された後続ジョブ（分析）も続けて実行する。
- スケジューラは `check_times`（`HH:MM` をカンマ区切り、ローカル時刻）を読み、`SchedulerTick` ごとに「直前 tick から現在までに到来した時刻」があれば全アドレスの `check` ジョブを投入する（同一分に二重投入しない）。設定変更は即時反映（毎 tick で読み直す）。
- CLI から `check` 等を実行するとき、サーバーが稼働中（`/control/status` が応答）なら `/control/jobs` に投入して完了までポーリング表示し、稼働していなければプロセス内で直接実行する。これにより同じ索引 DB への同時書き込みを避ける。

## 9. HTTP

### 9.1 共通

- `/api/v1/*` は Cookie 認証。未認証は 401 `{"error":"unauthorized"}`。権限不足は 403 `{"error":"forbidden"}`。検証エラーは 400 `{"error":"<message>"}`。
- `/control/*` はループバック（127.0.0.1 / ::1）からのみ。
- 応答の日時は RFC 3339（UTC）文字列。`sql.NullTime` は `null` または文字列で返す（応答用の DTO を `dto.go` で組み立てる）。
- ジョブを投入するエンドポイント（`POST /api/v1/jobs`、`.../check`、`.../analyze`、`POST /control/jobs`）は `{job: JobDTO, created: boolean}` を返す。新規なら 201、同一の未完了ジョブが既にあればそれを 200 `created: false` で返す。
- 未知の `/api/v1/*`、`/web/*`、`/control/*` は JSON の 404 を返す（SPA の shell は返さない）。

### 10.4 ユニバーサルデザイン

- 本文 16px 以上、行間 1.5 以上、コントラスト比 4.5:1 以上。色だけに頼らず、状態はアイコン + 文字でも示す。
- すべての操作要素にフォーカスリング、`aria-label`、44px 以上のタップ領域。テーブルは幅が狭いときカード表示に切り替える。
- Markdown は `react-markdown` で表示し、`rehype` 系のサニタイズは使わず（内部生成のため）リンクは新規タブで開く。
- 纏めグループ一覧の並び替え（最終日時の昇降順 / 件数 / 重大度）はクライアント側で行い、状態・対応者区分・検索語は URL のクエリに保持する。

## 11. データベース

- マスター DB: SQLite（`modernc.org/sqlite`、CGO 不要）、goose 管理。DSN で `busy_timeout(5000)`、`journal_mode(WAL)`、`foreign_keys(1)`。
- 索引 DB: 同じドライバ。スキーマは `app/models/mailindex.go`。テーブル定義は [テーブル定義.md](テーブル定義.md)。

## 12. ビルドとリリース

- `make lint`: `go vet` / `staticcheck` / `yarn lint`。`make test`: `go test ./...`。
- `make`: フロントエンドをビルドしてから Windows / Linux / macOS の amd64 / arm64 向けにクロスビルド。
