# システム設計書 - MailCare

本書は MailCare の設計を記述します。実装は本書の契約（パッケージ境界・関数シグネチャ・API 形状）に従います。システムの振る舞いを変更した場合は本書を更新してください。

## 1. 用語定義

| 用語（日本語） | English | 説明 |
| --- | --- | --- |
| 利用者 | User | Web 画面にログインして閲覧・操作する人（`users` テーブル） |
| 管理者 | Administrator | 役割 `admin` の利用者。利用者管理・設定・メールアドレス登録・ツール実行ができる |
| 一般利用者 | Member | 役割 `user` の利用者。閲覧専用（ダッシュボード、アラート、メール、ジョブ履歴の参照）と自分のプロファイルの変更だけができる |
| 運用者 | Operator | サーバーの起動・停止、CLI 操作、データディレクトリの管理をする人 |
| データディレクトリ | Data directory | 実行時データ（DB、メール原文、エージェント作業領域）を置くディレクトリ |
| マスター DB | Master database | `data/mailcare.db`。利用者・トークン・設定・メールアドレス・ジョブを保持する |
| 索引 DB | Mail index | `data/mails/<address>.sqlite`。メールアドレス単位の索引。原文ファイルから再生成できる派生データ |
| メールアドレス | Mailbox | 監視対象の 1 メールアドレスとその IMAP 接続設定（`mailboxes` テーブル） |
| 受信 | Fetch | IMAP から未取得メールを取り込み、原文を保存して索引に載せる処理（判定・纏めはしない） |
| 纏め | Grouping | 未処理のメールを判定し、カテゴリと対応単位でグループに束ねる処理 |
| 解析 | Analysis | エージェントで対応対象のグループを分析する処理 |
| 同期 | Sync | 1 アドレスについて受信 → 纏め → 解析投入を続けて行う処理。「全アドレス同期」は有効な全アドレスに 1 件ずつ投入する |
| 原文 | Raw message | `.eml` として保存した受信メールそのもの |
| メールキー | Message key | 1 メールを表すファイル名の基底（`YYYYMMDD-HHMMSS_<12桁hex>`） |
| バウンス | Bounce | メールデーモン（MAILER-DAEMON 等）が送る配信不能・遅延などの通知メール |
| 対象判定 | Classification | 受信メールがバウンスかどうか、どの種類かを判定する処理 |
| 纏めグループ | Bounce group | バウンスを「対応基準単位」で束ねたもの（`groups` テーブル）。対応対象のグループがアラートに載る |
| カテゴリ | Category | グループが表す問題の種類（IP ブロック、送信元拒否、認証失敗、宛先不明、容量超過 など）。対応単位・対応対象かどうかを決める |
| 対応単位 | Action unit | 管理者が対応する対象そのもの（送信サーバーの IP、送信元アドレス、送信ドメイン、当方の MTA。対象外なら宛先アドレス・宛先ドメイン）。`groups.unit_value` |
| 判断主体 | Authority | 結果を決めている相手（ブラックリストの提供元、宛先ドメイン）。登録先が違えば別グループになる。`groups.authority` |
| 対応対象 | Actionable | メールサーバー管理者が対応すべきグループ（`groups.actionable` = 1）。宛先側の問題（宛先不明・容量超過など）は対象外 |
| 診断テンプレート | Diagnostic template | 診断文からアドレス・IP・ID・数値などの揺れを除いた正規化文字列。カテゴリを判定できない場合の纏めの鍵になる |
| 対応者区分 | Responsible party | グループに対して対応すべき立場（`sender` 送信側サーバー管理者 / `recipient` 宛先アドレスの管理者 / `domain` 宛先ドメイン管理者 / `unknown`） |
| エージェント | Agent | 外部 CLI（Codex CLI 等）。纏めグループの原因分析と対応方法の提案を作成する |
| プロバイダー | Provider | エージェント CLI の種類（`codex` ほか、追加可能） |
| 分析報告 | Agent report | エージェントが作成した分析結果（`agent_reports` テーブルと `REPORT.md`） |
| ジョブ | Job | バックグラウンド処理の 1 単位（同期 / 受信 / 纏め / 解析 / 再索引 / 再判定）。`jobs` テーブル |
| ワーカー | Worker | ジョブを実行する goroutine。数は設定 `workers`。同じ IMAP サーバー・同じ索引・エージェントを使うジョブは直列化される |
| スケジューラ | Scheduler | 設定されたチェック時刻に全アドレス同期を投入する常駐処理 |
| 通知 | Notification | 対応対象の纏めグループの要約を通知先の利用者へメールで送る機能。SMTP 設定と通知設定（時刻・間隔・通知先）から成る |
| 通知先 | Notification recipient | 通知メールを受け取る利用者。利用者に任意で登録したメールアドレス（`users.email`）へ送る |
| 公開 URL | Public base URL | 通知メール内のリンクの元になる、利用者がブラウザで開く MailCare の URL（設定 `public_base_url`） |
| トークン | Token | 将来の API 実装のために予約した秘密文字列（`mlc_` 接頭辞）。利用者とは無関係で、ログインには使わない |
| デフォルトトークン | Default token | サーバー起動時にトークンが 1 件も無ければ自動作成される識別子 `default` のトークン（`is_default` = 1） |
| セッション | Session | Web ログイン後の Cookie（`mlc_session`）による認証状態 |
| コントロールエンドポイント | Control endpoint | ループバックからのみ使える停止・状態確認・ジョブ投入用 HTTP エンドポイント |
| SPA | Single Page Application | バイナリに埋め込まれて配信される React 製の Web 画面 |

## 2. 全体構成

```text
+---------------------------------------------------------------------------+
| mailcare (single binary)                                                  |
|                                                                           |
|  main.go -- kong CLI --> app/modules (commands, jobs, scheduler, auth)     |
|                              |                                            |
|            +-----------------+-----------------+                          |
|            v                 v                 v                          |
|   app/modules/mailengine  app/modules/agent   app/workers (HTTP server)   |
|   IMAP取得/解析/判定/纏め   エージェントCLI実行     Web :9790                  |
|            |                 |                   /api/v1/*  JSON (cookie) |
|            v                 v                   /web/*     login/logout  |
|         app/models  <-------+                    /control/* loopback only |
|            |                                     /*         embedded SPA  |
|   +--------+---------+                                                    |
|   v                  v                                                    |
| data/mailcare.db   data/mails/<address>.sqlite + <address>/*.eml ...       |
|                    data/agent/<address>/<group_key>/                       |
|                                                                           |
|  embed.go: app/migrations/*.sql, frontend/dist/**, templates/**           |
+---------------------------------------------------------------------------+
```

- HTTP サーバーは Web サーバー 1 つ（既定ポート 9790）。外部公開 API は無く、`/api/v1/*` は Web 画面専用の内部 API（Cookie 認証）です。
- 依存方向は `main -> workers -> modules -> {mailengine, agent} -> models` の一方向です。`modules` から `workers` のサーバーを起動するため、`workers` が `init()` で `modules.StartServer` を登録します。
- `mailengine` と `agent` はマスター DB に触れません。必要な値（メールアドレス行、復号済みパスワード、パス）は `modules` が渡します。

## 3. データ配置

```text
data/
  mailcare.db                 マスター DB
  mailcare.key                秘密鍵（32 バイト、hex、0600）
  mails/
    user@example.com/         原文ディレクトリ（アドレスを安全化した名前）
      20260901-120000_ab12cd34ef56.eml
      20260901-120000_ab12cd34ef56.txt
      20260901-120000_ab12cd34ef56.html   (HTML パートがある場合のみ)
      20260901-120000_ab12cd34ef56.json
    user@example.com.sqlite   索引 DB
  agent/
    user@example.com/
      <group_key>/PROMPT.md, RESULT.log, REPORT.md, AGENTS.md
```

### 3.1 アドレスの安全化（`mailengine.SanitizeAddress`）

- 使用可能文字は `A-Z a-z 0-9 . _ - @ +`。それ以外（`< > : " / \ | ? *`、制御文字、空白、非 ASCII）は `_` に置き換える。
- 末尾の `.` と空白は Windows で不可のため `_` に置き換える。
- Windows 予約名（`CON`, `PRN`, `AUX`, `NUL`, `COM1-9`, `LPT1-9`）に一致する場合は先頭に `_` を付ける。
- 結果が空なら `_`。大文字小文字は保持する（衝突検出のためアドレスは登録時に小文字化して保存する）。

### 3.2 メールキー

`<日付>_<hash>`。日付は `Date` ヘッダー（無ければ INTERNALDATE、無ければ取得時刻）の UTC を `YYYYMMDD-HHMMSS` で表し、hash は `sha1(folder + "\x00" + uidvalidity + "\x00" + uid)` の先頭 12 桁（hex）。同一メールは常に同じキーになる。UIDVALIDITY が変わるとキーも変わるため、チェック時は Message-ID が索引済みのメールを重複として取り込まない（`Skipped` に数える）。

## 4. 認証と権限

- 利用者はユーザー名、表示名、任意の通知用メールアドレス（`users.email`。空なら通知先にならない）、画面の言語（`users.language`: `ja` / `en`、既定 `ja`）、表示用タイムゾーン（`users.timezone`、IANA 名、既定 `Asia/Tokyo`）、テーマ（`users.theme`: `auto` / `light` / `dark`、既定 `auto` = ブラウザの設定に従う）、役割を持つ。言語とテーマはブラウザから自動判別せず、利用者の設定に従う（ログイン前の画面は日本語・自動テーマ）。
- 利用者の入力項目の並びは全画面で統一する: ユーザー名 → 表示名 → メールアドレス → 言語 → タイムゾーン → テーマ →（管理者の利用者管理のみ）役割 → パスワード。
- 日時の扱い: データベースにはすべて UTC で保存する。Web 画面はログイン利用者のタイムゾーンで変換して表示し、API の応答は RFC 3339（UTC）のまま。CLI の表示と通知メールの日時はサーバーのローカル時刻。同期時刻（`check_times`）と通知時刻（`notify_time`）はサーバーのローカル時刻で実行し、設定画面にその旨を表示する。
- 利用者はユーザー名とパスワード（bcrypt、コスト 12）でログインする。トークン（`mlc_` + 40 桁 hex、有効期限任意）は利用者と無関係な将来の API 用の予約機能で、ログインには使えない。
- デフォルトトークン: サーバー起動時にトークンが 1 件も無ければ識別子 `default`（無期限、`is_default` = 1）を作成し、値をログに 1 度だけ出す。トークンはあるがデフォルトが無い場合、識別子 `default` のトークンがあればそれをデフォルトにし、無ければ何もしない（他のトークンを昇格させない）。自動生成されるのは `default` だけで、利用者の作成や DB ファイルの作成とは連動しない。
- 初回起動で利用者が 0 人のときは Web が初期設定画面（`/setup`）を表示し、最初の管理者を作成する。CLI の `user create --role admin` でも作成できる。
- セッションは AES-256-GCM で封印した Cookie（`mlc_session`、HttpOnly、SameSite=Lax）。中身は `user_id`、`sha256(password_hash)`、有効期限、保持フラグ。パスワード変更で既存セッションが無効になる。
- ログイン画面の「ログインを保持する」（`remember`）を付けると Max-Age 付きの永続 Cookie（既定 720 時間、スライド更新は 24 時間に 1 回）になる。付けない場合（既定）はブラウザを閉じると消えるセッション Cookie で、サーバー側の有効期限は 24 時間、更新はしない。初期設定でのログインは保持なし。
- 権限:

| 操作 | admin | user |
| --- | --- | --- |
| ダッシュボード、アラート、メール、ジョブ履歴の閲覧 | o | o |
| 同期・受信・纏め・解析・再索引・再判定の実行（ツール） | o | - |
| 纏めグループの状態変更（open / resolved / ignored）、再分析 | o | - |
| プロファイル（自分の通知用メールアドレス、パスワード変更。右上の利用者名メニュー） | o | o |
| 設定メニュー全体（一般設定 / 通知 / メールアドレス / 利用者 / トークン） | o | - |
| トークンの発行・一覧・削除（将来の API 用の予約機能。利用者とは無関係） | o | - |
| 通知設定（SMTP・通知先・時刻・間隔）、テスト送信、今すぐ送信 | o | - |
| メールアドレスの追加・変更・削除、接続テスト | o | - |
| ツールの実行全般（一般利用者にはジョブ履歴のみ表示） | o | - |
| 設定（チェック時刻、エージェント）の変更 | o | - |
| 利用者管理 | o | - |
| ツール（再索引・再判定・全体分析） | o | - |

## 5. 受信・纏め（`app/modules/mailengine`）

受信（`FetchMailbox`）、纏め（`GroupMailbox`）、解析（`agent.AnalyzeGroup`）は互いに独立した関数で、制御側（`app/modules/jobs.go`）がジョブとして個別に、または同期ジョブとして順に呼び出す。受信は判定・纏めをせず `messages.classified = 0` で索引に載せるだけで、纏めは `classified = 0` のメールだけを処理する（全件やり直しは `full = true`）。

### 5.1 受信（`FetchMailbox`）

1. IMAP に接続（`imap_security`: `ssl` = IMAPS / `starttls` / `none`）、ログイン、`folder`（既定 `INBOX`）を SELECT。
2. 対象期間: 索引 DB にそのアドレスのメールが 1 件も無い（初回）なら `initial_days`（既定 90 日）、それ以外は `recent_days`（既定 30 日）。`SEARCH SINCE <日付>` で UID を列挙する。
3. UIDVALIDITY が前回と異なる場合も同じ手順で、索引に無い (uidvalidity, uid) のみを取り込む（重複はキーで排除される）。
4. 未取得の UID をまず `FETCH (UID RFC822.SIZE)` で確認し、`MaxMessageSize` を超えるものは本文を取得せずスキップして記録する。残りを `FETCH (UID INTERNALDATE RFC822.SIZE BODY.PEEK[])` で取得する（`\Seen` を付けない）。
5. 原文を `.eml` に保存し、解析結果を `.txt` / `.html` / `.json` に保存し、索引に `messages` 行（`classified = 0`）を追加する。`FetchResult`（取得数・スキップ数・UIDVALIDITY）を返す。判定と纏めは行わない。

### 5.2 解析（`.json` の内容 = `ParsedMessage`）

`go-message`（`charset` 登録で ISO-2022-JP 等に対応）で解析する。ヘッダー: Message-ID、Subject（MIME デコード済み）、From（アドレス / 表示名）、To（アドレス / 表示名）、Date、Return-Path、Auto-Submitted、Content-Type。本文: 最初の `text/plain` と `text/html` を UTF-8 に変換して `.txt` / `.html` に保存する（`.json` は本文を重複して持たない）。

本文の採用規則（判定・抽出に使う「有効本文」）: `text/plain` と `text/html` はそれぞれ「空白以外の内容があるか」を判定して `has_text` / `has_html` に記録する。有効本文は、plain に有効な内容があれば plain（両方にあっても plain 優先）、plain が無いか空白のみなら HTML からタグ・スタイル・スクリプトを除いてテキスト化したもの（`<br>` / `<p>` / `<div>` / `<tr>` は改行、`&nbsp;` 等の実体参照は復元）、どちらも無ければ空とし、採用した側を `body_source`（`text` / `html` / 空）に記録する。次の 5 パターンをすべて扱う: plain のみ、HTML のみ、plain + HTML、plain（パートはあるが空）+ HTML、plain + HTML（パートはあるが空）。`.json` には IMAP 由来の識別情報 `source`（message_key、folder、uidvalidity、uid、size、received_at、fetched_at）も入れ、再索引で `messages` 行を復元する。`.json` が無い（手で複製した）原文は uidvalidity 0、folder 空、uid = キーの FNV-32 で登録する。壊れたメールでも panic せず、読めたヘッダーだけで索引する。`multipart/report` の `message/delivery-status` パートは per-recipient フィールド（Final-Recipient、Original-Recipient、Action、Status、Diagnostic-Code、Remote-MTA）と per-message フィールド（Reporting-MTA、Arrival-Date）を構造化する。`message/rfc822` または `text/rfc822-headers` パートからは元メールの Message-ID、Subject、From、Date を取る。

### 5.3 対象判定（`classify.go`、纏めフェーズの第 1 段階）

ルールは Go のテーブル（`[]classifyRule`）として持ち、上から評価して最初に一致した結果を採用する。判定理由（`classify_reason`）にルール名を記録する。

| 順 | 条件 | 結果 |
| --- | --- | --- |
| 1 | `Content-Type: multipart/report; report-type=delivery-status`、または `message/delivery-status` パートを持つ（`dsn_report`） | バウンス。`Action` に `failed` があれば `failed`、`delayed` のみなら `delayed`、成功（`delivered` / `relayed` / `expanded`）のみなら `other`、Action が無ければ文言で判定 |
| 2 | From または Return-Path のローカル部が `mailer-daemon` / `postmaster` / `mail-daemon`（`+` / `-` の接尾辞も可、大文字小文字無視）（`daemon_sender`） | バウンス。件名・本文で `delayed` / `failed` を判定 |
| 3 | 件名が既知パターンに一致（`subject_pattern`）（`Undelivered Mail Returned to Sender`、`Delivery Status Notification`、`Mail delivery failed`、`Returned mail`、`Undeliverable`、`failure notice`、`Delivery Failure`、`Non-Delivery`、`Mail System Error`、`配信不能`、`配信できません`、`送信できません`、`Delayed Mail`、`Warning: could not send` 等） | バウンス（`Delayed` / `Warning` を含めば `delayed`、それ以外は `failed`） |
| 4 | `Auto-Submitted: auto-replied` または件名が `Out of Office` / `自動返信` / `不在` 等（`auto_reply`） | `auto_reply`（`is_bounce` = 1、`bounce_kind` = `auto_reply`） |
| 5 | From の表示名が `Mail Delivery System` / `Mail Delivery Subsystem` / `Mail Administrator` / `Postmaster` 等（`daemon_display_name`） | バウンス（`other`） |
| - | いずれにも一致しない | 対象外（`is_bounce` = 0） |

判定した `failed` / `delayed` / `other` のバウンスからは `bounces` 行の各値を抽出する。`smtp_code` は通知に 3 桁の応答コードが実際にある場合だけ入れる（無ければ空。プレースホルダーは合成しない）。delivery-status パートを優先し、無ければ本文から Postfix / Exim / qmail / Sendmail / Exchange / Gmail 形式を正規表現で拾う（例: `<addr>: host <mta>[<ip>] said: <smtp> <status> <text>`、`550 5.1.1 <addr>...`、`The following address(es) failed:` の次行、`Final-Recipient:` 行）。

`responsible` は状態コードから機械的に決める（エージェントが後で上書きしうる）。

| 状態コード | responsible |
| --- | --- |
| 5.1.1, 5.1.0, 5.1.3, 5.1.6, 5.2.1, 5.2.2, 4.2.2 | `recipient` |
| 5.1.2, 5.4.4, 5.4.6, 5.1.10, 5.4.1 | `domain` |
| 5.7.x, 4.7.x, 5.3.0, 5.5.x, 5.6.x | `sender` |
| 4.4.x, 4.3.x, 4.2.x | `sender`（遅延は送信側で監視） |
| その他 / 不明 | `unknown` |

状態コードが取れなかった場合は診断文の語句で推定する（`user unknown` / `no such user` / `mailbox unavailable` → `recipient`、`domain not found` / `no MX` / `DNS` / `connection timed out` → `domain`、`spam` / `blocked` / `blacklist` / `policy` / `SPF` / `DKIM` / `DMARC` / `too large` → `sender`）。

### 5.4 纏め（`GroupMailbox`: `category.go` + `grouping.go`）

纏めは「管理者が何に対して動くか」の単位で束ねる。バウンス 1 件ごとに状態コードと診断文からカテゴリを判定し、カテゴリが対応単位（`unit_value`）と判断主体（`authority`）を決める。宛先アドレスや相手 IP が違っても対応単位が同じなら同じグループになり、ブラックリストの登録先が違えば別グループになる。

| カテゴリ | 対応対象 | 判定の手掛かり（診断文 / 状態コード） | unit_value | authority |
| --- | --- | --- | --- | --- |
| `ip_blocked` | 1 | `blocked` / `blacklist` / `block list` / `listed` / `rbl` / `dnsbl` / `spamhaus` / `barracuda` / `spamcop` / `sorbs` / `uceprotect` / `proofpoint` / `cloudmark` / `Our system has detected` / `unsolicited mail originating from your IP` / `poor reputation` / 5.7.1 や 4.7.0 で IP に言及 | 診断文中の当方の送信 IP（`[203.0.113.5]` 形式など。無ければ `reporting_mta`） | ブラックリストの提供元（診断文の URL / ホスト名から抽出した `spamhaus.org` 等）。無ければ宛先ドメイン |
| `rate_limited` | 1 | `too many` / `rate limit` / `try again later` / `throttl` / `temporarily rate limited` / 4.7.0 で IP ブロックの語が無い | 送信 IP（無ければ `reporting_mta`） | 宛先ドメイン |
| `auth_failure` | 1 | `spf` / `dkim` / `dmarc` / `not authorized` / `unauthenticated` / `reverse dns` / `ptr` / `helo` / 5.7.23〜5.7.27 | 送信ドメイン（元メールの差出人のドメイン。無ければ `reporting_mta`） | 宛先ドメイン |
| `sender_blocked` | 1 | `sender address rejected` / `sender ... blocked` / `sender ... denied` / `blocked using` が送信元アドレスを指す / 5.7.1 で送信元アドレスに言及 | 元メールの差出人アドレス（無ければ送信ドメイン） | 宛先ドメイン |
| `content_rejected` | 1 | `spam` / `content` / `virus` / `malware` / `attachment` / `message rejected` / `rejected due to policy`（上記に該当しない） | 元メールの差出人アドレス | 宛先ドメイン |
| `message_too_large` | 1 | `too large` / `message size` / `exceeds` / 5.2.3 / 5.3.4 | 元メールの差出人アドレス | 宛先ドメイン |
| `server_config` | 1 | `relay` / `tls` / `starttls` / `encryption required` / `helo command rejected` / 5.5.x / 5.3.0 / 5.6.x | `reporting_mta`（当方の MTA） | 宛先ドメイン |
| `unknown_failure` | 1 | 上記のどれにも該当しない `failed` / `other` | 宛先ドメイン | `<状態コード> <診断テンプレート>` |
| `user_unknown` | 0 | 5.1.1 / 5.1.0 / 5.1.3 / 5.1.6 / 5.1.10 / `user unknown` / `no such user` / `recipient not found` / `recipnotfound` / `does not exist` | 宛先アドレス | （空） |
| `mailbox_full` | 0 | 4.2.2 / 5.2.2 / `over quota` / `out of storage` / `mailbox full` | 宛先アドレス | （空） |
| `mailbox_disabled` | 0 | 5.2.1 / `disabled` / `inactive` / `suspended` | 宛先アドレス | （空） |
| `domain_not_found` | 0 | 5.1.2 / 5.4.4 / 5.4.6 / `domain not found` / `no mx` / `unrouteable` / `name service error` | 宛先ドメイン | （空） |
| `delivery_delay` | 0 | `delayed` 種別、4.4.x / `connection timed out` / `greylist` | 宛先ドメイン | （空） |

- ルールは `category.go` の `[]categoryRule` テーブルで、上から評価して最初に一致したものを採用する。実装上の評価順: (1) 宛先側を明確に示す状態コード（5.1.1 / 5.1.0 / 5.1.3 / 5.1.6 / 5.1.10 → `user_unknown`、4.2.2 / 5.2.2 → `mailbox_full`、5.2.1 → `mailbox_disabled`、5.1.2 / 5.4.4 / 5.4.6 → `domain_not_found`）、(2) `ip_blocked`、(3) `rate_limited`、(4) 種別 `delayed` → `delivery_delay`、(5) `auth_failure`、(6) `sender_blocked`、(7) `message_too_large`、(8) `content_rejected`、(9) `server_config`、(10) 宛先側の文言（`user_unknown` / `mailbox_full` / `mailbox_disabled` / `domain_not_found` / `delivery_delay`）、(11) `unknown_failure`。`message_too_large` を `content_rejected` より先に置くのは "Message rejected: size exceeds" の誤判定を避けるため。
- カテゴリの定義（対応対象、対応者区分、対応単位、判断主体）は `categoryDefs` テーブルに持つ。`responsible` はカテゴリから決め、`bounces.responsible` と `groups.responsible` の両方に同じ値を書く: 対応対象のカテゴリ → `sender`（`unknown_failure` は `unknown`）、`user_unknown` / `mailbox_full` / `mailbox_disabled` → `recipient`、`domain_not_found` / `delivery_delay` → `domain`。
- 送信 IP の抽出: 診断文中の `[ip]` / `(ip)` → `ip` / `address` / `host` / `your` / `originating` / `client` などの直後の IP → 任意の IP リテラルの順で探し、相手 MTA の IP とループバックを除く。無ければ `reporting_mta`。
- ブラックリスト提供元の抽出: 既知の提供元テーブル（spamhaus.org、spamcop.net、sorbs.net、barracudacentral.org、uceprotect.net、proofpoint.com、cloudmark.com、invaluement.com、abuseat.org、mailspike.net、spamrats.com、senderscore.org、surbl.org、uribl.com、psbl.org、nixspam.org、blocklist.de、mail-abuse.com、lashback.com、junkemailfilter.com、trendmicro.com、mimecast.com、talosintelligence.com、spameatingmonkey.net）→ 無ければ listing の語があるときに文中の URL / ホスト名の登録可能ドメイン（宛先・送信・MTA のドメインと大手メールサービスのヘルプ URL は除外）→ 無ければ宛先ドメイン。
- 元メールの差出人が取れない場合、送信元アドレスは診断文中の宛先以外のアドレス → 送信ドメイン → `reporting_mta` の順で補う。
- 診断テンプレート（5.4 旧仕様のとおり: アドレス → `<addr>`、IP → `<ip>`、ホスト → `<host>`、ID → `<id>`、日付 → `<date>`、数値 → `<n>`、SMTP コードと状態コードは保持）は `bounces.diagnostic_template` に保存し、`unknown_failure` の authority と表示に使う。
- グループキー: `sha1(category + "|" + unit_value + "|" + authority)` の先頭 16 桁（hex）。`unit_value` と `authority` は小文字化・前後空白除去して比較する。
- 表示名は保存しない。CLI・ログ・通知メールでは `models.BounceGroup.Label()`（`<category>: <unit_value> @ <authority>`）、Web ではカテゴリから翻訳した見出しを組み立てる。
- 増分: `classified = 0` のメールだけ判定・抽出し、グループに `UpsertGroup` → `RefreshGroupCounters`（メール数が増えたグループは `needs_analysis = 1`）。`auto_reply` と対象外メール（`is_bounce` = 0）はグループに入れない（`group_key` = ""）。処理済みは `classified = 1`。
- 全件（`full = true`）: `ClearMailClassification` 後に全メールを処理し、`DeleteEmptyGroups` で空グループを消す。既存グループの状態と分析報告は保持する（キーが同じ限り）。
- 戻り値 `GroupResult`: 処理したメール数、バウンス数、`GroupsTouched`（メールが増えた対応対象グループのキー）、グループ総数。

### 5.5 再索引・再判定

- `Reindex`（受信相当 + 全件纏め）: まず旧索引（スキーマが古くても直接開く）から `groups` の状態（state、state_updated_at、needs_analysis、message_count）と `agent_reports` の全行を読み出し、`<address>.sqlite.rebuild` に新しい索引を構築する。`.eml` を全件解析（`.txt` / `.html` / `.json` も再生成）→ 判定 → 纏め。キーが再び現れたグループには状態と分析報告を引き継ぎ（`needs_analysis` は旧値 OR メール数が増えた）、現れなかったグループの報告は捨てる。最新の完了報告の対応者区分を再適用し、成功したときだけ本体と入れ替える（中断・失敗しても旧索引は残る）。
- 再判定は `GroupMailbox(full = true)`: `messages`・`groups`・`agent_reports` を残し、`ClearMailClassification`（`bounces` とメールの判定列のみ消す）後に `.json` + `.txt` / `.html`（無ければ `.eml`）から判定と纏めをやり直す。グループは `UpsertGroup` で説明列だけ更新され（状態は保持）、メール数が増えたときだけ `needs_analysis` が立つ。メールが 1 件も無くなったグループは `DeleteEmptyGroups` で削除され、その報告もカスケードで消える。最新の完了報告の対応者区分を再適用する。
- 索引 DB の `user_version` が古い場合、`OpenIndex` が自動で再索引する。

## 6. エージェント（`app/modules/agent`）

### 6.1 プロバイダー

`Provider` インターフェース（`Name` / `Label` / `Command`）を `provider_<name>.go` で実装し `init()` で登録する。任意で `RateLimitDetector`（`DetectRateLimit(out) RateLimitOutcome`）を実装すると、利用上限・レート制限の判定をプロバイダー固有にできる（未実装なら共通のマーカー判定）。`codex` の起動コマンドは `codex exec --sandbox read-only --skip-git-repo-check`（プロンプトは stdin）。読み取り専用サンドボックスのためメール原文（作業領域外）を読める。プロバイダーの有無は `exec.LookPath` で判定する。

解析は纏めフェーズの一部ではなく、纏め完了後に制御側が「対応対象かつ `needs_analysis = 1`（新規、または既存グループにメールが増えた）」のグループについて投入する。対象外（宛先側）のグループは解析しない。

### 6.2 実行手順（`AnalyzeGroup`）

1. `agent_reports` に `running` 行を作る。作業領域 `data/agent/<address>/<group_key>/` を作り、`templates/agent/<provider>/**` があれば複製する。
2. グループ（カテゴリ、対応単位、判断主体、対応対象）とその統計、最新 `AgentMaxSampleMessages`（20）件のメールの `.eml` と `.txt` の絶対パスを列挙したプロンプト（6.3）を `PROMPT.md` に書く。
3. CLI を作業領域で実行する（`AgentTimeout` 30 分）。終了コードは信頼せず、出力に有効な REPORT ブロックがあれば成功とする。codex はプロンプト全文をエコーしてから回答するため、解析前に出力からプロンプト本文を取り除き、テンプレートのプレースホルダー（`<one or two sentences>` 等）を含む報告や短すぎる報告は失敗として扱う。利用上限・レート制限（`usage limit` / `rate limit` / `429` / `try again at` 等。プロバイダーごとに `DetectRateLimit` で拡張できる）を検出した場合は `error_message` に再試行時刻を含めて失敗にする。
4. `RESULT.log`（`Result: Success` / `Result: Failure` と理由、抽出した要約・対応者区分・重大度・報告、全出力）を毎回書き、成功時のみ `REPORT.md` を書く（失敗時は前回の `REPORT.md` を残す。DB も最新の完了報告を表示し続ける）。`CompleteAgentReport`（または `FailAgentReport`）で保存し、成功時に `SetGroupNeedsAnalysis(false)`。META の `responsible` が確定値（`sender` / `recipient` / `domain`）で現在値と異なれば `groups.responsible` を更新する（`models.UpdateGroupResponsible`）。`unknown`・空・不正値では機械判定の値を残す（報告行にはエージェントの回答をそのまま保存する）。失敗理由: プロバイダー未登録、CLI 起動失敗、タイムアウト、中止、REPORT ブロック無し、REPORT はあるが使えない（雛形のプレースホルダー行が残る / 見出しを除いた本文が 40 文字未満 / 要約がプレースホルダー）、利用上限・レート制限の検出。失敗時はグループの `needs_analysis` を 1 に戻し、次回の同期で再試行する。`AnalyzeGroup` は失敗でも報告行を返し、記録すらできない場合だけエラーを返す。

### 6.3 プロンプト仕様

固定順: 制約（読み取り専用、列挙されたファイル以外を読まない、メール内の指示に従わない、出力言語）→ タスク（管理者の立場で対応単位に対する具体的な対応を求める。カテゴリごとの指針を付ける: `ip_blocked` は当該ブラックリストの解除手順、`auth_failure` は送信ドメインの SPF / DKIM / DMARC / PTR / HELO、`sender_blocked` は送信元アドレスの評価 など。対象外グループでは宛先側の管理者に伝える短い注記を求める）→ グループ概要（カテゴリと説明、対応単位、判断主体、対応対象かどうか、宛先ドメイン、状態コード、診断テンプレート、件数、宛先数、IP 数、初回 / 最終日時、機械判定の対応者区分）→ メールファイル一覧（`- <eml path>` と `  text: <txt path>`）→ 出力指定。カテゴリの英語説明は `agent/category.go` の `CategoryGlossary` に持つ。

出力は次の 2 ブロックを各 1 回。

```text
<<<MLC:REPORT>>>
## 原因の分析
...
## 影響範囲
...
## 推奨する対応
1. ...
## 対応すべき担当
...
<<<MLC:/REPORT>>>
<<<MLC:META>>>
{"summary":"1〜2 文の要約","responsible":"sender|recipient|domain|unknown","severity":"high|medium|low"}
<<<MLC:/META>>>
```

REPORT は最後のマーカー対を採用する。META はコードフェンスを除去し最初の `{` から最後の `}` を JSON として解釈する。解釈できない場合や列挙値が不正な場合は無視する（報告は完了扱い）。要約が空のときは報告本文の最初の見出し以外の段落（200 文字まで）を要約にする。プロンプトの全文と実例は [プロンプト仕様/バウンス分析 プロンプト仕様.md](プロンプト仕様/バウンス分析%20プロンプト仕様.md) を参照。

| kind | mailbox_id | target | 処理 |
| --- | --- | --- | --- |
| `sync` | 指定 | - | `FetchMailbox` → `GroupMailbox(full=false)` → 対応対象で `needs_analysis` のグループ（新着で増えたもの、前回の解析が失敗したもの）があれば `analyze`（target 空）を投入 |
| `fetch` | 指定 | - | `FetchMailbox` のみ。結果を `mailboxes` に記録 |
| `group` | 指定 | - | `GroupMailbox(full=false)` → `analyze`（target 空）を投入 |
| `analyze` | 指定 | 空 = `needs_analysis` かつ対応対象のグループ / グループキー / `*` = 対応対象の全グループ | `agent.AnalyzeGroup` |
| `reindex` | 指定 | - | `Reindex` → `analyze`（target 空）を投入 |
| `reclassify` | 指定 | - | `GroupMailbox(full=true)` → `analyze`（target 空）を投入 |
| `notify` | NULL | 空 = 通知先へ送信 / `test:<address>` = テスト送信 | 通知メールの組み立てと送信（7.5） |

- `mailbox_id` が NULL のジョブは「展開ジョブ」で、実行時に対象アドレス（`sync` / `fetch` は有効なアドレスのみ、それ以外は全アドレス）ごとに同種のジョブを 1 件ずつ投入して即終了する（結果は「queued N jobs」）。これにより全アドレス同期（全処理）は ワーカー数の範囲で並列に進む。
- 後続の `analyze` 投入は `agent_enabled` かつプロバイダーの CLI が PATH にあるときのみ行う。`requested_by` は `cli` / `scheduler` / `web:<username>`。展開で作られた子ジョブは親の `requested_by` を引き継ぐ。
- 同じ種別・メールアドレス・対象の未完了ジョブがあれば重複投入しない（`HasActiveJob`）。
- 進捗は 500 ミリ秒に 1 回まで DB に書き、最新 200 行を保持する。サーバー起動時に `running` のまま残ったジョブと分析報告を `error` にし、30 日より古い完了ジョブを削除する。

### 7.2 ワーカーと直列化

- ワーカー数は設定 `workers`（既定 2、1〜16。`service start --workers N`、`settings set workers N`、Web の一般設定）。ワーカーは同時に実行できるジョブ数であり、同時にアクセスするメールアカウント数の上限でもある。
- ジョブは実行時に「資源キー」の集合を占有する。占有中のキーを必要とするジョブは待機し（`queued` のまま）、キーが空いた時点で開始する。

| kind | 占有する資源キー |
| --- | --- |
| `sync`, `fetch` | `host:<imap_host 小文字>`、`mailbox:<address>` |
| `group`, `reclassify` | `mailbox:<address>` |
| `analyze` | `agent`、`analyze:<address>` |
| `reindex` | `mailbox:<address>`、`agent`（索引ファイルを入れ替えるため解析と同時に走らせない） |
| `notify` | `notify` |
| 展開ジョブ（mailbox NULL） | なし |

- 同一 IMAP サーバーのアカウントは `host:` キーで直列化され、先行ジョブの完了を待って順に開始する。エージェント CLI は `agent` キーで常に 1 本ずつ実行する。
- ワーカーは `queued` を古い順に走査し、資源キーが空いている最初のジョブを取る（`ClaimNextRunnableJob`）。
- CLI のプロセス内実行（`RunJobInline`）は同じ実行器を使い、自分が投入したジョブ（展開で生じた子と後続の解析を含む）を順に実行する。

### 7.3 スケジューラ

`check_times`（`HH:MM` をカンマ区切り、ローカル時刻）を読み、`SchedulerTick` ごとに「直前 tick から現在までに到来した時刻」があれば全アドレス同期（`sync`、mailbox NULL）を投入する（同一分に二重投入しない）。設定変更は即時反映（毎 tick で読み直す）。

### 7.4 通知（`notify.go`）

- SMTP 設定: `smtp_host`、`smtp_port`（既定 587）、`smtp_security`（`ssl` = SMTPS 465 / `starttls`（既定）/ `none`）、`smtp_username`、`smtp_password_enc`（秘密鍵で暗号化）、`smtp_from`（送信元アドレス。表示名は `MailCare`）。認証は PLAIN、対応していなければ LOGIN。`none` は平文のため注意書きを表示する。
- 通知設定: `notify_enabled`（既定 0）、`notify_time`（`HH:MM`、1 つ、既定 `09:00`。サーバーのローカル時刻）、`notify_interval_days`（1〜7、既定 1 = 毎日）、`notify_user_ids`（通知先の利用者 id をカンマ区切り）、`public_base_url`（例 `https://mailcare.example.com`。空なら `http://<web_listen または localhost>:<web_port>` を使う）、`notify_last_sent_at`（最終送信日時、内部用）。
- 送信条件: SMTP ホストと送信元がある、通知先に選ばれた利用者のうちメールアドレスが設定されている者が 1 人以上いる、対象グループが 1 件以上ある。いずれかを満たさなければ送信せず、理由をジョブ結果に記録する（`skipped: SMTP host or sender address is not set` / `no recipient is selected` / `none of the selected recipients has an email address` / `no open actionable group has a completed report`）。`notify_enabled` は定時送信だけを制御し、「今すぐ送信」（Web / CLI `notify`）は無効でも送る。成功時の結果は `sent N group(s) to <addresses>`。
- 送信タイミング: スケジューラが `SchedulerTick` ごとに評価し、`notify_enabled` のとき、直前 tick から現在までに `notify_time` が到来し、最終送信日から暦日で `notify_interval_days` 日以上経っていれば `notify` ジョブを投入する（同一分に二重投入しない。再起動後に過去分を遡って送らない。最終送信が無ければ最初の到来で送る）。
- 内容: 全メールアドレスの索引から「対応対象で状態が `open`、かつ完了した分析報告のあるグループ」を集め、メールアドレスごとの見出しの下に 1 グループ 1 ブロックで並べる。ブロックは「カテゴリ名と対応単位（判断主体）」「対象メール件数（宛先数・初回 / 最終日時）」「報告の要約（`agent_reports.summary`。無ければ報告本文の冒頭）」「そのグループを開く URL（`<public_base_url>/alerts/<mailbox_id>/groups/<group_key>`）」。件名は `[MailCare] 対応が必要なアラート N 件 (YYYY-MM-DD)`。本文は UTF-8 の text/plain で、テンプレートは `templates/mail/notification_ja.txt`（件名も同ファイルの `subject` テンプレート）、カテゴリの日本語名は `templates/mail/categories_ja.txt`、テスト送信は `templates/mail/test_ja.txt`。1 通に全ブロックを入れ、通知先全員を To に並べて 1 回で送る。送信元は `MailCare <smtp_from>`、件名は RFC 2047、本文は 8bit（998 バイト超の行があれば base64）。
- テスト送信: 通知設定画面の「テスト送信」（`POST /api/v1/notifications/test`、`{to?}` 省略時は自分のメールアドレス）は SMTP 設定だけを検証する短いメールを送る。「今すぐ送信」（`POST /api/v1/notifications/send`）は条件を満たせば通常の通知を送り、`notify_last_sent_at` を更新する。

### 7.5 CLI からの投入

CLI から `sync` / `fetch` / `group` / `analyze` / `reindex` / `reclassify` / `notify` を実行するとき、サーバーが稼働中（`/control/status` が応答）なら `/control/jobs` に投入して完了までポーリング表示し、稼働していなければプロセス内で直接実行する。これにより同じ索引 DB への同時書き込みを避ける。

## 9. HTTP

### 9.1 共通

- `/api/v1/*` は Cookie 認証。未認証は 401 `{"error":"unauthorized"}`。権限不足は 403 `{"error":"forbidden"}`。検証エラーは 400 `{"error":"<message>"}`。
- `/control/*` はループバック（127.0.0.1 / ::1）からのみ。
- 応答の日時は RFC 3339（UTC）文字列。`sql.NullTime` は `null` または文字列で返す（応答用の DTO を `dto.go` で組み立てる）。
- ジョブを投入するエンドポイント（`POST /api/v1/jobs`、`.../sync`、`.../analyze`、`POST /control/jobs`）は `{job: JobDTO, created: boolean}` を返す。新規なら 201、同一の未完了ジョブが既にあればそれを 200 `created: false` で返す。
- 未知の `/api/v1/*`、`/web/*`、`/control/*` は JSON の 404 を返す（SPA の shell は返さない）。

## 10. フロントエンド

### 10.1 構成

Vite + React 19 + TypeScript + Tailwind CSS v4 + react-router-dom + i18next（ja / en）+ react-markdown（分析報告の表示。別チャンクに遅延読込）。言語とテーマは利用者の設定（`users.language` / `users.theme`）に従い、ブラウザからの自動判別や localStorage への保存はしない。ログイン前は日本語・自動テーマ。テーマは `light-dark()` トークンを使い、`auto` は `color-scheme: light dark`（ブラウザ設定に追従）、`light` / `dark` は `<html>` に `color-scheme` を固定して切り替える。日時は利用者のタイムゾーンで整形する。全画面レスポンシブ（スマートフォン縦 360px〜、タブレット縦 768px、タブレット横 1024px、PC 1280px 以上）。開発時は `vite.config.ts` のプロキシで `/api` と `/web` を `localhost:9790` へ転送する。

| `src/api/client.ts` | エンドポイントごとの型付き関数。401 は `/login?next=...` へ遷移（`/me` とログインは除く）、503 は 1.5 秒後に 1 回再試行 |

### 10.2 ナビゲーション（ヘッダー）

`ブランド（MailCare、クリックでダッシュボード）` `バージョン` | `アラート` `メール` `ツール` `設定（ドロップダウン: 一般設定 / 通知 / メールアドレス / 利用者 / トークン）` | 利用者名（アイコンなしのドロップダウンで、クリックするとプロファイル / ログアウトを表示）。言語切替のアイコンは置かない（言語はプロファイルで設定）。幅 1024px 未満ではハンバーガーメニューに畳む。設定のラベル自体をクリックすると説明付きの設定メニュー画面（`/settings`）へ遷移する。設定メニューは全体が管理者専用で、一般利用者にはナビゲーションに表示しない（URL を直接開いた場合は「管理者のみ」の案内を表示する）。設定メニュー画面はタイトルの右に「管理者のみ」のバッジを 1 つ表示し、項目ごとのバッジは付けない。アラート・メール・ダッシュボードなど設定以外の画面でも、一般利用者には「メールアドレスを追加」への導線を出さず、未登録時は管理者へ依頼する旨の案内だけを表示する。ツールは一般利用者にも表示し、説明バナーとともに実行ボタンを無効化する。

### 10.4 ユニバーサルデザイン

- 本文 16px 以上、行間 1.5 以上、コントラスト比 4.5:1 以上。色だけに頼らず、状態はアイコン + 文字でも示す。
- すべての操作要素にフォーカスリング、`aria-label`、44px 以上のタップ領域。テーブルは幅が狭いときカード表示に切り替える。
- Markdown は `react-markdown` で表示し、`rehype` 系のサニタイズは使わず（内部生成のため）リンクは新規タブで開く。
- 纏めグループ一覧の並び替え（最終日時の昇降順 / 件数 / 重大度）はクライアント側で行い、状態・対応者区分・検索語は URL のクエリに保持する。

## 11. データベース

- マスター DB: SQLite（`modernc.org/sqlite`、CGO 不要）、goose 管理（初回リリースは `0001_init.sql` の 1 本）。DSN で `busy_timeout(5000)`、`journal_mode(WAL)`、`foreign_keys(1)`、`_time_format=sqlite` を設定する。
- 索引 DB: 同じドライバ。スキーマは `app/models/mailindex.go`（`messages` / `groups` / `agent_reports` の 3 表。バウンス抽出結果は `messages.detail_info` の JSON 列に内包し、グループ統計は `json_extract` で集計する）。
- 設計方針: 行の単純な属性は実列にし、JSON 列は列名を `*_info`（`detail_info`）として構造化された抽出結果（`messages.detail_info`）、まとまった接続設定（`mailboxes.detail_info`。`protocol` キーで種類を示す）、自由文の出力（`jobs.detail_info`）の 3 箇所だけに使う。グループの表示名は保存せず、カテゴリ・対応単位・判断主体から組み立てる。列長・列挙値は CHECK 制約で守り、日時は UTC で保存する。`tokens` と `settings` はテンプレートのまま。サービス起動パラメータ（待受アドレス・ポート・ワーカー数・チェック時刻）は既定値と異なる場合だけ `settings` に保存し、既定値になれば行を消す。
- テーブル定義は [テーブル定義.md](テーブル定義.md) を参照。
